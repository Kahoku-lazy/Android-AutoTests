## 2. 图的设计思路（按「读者先建立什么」排序）

1. **流向右、执行层向左**：第一行 `浏览器 → Vue SPA → Daphne ASGI → Django+DRF → MySQL` 从左到右（请求方向），第二行 `task_runner → backend_bridge → ae_harness → 硬件支撑引擎` 从右到左（下发方向）。两条线在中部交汇，读者一眼看出「上行是通道、下行是执行」。
2. **节点卡三行**：`主标（Vue 3.5 SPA） / 职责（Pinia · 10 个业务模块） / 运行标记（Vite :5173）`。第一行是「他是什么」，第二行是「他由什么组成」，第三行是「他在哪跑」。三行**全部是可核对的事实**，没有形容词。
3. **语义类型决定颜色**：前端/后端/数据库/安全/外部各一色，图例写「类型 + 个数」（前端 1 · 后端 5 · 数据库 1 · 安全 1 · 外部 3）。颜色不是装饰，是分类器。
4. **区域边界表达纪律**：只画了一个框——`engines/ · 零 django / apps.* 依赖`，把「这一坨不许反向依赖上层」变成图形约束。**框是规则，不是分组**。
5. **边写动作，不写次数**：`HTTPS`、`axios · /api`、`鉴权放行`、`submit`、`注入配置`、`create_agent`、`tool 调用`、`推理请求`、`ADB / 串口`。因为这张图要回答「一次任务怎么走」，不是「引用了几次」。
6. **留白纪律**：三行节点等高、行距恒定、端口只从边中点出入、没有一条线穿过节点。
7. **图外三张卡**：`三层分工 / 执行闭环 / 当前边界`——把图讲不清的结论补在下面，而不是塞进图里。

## 3. 与我们的差异（为什么不能照抄）

| ARCH 的前提 | 我们仓库的实际 |
| --- | --- |
| 数据是人工语义（spec.json 手写 235 行） | 看板数字全部由 `gen_board_data.py` 生成，图上的边必须能追到 AST |
| 图的唯一产物，值得为它做 800 KB viewer | 图只是页面第 1 节，上面还要滚两节 |
| 多主题/多风格是卖点 | 平台只有一套纸面主题（doodle-craft） |
| 节点是运行时组件，天然带「职责」 | 节点是目录，能写的事实是单元数 / 文件数 / 行数 |
| 边写动作（submit / create_agent） | 边能写的是 import 次数与 HTTP 处数 |

## 5. 它自己的「流程」（我们要复用的部分）

从 spec.json 的结构可以反推作者顺序，这也是本 skill 的七步流程来源：

1. `meta.title / locale / quality_profile` —— 先定图的身份。
2. `meta.views[]` —— 先写清「这张图要讲哪几条链路」（请求链路 / 任务执行 / 设备与证据），再画。
3. `components[]` —— 每个组件先给 `id / type / label / sublabel / tag / pos / size`，**先有事实栏，再有坐标**。
4. `boundaries[]` —— 用 `wraps` 声明框住谁，`pad` 给内距；框是数据，不是手绘。
5. `connections[]` —— 每条边 `from / to / label / variant`，方向即语义。
6. `cards[]` —— 图讲不完的结论放这里。
7. 渲染后再做视觉校验（仓库里 `arch-平台架构图.browser-check.json` / `visual-check.*.png` 就是这一步的产物）。

→ 我们的版本把这些字段压成一张 `LAYOUT` 表 + 一份快照数据，视觉校验换成 Playwright 截图 + `getBBox` 量文字。
