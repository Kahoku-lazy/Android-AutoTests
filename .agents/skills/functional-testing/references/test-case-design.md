# Test Case Design Specification

## 0. 测试目的

代码审查能看到语法和逻辑，但看不到：运行时状态、数据同步、性能瓶颈、安全漏洞、边界崩溃。
功能测试的目标是**发现代码审查无法发现的问题**，分为两类：

| 类型 | 定义 | 示例 |
|------|------|------|
| **代码 Bug** | 实现与预期不符 | 删除后数据未同步、catch 静默吞错 |
| **设计 Bug** | 功能设计本身有缺陷 | 缺少 401 认证、无并发保护、SQL 注入风险 |

发现后必须输出测试报告，标注 Bug 类型和严重级别。

## 1. 五维测试模型

每条业务场景从五个维度评估是否需要覆盖：

```
                     ┌─ 功能
                     │   数据一致性：展示数据 = 源数据
                     │   功能行为：操作 → 同步变动
                     │
        ┌─ 数据表单 ─┤
        │  字段校验   │
        │  类型约束   ├─ 接口/API
        │  业务规则   │   请求验证：必填/类型/格式
        │  默认值     │   响应格式：ok/data/error 一致
        │            │   HTTP 状态码：200/400/401/404/409
        │            │   错误信息：清晰、不泄露内部细节
        │            │
        └─ 安全 ─────┤
           认证：未认证拒绝 401        └─ 性能
           授权：用户数据隔离             响应时间：API < 阈值
           加密：敏感字段加密存储         模块加载：Vite 编译 < 阈值
           防注入：XSS/SQL 注入          并发：多用户不冲突
           防泄露：错误消息不暴露路径
```

> **规则**：每个场景至少覆盖 3 个维度。新增端点必须覆盖 [接口+安全+功能]。修改逻辑必须覆盖 [功能+数据表单+性能]。

## 2. 五维判断标准

### 2.1 功能维度

```
数据一致性:
  每一项展示数据 → 找到源模块/API → 对比值是否一致
  不一致 → 🟡 设计 Bug：统计逻辑未同步

功能行为:
  增 → 关联数据同步增加
  删 → 关联数据同步减少（物理删除非软删除）
  改 → 关联数据同步更新
  不同步 → 🔴 代码 Bug：缺少乐观更新或刷新
```

### 2.2 接口/API 维度

```
请求验证:
  [ ] 必填字段缺失 → 400 + 明确错误信息
  [ ] 字段类型错误 → 400（非 500 崩溃）
  [ ] JSON 格式错误 → 400（非 500 崩溃）
  [ ] 字段超长 → 400 或自动截断

响应格式:
  [ ] 成功 → {"status": true, "data": ...}
  [ ] 失败 → {"status": false, "message": "..."} + HTTP 状态码
  [ ] 列表 → 有分页或数量限制

HTTP 状态码:
  200=成功, 400=参数错误, 401=未认证, 403=无权限, 404=不存在, 409=冲突, 500=服务错误

未覆盖 → 🟡 设计 Bug：缺少输入校验
```

### 2.3 安全维度

```
认证:
  [ ] 无 token 访问 → 401（非 200 + user_id=None）
  [ ] 错误 token → 401
  [ ] 过期 token → 401

授权:
  [ ] 用户 A 不能操作用户 B 的数据
  [ ] 设备锁只能由持有者释放

加密:
  [ ] api_key/password 在 DB 中加密存储（非明文）
  [ ] 前端 API 响应中已脱敏

防注入:
  [ ] XSS：输入 <script> 不执行
  [ ] SQL 注入：输入 '; DROP TABLE-- 不执行

防泄露:
  [ ] 错误消息不含堆栈/路径/SQL
  [ ] 日志不含 password/api_key

未覆盖 → 🔴 代码 Bug：安全漏洞
```

### 2.4 数据表单维度

```
字段校验:
  [ ] 必填字段空值 → 拒绝
  [ ] 字符串超长 → 拒绝或截断
  [ ] 枚举值非法 → 拒绝
  [ ] 数字范围越界 → 拒绝

类型约束:
  [ ] JSONField 传字符串 → 拒绝
  [ ] IntegerField 传字符串 → 拒绝
  [ ] BooleanField 传字符串 → 正确转换或拒绝

默认值:
  [ ] 字段省略 → 使用 Model 默认值（非 null/崩溃）
  [ ] 空字符串 "" 与 None 区分正确

业务规则:
  [ ] 状态机转换合法性（ONLINE → BUSY 合法，DISCONNECTED → BUSY 非法）

未覆盖 → 🟡 设计 Bug：缺少数据校验
```

### 2.5 性能维度

```
响应时间:
  [ ] 列表 API < 500ms
  [ ] 创建/删除 API < 1000ms
  [ ] 前端模块加载 < 2000ms

稳定性:
  [ ] 连续 10 次请求无失败
  [ ] 大列表（100+ 条）不超时

并发:
  [ ] 同一资源并发操作不脏写
  [ ] 设备锁并发获取不重复分配

未覆盖 → 🟢 优化建议（非阻塞）
```

## 3. 用例编号

```
{MODULE}-{DIMENSION}-{NN}

DIMENSION: FUNC(功能) | API(接口) | SEC(安全) | DATA(数据表单) | PERF(性能)

示例: AI-SEC-01 = AI 助手, 安全维度, 第 1 条
      DASHBOARD-FUNC-01 = 仪表盘, 功能维度, 第 1 条
```

## 4. 用例编写格式

每条用例必须用非技术人员也能读懂的语言描述。核心原则：**如果产品经理看不懂这条用例在测什么，用例就是不合格的**。

```markdown
### {编号}: {一句话描述 — 用业务语言，非技术语言}

**测什么**（谁都能看懂）:
{用 1-2 句话解释：这条用例验证什么业务功能，为什么这个验证重要}

**怎么测**（技术人员执行用）:
1. {操作步骤}
2. {验证点}

**断言**: {具体的预期结果，可用代码验证}

**如果失败意味着什么**（帮助非技术人员理解严重性）:
- {失败的业务影响}
```

**语言要求**:

| 禁止（技术语言） | 正确（业务语言） |
|------|------|
| "验证 Stats API 返回格式正确" | "验证仪表盘页面能正常加载并显示统计数据" |
| "AssertionError: dashboard.online != pool_online" | "仪表盘显示 2 台在线设备，但设备池实际只有 1 台——数据不一致" |
| "FUNC-01: 在线设备数一致" | "仪表盘的设备数量与设备管理页面的数量应该一致" |

**描述模板**:

```
仪表盘统计场景:
- "验证仪表盘显示的在线设备数，与设备管理页面中的实际在线设备数一致"
- "验证仪表盘显示的智能体数量，与 AI 助手页面的智能体数量一致"
- "新增一个智能体后，仪表盘的智能体计数应该自动 +1"

AI 助手场景:
- "验证删除智能体后，数据库中不再存在该智能体的记录"
- "验证创建智能体时填写的 API 密钥，在数据库中被加密存储而非明文"
- "验证前端删除按钮点击后，即使网络请求失败，也会弹出错误提示而非静默失败"
```

## 5. 覆盖率要求

| 变更类型 | 最少覆盖维度 | 最少用例 |
|---------|:--:|:--:|
| 新增 API 端点 | FUNC + API + SEC | 5 |
| 修改 API 端点 | API + SEC + DATA | 4 |
| 新增前端页面 | FUNC + PERF | 3 |
| 修改前端逻辑 | FUNC + DATA | 3 |
| 数据库 Model 变更 | DATA + FUNC | 3 |
| Bug 修复 | FUNC + SEC | 2（复现+回归） |

## 6. 测试报告模板

报告必须包含足够细节用于决策和方向调整，不能只有结论。

### 6.1 执行摘要

```markdown
## 测试报告 — {模块名}

**范围**: {模块} | **时间**: {now} | **总耗时**: {total_ms}ms | **环境**: {env}
**结论**: {一句话，如 "功能/接口/安全/数据正常，性能需优化"}
**建议**: {下一步行动，如 "Stats API 加 Redis 缓存后重新测 PERF 维度"}
```

### 6.2 逐用例详情

每条用例必须列出实际值与预期值，决策者能据此判断测试是否真实有效：

```markdown
### 用例详情

| # | 编号 | 维度 | 描述 | 预期值 | 实际值 | 结果 | 耗时 |
|---|------|------|------|--------|--------|:--:|:--:|
| 1 | DASHBOARD-FUNC-01 | FUNC | 在线设备数一致 | online=1 | online=1 | PASS | 45ms |
| 2 | DASHBOARD-FUNC-02 | FUNC | 用例数一致 | total=2 | total=2 | PASS | 38ms |
| ... | ... | ... | ... | ... | ... | ... | ... |
```

### 6.3 维度覆盖热力图

展示哪个维度强哪个弱，指导下次测试方向：

```markdown
### 维度覆盖

| 维度 | 用例数 | 通过 | 失败 | 通过率 | 热力 | 建议 |
|------|:--:|:--:|:--:|:--:|:--:|------|
| FUNC 功能 | 6 | 6 | 0 | 100% | ████████ | 覆盖充分，可减少 |
| API 接口 | 3 | 3 | 0 | 100% | ████████ | 覆盖充分 |
| SEC 安全 | 2 | 2 | 0 | 100% | ████░░░░ | 建议补并发权限测试 |
| DATA 数据 | 2 | 2 | 0 | 100% | ████░░░░ | 建议补边界值(null/超长) |
| PERF 性能 | 2 | 1 | 1 | 50%  | ██░░░░░░ | **需要重点加强** |
```

热力图: 通过率 >= 80% 且用例 >= 3 → 充分(██); 通过率 < 80% → 薄弱(░░); 用例数 < 3 → 待扩充

### 6.4 Bug 证据清单

每个 Bug 必须附带可复现的证据，证明它是真实存在的：

```markdown
### Bug 发现

#### BUG-01 [HIGH] [CodeBug] Dashboard Stats API 响应超时

| 属性 | 值 |
|------|------|
| 发现用例 | DASHBOARD-PERF-01 |
| 严重度 | HIGH — 影响用户体验，每次打开仪表盘需等待 2 秒 |
| 证据 | 10 次请求平均值 2104ms，最大值 2187ms，阈值 500ms |
| 原始数据 | [2104, 2098, 2110, 2156, 2087, 2103, 2187, 2091, 2105, 2099] ms |
| 根因分析 | Stats API 串行执行 6+ ORM 查询(devices/cases/elements/runs/agents/reports)，无缓存 |
| 修复建议 | 1. 对不常变的数据(agents/reports)加 Redis 缓存 TTL=60s |
|         | 2. 或用 Django ORM select_related/prefetch_related 减少查询次数 |
| 复现方法 | `curl http://localhost:8765/api/dashboard/stats/ -H "Authorization: Bearer $TOKEN"` |
```

### 6.5 测试方向建议

根据本次结果，调整下次测试重点：

```markdown
### 下次测试方向

| 优先级 | 维度 | 行动 | 原因 |
|:--:|------|------|------|
| P0 | PERF 性能 | 修复后复测 Stats API | 当前 50% 通过率，有 1 个 HIGH Bug |
| P1 | SEC 安全 | 增加并发权限测试 | 当前仅 2 条用例，覆盖不足 |
| P1 | DATA 数据 | 增加边界值测试 | null/超长/负数未覆盖 |
| P2 | FUNC 功能 | 可减少至 3-4 条 | 6 条全通过，覆盖已充分 |
```

### 6.6 趋势对比（如有历史数据）

```markdown
### 趋势

| 指标 | 上次 | 本次 | 变化 |
|------|:--:|:--:|:--:|
| 通过率 | 100% | 93% | ↓ 7% |
| PERF 通过率 | 100% | 50% | ↓ 50% (新增性能测试) |
| Bug 数 | 0 | 1 | +1 (新发现) |
```
