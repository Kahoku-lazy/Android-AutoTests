# 前端方案设计流程（可执行版）

> 适用场景：需求方说「这个界面想改成 XXX 效果，先出方案 / 不改代码 / 给我看看」。
> 产出物：一份**自包含单文件 HTML**（左侧章节导航 + 右侧可点原型）+ 一张关键帧截图，放在 `temps/`。
> 本条流程只到「人点头」为止；开工必须另走 OpenSpec（见阶段 9）。

---

## 0. 先加载两个技能（不加载不许往下写）

```
skill(frontend-change-plan)   # 方案与原型的生产流程、章节契约、自检清单
skill(doodle-craft)           # 视觉语言：令牌、线型、组件选型、硬规则
```

- `frontend-change-plan` 决定**怎么写这份方案**（结构、原型骨架、边界）。
- `doodle-craft` 决定**长什么样**（颜色只取令牌、线型只用实线（除白名单三件）、阴影模糊恒为 0、圆角二值写法）。
- 两者冲突时：视觉以 `frontend/src/shared/styles/tokens.css` 与实际组件代码为准。

---

## 1. 事实核查（禁止凭空写方案）

### 1.1 找到真实代码位置

```powershell
# 页面路由与模块
Get-Content frontend\src\router.ts | Select-String "<页面路径>"
Get-ChildItem frontend\src\modules\<模块> -Recurse -File |
  ForEach-Object { $_.FullName.Replace("...\modules\<模块>\", "") }

# 页面根元素（决定版式与作用域）
Get-Content frontend\src\modules\<模块>\index.vue | Select-Object -First 110
```

必须读出的四个事实：

| 事实 | 从哪读 | 用途 |
| --- | --- | --- |
| 页面根 class | 模块 `index.vue` 根元素 | 是否带 `wb-shell`（主题作用域）、是否 `doc-page--fixed` |
| 要改的那个控件 | grep 目标文案 / class | 现状到底用的是什么组件，别猜 |
| 共享件是否已有 | `frontend/src/shared/components/` | 能复用就不新造 |
| 令牌与线型 | `tokens.css` + `doodle-craft` | 颜色/字号/圆角/阴影取值 |

### 1.2 先查「是不是已经做过了」

```powershell
Get-ChildItem openspec\changes\archive -Directory | Where-Object { $_.Name -match "<关键词>" }
Get-ChildItem openspec\specs -Directory | Where-Object { $_.Name -match "<关键词>" }
Select-String -Path openspec\specs\*\spec.md -Pattern "<关键词>" | Select-Object -First 20
```

命中归档/在册 spec 时：**把「已实现」写进方案**，不要重复开单。

### 1.3 把现状的样式读出来（提案要能指出具体错在哪）

```powershell
# 例：读某组件的真实皮肤
$css = Get-Content frontend\src\shared\styles\workbench-theme.css
$i = (Select-String -Path frontend\src\shared\styles\workbench-theme.css -Pattern "<选择器>" | Select-Object -First 1).LineNumber
$css[($i-1)..($i+30)]
```

> 注意：PowerShell 控制台里中文可能显示成乱码（编码显示问题），文件本身是 UTF-8。**以 `read` 工具读到的内容为准**，不要据此判断文件损坏。

---

## 2. 写「现状 + 问题」，最多三条

每条都要能指到代码或截图上的具体位置，例如：

- 颜色错位：选中态用 `--c-dashboard`，而模块色是 `--c-device`；
- 形状不连：控件与面板是两套几何，切换像按按钮；
- 层级平：控件字号与面板标题接近，视线顺序不对。

写不出具体证据的「感觉不好看」不要写进方案。

---

## 3. 选型：2–3 个变体 + 推荐 + 降级

| 要素 | 要求 |
| --- | --- |
| 变体数量 | 2–3 个，形态上必须有真实差别（不是换颜色） |
| 推荐 | 明确写「推荐 A」，并给一句理由（最贴合需求原话） |
| 降级 | 写清 B 在什么条件下用（实现成本 / 不想引入新技术） |
| 代价 | 每个变体都要写实现代价（是否需要 `clip-path`、是否要动共享组件） |

---

## 4. 做原型（单文件 HTML）

### 4.1 文件位置与命名

```
temps/<topic>-proto.html          # 方案 + 可点原型
temps/<topic>.png                 # 关键帧截图（给聊天里直接看）
```

**禁止**改 `frontend/` 下任何文件。写完用这条命令自证：

```powershell
git status --porcelain frontend   # 本次方案不应新增任何条目
```

### 4.2 结构契约（顺序固定）

1. 总方案（一段话 + 现状问题 + 两条路线对比表）
2. 方案 A（可点原型 + 令牌说明）
3. 方案 B（可点原型 + 不推荐/降级理由）
4. 交互与状态（默认 / 悬停 / 选中 / 键盘 / 回落）
5. 令牌与复用（取值来源表 + 实现落点 + 风险提示）
6. 落地与不做（P0/P1/P2 + 明确不做清单）

左侧放 `position: sticky` 的章节导航，锚点跳转。

### 4.3 颜色诚实标注

- 原型里可以用示意色，但**必须写清令牌名**（`--c-device` / `--paper` / `--ink`），并注明「色值以 `tokens.css` 为准」。
- 不要把原型里的 `#6bcb77` 说成产品规范。

### 4.4 交互骨架（最小 JS）

```js
document.querySelectorAll('.tab').forEach((tab) => {
  tab.addEventListener('click', () => {
    document.querySelectorAll('.tab').forEach((t) => {
      const on = t === tab
      t.classList.toggle('--on', on)
      t.setAttribute('aria-selected', String(on))
    })
    document.querySelectorAll('[data-body]').forEach((b) => {
      b.hidden = b.dataset.body !== tab.dataset.key
    })
  })
})
```

两套变体各用独立 class 前缀（`bm` / `idx`），避免互相污染。

## 5. 渲染校验（必须做，不能只写不验）

```powershell
$chrome = "C:\Program Files\Google\Chrome\Application\chrome.exe"
$out = "D:\...\temps\<topic>.png"
Remove-Item $out -ErrorAction SilentlyContinue
$ud = "D:\...\temps\cp-$(Get-Random)"
& $chrome --headless=new --disable-gpu --hide-scrollbars --user-data-dir="$ud" `
  --window-size=1500,1400 --screenshot="$out" "file:///D:/.../temps/<topic>-proto.html"
Start-Sleep -Seconds 2
Test-Path $out
```

然后用 `read_image` 看渲染结果，**逐项检查**：

- [ ] 控件是否真的画出来了（不是空白/塌陷）
- [ ] 形状的缺口/接合处有没有露底、错位、白缝
- [ ] 选中态与未选中态是否一眼可分
- [ ] 文本有没有溢出/被裁
- [ ] 左侧导航与锚点是否正常

发现问题就改 CSS 再截一次，**不要凭想象交付**。

---

## 6. 常见渲染坑（本次实际踩到的）

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 书签/色块完全不见 | 用 `<span>` 承载 `width/height`，行内元素不吃尺寸 | 给形状层 `display: block` |
| V 形缺口边缘出现白缝 | 双层 `clip-path`（外墨边 + 内填充）内缩 2.5px 后，缺口深度没同步减 | 内层用 `calc(100% - (12px - 2.5px))`，让缺口尖点对齐 |
| 缺口处露出灰色底 | 控件只 `margin-bottom: -2.5px`，缺口悬在面板外 | 负边距加大到缺口深度（如 `-11px`），让控件真正插进面板 |
| 截图命令报错但没文件 | Chrome 复用实例 / 输出文件被占用 | 先 `Remove-Item`，再用随机 `--user-data-dir`，并 `Start-Sleep` 后检查 |
| 用 Python heredoc 写大段 HTML 报语法错 | PowerShell 对 `@"..."@` + 三引号转义冲突 | 大段文件用 `write` 工具写；小改动用 `edit` 或短字符串 `replace` |

## 7. 方案自检（交付前逐条过）

- [ ] 只动 `temps/`，`git status --porcelain frontend` 为空
- [ ] 每个颜色都能对应到令牌名；没有把示意色说成规范
- [ ] 线型：除 `KpiCard` / `AgentRouteCard` 外全部实线
- [ ] 阴影模糊半径为 0，圆角为二值写法
- [ ] 至少两个变体，且有一个明确推荐
- [ ] 有「明确不做」清单（防范围蔓延）
- [ ] 交互包含键盘与 `prefers-reduced-motion`
- [ ] 原型可点击，两个变体互不干扰
- [ ] 截图渲染无塌陷、无白缝
- [ ] 结论先行：第一段就能看出推荐哪个方案

---

## 8. 交付给需求方

用 `present` 把 HTML 卡片交出去，并在回复里：

1. 第一段写结论（推荐哪个 + 为什么）；
2. 贴关键帧截图；
3. 给规格表（尺寸 / 颜色令牌 / 接合方式）；
4. 给「现状问题」三条以内；
5. 最后列 2–3 个**需要对方决定的点**（形态、尺寸、是否保留装饰元素）。

> 需求方可能连续几轮都在调细节（颜色、字号、对齐）。每轮只改原型、不改代码；改完重新截图再发。

---

## 9. 通过之后：交棒 OpenSpec

方案被点头 ≠ 可以写代码。按仓库规范走：

```
/opsx:propose <change-id>     # proposal + specs delta + design + tasks
/opsx:apply                   # 实现
/opsx:archive                 # 归档
```

把方案里的范围与 P0/P1/P2 直接当作 change 的输入；HTML 方案作为 `proposal.md` 的 Why 依据或 `design.md` 的引用来源。

实现完成后跑前端门禁：

```powershell
cd frontend
npx vue-tsc --noEmit
npm run build:check
npm run lint:styles
npm run lint:lines
npx vitest run tests/<模块>
```
