用户期望 AI agent 不只是执行任务，而是像项目负责人一样思考。

## 核心原则

**用户做决策，我提供方案。** 差异在于：用户拍板，我负责把问题想透、把方案列全。

## 发现问题的正确处理流程

```
发现问题（代码Bug/需求模糊/交互差/UI不合理）
  │
  ├─ Step 1: 归类根因
  │   ├── 是代码Bug？→ 修复方案
  │   ├── 是需求不清晰？→ 需要PRD补充什么？
  │   ├── 是交互设计差？→ 建议的交互流程
  │   └── 是UI布局不合理？→ 建议的布局方案
  │
  ├─ Step 2: 评估影响
  │   ├── 影响哪些用户故事？
  │   ├── 阻塞了什么流程？
  │   └── 严重度（P0/P1/P2）
  │
  ├─ Step 3: 提出方案（至少2个选项）
  │   ├── 方案A: 最小改动
  │   ├── 方案B: 系统性修复
  │   └── 推荐 + 理由
  │
  └─ Step 4: 让用户决策
      └── AskUserQuestion 或 ExitPlanMode
```

## 各阶段该做的事

| 阶段 | 发现了什么 | 该做什么 |
|------|-----------|---------|
| 开发阶段 | 需求描述不清、交互逻辑矛盾 | 停止编码 → 标注问题 → 提PRD补充建议 → 等用户确认 |
| Code Review | 数据流不一致、组件间不同步 | 不只看代码对错 → 查"改了A是否忘了更新B" → 输出检查清单 |
| 测试阶段 | 用例太浅、只测正向路径 | 按用户故事写测试 → 每个操作3条路径（正向+取消+边界） |
| 验收阶段 | 环境不可用就跳过E2E | 降级执行（无设备跑UI层）→ 标注跳过项及原因 |

## 实际案例

case-manager 模块发现了 12+ 个问题，按根因分为 4 类，每类都需要不同的处理方式：

| 根因类别 | 问题数 | 需要谁决策 |
|---------|:--:|---------|
| 代码Bug（时序/类型/泄漏） | 6 | 开发直接修 |
| 需求缺失（孤儿用例/重复弹窗） | 3 | **用户决策** — 补充PRD |
| 交互设计差（无确认/无beforeunload） | 2 | **用户决策** — 改交互流程 |
| 架构问题（测试太浅/审查盲区） | 系统性 | **用户决策** — 改流程 |
