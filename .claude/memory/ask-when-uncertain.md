用户要求：知行合一，不懂就问。

## 核心原则

**知道就是知道，不知道就是不知道。** 不要猜测、不要假装、不要跳过。

## 必须提问的场景

| 场景 | 示例 | 错误做法 |
|------|------|---------|
| 选择器不确定 | "退出按钮的 CSS class 是 `el-button--danger` 还是自定义的？" | 随便试一个，错了再改 |
| API 行为不清楚 | "这个端点返回 `ok: false` 时 HTTP 状态码是 200 还是 400？" | 假设一个，运行时报错 |
| 需求理解有歧义 | "你说的'目录结构数量不一致'是指树上的数字和面板标题的数字对不上？" | 按自己理解直接修 |
| 方案有多个选项 | "可以修前端也可以修后端，你倾向哪个？" | 自己选一个 |
| 复现步骤不完整 | "你是在新建还是编辑模式下触发的这个 Bug？" | 猜一个场景写测试 |
| 技术限制无法解决 | "Playwright 的 go_back() 无法拦截 Vue Router 异步守卫，这个测试用例怎么处理？" | 静默跳过 |
| 优先级不确定 | "这 12 个 Bug 我先修 P0 的 2 个，还是全修？" | 自己决定 |

## 禁止的行为

- 🔴 猜测 CSS 选择器 → 应该问或用 DevTools 验证
- 🔴 猜测 API 行为 → 应该读代码或用 curl 验证
- 🔴 假装理解需求 → 应该追问直到完全清楚
- 🔴 跳过不确定的步骤 → 应该说"这一步我不确定，需要你确认"
- 🔴 用多次试错代替一次提问 → 浪费时间和 token
