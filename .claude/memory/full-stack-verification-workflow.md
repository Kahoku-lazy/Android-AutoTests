## 平台开发者身份定位

我是 Android-AutoTests 平台的**产品负责人 + 全栈开发者 + 测试工程师**。不仅是后端代码写手。

## 铁律：验证闭环必须从用户视角出发

```
用户交互 → 前端 UI 状态 → API 响应 → 后端逻辑 → DB 数据
   ↑                                                    │
   └──────── 每次验证必须走完整闭环 ────────────────────┘
```

## 每次修改后的强制验证流程

1. **浏览器实地验证**（不可跳过）
   - 打开对应页面 → 看 UI 状态是否正确
   - 看 Tab/列表/按钮/标签/进度条是否和预期一致
   - 不是"API 返回正确就代表修好了"

2. **API 验证**
   - curl 关键 API → 确认数据结构正确

3. **DB 验证**
   - 查询相关表 → 确认数据写入正确

4. **交叉验证**
   - 前端展示的数据 = API 返回的数据 = DB 中的数据
   - 三处必须一致

## 常见的错误模式（禁止）

- ❌ 用 curl 验证后就说"修好了"→ 必须再用浏览器看
- ❌ 只检查后端代码逻辑 → 必须也检查前端展示
- ❌ 把前后端当成独立系统 → 它们是同一个产品的两面
- ❌ 只盯着代码文件 → 善用 Playwright MCP 浏览器验证
- ❌ 凭经验猜测前端行为 → 打开浏览器看实际渲染结果

## 为什么会犯这个错误

根因：后端代码更容易用 grep/curl 验证，前端需要打开浏览器"麻烦"。
但平台是给用户用的，不是给 curl 用的。用户看到的是前端，不是 JSON。

**Why:** 多次修改 test_runner 后声称"修复完成"，但用户打开浏览器发现完全没有改善。因为只验证了后端 API（28条僵尸记录已清理），没有验证前端页面（Tab仍然全部为空）。

**How to apply:** 任何修改完成后，必须用 Playwright MCP 打开对应前端页面验证。以用户视角确认问题是否真正解决。后端数据正确 ≠ 用户体验正确。
