# 需求矛盾分析方法

> 文档迭代后自动执行的一致性校验流程
> 版本：v1.0 · 日期：2026-06-30

---

## 一、触发条件

| 时机 | 触发 |
|------|:--:|
| PRD 版本递增后 | ✅ |
| 技术代码结构更新后 | ✅ |
| 新增/删除/重命名模块后 | ✅ |
| 基础架构方案修改后 | ✅ |
| 每日工作结束前（兜底） | ✅ |

---

## 二、检查维度（8 维）

### 2.1 架构一致性

| 检查项 | 对比文档 | 重点 |
|--------|---------|------|
| 架构风格 | 基础架构方案 vs 技术代码结构 | 是否保持"基础框架+功能层"两层 |
| 目录结构 | 技术代码结构 §一 vs 基础架构方案 §二~四 | 目录名是否一致 |
| 通信规则 | 基础架构方案 §五 vs 技术代码结构 | 规则条款是否一致 |

### 2.2 模块一致性

| 检查项 | 对比文档 | 重点 |
|--------|---------|------|
| 模块数量 | 当前实现架构方案 §2.2 ↔ 子PRD 目录 | 6 个模块完整 |
| 模块名称 | 技术代码结构 ↔ 子PRD 文件名 | 中英文/编号一致 |
| 模块状态 | 技术代码结构 ↔ 子PRD ↔ 全局PRD §8 | ✅/⏳/⬜ 标注一致 |
| 前后端映射 | 技术代码结构 §三 ↔ 实际代码目录 | 真实存在 vs 文档声明 |

### 2.3 技术栈一致性

| 检查项 | 对比文档 | 重点 |
|--------|---------|------|
| 前端栈 | 全局PRD §5 ↔ 基础架构方案 §二 | Vue/Vite/Element Plus/Pinia 版本一致 |
| 后端栈 | 全局PRD §5 ↔ 基础架构方案 §三 | Django/DRF/Daphne/Channels 版本一致 |
| 数据库 | 全局PRD vs 基础架构方案 §四 | MySQL/SQLite 选择一致 |
| 功能归属版本 | 子PRD 功能状态 ↔ 全局PRD §6 里程碑 | Element Plus在v2、数据工厂在v4 |

### 2.4 版本路线一致性

| 检查项 | 对比文档 | 重点 |
|--------|---------|------|
| 版本列表 | 全局PRD §6 ↔ 基础架构方案 §八 ↔ 技术代码结构 | Phase 编号顺序 |
| 功能归属 | 全局PRD §8 ↔ 子PRD 各文件 | v2/v3/v4 分配一致 |
| 工作量 | 全局PRD vs 竞品对比 | 天数误差 ≤20% |

### 2.5 数据库一致性

| 检查项 | 对比文档 | 重点 |
|--------|---------|------|
| 表名前缀 | 基础架构方案 §四 ↔ 技术代码结构 §二 ↔ 子PRD | 前缀一致 |
| 表名 | 同上 | 具体表名一致 |
| 表数量 | 当前实现架构方案（6组18张） ↔ 命名统一标准 | 18 ± 2 范围内 |

### 2.6 API 一致性

| 检查项 | 对比文档 | 重点 |
|--------|---------|------|
| 端点数量 | 技术代码结构 §二 ↔ 子PRD | v1已实现 vs 全部规划 需标注 |
| 端点路径 | 子PRD ↔ 基础架构方案 | `/api/{domain}/*` 前缀匹配 |

### 2.7 规则一致性

| 检查项 | 对比文档 | 重点 |
|--------|---------|------|
| Agent 约束 | 基础架构方案 §五~六 ↔ 技术代码结构 ↔ 代码Review规则 | 规则条款覆盖度 |
| 代码 Review | 代码Review规则 ↔ 基础架构方案 | 检查项相互引用 |

### 2.8 跨文档引用一致性

| 检查项 | 重点 |
|--------|------|
| 文档内链接 | `[xxx](../02-PRD需求/...)` 目标文件存在 |
| 模块编号 | 所有文档中模块编号 `01~10` 一致 |
| PRD 版本号引用 | 架构 doc 的关联 PRD 版本号 ≤ PRD 实际版本号 |

## 三、严重等级定义

| 等级 | 定义 | 处理 |
|:--:|------|------|
| **P0** | 表名不同 / API端点数量差异 > 5 / 模块名称不同 | 立即修复，代码不可继续 |
| **P1** | 功能归属版本不同 / 规则缺失 / 工作总量差异 > 30% | 当次迭代修复 |
| **P2** | 表数量差 1~2 / 端点路径个别不一致 / 表述精度差异 | 下次迭代修复 |
| **P3** | 措辞差异 / 链接指向旧路径 | 记录，不阻塞 |

## 四、执行流程

> **前置步骤**：执行跨文档一致性检查前，先对涉及的单份文档执行 Stage-Gate 质量评审（参考 PM-Project `gate-review` Agent 方法论）：
> - PRD 发生了变更 → 先跑 Gate 1（PRD 评审 19 项）
> - 架构文档发生了变更 → 先跑 Gate 2（架构评审）
> - 先确保单份文档质量过关，再跑跨文档一致性扫描。避免"两份都有错误的文档互相矛盾"的假阴性。

```
Step 1: 前置评审 — 对变更文档跑 gate-review（单份质量检查）
Step 2: 确定范围 — 本次迭代改了哪些文档？
Step 3: 8 维全量扫描 — 对所有文档执行 §2 的交叉对比
Step 4: 分级标注 — 每项矛盾标注 P0~P3
Step 5: 输出报告 — 用本方法学的 §五 模板
Step 6: 修复 — P0/P1 必须修，P2 记录
Step 7: 归档 — 报告存入 `01-技术架构/`，命名 `一致性分析报告-{YYYYMMDD}.md`
```
