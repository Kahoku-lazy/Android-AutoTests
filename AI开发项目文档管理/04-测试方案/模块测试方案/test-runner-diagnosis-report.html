🔴 P0 · 严重漏洞（7 项）

#1 Tab 分类超出 PRD 状态机 P0 · 前端
前端实施了 6 个 Tab（全部/执行中/等待中/已完成/未完成/未执行），但 PRD §1.1 原始状态机只定义 4 状态，PRD §6 组件树只列出 4 个 Tab。PRD 已同步升级至 v4.2 解决此矛盾。
违反 §1.1 状态机违反 §6 组件树违反 US-02
#2 TaskDetail.vue 引用未定义常量 STORAGE_KEY P0 · 前端
TaskDetail.vue:275 使用了 localStorage.getItem(STORAGE_KEY)，但 STORAGE_KEY 只在 index.vue:17 中定义，TaskDetail.vue 中未声明。运行时会抛出 ReferenceError: STORAGE_KEY is not defined。
违反 §8 规划中修复：删除 localStorage 逻辑，统一走 API
#3 TaskDetail.vue taskStatusInfo 逻辑错误 P0 · 前端
原代码中 taskStatusInfo() 只要 caseItems 非空且非等待就返回"已完成"，不检查 outcome 字段。被用户停止的任务（outcome='stopped'）在详情页也会显示"✅ 已完成"。（注：此问题已在最新代码中修复，outcome 判断已添加。）
违反 §2.6已修复 ✅
#4 异常终止不更新 TaskCard 状态 P0 · 后端
_execute_tests 的 except 块只更新 TestRunRecord.status='FAILED'，不更新 TaskCard。finally 块也不更新 TaskCard.outcome。异常终止的任务在 TaskCard 中永远看不到结果，前端状态卡住。
违反 US-02违反 US-03修复：except/finally 中更新 TaskCard
#5 TaskCard 三字段状态双轨制 P0 · 后端
status（后端更新）、running（前端 save API）、outcome（前端 save API）三个字段各自独立更新，无一致性保证。前端 save API 可以任意覆盖后端设置的状态，缺乏写保护。
违反 §1.1 状态机修复：统一由后端管理 status，前端只读
#6 WebSocket run_finished 始终设 outcome='completed' P0 · 逻辑
前端 WebSocket handler 中 run_finished case 硬编码 task.outcome = 'completed'，即使用户主动点击停止（前端已设 outcome='stopped'），WS 消息延迟到达后也会覆盖为 'completed'。应该检查当前 outcome 是否已被设为 stopped。
违反 US-03修复：检查现有 outcome，stopped 时不被覆盖
#7 AI 助手执行不创建 TaskCard P0 · 关联
AI 助手通过 AgentScope Tool run_test 调用 POST /api/runner/run 时不传 client_task_id，也不创建 TaskCard。前端任务列表看不到 AI 发起的执行。与 PRD US-05「跨设备同步」和全局 PRD AI-06 预期不一致。
违反 US-05违反 AI-06修复：AI Tool 调用前自动创建 TaskCard

🟠 P1 · 高风险（5 项）

#8 REST 端点无 JWT 鉴权 P1 · 安全
全部 10 个 REST 端点都使用 @csrf_exempt 装饰器，没有一个检查 request.user_id 或验证 JWT token。只有 WebSocket consumer 强制 JWT 验证。任何人知道 API 地址即可操作任务卡片和测试执行。
违反安全规则修复：添加 JWT 中间件验证
#9 task_card_list 硬编码空 currentCaseTitle/currentIteration P1 · 后端
views.py:670-671 中这两个字段永远返回空字符串和 0。前端刷新页面后无法恢复当前执行进度（当前用例名、当前轮次），只能依赖 WebSocket 实时更新。
违反 US-02修复：从 TaskCard 或 TestRunRecord 读取实时值
#10 WebSocket 无断线重连机制 P1 · 逻辑
connectTaskWS 没有重连逻辑。WebSocket 断开后：执行中的任务继续在后端运行，前端不再收到更新，任务完成后 outcome 不会被更新，任务永远停留在 running=true 状态。
违反 §8 规划中修复：添加指数退避重连
#11 TaskCard 缺少关键索引 P1 · 数据库
status 字段无索引，每次过滤排队任务需全表扫描；device_serial 无索引，按设备过滤时性能差；creator 无索引。
修复：添加 status + device_serial 联合索引
#12 _device_busy vs dp_devices.status 两套设备状态 P1 · 关联
test-runner 使用内存 _device_busy 集合管理设备忙状态，device-pool 使用 dp_devices.status 和 locked_by 字段。两套系统独立运行，互不同步。dp_devices 的 status/locked_by 不被 test-runner 使用。
违反 DP-03修复：统一使用 dp_devices 作为设备状态真相来源

🎯 三大核心矛盾

  1. PRD 状态机 vs 前端 Tab：前端 6 Tab 拆分已通过 PRD v4.2 升级同步解决。status 字段保持 4 值（idle/queued/running/done），outcome 字段在 done 状态下做二级区分（completed/stopped/interrupted/error）。
  2. 三字段状态管理混乱：TaskCard 的 status/running/outcome 各自独立更新、无一致性保证、无写保护。需要统一为：后端管理 status，前端通过 outcome 区分终态，running 由 status 推导。
  3. "已完成"定义四处不一致：后端 _mark_done（所有非异常结束都设 completed）、前端 taskStatusInfo index.vue（outcome==='completed'）、前端 TaskDetail.vue（已修复）、WebSocket handler（硬编码 completed）。需要统一为：正常完成→completed，主动停止→stopped，异常→interrupted/error。
