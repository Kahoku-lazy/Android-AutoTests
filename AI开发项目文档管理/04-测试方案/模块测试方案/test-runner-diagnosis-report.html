二、架构缺陷 — P0 致命级 × 3

P0-1 七套独立状态系统，无统一状态机

"设备是否在执行任务"由 7 个互不通信的变量共同决定。每次状态变更需同步更新 3-4 个变量，没有任何事务保证。任何一个更新失败 → 状态永久分歧。

变量位置生命周期重启后角色
_device_busyrunner.py:104进程级清空调度第一判定源
_active_runsrunner.py:101进程级清空运行状态缓存
_device_queueviews.py:48进程级DB重建(部分丢失)任务队列
_run_client_taskviews.py:51进程级永久丢失run_id→task_id 映射
TaskCardmodels.pyDB保留任务卡片真相
TestRunRecordmodels.pyDB保留执行记录真相
Devicedevice_pool/models.pyDB保留设备状态真相

正确设计应是一个统一状态机：

IDLE → QUEUED → ACQUIRING → RUNNING → FINALIZING → IDLE
 ↑                      ↓
 └──────── ERROR ←──────┘

每个状态转换由一个函数原子性地更新所有相关状态。

关键缺陷：调度决策先查内存 _device_busy（第一判定源），再查 DB Device.status（兜底），而 _start_next_queued 中更极端——只查内存不查 DB。内存优先的调度逻辑在重启和多进程场景下天然不可靠。

P0-2 Fire-and-Forget 调度链 — 无监控、无恢复

整个异步调度链由 4 处 asyncio.create_task 组成，全部 fire-and-forget，不保存返回值。任何一处静默异常 → 调度链永久断裂，队列中剩余任务永远得不到执行，且无任何日志告警。

start_test_run (views.py)
  └─→ asyncio.create_task(delayed_execute(...))     ← ① 无追踪
        └─→ _execute_tests(...)
              └─→ runner.run(...)
                    └─→ finally: _schedule_next_queued(serial)
                          └─→ asyncio.create_task(            ← ② 无追踪
                                _start_next_queued(...))
                                └─→ _execute_tests(...)
                                      └─→ finally: ... 递归 → ③④ 继续 fire-and-forget

当前 3 个 queued 任务（ID-1760/1762/1763/1764）正是因此卡死——它们被恢复进 _device_queue 但调度链从未成功启动消费。缺失的机制：

  • 无 task.add_done_callback — 异常被完全吞没
  • 无 u2.connect 超时 — 依赖系统 TCP 超时，可能阻塞数分钟
  • 无 runner.run() 总超时 — 理论上可无限运行
  • 无心跳检测 — runner.run() 卡在 u2 调用上无法被外部感知
  • 无看门狗/死信队列 — 失败的任务不会自动重试

P0-3 双重所有权 — test_runner 与 device_pool 各自控制设备

test_runner 完全绕过 device_pool 的连接管理和锁保护机制。两个系统互不知道对方在做什么：

资源test_runner (独立)device_pool (全局)协调？
u2 连接u2.connect(serial) 独立创建DevicePool.d 单例缓存无锁
忙标记_device_busy 内存 setDevice.status + occupied_by DB手动双写
任务队列_device_queue 内存 dictDeviceQueue DB 模型不通信
u2 锁无DevicePool._u2_lock绕过

后果：如果用户同时在元素定位页 dump UI + 执行引擎跑用例 → 两个 u2 连接并发操作同一设备 → 行为不可预测。此外 DevicePool 的 _u2_lock 确保截图流(2fps)与其他操作互不干扰，但 test_runner 完全绕过了这个保护。

六、前端风险分析

P1 假连接场景 A — 后端崩溃前端不知

后端重启 → _active_runs 清空 → 前端 WS 触发 onclose → 仅打印"日志断开" → 不会自动将 running 改为 false → TaskCard 持续显示"执行中" → 用户刷新页面后孤儿恢复才生效。

P1 假连接场景 B — 过时 runId 静默失效

前端 task.runId 存在但后端无对应活跃运行 → WS 连接成功（consumer 不校验 runId 是否存在）→ 注册成功后永远收不到消息 → WS 不会触发 onclose → 前端静默卡死，无任何提示。

P1 假连接场景 C — stale client_task_id

_run_client_task 映射丢失 → GET /api/runner/active 返回的 client_task_id 为空 → TaskDetail 轮询 active.client_task_id === task.value.id 永远不匹配 → 排队任务已被调度执行但前端检测不到。

P1 其他前端问题

  • WS 断开无重连机制 — ws.onclose 只打印日志，TaskDetail 进入静默状态后进度不再更新
  • 后端 _execute_tests 异常后 WS 可能已断 — 调用 on_device_error 时前端可能已收不到，只能靠下次 saveTask 轮询(3s)发现 outcome 变化
  • interrupted 状态仅页面刷新后可见 — 孤儿恢复在 API 调用时触发，不刷新则持续显示"执行中"
  • status 和 outcome 语义重叠 — deriveTaskStatus 中混合判断 status(idle/queued/running/done) 和 outcome(completed/stopped/interrupted/error)，边界场景不一致
  • 无超时检测 — 前端不检测任务是否超时，不主动探测后端存活
  • device_error 无结构化信息 — WS 消息只带 msg.error 字符串，无错误码/堆栈

P0 Device 状态双重翻转 — 竞态时间窗口

runner.run() 的 finally 提前释放设备，而此时 _execute_tests 还在写数据库：

T1: runner.run().finally → dp_release_device → Device.status=ONLINE  ← 提前释放!
T2: 此时 _execute_tests 仍在执行 persist/finalize_run/_mark_done (写DB)
T3: 另一个请求查询 Device → 看到 ONLINE → 尝试获取设备 → 成功
T4: TaskCard 还是 running，结果还没写完
T5: _execute_tests.finally → dp_release_device → ONLINE (已是 ONLINE，no-op)

结果: 一个设备同时有两个"进行中"的任务关联
