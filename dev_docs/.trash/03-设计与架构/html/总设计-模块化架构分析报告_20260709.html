核心结论

项目采用了「按业务域拆分」的模块化设计思路，功能确实是模块逐个累加起来的。前后端在物理和部署上完全独立，但并非「零耦合」——存在有意的集成耦合（业务流程串联）和少量违规耦合（2 处防火墙穿透）。

准确定义：模块化单体（Modular Monolith）——前后端分离、业务按域拆分，模块间通过 HTTP API 契约和受控的后端 api.py 协作。

10改进建议

P1
修复 2 处防火墙穿透
dashboard 和 ai_assistant 直接 import test_runner.runner._active_runs。应在 test_runner/api.py 暴露 list_active_runs_summary() 公开函数，dashboard 通过 api 层调用。
P2
前端跨模块 API 调用可集中管理
当前 test-runner、case-manager 的 api.js 中标注了「跨模块」调用，分散但可接受。若模块继续增多，可抽 shared/cross-api.js 统一管理跨域 HTTP 调用，便于追踪依赖。
P2
共享 models/ 包文档化
models/step_types.py 和 models/test_models.py 被 test_runner 和 agentscope_service 共用。长期可下沉为 shared/domain/ 并补充接口文档，明确其为「共享领域模型」而非某个 App 的私有代码。
P3
模块内巨型文件拆分
不影响模块间边界，但影响模块内可维护性。ChatView.vue（3,334 行）、views.py（CC=49）等应优先在各自模块内部拆分（详见《模块代码复杂度分析报告》）。
