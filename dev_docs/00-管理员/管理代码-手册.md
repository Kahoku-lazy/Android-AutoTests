## 核心问题

如何让 AI 改代码「可回滚、可审查、可证明修好」？

## 管理代码 — 设计文档

## 管理目标

- PR 小而可审，禁止无 PRD 的大爆炸改动  
- 契约（API / 防火墙）优先于实现细节  
- 每个修复有前端可见验收证据  
- 关键缺陷进入 BUGS / Memory

## 管理机制

1. **入口**：Issue / 任务拆分计划 → 全栈开发领取  
2. **约束**：安全（无硬编码密钥）、数据（前端只从 API 来）  
3. **审查**：`代码Review规则` + reviewer / quality-gate  
4. **归档**：开发工作记录按模块写入 `05-开发与测试/开发工作记录与审查结果/`

## 管理代码 — 实践结果

## 已落地

| 实践 | 结果 |
|------|------|
| 模块化 App + 前端 modules | 七业务域边界清晰 |
| Review / BUGS / 诊断手册 | 已模块化归档到开发记录 |
| test-runner 根因 Memory | 状态机绕过等教训已沉淀 |
| 质量评估指出的安全短板 | JWT 等问题已记入复盘，待闭环修复 |

## 待加强

- CI 门禁仍弱（复盘已标出）  
- 模块级「开发工作记录」多数仍为占位  
- 自动化回归覆盖不足

## 管理代码 — 总结与归纳

1. **修好 = 用户可见行为正确**，不是接口 JSON 看起来对。  
2. **边界违规要当 P0 管理**，否则模块化只是目录游戏。  
3. **审查规则要可执行**：没有分级与否决权，Review 会流于形式。  
4. **教训入库**：同一类 bug 出现第二次，是管理失败不是运气问题。

## 管理代码 — 成果模型

## 推荐产出物模型

```
代码管理包/
├── 变更说明（关联 PRD/Issue）
├── 影响面（模块 / API / 表）
├── Review 结论（分级）
├── 验收证据（截图/录屏/用例）
├── 回归范围
└── Memory / BUGS 更新记录
```

## 验收标准（管理员）

- [ ] 有对应需求或 Issue  
- [ ] Review 无未关闭 MUST  
- [ ] 浏览器路径已验证  
- [ ] 相关测试记录已更新
