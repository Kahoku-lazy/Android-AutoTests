一、项目初识阶段 — 从零开始

背景：此时没有任何文档与代码。以下为从零启动一个项目的完整工作流。

第一阶段：立项

1.1 产品定位
明确产品定位与用户
为什么要做这个产品？面向哪类用户？哪些客户有需求？哪些人会频繁使用？输出一句话定位 + 目标用户画像。
1.2 竞品分析
研究竞品技术、设计与思路
研究同类项目：它们的技术栈是什么？架构怎么设计？有哪些做得好的？有哪些做得不好的？
1.3 灵感分析
从多项目寻找设计灵感
分析多种同类型项目，找设计灵感。思考如何提升用户体验，改善产品交互与功能性。
1.4 价值评估
通过竞品市场与收益评估价值
竞品有多少用户？盈利模式是什么？这个赛道是否值得投入？输出立项验证报告。
📁 产出物存放在：dev_docs/01-立项与设计/立项验证/

第二阶段：需求与设计

2.1 产品需求
输出完整的产品需求文档
→ 需求大纲：项目定位 · 用户画像 · 业务逻辑架构 · 模块交互场景
→ 子模块 PRD：功能定位 · 页面交互 · 数据表单 · 异常场景 · 功能边界
→ 每个功能点附带验收条件 + 测试方案
2.2 架构设计
输出项目架构设计
→ 架构大纲：三层分离 · 模块依赖 · 交互边界 · 部署 · 设计决策
→ 子模块 ARCH：组件树 · API 设计 · 数据模型 · 交互时序 · 跨模块通信
→ 技术选型、命名标准、UI 设计素材
2.3 需求评审
评审需求文档
需求是否覆盖所有用户场景？验收条件是否可测试？功能边界是否明确？异常场景是否完整？
2.4 架构评审
评审架构设计
架构三层边界是否清晰？模块间交互是否合理？技术选型是否合适？数据模型是否完整？
📁 产出物：dev_docs/02-PRD需求/ + dev_docs/03-设计与架构/

3.1 任务拆分
根据需求与架构拆分任务
按模块拆分开发任务，明确每个任务的输入（PRD 功能块）、输出（代码 + 自测结果）、依赖关系。
3.2 需求迭代
需求端负责需求与功能设计迭代
开发过程中发现需求不明确 → 回 PRD 补充验收条件。发现功能边界冲突 → 回需求大纲调整边界定义。
3.3 功能开发
开发端按需求实现功能
代码不偏离架构设计 → 对照 ARCH 文档的文件结构。功能正确实现 → 对照 PRD 验收条件。写完自测 → 对照 DEVELOPMENT_CHECKLIST。
3.4 测试验证
测试端根据需求制定方案并验证
测试方案来源 = PRD 中的测试场景（前置→操作→期望）。输出：测试结果 + checklist 表单，确保功能与需求一致，核心业务链路没有问题。
3.5 三方评审
需求 · 开发 · 测试 三方信息同步
对照进度 → 确保文档与代码同步 → 测试结果与开发进度同步。三方中任何一方发现不一致 → 标记为阻塞项。
3.6 问题复盘
高频问题、验证问题复盘
记录：现象 → 根因 → 解决方案 → 测试方案。同类问题≥3次 → 新增规则到 DEVELOPMENT_CHECKLIST 或 .claude/rules/。确保不重复漏到交付阶段。

第四阶段：发布与项目风险评估

4.1 全功能验收
交付前对照需求验收一遍
以 PRD 验收条件为基准，逐功能走一遍完整的用户操作流程。核心链路（设备→元素→用例→执行→报告）必须全部通过。
4.2 风险评估
评估项目发布风险
哪些功能是新增的（高风险）？哪些是修改的（中风险）？哪些未改动（低风险）？有没有跨模块改动（高风险）？
4.3 安全 · 性能 · 稳定性
非功能需求检查
JWT 鉴权是否正常？API Key 是否正确加密？有没有 SQL 注入风险？大页面加载是否超过 3 秒？并发锁定是否安全？
4.4 易用性检查
考虑生产环境的易用性问题
首次使用是否有引导？错误提示是否用户能看懂（无技术术语）？没有设备时是否有清晰的操作指引？

第五阶段：产品交付

5.1 部署文档
部署步骤与依赖清单
环境要求（OS/Python/Node/ADB）、依赖安装（pip/npm）、数据库初始化、Redis 配置、一键启动脚本验证。
5.2 用户文档
快速上手指南
从登录到完成第一次测试的完整操作指南。含截图和常见问题解答。
5.3 回滚预案
发布失败的回滚方案
数据库 migration 回滚步骤、上一版本备份位置、回滚后验证清单。
5.4 监控与告警
上线后的监控指标
关键 API 错误率、设备连接成功率、执行引擎队列积压、前端页面加载时间。异常时通知谁？

代码实现

需求变更 → 代码修改
按变更级别执行
🔴 大改：PRD→ARCH→代码 全走一遍
🟡 增量：PRD加验收项→代码→跑CHECKLIST
🟢 修补：改代码→检查PRD受影响项
⚪ 重构：改代码→更新ARCH文件路径
发现 Bug
四层下钻定位
L1 浏览器 → L2 前端编译 → L3 API → L4 数据库。对照 PRD 确认「预期行为」vs「实际行为」的差异。对照 ARCH 检查是否架构边界被破坏。
Bug 修复后
回归测试 + 规则沉淀
跑受影响模块的 PRD 验收条件。跑 gen_arch_stats.py --check-md 确认没有破坏其他模块。
同类型 Bug ≥3 次 → 新增规则到 CHECKLIST 或 .claude/rules/。

测试保障

①
功能有没有问题？
走 PRD 验收条件 → 逐条打勾 → 核心链路全走一遍
②
是不是按需求做的？
对比 PRD 功能描述 vs 代码行为 → 不一致 = 未通过
③
架构有没有偏离？
gen_arch_stats.py --check-md → 数字不一致 = 漂移告警
④
改了A，B坏了没？
gen_arch_stats.py --check-boundaries → 跨模块写违规告警
⑤
核心链路通不通？
设备→元素→用例→执行→报告 端到端走一遍
⑥
改了文档没有？
代码改了对应的 PRD/ARCH 更新了吗？CHECKLIST 需要加新项吗？

如何确保 AI 按你的想法执行 — 验收措施

①
文档先行
PRD 写清楚了才动手。AI 不能在没有验收条件的情况下自由发挥。
②
CHECKLIST 守门
代码写完必须跑 CHECKLIST 自检。28 条全部通过才能提交给你验收。
③
自动检测不漂移
gen_arch_stats.py --check-md。数字不一致 → AI 自动检测到并修复。
④
变更级别判定
AI 必须先判断这次改动的级别（🔴🟡🟢⚪），再决定走什么流程。
⑤
先方案后执行
🔴大改必须先出方案等你审批。通过后才动手写代码。
⑥
结果对照 PRD
AI 输出验收结果时，逐条对照 PRD 验收条件，标注通过/失败/跳过。

如何测试你的设计是否帮助 AI 理解项目

测试方法目的判定标准
盲测：只给 PRD，不给 ARCH PRD 是否足够清晰？ AI 能否仅凭 PRD 理解功能行为并写出正确的交互逻辑？如果 AI 反复问"这个按钮点完会怎样"→ PRD 不够细。
盲测：只给 ARCH，不给 PRD ARCH 是否描述了结构？ AI 能否仅凭 ARCH 把新增文件放在正确的目录下？能否理解模块间的调用方式？
越界测试 CHECKLIST 是否有效？ 故意让 AI 做一个跨模块越界的操作（如在仪表盘加写操作）。CHECKLIST 能否捕获到这个违规？
变更测试 文档体系是否防漂移？ 改一个 API 端点但不更新 ARCH 文档。gen_arch_stats.py --check-md 是否检测到差异？
干扰测试 文档是否简洁有效？ 给 AI 一个过时的旧版 PRD（含 14 种步骤）。AI 是否会注意到 StepType 枚举已更新为 17 种？是否会对照 gen_arch_stats.py 的输出？
设计好坏的核心指标：AI 在没有你额外解释的情况下，仅凭 PRD + ARCH + CHECKLIST + gen_arch_stats.py，能否独立完成一个功能并输出正确的验收结果？
