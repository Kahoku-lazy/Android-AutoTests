三、你提问后我的处理流程

完整处理链路（从收到消息到回复）

收到消息
→
判断类型
→
确定范围
→
获取信息
→
推理/执行
→
输出结果

Step 1: 判断消息类型

A
纯问答："这个模块做什么的？"→ 只读，不需要改代码。直接读文档回答。
B
代码修改："改一下这个功能"→ 需要评估影响面、改代码、验证。走完整流程。
C
文档维护："更新一下 PRD"→ 只改文档，不改代码。
D
运行验证："跑一下看看"→ 启动应用，操作验证，输出结果。

Step 2: 确定范围和级别

🔴
大改：新增模块/改枚举/改架构。先读 PRD→ARCH→出方案→等你确认→执行。
🟡
增量：加功能/加 API。先读 PRD→加验收条件→改代码→跑 CHECKLIST。
🟢
修补：改文案/修 CSS。读 PRD 确认受影响项→改代码→检查。
⚪
重构：搬家/改名。改代码→更新 ARCH 路径→跑 gen_arch_stats.py。

Step 3-6 的具体行为（以代码修改为例）

3
获取信息：读 PRD 对应功能块（知道要做成什么样）→ 读 ARCH 对应模块（知道文件在哪、组件树、API）→ 用 Grep/Glob 定位要改的文件 → Read 打开文件确认当前内容。
4
推理/执行：如果是🔴大改 → EnterPlanMode 出计划等你批。如果是🟡增量 → 直接编辑，编辑完跑 gen_arch_stats.py 确认数字没漂移。如果是🟢修补 → 一次性改完。
5
自检：对照 DEVELOPMENT_CHECKLIST 逐项确认。PRD 验收条件与改动的代码行为是否一致？ARCH 结构描述是否需要更新？gen_arch_stats.py 是否通过？有没有跨模块越界？
6
输出：说明改了什么 + 为什么这样改 + 对照了哪些 PRD 验收条件 + gen_arch_stats 结果。如果你需要操作验证，会告诉你如何验证。

我什么时候会主动读文档（不是被动等你要求）

🔴 大改动时

先读 PRD（理解功能意图）→ 再读 ARCH（理解技术约束）→ 再读代码（看现有实现）。三个都读完了才动手。

🟡 增量时

先读 PRD 对应功能块（确认验收条件）→ 读 ARCH 对应模块（确认文件位置）→ 改代码。

🟢 修补时

直接读代码改。改完后对比 PRD 异常场景确认文案一致。ARCH 通常不需要动。
五、编写代码时我如何思考

思考链路（以"给元素表格加一个筛选条件"为例）

① 定位

前端在哪？
→ frontend/src/modules/element-locator/
→ ElementManager.vue

后端在哪？
→ apps/element_locator/
→ views.py

② 参照

已有的筛选 Tab 怎么写的？
→ Grep "filter" 或 "Tab"
→ 读已有代码的 DOM 结构和事件处理
→ 用同样的模式

③ 模仿

复制已有筛选 Tab 的结构
→ 改 label/筛选逻辑
→ 编码风格完全对齐
→ 不引入新的写法

④ 验证

改完后：
→ PRD 验收条件打勾
→ gen_arch_stats.py 通过
→ CHECKLIST 组 1/2/4 通过
→ 浏览器操作确认

我遵循的代码风格约束

我会做的
→ 模仿已有代码的命名、注释密度、缩进风格
→ 新增 API 用 {ok, data|error} 统一格式
→ 前端组件用 PascalCase.vue，JS 变量 camelCase
→ 数据库表用正确前缀（el_/dp_/cm_...）
→ 读 PRD 异常场景确认错误提示文案
→ 改完跑 gen_arch_stats.py
我不做的
→ 前端直连数据库
→ 跨 App import 内部实现（service/runner/consumer）
→ 仪表盘中写 INSERT/UPDATE/DELETE
→ 错误提示暴露技术术语给用户
→ 硬编码 API Key 或密码
→ 静默吞异常（catch 必须 log 或报错）
