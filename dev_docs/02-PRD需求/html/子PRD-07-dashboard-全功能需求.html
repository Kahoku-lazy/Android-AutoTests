🎯 第一部分：业务视角 — 仪表盘是做什么的

1 功能定位

仪表盘是登录后的首页聚合层：不拥有业务写操作、无自有业务表，只做跨模块只读统计 + 导航入口。

一句话：让测试工程师打开平台后，3 秒内看清设备是否可用、用例库规模、有没有任务在跑、近 12 天质量趋势，并一键跳到常用工作流。

2 用户故事

US-01 · 测试工程师 · 每日开工
登录后进入仪表盘，一眼看到设备 / 用例 / 执行健康度。
验收：/dashboard 加载后 KPI 卡片来自 API，禁止硬编码假数据。
US-02 · QA 负责人 · 周会前
查看近两周执行成功 / 失败趋势，决定本周修 Bug 还是扩覆盖。
验收：趋势图具备 labels + success / failed / new_cases 序列（近 12 日）。
US-03 · 测试工程师 · 快速开工
从首页一键跳到新建用例、执行测试、元素截图、AI 对话、报告。
验收：快捷操作路由正确（见 §5 F-05）。
US-04 · 任意登录用户 · 空库 / 新环境
无数据时页面不崩，有合法空态。
验收：全 0 仍渲染；任务区 / 活动区有空态文案。
US-05 · 项目经理 · 周报
拿到成功 / 失败 / 本周新建用例摘要数字，截图进周报。
验收：任务面板顶部 3 个摘要筹码来自 execution_summary。

3 解决的痛点

没有仪表盘之前

  • 要分别打开设备 / 用例 / 执行 / 报告页才能拼出「平台健康度」
  • 质量趋势靠翻历史记录，无法判断恶化还是偶发
  • 不知道此刻有没有任务在跑，要进执行引擎才看见
  • 常用入口分散，每天重复点侧边栏

有了仪表盘之后

  • 一屏聚合：KPI + 趋势 + 任务 + 活动
  • 趋势判断：12 日三色柱状图
  • 实时感知：运行中任务红点 + 活跃列表
  • 零跳转开工：快捷操作 + 7 模块 Bento 导航

10 端到端数据链（总览）

Dashboard 不写库。每条 UI 数字都能追溯到「哪张表 → 哪个聚合 → 哪个 JSON 字段 → 哪个组件」。

用户打开 /dashboard │ ├─ onMounted → Promise.allSettled │ ├─ GET /api/dashboard/stats/ ──► KPI / 趋势 / 任务 / Footer │ └─ GET /api/dashboard/activities/ ──► ActivityTimeline │ ├─ 点击「刷新」→ 仅重拉 stats（activities 不刷新，现网行为） │ └─ 点击快捷/导航 → router.push（无写操作）

⚙️ 状态机 — 页面 / 任务 / 系统三套状态

11 页面加载状态机

控制变量：loading（首屏）· refreshing（手动刷新）。二者互不替代。

┌─────────────┐ │ idle │ loading=false, refreshing=false │ （可交互） │ └──────┬──────┘ onMounted │ 点击「刷新」 ▼ ┌──────────────────────────────┐ │ loading=true │ │ StatsCard → skeleton │ │ （activities 同步请求） │ └──────────────┬───────────────┘ │ allSettled 结束 ▼ ┌──────────────────────────────┐ │ loading=false │ │ 成功：写入 refs │ │ 失败：须提示错误（AC-02） │ ← 现网 catch{} 静默，违规 └──────────────┬───────────────┘ │ 点击刷新 ──────┤ ▼ ┌──────────────────────────────┐ │ refreshing=true │ │ 按钮 loading；KPI 可保留旧值 │ │ 仅重拉 stats │ └──────────────┬───────────────┘ │ finally ▼ ┌─────────────┐ │ idle │ └─────────────┘
状态UI 表现允许操作退出条件
idle完整内容 / 空态刷新、导航、快捷onMounted / 点刷新
loadingKPI skeleton导航仍可用请求 settled
refreshing刷新按钮转圈避免重复点（按钮 disabled via loading）请求结束须复位
error（需求）ElMessage + 保留旧数据或空态可重试用户关闭 / 再次刷新

11.1 任务结果状态机（F-03）

后端 _case_result_status(passed, failed) 判定终态；活跃运行强制 running。 前端 TaskResultPanel.statusMeta 映射图标。

┌──────────┐ │ idle │ passed=0 ∧ failed=0 │ ○ 未执行│ （聚合窗口内无结果则跳过不入列表） └────┬─────┘ │ 出现 TestResult / 或进入活跃运行 ┌───────────────┼───────────────┐ ▼ ▼ ▼ ┌────────────┐ ┌────────────┐ ┌────────────┐ │ running │ │ success │ │ failed │ │ ▶ 执行中 │ │ ✓ 全通过 │ │ ✗ 全失败 │ │ 活跃运行 │ │ failed=0 │ │ passed=0 │ │ │ │ passed>0 │ │ failed>0 │ └─────┬──────┘ └────────────┘ └────────────┘ │ 运行结束，写入 TestResult ▼ ┌────────────┐ │ partial │ passed>0 ∧ failed>0 │ △ 部分失败│ └────────────┘ 判定伪代码： if running_in_active_set: return "running" if passed==0 and failed==0: return "idle" if failed==0: return "success" if passed==0: return "failed" return "partial"
状态图标进入条件UI
running▶活跃运行字典 / 公开 API 摘要任务行置顶倾向；KPI 红点
success✓窗口内全 pass绿态
failed✗窗口内全 fail红态
partial△既有 pass 又有 fail黄态
idle○无结果（通常不入列表）灰态

子用例 cases[].status 使用同一套枚举；运行中任务的子项全部为 running。

11.2 系统状态机（Footer）

system_status 判定（后端 dashboard_stats）： if devices.online > 0 OR devices.total == 0: → "normal" → Footer「正常运行」 else: → "no_devices" → Footer「无设备连接」 含义： · total==0：全新环境，不算异常 → normal · total>0 且 online==0：有登记设备但全不可见在线 → no_devices
状态条件文案用户动作建议
normal有在线设备，或库中无可见设备正常运行可开工
no_devices有可见设备记录但 online=0无设备连接去设备管理检查 ADB / 锁定

11.3 设备可见性状态（KPI 口径，只读投影）

Dashboard 不驱动设备状态迁移，只投影 device-pool 状态到 KPI。口径必须与设备列表一致。

Device.status ONLINE ──┐ BUSY ──┼──► 计入 online & total（可见） │ OFFLINE ─┼──► 从 Dashboard total 中排除（隐藏） DISCONNECTED ┘ KPI「在线设备」= count(ONLINE∪BUSY) / count(可见)

13 Dashboard 模块专属 AI 提示词

【角色与任务】

你是 Dashboard 模块（Android-AutoTests 仪表盘聚合层）的专属高级开发工程师。 你的任务是严格按照以下约束在该模块内生成或重构代码，任何超出边界的代码都将被视为不合格。

【绝对红线 — 严禁违反】

规则要求
1. 依赖隔离 ✅ 允许 Django ORM（跨 App 只读）· models/constants.py · @/shared/api-client.js · animal-island-vue · @/shared/animations.js
🔴 严禁 import 其他 App 的 service.py / runner.py / 内部私有变量（含 _active_runs）
🔴 严禁 前端组件直接 import api-client（必须通过模块 api.js）
🔴 严禁 前端 import Element Plus（Dashboard 是纯动森 UI 模块）
2. 禁止魔法值 状态字符串必须用 Enum：DeviceStatus.ONLINE（不是 "ONLINE"）
前端配色必须用 CSS 变量：var(--success)，不是 #6fba2c
3. 禁止裸奔 所有 view 必须 @csrf_exempt
必须返回 {ok: true|false, data/error: ...} 格式
catch {} 是 💀 死罪 — 必须重置 loading/refreshing 状态，并 ElMessage.error（或等价）提示用户
4. 日志规范 🔴 禁止 print() / console.log()
✅ 后端：logging.getLogger(__name__).info/warn/error（带 user_id + 耗时）
✅ 前端：console.error() 仅用于开发调试

【代码生成要求】

要求详情
附带单元测试 每次生成业务代码后必须同步输出测试：后端 3 类断言（正常 / 空库 / 未认证），前端 2 类断言（正常渲染 / 空数据）
Migration 脚本 涉及数据库变更时必须提供（注：Dashboard 无自有表，此条不适用）
代码风格 Python: snake_case · JS: camelCase · Vue: PascalCase 文件 / kebab-case 模板
私有函数 辅助函数以 _ 前缀命名（如 _safe_pct、_daily_execution_series）
组件组织 前端子组件放 components/ 目录，每个组件单一职责
功能范围 仅改 apps/dashboard/ 与 frontend/src/modules/dashboard/；活跃运行须经 test_runner.api 公开函数，禁止穿透

【数据流转铁律】

  • Dashboard 是只读聚合层：只做 SELECT，禁止 INSERT / UPDATE / DELETE
  • ORM 对象在 view 函数内部消费，返回前转换为纯 dict
  • 前端数据只从 API 获取：ref([]) 初始化为空，禁止硬编码假数据

【接口契约 — 禁止修改】

AI 的职责是实现接口内部逻辑，不得修改以下 4 个端点的响应格式：

端点方法响应格式
/api/dashboard/stats/GET{ok, data: {devices, cases, charts, execution_summary, recent_tasks, ...}}
/api/dashboard/activities/GET{ok, data: [...]}
/api/devices/stats/GET{ok, data: {online, busy, offline, total}}
/api/cases/stats/GET{ok, data: {total, enabled, disabled}}

📋 将此提示词作为 Dashboard 模块的 System Prompt 前缀，Agent 在修改该模块代码时自动加载
