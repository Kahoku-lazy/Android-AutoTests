CI/CD 是什么？

🔄 CI — 持续集成

Continuous Integration

开发者频繁地将代码合并到主干，每次合并自动触发构建和测试。

核心流程

Push 代码 → 自动编译 → 代码检查 → 跑测试 → 通知结果
几分钟内知道代码有没有"搞坏"

解决什么问题

  • ✅ 不再攒一周代码再合并（地狱级冲突）
  • ✅ 每次提交自动验证，坏了立刻知道
  • ✅ "在我机器上能跑" → CI 环境是标准化的

🚀 CD — 持续交付/部署

Continuous Delivery / Deployment

CI 通过后，自动（或一键）把代码推到目标环境。

两种 CD

持续交付 CI 通过 → 代码随时可发布，但发布按钮由人点击
持续部署 CI 通过 → 全自动推到生产环境，无需人工干预

典型流水线

CI 通过 → 打包 → 部署到测试环境 → 冒烟测试 → 部署到生产

项目现状评估

结论：❌ 当前不符合 CI/CD 标准

项目功能完备（7 个前端模块 + 6 个 Django App + AgentScope AI 引擎 + Redis + ChromaDB）， 代码量和复杂度已达到必须上 CI/CD 的阶段。 但目前 CI/CD 配置为零，质量保障完全依赖 .claude/rules/ 文档规则 + AI 自觉执行。

CI/CD 必备要素 项目现状 判定
CI 流水线文件 .github/workflows/ 目录不存在 缺失
自动化编译检查 vite build / python manage.py check 靠人工跑 缺失
自动化测试 有测试模块但无 CI 自动触发运行 缺失
代码质量门禁 依赖文档约束（五阶段流程、质量门禁），无自动执行 半人工
安全检查（凭据扫描） 依赖 reviewer agent，无自动 grep 扫描 半人工
Docker 容器化 无 Dockerfile，无 docker-compose 缺失
自动部署 全靠 python run.py start 手工启动 缺失
Git Hooks 无 pre-commit / pre-push 钩子 缺失
分支保护规则 无 PR 必审、CI 通过才能合并等规则 缺失
制品/构建缓存 无 缺失

⚠️ 核心矛盾

你的 CLAUDE.md 里有一套完整的质量体系——五阶段流程、三省吾身、质量门禁、reviewer/tester agent—— 这本质上是用 AI 纪律代替 CI 自动检查。

但 AI 纪律依赖"人（或 AI）记得执行"，而 CI 是 100% 强制执行。

举例：你说 🔴 禁止：curl API 返回正确就声称"修好了"—— 没有 CI 时这条规则全靠自觉。有了 CI，每次 push 自动打开浏览器验证（Playwright），不通过就标记 ❌，没有商量余地。

三阶段渐进式 CI/CD 方案

不追求一步到位。按收益/成本排序，每阶段独立可用，逐步叠加。

Phase 1：基础 CI — 编译 + 安全扫描

每次 push 自动检查，杜绝低级错误
⏱ 第 1 周
2-3 小时配置

流水线步骤

📤 git push → 🐍 Python 编译检查 → 🖥 前端编译检查 → 🔍 凭据安全扫描 → 📋 代码格式检查 → ✅ 通过 / ❌ 失败通知

解决的问题

  • 禁止"编译不过就提交"——CI 直接拦截
  • 禁止硬编码凭据合入仓库——自动 grep 扫描
  • 强制代码格式化——ruff + prettier 自动检查
  • PR 页面直接看到 ✅/❌ 状态

Phase 2：自动化测试 + 代码质量门禁

每次 PR 自动跑测试，用 Playwright 打开浏览器验证
⏱ 第 2-3 周
8-12 小时配置

流水线步骤

🔀 Pull Request → 📦 Phase 1 检查 → 🧪 Django 单元测试 → 🌐 Playwright E2E
🔬 API 往返验证 → 📊 覆盖率报告 → ✅ 门禁通过 → 允许合并
❌ 任一失败 → 阻止合并

解决的问题

  • 杜绝"改了 A 模块，炸了 B 模块"——全量回归测试自动跑
  • Playwright 打开浏览器验证：登录 → 各模块页面加载 → 确认不白屏
  • API 往返验证：POST 创建 → GET 读取 → 数据一致性检查（解决 el-cascader 之类类型陷阱）
  • 覆盖率报告自动生成，低于阈值阻止合并

Phase 3：Docker 化 + 自动部署

一键部署到测试/生产环境
⏱ 第 3-4 周
12-16 小时配置

解决的问题

  • 消除"我机器上能跑"——Docker 保证环境一致性
  • 新开发者入职：docker compose up 一条命令启动全部服务
  • 合并到 main → 自动部署到测试服务器 → Playwright 冒烟测试 → 通过后自动部署生产

实施路线图

第 1 周 · Phase 1

基础 CI 流水线上线

创建 .github/workflows/ci-phase1.yml → 配置 Python + Node.js 编译检查 → 添加凭据安全扫描 → 添加 ruff + prettier 格式检查 → 配置分支保护规则（main/Kahoku 分支要求 CI 通过才能合并）

第 2 周 · Phase 2a

自动化测试接入

编写 Django pytest 测试用例 → 接入 coverage 覆盖率检查（阈值 40%） → 编写 Playwright 冒烟测试（登录 + 7 个模块页面加载检查） → 接入 API 往返验证（POST+GET 数据一致性）

第 3 周 · Phase 2b

质量门禁上线

配置 PR 模板（含自检清单） → 设置 GitHub 分支保护：必须 CI 通过 + 至少 1 人 Review → 接入 coverage report artifact → 配置 Slack/钉钉通知（CI 失败时告警）

第 4 周 · Phase 3

Docker 化 + 自动部署

编写 Dockerfile + docker-compose.yml → 配置多阶段构建（减小镜像体积） → 编写 CD 流水线（合并 main → 构建镜像 → 部署测试环境） → 配置 healthcheck + 自动回滚策略
