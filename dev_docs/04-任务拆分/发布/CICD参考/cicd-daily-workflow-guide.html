引入 CI/CD 前后的变化

❌ 以前（无 CI/CD）

  • 😰 写代码 → 手动跑编译 → 经常忘了跑
  • 😰 改了 A 模块 → 不知道 B 模块炸了
  • 😰 密码不小心写死在代码里 → 靠运气发现
  • 😰 回忆录式提交："这个改了啥来着？"
  • 😰 合并冲突时找不到问题引入点
  • 😰 部署全靠 SSH + 手工敲命令

✅ 现在（有 CI/CD）

  • 🤖 push → 自动编译 → 几分钟内知道结果
  • 🤖 每次 push 全量检查 → 模块间破坏性改动立即发现
  • 🤖 自动扫描硬编码密码 → 写错直接拦截
  • 🤖 每个 commit 都有清晰的 CI 状态
  • 🤖 PR 页面直接看到哪个 commit 引入了问题
  • 🤖 合并 → 自动部署 → 健康检查

🔍 每一步在做什么

1

本地开发 — 在 Aaron 分支写代码

这是你最熟悉的环节。Vue 前端改 UI，Django 后端写 API，跟以前完全一样。

💡 唯一新增的习惯：写完代码后，本地先跑一下编译检查，确保不会推到 GitHub 才报错。

# 提交前本地自检（30 秒） cd Android-AutoTests python manage.py check # Django 配置检查 cd frontend && npx vite build # 前端编译
2

git push — 推到 GitHub，CI 自动启动

这就是你刚才做的事。敲下 git push 后，GitHub 检测到你的 push，自动启动 .github/workflows/ci-phase1.yml 里定义的流水线。

💡 完全自动化——你不需要做任何事，push 就是起跑信号。

3

CI 自动跑 — 三个检查员同时工作

你的 CI 流水线有 3 个 Job，它们并行运行，互不等待。哪个先跑完就先出结果。

Job（检查员）它做什么它在检查什么
backend-check pip install → Django check → ruff 格式 → ruff lint Python 代码能不能跑、格式对不对、有没有明显的代码质量问题
frontend-check npm ci → vite build → prettier 格式 Vue/JS 代码能不能编译成功、代码格式统不统一
security-scan grep 扫描 5 类硬编码凭据 有没有不小心把密码/API Key 写在代码里

💡 并行是什么概念？

三个 Job 各自在一台独立的云服务器上跑，同时开始，谁先跑完谁先汇报。最慢的那个决定了总时间。
你的项目：backend ~3min + frontend ~3min + security ~30s = 总共约 3-4 分钟出全部结果。

4

全部通过 — 出现三个绿色对勾

所有 Job 返回 ✅，你的 PR 页面显示：

backend-check — Success    frontend-check — Success    security-scan — Success

💡 这三个绿勾意味着：你的代码编译通过、格式规范、没有硬编码密码。可以放心让别人 Review。

5

创建 Pull Request — Aaron → Kahoku

在 GitHub 上创建 PR，把 Aaron 分支的改动请求合并到 Kahoku。

你的项目已配置了 PR 模板（.github/pull_request_template.md），创建 PR 时会自动填充一个自检清单。

💡 PR 创建后，CI 会再跑一次（因为 PR 有自己的触发条件）。如果 PR 页面出现三个绿勾 + 绿字 "Merging is allowed"，就说明可以合并了。

6

Code Review — 至少 1 人审查

你的 Kahoku 分支已配置了保护规则：必须至少 1 人审批 + CI 全绿才能合并。

Reviewer 在 PR 页面查看 diff、写评论、点 Approve。如果有问题，点 Request Changes，你需要修改后再 push。

7

合并 — 代码进入主分支

所有的灯都绿了：CI ✅、Review ✅。点击 Merge → 你的改动正式成为项目的一部分。

💡 合并后可以在本地切回 Kahoku 拉最新代码：git checkout Kahoku && git pull

8

CD 部署 — 自动推到目标环境

Phase 1 还没实现这一步，但这是 Phase 3 的目标。合并到 Kahoku 后自动触发部署流水线：

构建 Docker 镜像 → 推到镜像仓库 → 部署到测试服务器 → 冒烟测试 → 通过后部署生产。

💡 部署出错？CI 会自动回滚到上一个正常版本。

CI 报错了怎么办？

CI 报错不是坏事——它是在帮你发现代码问题，阻止有问题的代码进入主分支。把 CI 当做一个免费的代码检查助手。

❌ 场景 1：backend-check 失败了

怎么看？ GitHub Actions → 点失败的 Job → 展开失败的 Step → 看红色报错行

常见原因 & 修复：

  1. ruff format --check 失败了 → 代码格式不对 → 本地跑 ruff format apps/ 自动修复，重新 commit push
  2. python manage.py check 失败了 → Django 配置有问题 → 本地跑一样的命令看详细报错
  3. pip install 失败了 → requirements.txt 有问题 → 检查依赖列表
❌ 场景 2：frontend-check 失败了

常见原因 & 修复：

  1. vite build 失败了 → Vue/JS 语法错误 → 本地跑 npx vite build 看详细错误
  2. prettier --check 失败了 → 代码格式不对 → 本地跑 npx prettier --write "src/**/*.{vue,js,css}" 自动修复
❌ 场景 3：security-scan 失败了

这是最需要认真对待的失败——说明你的代码里有硬编码的密码或 API Key。

常见原因 & 修复：

  1. 你在代码里写了 api_key = 'sk-abc123...' → 改为 api_key = os.environ.get('KEY_NAME', '')
  2. 你在代码里写了 password = 'admin123' → 改为从环境变量或数据库读取
  3. 点击 Job 日志，滚动到红色 ❌ 行，它告诉你是哪个文件哪一行有问题

💡 修复 CI 报错的标准流程

打开 GitHub Actions 日志 → 定位红色 ❌ 行 → 读报错信息 → 本地修复 → git add + commit + push → CI 自动重跑 → 等待变绿 ✅

日常场景演练

✅ 正常的一天（10 分钟）
  1. 拉代码：git checkout Aaron && git pull origin Kahoku — 先同步主分支最新代码
  2. 写代码：修改 apps/ai_assistant/views.py，加一个新 API
  3. 本地检查：python manage.py check — 确认 Django 配置正常
  4. 提交：git add -A && git commit -m "feat: 新增 AI 助手 API" && git push
  5. 等待 3 分钟：去 github.com/Kahoku-lazy/Android-AutoTests/actions 看流水线进度
  6. 三个绿勾亮了：✅ 创建 PR，填写模板，请求 Review
  7. Review 通过后合并：点击 Merge → 完成！
⚠️ 出问题的一天（修复后再提交）
  1. push 后 2 分钟：收到 GitHub 邮件/通知 — CI 失败了 ❌
  2. 打开 Actions 页面：frontend-check ❌ — 点进去看日志
  3. 发现报错：prettier --check 提示 ChatView.vue 格式不对
  4. 本地修复：cd frontend && npx prettier --write "src/**/*.{vue,js,css}"
  5. 再次提交：git add -A && git commit -m "style: prettier 格式化" && git push
  6. CI 自动重跑：这次全部变绿 ✅
  7. 创建 PR：没有任何阻拦
🔄 多人协作的一天（未来场景）
  1. 同事 Alice 也 push 了她的改动，CI 全绿，她提了 PR
  2. 你也提了 PR，但你的改动和 Alice 的改到了同一个文件
  3. Alice 的 PR 先合并了 → 你的 PR 显示 "This branch is out-of-date"
  4. 因为 Kahoku 开了 strict 模式（分支必须紧跟主分支最新提交），你需要：
# 同步主分支最新代码到你的分支 git checkout Aaron git pull origin Kahoku # 拉取 Kahoku 最新（含 Alice 的合并） # 如果有冲突 → 解决冲突 git push # CI 再跑一次
