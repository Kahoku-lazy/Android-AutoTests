前端显示

frontend/src/modules/test-runner/
  • 任务卡片列表 + 状态筛选（执行中/等待中/已完成/未完成）
  • TaskDetail 详情页 — 用例步骤实时状态 + 日志面板

调度器

apps/test_scheduler/（新建 App）
  • 接收前端 + AgentScope 的任务请求（统一入口）
  • 设备队列管理 — FIFO 入队、出队、取消排队
  • 并发控制 — 同设备同时只允许一个任务执行
  • TaskCard 状态机 — idle → queued → running → done
  • TaskCard CRUD — 创建/保存/删除任务卡片
  • WebSocket 事件路由 — 把执行器回调转发给前端
  • 启动恢复 — 服务重启后重建内存队列
  • 协议监管 — 心跳检测、序列号对账、健康端点
⚙️

执行器

apps/test_runner/（精简保留）
  • 接收调度器委托 — 在已锁定的设备上执行用例
  • 14 种步骤映射 — click / wait / verify_text / …
  • u2 操作 + 崩溃恢复 + 重连重试
  • 进度上报 — 通过回调接口报告每一步结果
  • 报告生成 — CSV + 日志文件
  • 不管设备锁、不管排队、不管谁在等
  • 不直接持有 WebSocket 引用

2 模块化之前通过协议来分工协作 — 协议清单设计

三层之间不直接 import 对方的内部实现，只通过下面三份协议交互。每份协议是一组带类型签名的接口清单。

协议一 前端 ↔ 调度器：HTTP REST

方法端点说明请求体响应
POST /api/scheduler/run 创建并启动任务 {case_ids, loop_count, device_serial, interval_seconds, client_task_id, start_at?, end_at?} {ok, runs: [{run_id, serial}], queued: [serial]}
POST /api/scheduler/run/:id/stop 停止运行中任务 {} {ok, stopped: true}
POST /api/scheduler/queue/cancel 取消排队任务 {client_task_id, device_serial} {ok, message}
GET /api/scheduler/active 查询活跃运行列表 — {ok, active: [{run_id, client_task_id, serial, ...}]}
GET /api/scheduler/run/:id/status 查询单个运行状态 — {ok, run: {status, case_results, ...}}
GET /api/scheduler/runs 历史运行记录 — {ok, runs: [...]}
GET /api/scheduler/tasks 任务卡片列表 — {ok, tasks: [...]}
POST /api/scheduler/tasks/save 保存任务卡片 {id, name, caseIds, deviceSerial, ...} {ok, task}
DELETE /api/scheduler/tasks/:id 删除任务卡片 — {ok}
GET /api/scheduler/monitor/:run_id 协议健康监控 — {ok, health, seq, latency_ms, clients}
GET /api/scheduler/run/:id/snapshot 状态快照（降级兜底） — {ok, status, step_states, case_progress, logs, seq_last}

协议二 调度器 ↔ 执行器：Python Callback 接口

执行器通过此接口向调度器报告进度。调度器实现这些方法，执行器只调用、不关心谁在听。

方法签名调用时机参数等级
async on_run_started(run_id) 预检通过，正式进入执行 run_id: str 关键
async on_case_started(run_id, case_id, case_title, loop_count) 开始执行一个用例 case_id: str, case_title: str, loop_count: int 重要
async on_step_started(run_id, case_id, iteration, step_index, total_steps, step_type, description) 开始执行一个步骤 step_index: int, step_type: str, description: str 普通
async on_step_result(run_id, case_id, iteration, step_index, total_steps, step_type, description, result) 步骤执行完成 result: "pass" | "fail" | "stopped" 普通
async on_iteration_result(run_id, case_id, iteration, result, duration_ms) 一轮循环结束 iteration: int, result: str, duration_ms: float 重要
async on_case_finished(run_id, case_id, pass_count, fail_count, rate) 一个用例的全部循环结束 pass_count: int, fail_count: int, rate: str 重要
async on_run_finished(run_id, summary, csv_path, log_path) 全部用例执行完成 summary: dict, csv_path: str, log_path: str 关键
async on_log(run_id, message) 任意时刻输出日志 message: str 普通
async on_device_error(run_id, error) 设备连接异常 error: str 关键

协议三 调度器 → 前端：WebSocket 事件流

调度器把执行器的回调事件 + 自身监管事件，统一通过 WebSocket 推送给前端。每条消息带 seq 序号。

事件 typepayload 字段频率前端效果
run_started{}1 次/run任务卡片亮起 "⚡ 执行中"
case_started{case_id, case_title, loop_count}1 次/case用例行高亮 "◆ 执行中"
step_started{case_id, iteration, step_index, total_steps, step_type, description}1 次/step步骤卡片变蓝 + 脉冲动画
step_result{...同上, result: "pass"|"fail"}1 次/step步骤变绿(✅)或变红(❌)
iteration_result{case_id, iteration, result, duration_ms}1 次/轮用例计数更新 "✅2 ❌1"
case_finished{case_id, pass, fail, rate}1 次/case用例标记完成，数字定格
run_finished{summary, csv_path, log_path}1 次/run进度条 100%，显示结论
log{message, level}不限日志区追加一行
device_error{error}0-1 次任务中断，显示错误
heartbeat{queue_depth, active_runs}每 5s更新连接状态灯

💡 三条时序约定：① 每条消息带 seq 递增序号，前端检测 gap → 触发对账； ② 广播用 gather + 2s 超时，慢客户端不拖垮其他人； ③ 关键事件 (run_started / run_finished / device_error) 必须 await 确认后才继续。

3 架构模式 · 功能定位 · 用户故事

3.1 架构模式：事件驱动的调度器模式

前端
发起任务 → 调度器
排队/分配 → 执行器
跑用例 → 调度器
转发事件 → 前端
实时更新

调度器是唯一入口——前端和 AgentScope 都通过调度器发起任务，不存在绕过的路径。 执行器是纯执行单元——接收已锁定的设备和用例列表，跑完后把结果交还给调度器。 前端是被动渲染——收到什么事件就展示什么状态，不做调度决策。

3.2 在平台中的功能定位

维度说明
平台角色执行引擎是 Android-AutoTests 平台的核心运转模块——用例管理定义了"测什么"，元素定位解决了"怎么找到"，执行引擎负责"真正跑起来"
上游依赖设备池（提供设备锁定/释放）→ 用例管理（提供用例定义）→ 元素定位（提供 XPath 定位符）
下游消费者报告生成（CSV/日志）→ AI 助手（AgentScope 通过调度器 API 发起任务）→ 前端仪表盘
与其他模块的关系执行引擎不拥有设备（device_pool 拥有）、不拥有用例定义（case_manager 拥有）、不拥有报告模板（report_generator 拥有）。它只负责调度和执行
关键约束一台设备同时只能执行一个任务；一个任务可以包含多个用例；每个用例循环 N 轮；步骤执行是阻塞同步操作（u2）

3.3 用户故事

测试工程师
我创建一个任务，选择用例和设备，点击执行
我想看到每个步骤的实时执行状态——哪个步骤正在跑、哪个通过了、哪个失败了——以及完整的执行日志。如果设备正忙，我的任务应该自动排队，设备空闲后自动开始。
测试工程师
我看到执行引擎页面时，默认显示正在执行的任务
我关心的是当前在跑什么、进度如何。已完成的历史任务可以切换到对应分类查看。同一台设备的等待任务应该清晰显示排队关系。
平台开发者
我新增一个步骤类型或调整执行逻辑
我只改执行器（adapter.py + executor.py），调度器和前端不受影响。协议接口不变，其他模块不需要重新测试。
平台开发者
我调整排队策略（比如优先级队列）
我只改调度器（queue_manager.py），执行器和前端不受影响。前端的 WebSocket 事件格式不变，照样渲染。
AI 助手用户
我用对话让 AI 帮我跑测试
AI 通过调度器 API 创建任务，和前端创建走同一条路径。任务在前端同样可见、可停止。不会出现"AI 在跑但我看不到"的情况。
平台管理员
服务重启后，之前排队的任务不丢失
调度器启动时从数据库恢复 TaskCard（status="queued"），重建内存队列。孤儿任务自动标记中断并释放设备。不需要手动清理。
4 当前与方案之间的对比 & 改进策略

4.1 现状 vs 方案对比

对比维度❌ 当前状态✅ 方案目标
模块边界 全部混在 test_runner 一个 App，views.py 1227 行，runner.py 473 行。调度、执行、查询不分 拆为三个独立模块：前端显示 / 调度器(test_scheduler) / 执行器(test_runner)，每个模块职责单一
AgentScope 路径 AgentScope RunTestTool 直接 import TestRunner，绕过排队机制和 TaskCard，AI 任务前端不可见 AgentScope 走调度器 API，和前端同一条路径，AI 任务也有 TaskCard、也排队、前端可见
设备状态 内存 _device_busy (set) 和 DB dp_devices.status (BUSY) 双重来源，各自维护，可能不同步 调度器统一管理设备状态，内存 + DB 同步写入，单一来源
事件通信 回调是 fire-and-forget (run_coroutine_threadsafe)，不等待完成；_broadcast 串行阻塞；无序列号 TREP 协议：seq 序号 + gather 并发广播 + 关键事件 await 确认 + 心跳监管

故障恢复 state_machine.py 直接 ORM 写 Device 表（违反防火墙#2）；恢复逻辑散落在 apps.py + recovery_helpers.py 调度器 recovery.py 统一启动恢复，通过 device_pool.api 释放设备（遵守防火墙#2）
文件规模 test_runner 合计 3136 行，单文件最高 1227 行（3× 上限） test_scheduler ~800 行 + test_runner ~1500 行（精简后），单文件 ≤ 400 行
可测试性 调度逻辑和执行逻辑耦合，无法独立测试排队策略或步骤执行 调度器和执行器可分别 mock 对方接口，独立单元测试
协议可见性 接口隐式存在于代码中，无文档、无版本、无监管 TREP v1.0 明确定义，有 monitor 端点、有健康状态灯、有降级兜底

4.2 改进策略：四阶段渐进式

不搞大爆炸式重构。每阶段独立可验证，不阻塞其他工作。

  1. 阶段 0：内部接口抽象（0 风险，不拆 App）

    在现有 test_runner 内部：
    · 把 _broadcast 改为 gather+timeout，加 seq 序号
    · 把 TestRunner.run() 内部的 acquire_device/release_device 移除，由 views.py 在调用前后管理
    · 新增 monitor 和 snapshot 端点
    · URL 不变、表不变、前端不变。编译通过即可验证。

  2. 阶段 1：提取调度器（新增 test_scheduler App）

    创建 apps/test_scheduler/：
    · 迁移 TaskCard Model、state_machine.py → scheduler
    · 提取 views.py 调度逻辑 → queue_manager.py + task_manager.py
    · 迁移 WebSocket consumers.py → scheduler
    · 挂载 /api/scheduler/* 路由，旧 /api/runner/* 保留转发
    · 前端暂时无感，旧 URL 仍然可用。

  3. 阶段 2：修复 AgentScope 绕过路径 + 前端适配

    · 改 agentscope_service/tools/runner_tools.py → 走调度器 api
    · 前端 api.js 指向新 /scheduler/* 路径
    · 前端加设备忙预检（同设备已有运行任务 → 立即 queued）
    · 前端加健康状态指示灯

  4. 阶段 3：清理旧代码 + 移除旧路由

    · 删除 test_runner 中已迁移的函数和文件
    · 移除旧 URL 转发
    · 最终文件行数全部 ≤ 400 行
