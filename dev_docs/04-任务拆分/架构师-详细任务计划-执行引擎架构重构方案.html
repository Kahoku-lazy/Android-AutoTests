一、设计原则 — 四个"单一"

这些原则是评估"改架构还是加代码"的判定标准。违反任一原则的方案都被否决。

原则 1：单一真相来源

每个状态只在一个位置存储。对于设备占用状态，DB Device 表是唯一真相。内存变量只是 DB 的只读缓存，不作为决策依据。消除 _device_busy / _active_runs / _device_queue / _run_client_task 四个内存变量。

原则 2：单一状态转换入口

所有状态变更通过 RunStateMachine.transition() 单一入口。该函数原子性地更新 TaskCard + TestRunRecord，任何一步失败则整体回滚。禁止代码中随意 task.status = 'xxx'。

原则 3：单一设备所有者

device_pool 是设备的唯一管理者。test_runner 通过"借用-归还"模式获取设备连接，不再自行创建 u2 连接。设备的所有锁/释放/超时检测由 device_pool 统一提供。

原则 4：单一调度循环

每个设备有且只有一个调度协程，循环消费该设备的任务队列。消除多入口的 fire-and-forget 调用链。协程的生命周期在 apps.py 中管理，启动时创建，关闭时优雅终止。

三、状态机设计：RunStateMachine

TaskCard 状态转换图

IDLE → QUEUED → RUNNING → DONE
QUEUED → CANCELLED→IDLE | RUNNING → ERROR

RunStateMachine API

class RunStateMachine:
    """TaskCard + TestRunRecord 原子状态管理器。所有状态变更的唯一入口。"""

    @staticmethod
    def enqueue(task_card: TaskCard, serial: str) -> None:
        """IDLE → QUEUED。将任务加入指定设备的等待队列。"""

    @staticmethod
    def dequeue(task_card: TaskCard) -> None:
        """QUEUED → RUNNING。从队列取出并开始执行。
        同时创建 TestRunRecord(status=RUNNING)。原子操作。"""

    @staticmethod
    def record_iteration(run_record, case_id, iteration, result, duration_ms):
        """追加一条 TestResult。"""

    @staticmethod
    def complete(task_card, run_record, summary, case_items):
        """RUNNING → DONE(outcome=completed)。
        原子更新: TestRunRecord.status=COMPLETED + TaskCard.status=done。"""

    @staticmethod
    def fail(task_card, run_record, error_msg, outcome='error'):
        """RUNNING → DONE(outcome=error|stopped)。
        原子更新: TestRunRecord.status=FAILED/STOPPED + TaskCard.status=done。"""

    @staticmethod
    def cancel(task_card):
        """QUEUED → IDLE。取消排队任务。"""

    @staticmethod
    def recover_orphans():
        """启动恢复: TaskCard(running)→interrupted + TestRunRecord(RUNNING)→FAILED。
        在 apps.py ready() 中调用。"""

关键实现细节

  • 原子性保证：transition() 内部所有 DB 操作在同一个 Django 事务中。任一操作失败 → 事务回滚 → 状态不变。
  • 幂等性：同一状态重复转换是安全 no-op（例如 DONE→DONE 直接返回）。
  • 合法性校验：非法转换（如 IDLE→DONE）抛出 InvalidTransition 异常。
  • 日志记录：每次状态转换记录 print(f"[state] {task_id} {from}→{to}")。
  • 数据一致性：run_record 和 task_card 的状态始终同步更新，不存在一个已更新另一个未更新的窗口。

四、调度器设计：DeviceScheduler

核心思路：每设备一个消费者协程

class DeviceScheduler:
    """每个 ONLINE 设备一个后台协程，循环消费该设备的任务队列。

    替代当前的:
      - _device_queue (内存 dict)
      - _start_next_queued + _schedule_next_queued (fire-and-forget 链)
      - 4 处 asyncio.create_task 无监控调用
    """

    _loops: dict[str, asyncio.Task] = {}  # serial → consumer coroutine

    async def start_device_loop(self, serial: str):
        """为设备启动消费者协程。在 apps.py ready() + 设备 ONLINE 时调用。"""
        if serial in self._loops:
            return  # 已在运行
        task = asyncio.create_task(self._consume(serial))
        task.add_done_callback(lambda t: self._on_loop_died(serial, t))
        self._loops[serial] = task

    async def _consume(self, serial: str):
        """单设备消费循环（核心调度逻辑）。
        1. 检查是否有 queued TaskCard for this serial
        2. 有 → borrow_device → 执行 → return_device → 回到 1
        3. 无 → sleep 2s → 回到 1
        4. 异常 → 记录日志，sleep 5s，回到 1（不退出循环！）
        5. 设备 OFFLINE → 停止循环
        """

    async def stop_device_loop(self, serial: str):
        """优雅停止设备的消费者协程。"""

    def _on_loop_died(self, serial, task):
        """协程意外死亡回调。记录日志 + 尝试重启。"""

风险 borrow_device 与现有 connect_device 的关系

connect_device 是用户在前端"连接设备"时调用的，设置 locked_by（用户绑定），属于 device_pool 的现有功能。

borrow_device 是 test_runner 在执行任务时调用的，设置 occupied_by（进程占用）。两者通过 DB 的 Device.status 和 Device.occupied_by 协调，不冲突。这个设计中，borrow_device 实际上复用了现有的 acquire_device 函数，只是增加了返回 u2 连接的能力。

验收标准：test_runner 不再创建独立 u2 连接；element_locator 和 test_runner 不能同时操作同一设备；设备状态始终准确

1. 进程重启

   → TestRunRecord(RUNNING) → FAILED

风险 迁移兼容性

  • TaskCard 旧数据：升级后首次启动时 recover_orphans() 会修复所有旧数据的不一致状态。无需手动迁移。
  • API 兼容：所有现有 REST 端点保持不变（返回格式不变）。前端无需大改。
  • rollback 方案：如果阶段 2 调度器有问题，可先回退到阶段 1（仅状态机），阶段 1 只替换状态更新逻辑，不改变调度行为。
  • device_pool API 新增：borrow_device 和 return_device 是纯新增，不影响现有 API。阶段 3 可独立回退。
