一、功能定位

一句话：把测试用例在真实设备上跑起来，产出结果。

输入

  • 测什么：来自 case_manager 的用例定义（steps_json）
  • 在哪测：来自 device_pool 的真实手机
  • 怎么跑：循环次数、轮间间隔、定时参数

输出

  • 每步结果：pass / fail / stopped
  • BUG 单：失败步骤自动汇总，编号展示
  • 测试报告：供 report_generator 消费
  • 执行日志：WebSocket 实时推送

模块协作关系

case_manager
用什么例 → device_pool
用什么手机 → 执行引擎
调度 + 执行 → report_generator
出什么报告
执行引擎是中枢：上游两个模块（用例、设备），下游一个模块（报告），外加 AI 助手通过 API 触发。 每个模块独立负责自己的领域，执行引擎不做用例管理、不做设备发现、不做报告渲染。

二、业务场景 — 以手机为单位的调度模型

每个场景的核心约束：一台手机在同一时间只能执行一个任务。多任务串行排队，多手机并行互不干扰。

S1: 1 手机 × 1 任务

用户选一台手机，创建一个任务，点执行。

检查空闲 → 占用 → u2 连接
→ 执行步骤 → 释放 → 完成

约束：手机 ONLINE、未被占用、u2 可达

S2: 1 手机 × N 任务排队

同一台手机连续提交多个任务。

任务A 执行中（手机忙）
任务B 排队 → A 完成 → B 出队
任务C 排队 → B 完成 → C 出队

约束：队列持久化（重启不丢）、FIFO、自动消费

S3: N 手机 × N 任务并行

手机 A 的任务队列和手机 B 的任务队列完全独立。

手机A 队列: 任务1,任务3,任务5
手机B 队列: 任务2,任务4,任务6
两部手机同时执行，互不影响

约束：每手机独立队列 + 独立协程 + 独立 u2 线程池

S4: N 手机 × M 任务分配 (M>N)

10 个任务分配给 2 台手机，每台 5 个。

用户指定每任务的 deviceSerial
各手机独立排队，独立消费

约束：任务创建时锁定设备分配

S5: 循环执行

同一用例跑 N 轮，每轮间隔可配。

第1轮 → sleep(interval) → 第2轮
  → ... → 第N轮

约束：每轮结果为独立 TestResult 行

S6: 定时执行

指定 start_at / end_at 时间窗口。

start_at 前 → 等待
start_at 到 → 开始执行
end_at 到 → 自动停止

约束：时间窗口在 delayed_execute 中检查

S7: 单步调试

CaseEditor 中逐步骤验证。

临时连接设备（observe 模式）
不锁定、不持久化

约束：设备不被批量执行占用

S8: AI 驱动执行

AI 助手对话触发，调用同一 API。

AgentScope Tool → POST /runner/run
→ 与手动执行完全相同的链路

约束：AgentScope 需在线，Tool 需注册

S9: 停止 / 取消

执行中停止或排队中取消。

停止：is_running=False → runner 退出 → release
取消：出队 → status 回 idle

约束：优雅终止，状态正确回写

S10: 崩溃恢复

服务重启，自动恢复。

orphan running → interrupted
stale TestRunRecord → FAILED
queued 任务 → 回到队列 → 自动消费
BUSY 设备 → 释放锁 → 恢复 ONLINE

约束：所有恢复在 recover_orphans 中完成

用户操作的完整交互流

  1. 进入执行引擎页面 → 看到任务列表 + 6 个 Tab 统计
  2. 点击"+ 新建任务" → 弹窗：填名称、选设备、选用例、设循环次数和间隔
  3. 点击"创建并执行" → 自动跳转详情页
  4. 详情页实时展示：WebSocket 推送日志、步骤逐条变色、进度条更新
  5. 执行完成 → 状态变为 ✅已完成，BUG 单自动汇总失败步骤
  6. 返回列表 → 对应 Tab 数量变化（执行中-1，已完成+1）

五、数据流转

完整链路：从前端点击到手机执行

① 前端
  newForm → createAndStart()
    → saveTaskToServer(task)        POST /runner/tasks/save → TaskCard 入库 (idle)
    → doStartTask(task)             POST /runner/run
      → initTaskProgress            (构建 caseItems 含 steps 定义)
      → body: {case_ids, loop_count, device_serial, client_task_id}

② start_test_run
  加载 TestDefinition(enabled=true) → TestCaseDef
  检查设备: is_device_busy(内存) → Device.status(DB) → dp_acquire_device
  设备忙 → 入队 (TaskCard=queued)
  设备空闲 → mark_device_busy → TaskCard=running → u2.connect → asyncio.create_task

③ _execute_tests
  创建 TestRunRecord (RUNNING)
  runner.run()
    → DeviceAdapter(u2.Device) 封装设备操作
    → StepExecutor 逐用例逐轮迭代
      → 每个步骤 → callback.on_step_started / on_step_result → WebSocket
      → 每轮结束 → callback.on_iteration_result → 前端更新 pass/fail
      → 失败步骤 → task.failedSteps 收集 → 前端 BUG 单汇总
    → ReportGenerator.save_csv / save_log 生成报告文件

④ 持久化
  批量 TestResult(iteration, result, duration_ms) 写入 DB
  TestRunRecord.status = COMPLETED / FAILED
  TaskCard.status = done, case_items/overall_pass/overall_fail 更新

⑤ 释放
  mark_device_idle → dp_release_device → Device.status=ONLINE
  _schedule_next_queued → 自动消费队列中下一个任务

⑥ 下游消费
  report_generator 读取 TestRunRecord + TestResult → 生成报告

六、状态机

TaskCard 状态转换图

IDLE
未执行 → QUEUED
等待中 → RUNNING
执行中 → DONE
已完成

QUEUED → CANCELLED | RUNNING → ERROR / STOPPED / INTERRUPTED
转换触发条件更新的表RunStateMachine 方法
IDLE → QUEUED设备忙时提交任务TaskCard.status=queuedenqueue()
QUEUED → RUNNING设备空闲，出队消费TaskCard=running + TestRunRecord 创建dequeue()
RUNNING → DONE所有用例执行完毕TaskCard=done + TestRunRecord=COMPLETED + TestResult 写入complete()
RUNNING → ERROR执行异常（设备断连等）TaskCard=done/error + TestRunRecord=FAILEDfail(outcome='error')
RUNNING → STOPPED用户手动停止TaskCard=done/stopped + TestRunRecord=STOPPEDfail(outcome='stopped')
RUNNING → INTERRUPTED服务崩溃，重启后恢复TaskCard=done/interrupted + TestRunRecord=STOPPEDfail(outcome='interrupted')
QUEUED → IDLE用户取消排队TaskCard.status=idlecancel()

原则

  • 单一入口：所有状态变更必须通过 RunStateMachine，禁止代码中直接 task.status = 'xxx'
  • 原子更新：TaskCard + TestRunRecord 在同一事务中更新，不存在一个更新另一个未更新的窗口
  • 幂等：同一转换重复调用是安全 no-op
  • 校验：非法转换（如 IDLE→DONE）抛出 InvalidTransition
  • 以手机为粒度：每台手机的队列和协程独立，状态隔离

七、排查方法 — 七个检查点

从用户看到"不对劲"开始，按顺序逐层排查。不能跳过前面直接看代码。
  1. ① 前端有没有发出请求？

    浏览器 DevTools Network 面板 → 点击按钮后有无 POST 请求？
    无 → JS 报错或按钮事件未绑定。有 → 看请求体和响应。

  2. ② API 返回了什么？

    HTTP 状态码？200 还是 500？ok:true 还是 ok:false？runs 有值还是 queued 有值？
    500 → 查后端日志具体报错。queued 有值 → 检查谁在占用设备。

  3. ③ 后端状态机走到了哪一步？

    task_card_save 成功？dp_acquire_device 成功？u2.connect 成功？runner.run() 进入 try 块？
    每个关键节点加 print，追踪到了哪一步。

  4. ④ 手机是否真的在执行？

    adb devices 确认手机在线。手机屏幕是否有变化？
    无变化 → u2 操作可能卡住了。查 CurrentThreadExecutor 是否 broken。

  5. ⑤ uiautomator2 健康检查

    python -c "import u2; d=u2.connect('serial'); print(d.info)"
    超时 → ATX agent 未运行。CurrentThreadExecutor broken → 线程池隔离失败。

  6. ⑥ 数据是否一致？

    TaskCard.status 和 running 字段是否矛盾？TestRunRecord 是否有对应记录？TestResult 是否写入？
    三表联查：task → run → results。

  7. ⑦ 结果是否展示？

    详情页显示是否正确？BUG 单是否正确生成？报告模块能否查到执行记录？

  • 不看浏览器就直接读代码 → 用户看到的现象才是起点
  • curl 通过就说修好了 → 必须用浏览器 UI 完整验证

八、uiautomator2 崩溃处理

问题 1: CurrentThreadExecutor 跨线程崩溃

条件：u2.connect() 在 A 线程创建 → 后续在 B 线程调用
  → CurrentThreadExecutor 检测到线程不匹配
    → RuntimeError("already quit or is broken")
      → 如果用了 run_in_executor(None)（默认线程池）
        → 污染 Django ORM 的 sync_to_async 线程池
          → 整个平台的 DB 操作全部瘫痪

处理：

  • u2 操作使用独立的 _u2_executor（ThreadPoolExecutor），不与 Django ORM 共用默认池
  • 检测到 executor broken → 标记设备 OFFLINE + 释放设备锁 + 通知前端 device_error
  • 不尝试重连同一设备，等设备恢复后重新 u2.connect

问题 2: u2 操作超时无响应

条件：手机 USB 松动 / 网络延迟 / ATX agent 卡死
  → u2.connect() 或 dump_hierarchy() 阻塞数分钟
    → Daphne worker 线程被占用
      → 其他请求无法处理

处理：

  • u2.connect() 设置超时（asyncio.wait_for）
  • 每个步骤执行设置总超时
  • runner 整体设置超时，超时后强制 mark_device_idle + 标记 outcome=timeout
  • 看门狗检测：如果 N 秒内无任何步骤进度，视为卡死

  3. ✅ 浏览器走通至少 2 遍完整流程
  4. ✅ 6 个 Tab 统计与实际一致

🔴 绝对禁止的交付方式

  • curl API 通过就说"修好了" → 必须浏览器完整验证
  • 改了代码没重启就声称"已修复" → 旧进程可能还在跑
  • 修了 A 不回归 B → 改了状态机必须回归所有场景
  • 环境脏了不清理 → 残留任务污染测试结果
