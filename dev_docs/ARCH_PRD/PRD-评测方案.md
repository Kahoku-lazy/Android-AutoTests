# 评测方案

> 2026-11-18。方案，不是实现。
> 配套 [PRD-评测与发布授权.md](PRD-评测与发布授权.md)。那份定谁能发布；这份定一次自测怎么跑、怎么判。
> 对照当前代码：一次工作流已经产出 `SopResult` 和 `RunRecord`。平台没有评测模块，也没有接入 OpenJudge。

## 1. 结论

自研一套小评测，只借 OpenJudge 的三条约定，不引入 `py-openjudge`。

| 借来的约定 | 在本平台怎么落地 |
| --- | --- |
| 评测只读已经发生的记录，不把业务再跑一遍 | 剧本先跑完，尺子再读 `SopResult` 和 `RunRecord` |
| 一把尺子只判一件事 | 五个纯函数，失败收成清单 |
| 代码尺子做门禁，模型尺子只做抽检 | 发布只认代码尺子 |

不借这些：1 到 5 分、加权求和、自动生成评分条文、两个回答互相比名次、再训练一个裁判模型、Langfuse。它们服务于训练奖励或外部追踪。本平台要的是能不能发布，一条不过就不能被别的高分抵消。

OpenJudge 官方文档把评测拆成三层：最终结果、单步、整条轨迹。本方案用同一层划分，但每层都是对或错，不是分数。见 [Evaluate an AI Agent](https://agentscope-ai.github.io/OpenJudge/get_started/evaluate_ai_agents/) 与 [Core Concepts](https://agentscope-ai.github.io/OpenJudge/get_started/core_concepts/)。

## 2. 评什么，不评什么

评测回答的是：

> 用平台准备好的剧本跑这条草稿，流程规则有没有被打破。

它不回答：

- 按钮、权限、排队是否符合接口契约。那些仍由现有 pytest 守着。
- 这台手机能不能真的回到桌面。那是真机冒烟，不作为发布条件。
- 这句话写得好不好。那是模型抽检，只进报告，不决定发布。

助手和工作流用同一套尺子，期望不同。

| 对象 | 一次自测在验证 |
| --- | --- |
| 工作流草稿 | 驳回是否留在同一步，次数是否正确，验收者是否没有改设备，阶段是否符合期望 |
| 助手草稿 | 同栏第二句是否仍是同一个实例，未勾选的工具是否没有被调用 |

助手没有 `phase` 时，阶段尺跳过，不默认判失败。

## 3. 一次自测的路径

```text
作者点自测
    |
    | 后端取草稿的当前内容，算指纹
    v
样本集（平台自带，作者不能改）
    |
    | 每条样本：剧本模型 + 假工具
    v
现有 run_sop / 对话一轮
    |
    +-- SopResult：阶段、每步 passed / attempts / message
    +-- RunRecord：工具、入参、角色、步骤名
    v
五把纯函数尺子
    |
    +-- 全过：记下「这个指纹通过」
    +-- 有失败：草稿仍可保存，不能发布
```

剧本模型不是第二个业务模型。它按样本顺序返回事先写好的交付或驳回，不联网。假工具只记录「谁在哪一步调用了什么」，不碰 adb。

指纹覆盖会改变运行结果的字段：绑定的配置、系统提示词、模型、工具勾选、工作流两侧名片、编排和种类。只改显示名、头像、笔色不算变。指纹变了，旧的通过作废。

## 4. 样本

一条样本分三块。三块不互相复制。

```yaml
id: desktop-rejected-once
title: 回到桌面被驳回一次后通过
enabled: true

stimulus:                        # 输入。驱动这一次运行
  task: 回到桌面，然后打开设置
  script:
    - {step: 回到桌面, role: executor, handover: 已按 Home}
    - {step: 回到桌面, role: verifier, passed: false, message: 还停在设置里}
    - {step: 回到桌面, role: executor, handover: 这次回到了桌面}
    - {step: 回到桌面, role: verifier, passed: true, message: 看见 dock 和图标}
    - {step: 打开设置, role: executor, handover: 已打开设置}
    - {step: 打开设置, role: verifier, passed: true, message: 看见连接和显示}

expect:                          # 期望。只写可判定的事实
  phase: COMPLETED
  steps:
    - {subject: 回到桌面, passed: true, attempts: 2}
    - {subject: 打开设置, passed: true, attempts: 1}
  constraints:
    verifier_write_tools: []
    attempts_within_max: true

trace:                           # 可选。默认不写
  sequence: []
```

三块的分工：

| 块 | 谁写 | 作用 |
| --- | --- | --- |
| stimulus | 超级管理员 | 让剧本模型和假工具有固定回应 |
| expect | 超级管理员 | 尺子的标准答案 |
| trace | 默认空 | 只有真要锁工具顺序时才填 |

剧本样本不把 stimulus 再抄进 `trace.sequence`。那样顺序尺永远是绿的，引擎把驳回算错时也发现不了。

助手样本用同一张表，只填它有的字段：

```yaml
id: same-lane-second-turn
stimulus:
  turns:
    - 你好
    - 上一句我说了什么
  unseen_tools: [adb_tap]
expect:
  same_instance: true
  unseen_tools: [adb_tap]
```

没有的字段就不要造一个失败。

样本可以停用，不能删除。停用后不再挡发布。历史自测结果仍指向旧样本，避免过去的记录失去出处。

样本集一旦变化，所有未发布草稿的通过作废。已发布版本已经冻结，不受影响。

## 5. 五把尺子

尺子的形状只有一种：

```text
失败或空 = 尺子(运行结果, 期望)
```

四条约束：

- 入参只有结果和期望。不读时钟、文件、网络，不再调模型。
- 不修改 `SopResult` 和 `RunRecord`。
- 期望里没有相关字段就跳过。
- 失败原因点名：哪一步、期望什么、实际什么。

OpenJudge 的三层，对应到这五把尺：

| 层 | 尺子 | 读哪里 |
| --- | --- | --- |
| 最终结果 | 阶段尺、步骤结论尺 | `SopResult.phase`、每步 `passed` 和 `attempts` |
| 单步 | 角色工具尺 | `RunRecord.steps` 的 `agent_role`、`tool`、`sop_step` |
| 轨迹 | 顺序尺、重复尺 | 同一步内的工具序列和相邻调用 |

### 5.1 阶段尺

```text
期望没有 phase                 跳过
result.phase 等于期望          过
否则                           「阶段期望 COMPLETED，实际 FAILED」
```

助手样本没有 phase，跳过。

### 5.2 步骤结论尺

按 `subject` 对齐，不按列表位置猜。

```text
期望 steps 为空                跳过
少一步或多一步                 失败
passed 或 attempts 不符        失败，两处都写进原因
```

「回到桌面」期望 2 次、实际 1 次时，原因就是这两句，不写「步骤不对」。

### 5.3 角色工具尺

```text
期望没有 verifier_write_tools 或 unseen_tools    跳过
验收者的工具落在禁止名单里                        失败
调用了样本未允许的工具                            失败
```

禁止名单写在样本里，不写死在函数里。第一批工作流样本的验收者禁止名单为空名单，表示一个写操作都不能有。空名单和「字段不存在」不是一回事：字段不存在才跳过。

### 5.4 顺序尺

只在 `trace.sequence` 非空时跑。比较「步骤名 + 角色 + 工具名」，不比较模型原文。

发布用的剧本样本保持序列为空，因此这把尺在发布门禁里通常跳过。它留给以后真模型抽检，或者某条样本故意要求固定工具顺序。

### 5.5 重复尺

```text
同一步、同一角色、同一工具、同一入参连续出现两次    失败
中间隔着验收者                                        不算连续
```

这把尺抓死循环，不抓合理重试。第一次被驳回后，执行者再按一次 Home，中间隔着验收，不算失败。

它对应 OpenJudge 的 `ActionLoopDetectionGrader`，但是对或错，不计算 `1 - 相似对 / 全部对`。相似对比例对发布没有意义，一次连续重复就该失败。

### 5.6 汇总

五把尺都跑完。失败收成清单。不加权，不取平均，不因为四把通过就把一把失败盖掉。

清单给作者看的是人话，同时保留机器可读的字段：

```text
sample: desktop-rejected-once
ruler:  steps
subject: 回到桌面
expected: attempts=2
actual:   attempts=1
text: 回到桌面期望尝试 2 次，实际 1 次
```

作者只看到自己这次的清单。超级管理员能看到全部草稿的清单。谁都看不到密钥。

## 6. 走一遍

样本是第 4 节的「驳回一次后通过」。剧本跑完后：

```text
阶段 COMPLETED
回到桌面：passed，attempts=2
打开设置：passed，attempts=1
验收者只调用了截图和界面读取
```

| 尺子 | 结果 |
| --- | --- |
| 阶段 | 过 |
| 步骤结论 | 过 |
| 角色工具 | 过 |
| 顺序 | 跳过，序列为空 |
| 重复 | 过 |

发布允许。

若引擎把第一次驳回当成整次失败，并提前进入「打开设置」：

| 尺子 | 结果 |
| --- | --- |
| 阶段 | 红，期望 COMPLETED，实际 FAILED |
| 步骤结论 | 红，回到桌面期望 2 次，实际 1 次 |
| 其余 | 跳过或过 |

发布拒绝。草稿还在。作者看到两句原因，不看到一个总分。

## 7. 和 OpenJudge 的取舍

| OpenJudge 的做法 | 本平台 | 原因 |
| --- | --- | --- |
| `GradingRunner` 并发跑多把尺子 | 自测时五把尺顺序跑完 | 发布样本少，并发没有收益 |
| mapper 把外部字段改名 | 直接读 `SopResult` 和 `RunRecord` | 记录就是自己的，不需要适配层 |
| LLM Grader，1 到 5 分 | 不进发布 | 官方偏好准确率约 75% 到 95%，不能让发布忽红忽绿 |
| 代码 Grader，0 到 1 | 收成对或错 | 门禁不需要程度分 |
| 多次投票、取平均 | 不做 | 代码尺子没有随机性 |
| 零样本生成评分条文 | 不做 | 条文会变成作者可以绕开的标准 |
| 用标注数据训练裁判模型 | 以后也不作为发布条件 | 本平台没有成规模的人标轨迹 |
| Langfuse / LangSmith | 不引入 | 已有 jsonl 和 HTML 报告 |

模型抽检以后可以加，但只是第六份报告，不增加第六把发布尺。它做的事只有一件：把某步的 `description` 和验收 `message` 交给一个模型，问「这句是不是在说这件事」。输出写进超级管理员的报告。`发布` 不读它。

在那之前，不安装 `py-openjudge`。官方教程要求的 Python 范围小于 3.13，本仓库是 3.13，引入前还得单独验证。

## 8. 第一批样本

只做能锁住已知规则的六条。不追求数量。

| 编号 | 对象 | 锁住的规则 |
| --- | --- | --- |
| W1 | 工作流 | 两步都一次通过，阶段 COMPLETED |
| W2 | 工作流 | 第一步驳回一次后再通过，attempts 为 2，且没有提前进入第二步 |
| W3 | 工作流 | 驳回次数用尽，阶段 FAILED，不开始下一步 |
| W4 | 工作流 | 验收者调用写操作，角色工具尺失败 |
| W5 | 工作流 | 同一步连续两次相同工具和入参，重复尺失败 |
| A1 | 助手 | 同栏第二句仍是同一个实例；未勾选的工具没有出现 |

W2 是发布门禁的代表样本。W4 和 W5 用来证明尺子本身会红，不能只准备「一定会过」的样本。

样本正文放在评测自己的数据目录，不写进助手或工作流的业务表。改一条样本就是改平台规则，走代码变更，不走运营页面。

超级管理员的页面只做三件事：看样本清单、停用或启用一条样本、看某次自测的失败清单。不在页面里改期望。

## 9. 谁在什么时候跑

| 时机 | 跑什么 | 不过会怎样 |
| --- | --- | --- |
| 每次提交代码 | pytest 用固定草稿跑 W1 到 W5、A1 | 提交门禁失败 |
| 作者点自测 | 同一套启用中的样本，对象换成他的草稿 | 不能发布，草稿还在 |
| 超级管理员改样本集 | 不自动重跑所有草稿 | 未发布草稿的旧通过作废，下次发布前必须再点一次 |
| 真模型、真机 | 不在本次 | 不挡发布 |

自测的剧本模型与 pytest 用同一套样本文件。不允许页面自测一套、提交门禁另一套。

一次自测有超时。超时记为失败，原因是「自测没有在时限内结束」，不能记成通过。超时不重试第二次，避免点一次按钮打出两次费用；剧本模型本身不联网，正常情况下也不会碰到这个分支。

## 10. 和发布的衔接

发布只认三件事同时成立：

1. 记录是草稿，作者对它有编辑权。
2. 最新一次自测的指纹等于当前内容指纹。
3. 那次自测的失败清单为空，且用的是当前启用的样本集。

缺一不可。超级管理员也不能跳过。否则「维护尺子的人」可以把自己的草稿直接放出去，门就开在了评测外面。

发布成功后按 [PRD-评测与发布授权.md](PRD-评测与发布授权.md) 冻结版本。评测不负责冻结，也不负责模型名单。

## 11. 验收

1. W2 在现有引擎上通过；故意把驳回改成进入下一步时，步骤结论尺变红，且发布被拒绝。
2. W4 的失败原因点名验收者和工具名。
3. 样本没有 `phase` 时，阶段尺跳过，不制造失败。
4. 作者看不到样本编辑入口；改请求调用样本修改接口，返回 403，样本不变。
5. 自测通过后改一个工具勾选，旧通过作废。
6. 停用 W5 后，新的自测不再跑它；旧自测记录仍能打开，并标明当时用的样本。
7. pytest 与页面自测读取同一份样本文件。
8. 自测日志和失败清单里没有密钥明文。
