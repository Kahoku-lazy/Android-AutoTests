## 二、62 个 error：一个根因

`auth.api`（38）、`auth.e2e`（15）、`device.api`（9）全部是 setup 阶段 `fixture 'api_session' / 'login_page' / 'e2e_account' not found`。

pytest 的 conftest 只对**自身目录及其子目录**生效：

```
tests/api/conftest.py     → api_session
tests/e2e/conftest.py     → e2e_account / login_page / steps
tests/auth/api/*          → 看不到 tests/api/conftest.py
tests/auth/e2e/*          → 看不到 tests/e2e/conftest.py
tests/device/api/*        → 看不到 tests/api/conftest.py
```

**修法**（两选一，推荐前者）：把两份 conftest 的公共夹具上提到 `tests/conftest.py`；或按模块复制/挪到 `tests/<模块>/api|e2e/conftest.py`。
判据：`pytest -q tests/auth tests/device -m "api or e2e"` 从 62 error 变为 0 error。

## 四、另一个环境级缺陷（会掩盖结果）

`deepeval 4.3.5` 的 pytest 插件在 `pytest_terminal_summary` 对每条 skipped 报告执行
`print(f"Test {report.nodeid} was skipped…")`，该 `print` 走 `rich`（markup=True）：参数化 id 里的 `[/login]`
被当成闭合标签 → `rich.errors.MarkupError`，**整场 session 以 traceback 结束**。
只要套件里有带方括号 id 的用例被 skip（`tests/perf` 的两条就是），默认命令必然在收尾崩溃。
临时规避：`-p no:deepeval`；根治（升级/固定 deepeval 或改插件调用方式）另开变更。

## 五、对 PR 验收的影响

1. **不要**把「全量套件绿」写进任何 PR 的验收条件 —— 它现在是红的，且不在本序列范围。
2. PR 验收口径统一为：CI `python` job 的 20 条阻塞门禁 + `frontend` job 的 10 条阻塞门禁全绿（本地等价命令见下）。
3. 涉及 `tests/` 的 PR（如 perf 预算）在描述里附「增量用例通过」与「基线未新增红」两句。
4. 62 个 setup error 的夹具层级问题值得单开一单（1 个根因、修完直接少 62 条红），建议排在 PR 序列之外、优先做。

## 六、一条会误导门禁的本地陷阱：依赖树跟着分支走

`frontend/package-lock.json` 在不同分支上不同（在制改动删掉了 `js-yaml` / `@types/js-yaml`，`Kahoku` 仍有）。
本地 `node_modules` 只反映**最后一次 `npm install` 时的清单**，于是：

- 在制改动分支上装好依赖后切到 `Kahoku` 基准分支 → `vue-tsc` 报 `Cannot find module 'js-yaml'`、`vitest` 同名失败；
- 反之则 `package.json` 已删的包还在树里，门禁「假绿」。

**规矩**：每条 PR 分支跑门禁前，先按该分支的 lock 装一次（`cd frontend; npm ci`；
若本机有 dev server 占着 `esbuild.exe` 导致 `EPERM unlink`，先停 dev server 或临时 `npm install --no-save <缺的包>` 补齐）。
