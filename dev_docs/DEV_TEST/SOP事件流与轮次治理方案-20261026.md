# SOP 事件流信息完整性与轮次治理方案

> 日期：2026-10-26　范围：`engines/agents`（fold / event_sink / workflow）+ `backend/apps/task_list`（event_store / task_reports）
> 性质：设计方案，不含代码改动。落地前需按 `OpenSpec` 四步走流程。

---

## 0. 结论

1. **9 项问题收敛成 10 个方案，其中 6 个是"补记"（几行到十几行），3 个是"容错加固"，1 个是可选项。**
2. **不改数据表结构、不加迁移**：`task_events.event_type` / `block_type` 都是无 choices 的 `CharField`，新增枚举值零成本；前端**完全不读 `event_type`**（只用后端给的 `label` / `detail`），新事件行天然可渲染。
3. **根治用例串号只改一处**：`case_title` 从"整任务绑一次"改成"每条用例开始时刷新"，报告侧不需要再靠 `step_seq` 回退去猜用例边界。
4. **轮次上限不用调小，要加兜底**：`60/30` 的预算本身合理，缺的是"总次数 + 总时长"这道闸。加闸后最坏 460 次/步的算式才有实际意义。
5. **两件事明确不做**：① 流式增量原文落库（会推翻现有的"增量折叠计数"设计，收益被 S2/S9 覆盖）；② 把 60 轮改小（注释已写明 30 轮会被试错吃满）。

## 2. 方案明细

### S1 用例名按用例刷新（P0）

**现状**

- `task_runner.py:45` 只绑一次：`bind_run_context(task_id, agent_id, task.case_title or "")`。
- `platform_run.py:160` 是 `for case in cases`，一个任务可跑 YAML 里全部用例。
- 结果：`event_store.py:130` 每行 `case_title` 都等于任务级标题（或空串）。
- 报告只能靠 `task_reports.py:617` 的 `step < last` 启发式切用例，**上一条用例只到第 1 步时会并成一条**。

**改法**：在 `event_sink.py` 加一个和 `set_step_context` 对称的轻量写入，不引入新的 token/reset 管理。

```python
# engines/agents/event_sink.py
def set_case_title(case_title: str) -> None:
    """更新当前运行的用例名。未绑定运行上下文时不做任何事。

    Args:
        case_title: 正在执行的用例标题。
    """
    ctx = _run.get()
    if ctx is None:
        return
    ctx.case_title = str(case_title or "")[:255]
```

```python
# engines/agents/workflow/platform_run.py  —— _drive_real 与 _drive_stub 的循环头
for case in cases:
    set_case_title(case.title)
    set_step_context(None, None)   # 清上一条用例残留的步骤号/尝试次数
    ...
```

**为什么可行**：`RunContext` 是可变 dataclass，`ContextVar` 的值是**同一个对象引用**；`database_sync_to_async` 的 `copy_context()` 复制的是上下文映射而非对象，所以工作线程里改字段，主线程立即可见——这与 `set_step_context` 现在的行为一致，不是新机制。

**影响面**：`event_store._row()` 无改动；报告侧无需改也能立刻"每行带对用例名"。用例切分改造（S4 顺带）是可选增强。

**验收**：`tests/graybox/unit/` 新增用例——模拟两条用例依次跑，断言写入行的 `case_title` 先后为两个不同标题，且第二段 `step_seq` 从 1 重新开始。

### S2 SOP 步骤起点落库（P0）

**现状**：SOP 引擎在每步开始/结束时 yield `CustomEvent(name="SOP_STEP_STARTED" | "SOP_STEP_ENDED")`（AgentScope `sop/_engine.py:121`、`:133`），`fold._flow_boundary`（`fold.py:66-71`）直接返回空 `StepResult`。

**改法**：只落 `SOP_STEP_STARTED`，不落 `SOP_STEP_ENDED`。

不落 ENDED 的理由：
- 起点序列已经能表达边界（终点 = 下一个起点 / 任务结束）；
- 落 ENDED 需要判断"这一步到底停在哪"，会与 `_stamp_step` 的步骤匹配逻辑打架（该步已 COMPLETED 时会错位到下一步），得不偿失；
- 步骤失败的信息在 `ReplyEndEvent.payload.finished_reason` 与任务 `result` 里已有。

```python
# engines/agents/messaging/fold.py —— 替换 _flow_boundary
def _flow_boundary(event, state: dict, kind: str, models) -> StepResult | None:
    """SOP 步骤起点交一条记录；其它自定义事件不落行。"""
    del models
    if kind != "CustomEvent":
        return None
    if str(getattr(event, "name", "") or "") != "SOP_STEP_STARTED":
        return StepResult()
    value = getattr(event, "value", None) or {}
    # 步骤边界不属于任何一轮发言，角色与模型显式留空，避免贴上上一步的模型名
    result = StepResult()
    result.log_lines.append(("-", f"步骤开始 | {value.get('step') or ''}"))
    result.records.append(
        EventRecord(
            event_type="SOP_STEP_STARTED",
            phase="开始",
            block_type="sop_step",
            payload={
                "step": str(value.get("step") or ""),
                "attempt": int(value.get("attempt") or 0),
            },
        )
    )
    return result
```

**配套改动**：`ui_auto_workflow.py:149 _stamp_step` 的匹配集合从 `{"running", "awaiting"}` 扩到 `{"running", "awaiting", "pending"}`。

理由：`SOP_STEP_STARTED` 到达时该步还是 `pending`，不改的话边界行 `step_seq` 为 `None`，报告里挂不到任何步骤上。扩成三态后，"第一个还没结束的步骤"就是当前步，语义正确。

**影响面**：每步每次尝试 +1 行；`_rounds` 会因 `phase` 切换多切一个块（见 S4）。

### S3 超轮次与运行时提醒落库（P0）

**现状**：`fold.step` 只认 11 种事件，其余落到空结果。被丢掉的两类恰恰是"为什么停"的证据：

| 事件 | 含义 | 何时产生 |
|---|---|---|
| `ExceedMaxItersEvent` | 推理轮次用尽、强制收尾 | AgentScope `_agent.py:3685`、`:3736`、`:3599` |
| `HintBlockEvent` | 运行时注入给模型的提醒（重复工具错误、上下文接近上限等） | `_agent.py:1634` |

**边界说明**：「`cur_iter` 刚撞到 60 轮、即将强制收尾」那一步的提示是 `Reasoning(hint=...)`，它只写进模型上下文、**不产事件**（`_agent.py:1181`）。所以本方案能看到"最终超轮次了"，看不到"即将强制收尾"的瞬间——后者要靠 `ReplyEndEvent.payload.finished_reason == "exceed_max_iters"` 判断，已经存在。

```python
# engines/agents/messaging/fold.py —— 在 handler 元组里加两项

    _flow_boundary,
    _reply,
    _hint,
```

```python
def _hint(event, state: dict, kind: str, models) -> StepResult | None:
    """运行时注入提醒：记下注入内容，用于解释模型行为突变。"""
    if kind != "HintBlockEvent":
        return None
    hint = str(getattr(event, "hint", "") or "")
    return _simple(_record(
        state, kind, "推理", "hint",
        payload={"hint": hint, "source": str(getattr(event, "source", "") or "")},
    ), f"运行时提醒 | {hint[:200]}")


def _exceed_max_iters(event, state: dict, kind: str, models) -> StepResult | None:
    """推理轮次用尽：这是'为什么突然收尾'的直接证据。"""
    if kind != "ExceedMaxItersEvent":
        return None
    return _simple(_record(state, kind, "结束", "hint", payload={}), "推理轮次用尽，强制收尾")
```

（`_simple` 是 3 行的辅助函数：收一条记录 + 一行日志，避免每个 handler 重复写 `StepResult()` 样板。）

**验收**：构造一个 `ExceedMaxItersEvent` 直喂 `fold.step`，断言产出一条 `event_type="ExceedMaxItersEvent"` 的记录；`HintBlockEvent` 同理，且 `payload.hint` 为全文。

### S5 每条用例新建角色（P1）

**现状**：`platform_run.py:154-155` 在 `for case` **循环外**建 executor/verifier，一个 Agent 实例贯穿整个任务 → 对话上下文跨用例累积。

后果两条：
1. 第 2 条用例第 1 步的输入 token 包含第 1 条用例的全部工具返回，成本单调上升；
2. `trigger_ratio=0.7` 触发压缩后，模型拿到的是摘要，行为不可解释。

**改法**：把三行移进循环。

```python
for case in cases:
    set_case_title(case.title)
    set_step_context(None, None)
    executor = build_executor()
    verifier = build_verifier()
    workflow = AgentSOPWorkflow(IncompleteHandoverGuard(executor.agent), verifier.agent)
    try:
        phase = await workflow.run_workflow(case.title, steps, opening)
    ...
```

**代价**：每条用例重建两套 toolkit（会扫 `engines/agents/skills/` 目录），实测在毫秒级；换来的是用例隔离，以及**与手工入口 `ui_auto_workflow.run_workflow()` 行为一致**（它现在就是每条用例新建）。

**不做替代方案的交换**：也可以只调小 `max_iters` 或加大 `trigger_ratio`，但那只是把问题推后。

### S6 运行预算兜底（P1）

**现状**：全链路无 `timeout`、无总轮次、无费用上限。最坏 `用例数 × 步数 × 460` 次模型调用。

**设计**：预算状态挂 `RunContext`（与 S1 同一机制），检查点放 `AgentEventsShow.show`（每一轮都经过这里，能在用例内打断），中断用内置 `RuntimeError`（AGENTS 禁止新增自定义异常类），终止信号用标志位而非异常类型，避免靠字符串匹配。

```python
# engines/agents/event_sink.py
import os, time

MAX_MODEL_CALLS = int(os.environ.get("SOP_MAX_MODEL_CALLS", "600"))
MAX_RUN_SECONDS = int(os.environ.get("SOP_MAX_RUN_SECONDS", "7200"))

@dataclass
class RunContext:
    task_id: int = 0
    agent_id: int = 0
    case_title: str = ""
    step_seq: int | None = None
    attempt: int | None = None
    model_calls: int = 0          # 本次任务已发生的模型调用次数
    started: float = 0.0          # 任务起点，monotonic 秒
    budget_exceeded: bool = False # 已超预算，调用方据此终止


def count_model_call() -> None:
    """给本次任务记一次模型调用；超次数或超时长时置位预算标志。"""
    ctx = _run.get()
    if ctx is None:
        return
    ctx.model_calls += 1
    over_calls = MAX_MODEL_CALLS > 0 and ctx.model_calls > MAX_MODEL_CALLS
    over_time = MAX_RUN_SECONDS > 0 and ctx.started > 0 and (
        time.monotonic() - ctx.started > MAX_RUN_SECONDS
    )
    if over_calls or over_time:
        ctx.budget_exceeded = True


def budget_exceeded() -> bool:
    """本次任务是否已超预算。未绑定时为 False。"""
    ctx = _run.get()
    return bool(ctx is not None and ctx.budget_exceeded)
```

```python
# engines/agents/messaging/messages.py —— AgentEventsShow.show 收尾处
        if record.event_type == "ModelCallEndEvent":
            count_model_call()
        ...
        if budget_exceeded():
            raise RuntimeError("运行预算超限")
```

```python
# engines/agents/workflow/platform_run.py —— _drive_real 里
            if budget_exceeded():
                return _budget_stop(completed, failed)
```

```python
def _budget_stop(completed: list[str], failed: list[str]) -> dict:
    """预算用尽：停止整轮，已完成的用例保留。"""
    return {
        "load_message": LOAD_OK,
        "reason": f"运行预算超限（模型调用上限 {MAX_MODEL_CALLS} 次 / 时长上限 {MAX_RUN_SECONDS} 秒）",
        "status": "fail",
        "completed": list(completed),
        "failed": list(failed),
    }
```

**行为链**：`show` 抛 `RuntimeError` → `run_workflow` 的 `except Exception` 记日志、事件流结束 → 回读 `engine.phase`（停在 running）→ 返回 `"running"` → `_drive_real` 判该用例 failed，但**先查 `budget_exceeded()`**，直接终止整任务，不再跑下一条用例。

**取值建议**：

| 参数 | 默认 | 依据 |
|---|---|---|
| `SOP_MAX_MODEL_CALLS` | 600 | 典型任务（1 用例 5 步 × 每步约 20 次真实调用）约 100 次，600 是 6 倍余量；最坏 2300 次会被截断 |
| `SOP_MAX_RUN_SECONDS` | 7200 | 单步最坏可跑近 1 小时，2 小时兜底整个任务 |

**验收**：把 `SOP_MAX_MODEL_CALLS` 设成 3 跑一条真 SOP（或喂假事件），断言任务以 `status=fail`、`reason` 含"运行预算超限"结束，且已落库事件不被丢弃。

### S7 批量写入降级与分片（P1）

**现状**：`event_store.flush()` 先 `insert_task_events(整批)` 再 `clear()`；抛错时 `_rows` 不清空 → 下次追加继续整批重试。若该批里有永远写不进去的行（例如 payload 超过 MySQL `max_allowed_packet`，实测本机 64MB），会一直失败到 `close()`，`close()` 再抛 → `task_runner` 只记一条 `backend_log.exception`，**剩余事件全部丢失**。

**改法一：整批失败降级逐行。**

```python
def flush(self) -> None:
    """把已结束的行写入数据库；整批失败时逐行重试，坏行丢弃但不拖累其余。"""
    if not self._rows or not self._task_id:
        self._rows.clear()
        self._bytes = 0
        return
    rows, self._rows, self._bytes = self._rows, [], 0
    try:
        api.insert_task_events(self._task_id, rows)
    except Exception:
        backend_log.exception("事件批量写入失败，降级逐行写 task_id=%s rows=%s", self._task_id, len(rows))
        rows = self._insert_one_by_one(rows)
    for row in rows:
        _add_usage(row, self._agent_id)

def _insert_one_by_one(self, rows: list[dict]) -> list[dict]:
    """逐行写入；写了哪些就返回哪些，失败行只记日志。"""
    written: list[dict] = []
    for row in rows:
        try:
            api.insert_task_events(self._task_id, [row])
        except Exception:
            backend_log.warning(
                "事件行写入失败已丢弃 task_id=%s seq=%s type=%s",
                self._task_id, row.get("seq"), row.get("event_type"),
            )
            continue
        written.append(row)
    return written
```

**改法二：按估算字节提前分片**（防止单批撑爆 packet）。

```python
_MAX_BATCH_BYTES = 8 * 1024 * 1024   # 远低于 64MB，留足余量

def _append_row(self, row: dict) -> None:
    """收下一行；满一批或超字节上限就落库。"""
    self._rows.append(row)
    self._bytes += len(json.dumps(row, ensure_ascii=False, default=str))
    if len(self._rows) >= _BATCH or self._bytes >= _MAX_BATCH_BYTES:
        self.flush()
```

**要点**：新实现先把 `rows` 摘出来再写，失败也不会重复写同一批（原实现失败后整批仍在 `_rows` 里，重试时行为未定义）。

**验收**：打桩让 `api.insert_task_events` 在第 2 批抛一次，断言：抛错那批里除故意坏行外全部落库、后续批次不受影响、`close()` 不抛异常。

### S9 块起始行（P2，可选）

**现状**：正文/思考只在 `*BlockEndEvent` 落一行（`fold.py:159-186`）。块中途被取消或进程被杀，整块文本连"曾经存在"的痕迹都没有。

**为什么不做周期心跳**：要救"进程被杀"，只有周期性增量落库有效；但那会推翻 `event_store._fold()` 现有的"增量只计数"设计，行数放大一个量级。**收益/成本不成立。**

**折中方案**：只落块**起始**行，成本 +2 行/轮，拿到"这里起过一段但没结束"的证据。

```python
def _content_start(event, state: dict, kind: str, models) -> StepResult | None:
    """正文/思考块开始：只留一条起痕，中断时能看出'起过但未结束'。"""
    block = {"TextBlockStartEvent": "text", "ThinkingBlockStartEvent": "thinking"}.get(kind)
    if block is None:
        return None
    state[f"txtat:{event.block_id}"] = _now()   # 起点以 Start 为准，比首个 delta 更准
    return _simple(_record(state, kind, "推理", block, payload={"started": True}), "")
```

配套：`_content_delta` 里的 `setdefault(f"txtat:...")` 可以删掉（Start 已经写了）；`_detail` 加一个"文本块开始 / 思考块开始"分支，避免空 detail。

**建议**：先上线 S1–S8，观察一个迭代。若实际没遇到过"中断后需要看半截思考"，S9 就不做。

### S10 文本日志单行上限（P3，可选）

**现状**：`event_log.write_line` 用 `" ".join(action.split())` 压平换行（保证一行一条），但没有长度上限——一段 100KB 的思考会写成 100KB 的单行，10MB × 4 的轮转很快被吃掉。

```python
_MAX_LINE = 4000

def write_line(model: str, action: str) -> None:
    del model
    text = " ".join(str(action or "").split()) or "-"
    if len(text) > _MAX_LINE:
        text = f"{text[:_MAX_LINE]}…(共 {len(text)} 字符)"
    agent_event_log.info(text)
```

落库的全文不受影响（这是纯日志侧改动）。
