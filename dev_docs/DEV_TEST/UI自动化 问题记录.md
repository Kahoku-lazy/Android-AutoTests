## 一、执行框架与预算

### 1.1 预算按任务固定 600 次

- **现象**：TASK-194「UI-全功能测试-01」跑 2885s、601 次模型调用后中断，12 条用例只完成 7 条，停在「快照」。
- **根因**：`SOP_MAX_MODEL_CALLS` 默认 600，是给"一条用例"定的绝对上限；任务里装 12 条就必然中途耗尽。
- **证据**：各用例调用数 — 定时 98 / 开关亮度 53 / **颜色 163** / 场景 69 / 音乐 56 / DIY 64 / 涂鸦 79 / 快照 19。
- **已修**：`25b79d16` — 默认 **300 × 用例数**（`SOP_MAX_MODEL_CALLS_PER_CASE`），未设配额时才回落 `SOP_MAX_MODEL_CALLS`；单测覆盖 1/3 条用例与回落路径。

### 1.2 运行时长上限 2 小时

- **现象**：`SOP_MAX_RUN_SECONDS` 默认 7200s。
- **已修**：`25b79d16` — 默认 **14400s（4H）**。

### 1.3 事件流被打断后没有原因

- **现象**：工具抛「日志为空 / 时间不满足 5 秒」时，`SOPEngine` 事件流直接结束，该步停在 running：既不记驳回也不重试，任务判 `未完成`，但**详情页看不到任何原因**。
- **已修**：
  - `30a54a07` 引擎捕获后写 `StepInterruptedEvent`（带 reason / step_seq / attempt）；
  - `9636f475` 报告 `steps[].interrupt` + 前端步骤行红标「日志中断」（hover 显示原因）；
  - `32265700` BUG 台账自动开「设备日志中断」单（`source_ref=task:log-interrupt`），detail 含步骤与原因。
- **限制**：历史任务（如 TASK-189）没有该事件，不回填。

## 二、日志证据

### 2.1 窗口只看起点后 5 秒

- **现象**：验收 `at=16:38:13`，真实日志 `16:38:09`（早 4 秒）→ 查不到 → 判失败；同样情况 17:39 出现一次（早 5 秒）。
- **根因**：判据方向单一，日志只要比交卷写的 `action_time` 早一点点就永远命中不了。
- **修法**：`823d4dc3` — 保持「起点 ~ 起点后 5 秒」，**起点之前一律不参与匹配**；命中回传 `offset_seconds`（恒 ≥ 0）；判定顺序改为"先看窗口是否命中，再判窗口是否盖满"。
- **配套**：验收提示词钉死 `at` 取值 —— 只能取「触发这条日志的那一次动作」的时间；给晚了整段漏，给早了会算成上一个动作。

### 2.2 试错记录：向前回看 10 秒（已回退）

- 第一版改法是让工具向前回看 10 秒，TASK-189 第 2 步因此判过（`offset=+0.229`），但规则本身错误：**日志只在动作触发后出现，向前看命中的是上一个动作的日志**。已回退，并补单测「起点之前的日志不算命中」。

### 2.3 设备日志断流

- **现象**：17:56:42 → 17:58:03 共 **81 秒**无任何行（连心跳都没有）；17:52:57 → 17:55:21 有 **144 秒**空档；`serial.log` 多次 `uart recv failed: [WinError 10054]`。
- **影响**：TASK-189/190 第 2 步日志查询落空 → 事件流中断 → 任务失败。
- **旁证**：同一文件里 17:27–17:35（通过那轮）有 25 条 BLE 流量、3 条关键词；17:50–18:00（失败那轮）**0 条 BLE、0 条关键词** —— 那段时间 App 根本没和灯具通信。
- **状态**：环境问题，未修；建议跑前手动确认链路（改一次亮度看日志有没有 BLE 行）。

### 2.4 编造关键词

- **现象**：涂鸦第 6 步写 `log.keyword: graffiti_configs_set_success`，该关键词在全量目录与 9.6MB 真机日志里**从未出现**。
- **影响**：该步永远查不到 → 必判失败。
- **已修**：改为页面判定（确认弹出「应用成功」且灯具变化）。
- **同类核查**：`snapshot` / `auto_play` / `effect` 在日志里同样 0 次命中 → 涂鸦、快照、趣味灯光、自动播放四类只按页面判定。

### 2.5 日志每次全文重解析

- **现象**：`check_device_log` 单次 8.7–20.7s；8.5MB / 82k 行，全量解析 1.56s + 运行时竞争。
- **已修**：`afb3f83a` — 按 `(size, mtime_ns, inode)` 增量尾读；实测首解析 1.00s、第二次 0.001s；单次检查降到 **2.07s**。

## 三、设备交互与定位

### 3.1 包名写反

- **现象**：用例与 `app_info` 写 `govee.home.com`，真机是 `com.govee.home`；`monkey -p govee.home.com` 报 `No activities found`，`am force-stop` 静默成功。
- **已修**：`94a1f08d` — 按 LAUNCHER 解析包名 + `am start -W -n`，`app_info` 更正并加警示。

### 3.2 `dumpsys window` 太慢

- **现象**：每次读前台 5.5s，`app_control` 单次约 12s。
- **已修**：`6b32991a` — 改用 `dumpsys window displays`（0.2s），启动 3.96s（其中 `am start -W` 3.2s 是真实冷启动）、停止 0.79s。

### 3.3 一次点击 4 趟往返、同一帧截两次

- **现象**：`screenshot_page` → `mark_dot`（内部又截一屏）→ 点击 → 再截图，单动作 14–18s；`mark_dot` 单轮 49 次 / 66.3s。
- **已修**：`4fc847c5` — `mark_dot` 签发帧 token，点击类工具复用该帧并回传点击后页面图；同一动作只截一屏。实测 136 → 98 次工具调用，`mark_dot` 49 → 33。
- **提示词配套**：核对与点击之间禁止再截图；点击后直接用回传图复核。

### 3.4 xpath 命中率只有 56%

- **现象**：9 次 `xpath_action` 只命中 5 次。两次失败原因：App 把文案写成「睡 眠」（按「睡眠」查不到）；`@text='定时'` 命中 2 个节点无法区分。
- **已修**：`c35a24bf` — 归一化匹配（去空白 / 全角转半角 / 忽略大小写）+ 最多 3 个候选一次 UI 树读完。实测命中率 **56% → 85%**。

### 3.5 多命中无法区分

- **现象**：`texts="定时"` 返回 2 个（(142,774)、(230,1684)），模型只能按坐标猜。
- **已修**：`c35a24bf` — 全部命中点画在同一张图上带序号，返回 `items[]`（序号/文本/坐标）+ token；点击用 `index` 选点，越界直接报错不点。

### 3.6 拖动没有反馈

- **现象**：时间选择器里 7 次 `drag_ratio`：4 次真实滚动 + 3 次"拖了不知道结果"的补拖，同一列把距离从 0.58 加到 0.68 再试。
- **根因**：拖动只回 `action_time`，看不到滚轮停在哪；起点还是估的。
- **已修**：`9446cccf` — `mark_dot` 支持终点（画起点 1 → 终点 2 + 箭头），拖动必须带 token 且帧内要有两个点；拖完回传页面图；提示词禁止原样重复同一次拖动。

### 3.7 滑块手柄 xpath 打不到（颜色·2）

- **现象**：颜色用例第 2 步「色温 >70%」：77 次工具 / **48 次 mark_dot** / 7 次拖动 / 3 次点击，19:40–19:51（**11 分钟**），被驳回 1 次（判「手柄在 50%」）。
- **根因**：
  1. `xpath_action(texts="色温,基础色")` 只返回文本标签坐标 `(189,1618)`，不是白圈手柄；模型只能目测，起点常落在轨道上 → 拖动无效；
  2. 页面不显示百分比，拖完只能再截图目测；手柄位置每次都变，模型仍按旧坐标起拖；
  3. 判据「手柄 >70%」只能目测，同一类画面两次给出 50% 与 85% 两种判断。
- **状态**：📝 待办（未改）。可选：改断言口径（最右端/可读数值）、点轨道代替拖动、用 `resource-id` 取滑块 bounds。

## 四、验收与提示词

### 4.1 弹窗/Toast 瞬时，验收看不到

- **机制**：
  1. 执行者与验收者是两个独立实例（每步隔离），验收看不到执行者的帧；
  2. 验收等执行者交完 handover 才开始，自己截图时弹窗（典型 2–3s）已消失；
  3. 纯 UI 版没有日志兜底 → 弹窗类断言必然容易失败。
- **状态**：📝 待办。四方案：A 断言改稳态（只改用例，首选）、B 有日志的改回日志、C 给验收注入执行者最后一帧（引擎 + spec，覆盖最广）、D 执行者复现弹窗（不推荐）。

### 4.2 验收证据分流

- **现象**：早期验收对日志型断言仍要截图、对页面型断言又去查日志，导致"缺一类证据判不通过"。
- **已修**：验收提示词按断言类型分流 —— 日志型以日志为唯一判据（不必截图、不因离开页面判失败）；页面型以截图为主（不调日志）；混合型两类都要。

### 4.3 验收要求不可得证据

- **现象**：要求执行者提供 base64 原文 / 落盘路径 —— 执行者工具集里没有。
- **已修**：提示词禁止要求工具无法产出的证据；驳回说明必须能在执行者工具集内执行。

### 4.4 执行者提前离开结果页

- **现象**：执行者先按 BACK 再交卷，验收重新截图看到的是详情页 → 判不通过。
- **已修**：提示词要求「交卷前停在本步结果所在的页面」并先截图留证。

### 4.5 handover 啰嗦

- **已修**：只写两块（逐条操作 + `action_time`、最终结果「达成/未达成」）；禁止"尚未/未完成/请下一步"这类话术。

## 五、用例与锚点

### 5.1 第 1 步锚点没有收益（已量化）

| 阶段 | 任务 | 第 1 步耗时 | 工具数 |
| --- | --- | ---: | ---: |
| 视觉优先，无锚点 | 184 | 125.9s | 13 |
| xpath 优先，无锚点 | 186 | 43.6s | 13 |
| xpath 优先，无锚点 | 189/191/193 | 24.8–33.2s | 9–10 |

- **状态**：📝 结论已记录；锚点可删可留。

### 5.2 同名/等价入口描述有歧义

- **现象**：H6810 详情页有两个「定时」（亮度条左侧 / 「更多」→「操作功能」第一行左侧），原描述只写「底部操作区的定时（约 0.21, 0.70）」，既没说是哪个又用坐标当锚点。
- **已修**：用例改为「任选其一」+ 区域 + 相邻元素，不再出现归一化坐标。
- **约定**：等价入口写"任选其一"；不等价入口写清区域与相邻元素并说明不要点另一个；不用坐标当锚点。

### 5.3 其余用例补齐锚点与关键词

- 12 条用例 / 58 步全部补齐 anchor（47 个），只给日志型断言加 log；涂鸦等四个无关键词功能只按页面判定。
- **状态**：✅ 已完成（用例文件在 `D:\Govee\data\H6810\`）。

### 5.4 用例设计产物与执行输入不闭环（已改设计，待上线验证）

- **问题**：设计工作流产出「七节 Markdown + 13 字段用例表」，执行侧要的是「每步 action/expected + anchor + log」。全仓库没有 Markdown→YAML 转换器，H6810 那 12 条是手写 + 反复改锚点。库里的 44 条真实用例中 164 步有 10 步是「2 人目视 / 拍摄测色 / 不判 PASS」这类机器做不了的动作。
- **改法**（OpenSpec 变更 `case-authoring-state-machine`）：产物换成三段式结构化数据——**需求状态机 → 业务流场景 → 用例**；两个角色（编写 + 验收）走一条 GoalPipeline；验收只判「数据与需求一致」与「无捏造」，可机器判的部分交给代码预检（`source` 必须是需求原文子串、引用必须已声明、用例数值必须可追溯到某条原文）。
- **已实测**：H717D 小需求跑一次真实流水线 → 6 状态 / 8 迁移 / 5 场景 / 11 用例，预检 0 确定性问题 0 告警，验收首轮通过，Markdown 与 Mermaid 由产物渲染。
- **仍缺**：产物还没导出成执行用 YAML（`anchor` / `log` 仍需人工补）；这条留作后续变更。

### 7.3 中断步骤无标记

- **已修**：见 1.3（步骤行「日志中断」红标 + BUG 单）。

### 7.4 关闭任务后仍在跑并继续计费（已修）

- **现象**：任务 `197`（结构化步骤-串口-全功能测试-02）09:47:20 点关闭，数据库当场写成 `cancelled`，但执行线程又跑了 **230 秒**：77 次设备操作（点击 18 / 标点 18 / 截图 15 / xpath 14 / 拖拽 4 / 应用控制 1 / 查日志 3 / 重置工具 3）、82 次模型调用、**¥0.9394**（关闭前 33 秒只花了 ¥0.0249）。真正停下靠的是 09:51:08 一条工具异常（`ExceptionGroup: One or more tool calls raised an exception`）打断事件流。
- **根因**（三层叠加）：
  1. AgentScope 默认吞取消：`ReActConfig.interruption_raise_cancelled_error` 默认 `False`，`Agent.reply_stream` 在 `except CancelledError` 里只发一条 `ReplyEnd(INTERRUPTED)` 就正常返回；并发工具路径还会 `uncancel()`。于是 `task.cancel()` 只等于「打断这一次回复」，SOP 引擎把它当成「本步失败」自动重试 —— 09:47:20.036 的 ReplyEnd 之后 3 毫秒就开始了同一步的第二次尝试。
  2. 取消信号只在**每条用例开头**检查一次，单用例任务永远命中不到。
  3. 关闭动作里立刻 `finalize_task` → 内部 `dispatch_device(serial)`，同设备排队任务会被放行；旧线程还在点屏幕，就出现两条任务抢一台手机。
- **已修**（变更 `task-cancel-immediate-stop`）：
  - 工作流在**每个事件边界**检查停止信号，命中即抛取消结束当前步骤；当前步作废，不生成判决、不触发重试。
  - 角色侧 `ReActConfig.interruption_raise_cancelled_error` 默认改为 `True` 并透传到 agentscope，取消能穿透角色层。
  - `cancel_running_task` 不再放行设备槽；放行统一在工作线程退出时执行，另设 60 秒兜底：线程仍未退出则写一条 `TaskCancelTimeoutEvent` 并强制放行。
  - 工作线程收尾先 `refresh_from_db`，任务已是 `cancelled` 时不覆盖终态。
- **自测**：`test_platform_cancel.py`（5 条）+ `test_task_cancel_dispatch.py`（6 条）+ `test_case_run_continuity.py`（7 条）全绿；未新增 `raises-doc` 告警。
- **真机复测**（任务 `198`「关闭功能测试-01」，10:41:08 关闭）：关闭后 **0 条事件、0 次模型调用、¥0**，工作线程已退出（进程内无 `ai-task-198` 线程）；总花费 ¥0.0113。关闭前最后一条事件早于点击 2.5 秒，因此本次无法从事件侧读出「停止延迟」的精确秒数。
- **界面口径**：关闭任务在详情页里，当前步与用例徽标显示「主动关闭」（中性灰），未执行的步骤仍显示「未执行」，已判 `FAIL` 的步骤不被改写。
- **非目标**：不引入「停止中」中间态；日志类工具异常打断整条用例的问题另立变更。

### 7.5 日志空洞把一条做成的用例判死，原因还丢了（已修）

- **现象**：任务 `201`（结构化用例测试-纯UI版本-01）里，`H6810 详情页开关与亮度功能测试` 判「未完成」，但执行者其实做成了：11:16:25 点电源键关灯（截图显示「设备已关闭」）、11:16:42 再点开灯（蓝灯 85%），11:16:59 提交 handover。42 秒后这条用例就结束了，第 3、4 步没跑，整轮任务从 `completed` 变成 `failed`。
- **根因**（三层）：
  1. **设备日志 36 秒空洞**（11:16:13–11:16:49）正好盖住两次点击；验收者在 11:17:06 并发查 `check_device_log(switch_off)` 与 `check_device_log(switch_on)`，两个窗口内都没有任何可解析行。
  2. 日志工具按当时的规格「中断本轮」`raise ValueError(LOG_EMPTY)`，`tool_wrapper` 把它转成 `DeveloperOrientedException`，AgentScope 把两个异常聚合成 `ExceptionGroup(2 sub-exceptions)` 穿透工作流，整条用例被结束。
  3. 中断事件由 `_emit_interrupt` 在**事件循环线程里同步**写库，恰好凑满 50 条一批 → Django `SynchronousOnlyOperation` → 整批 50 条（seq 651–700，含写着原因的 `StepInterruptedEvent`）逐行重试后全丢。`task_media` 里还留着 event_seq 652/658/664/676/699 的截图，事件行却没了 —— 报告只剩「未完成」，没有原因。
- **已修**（变更 `interrupt-reason-and-log-evidence`）：
  - 日志工具窗口为空 / 未盖满 5 秒时返回 `FAIL` + `reason` + `evidence_missing`，不再抛异常；验收提示词同步写明「证据不可用 ≠ 执行失败」。
  - 工作流用 `_ResilientSOPStep` 把中断收敛到单步：记原因、不重试、**继续跑后续步骤**；被中断的步骤记 `FAIL` 并计入失败统计，失败原因写清「第几步 + 中断类别 + 原文」。
  - `_emit_interrupt` 改走 `event_sink.emit_record`（记录直写接收方 + 线程转交），事件写入失败的行留在缓冲里重试（上限 500 行），不再整批丢。**原版误走 `show_event`**：那条路要按 AgentScope 事件类型名折叠，`EventRecord` 认不出会被静默丢成空结果，所以任务 201/204 里 `StepInterruptedEvent` 一条都没落库（见下方补修）。
  - 报告步骤行新增 `interrupt_kind`：区分「日志中断」（证据不可用）与「异常中断」（执行层异常），悬停看原因全文。
- **自测**：`test_step_interrupt_continue.py`（7 条）+ `test_tool_serial.py`（14 条）+ `test_event_store_resilience.py`（4 条）+ `test_task_report_interrupt.py`（3 条）全绿；前端 `tests/task-list` 141 条全绿。
- **注意**：任务 201 的历史事件里那条中断事件已经丢了，所以旧任务页面上看不到原因；本修复只对新产生的运行生效。
