- 有/无锚点的工具构成**完全一致**（`app_control 1 + xpath 1 + click 1 + 截图 2~3`），锚点没减少任何一次调用；

- 第 1 步真正的提速来自 **xpath 优先 + 帧 token**：125.9s → 43.6s → ~27s，工具 13 → 9；
- 第 1 步是扁平入口（桌面 → 点卡片），模型不需要"找入口"，锚点没有提供它缺的信息。

## 四、颜色用例第 2/4 步为什么这么贵

### 第 2 步「色温 >70%」：滑块拖动循环

- 77 次工具调用：截图 7 / **mark_dot 48** / xpath 7 / 拖动 7 / 点击 3；
- 时间跨度 19:40:36 → 19:51:25（**约 11 分钟**），期间被**驳回 1 次**：
  - 第一次验收：「色温滑块手柄位于条宽 **50%** 处，并未处于 70% 以上」；
  - 重试后验收：「手柄停在约 **85%~90%**，明显大于 70%」通过。

三条根因：

| # | 根因 | 证据 |
| --- | --- | --- |
| a | **xpath 定位不到滑块手柄**：`xpath_action(texts="色温,基础色")` 返回的是文本标签坐标 `(189, 1618)`，不是白圈手柄；模型只能目测，起点常落在轨道上 → 拖动无效 | 事件 1056–1059 |
| b | **拖动无反馈**：页面不显示百分比，拖完只能再截图目测；手柄位置每次都变，模型仍按旧坐标起拖 → 8 次拖动 | 起点在 0.497 / 0.527 / 0.5 / 0.663 之间来回 |
| c | **判据主观**：「色温 >70%」只能目测色条上手柄位置，同一类画面两次给出 50% 与 85% 两种判断 | 两条 verdict 文本 |

## 五、弹窗类断言：验收为什么看不到

机制：

1. 执行者与验收者是**两个独立实例**（每步隔离），验收看不到执行者的上下文帧；
2. 验收要等执行者交完 handover 才开始，它自己 `screenshot_page` 时，Toast/弹窗（典型 2–3s）已消失；
3. 纯 UI 版没有日志兜底 → 弹窗类断言必然容易判不通过。

方案对比：

| 方案 | 做法 | 代价 | 覆盖 |
| --- | --- | --- | --- |
| A | 断言改成弹窗消失后的**稳态结果**（列表出现新项、开关状态、灯具变化） | 只改用例 | 高 |
| B | 有日志的动作改回日志判据 | 只改用例 | 中（涂鸦/快照/趣味灯光/自动播放无日志关键词） |
| C | 给验收「读执行者本步最后一帧」的能力（或随 handover 注入该帧） | 引擎 + spec 改动 | 最高 |
| D | 执行者交卷前复现弹窗 | 不可控、可能改状态 | 低 |

现状里执行者截图**已经落库**（任务详情可见），只是验收 Agent 的上下文里没有它——C 本质是"接线"，不是重新采集。
