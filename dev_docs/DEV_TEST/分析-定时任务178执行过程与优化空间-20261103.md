# 分析 — 定时任务 TASK-178 执行过程与优化空间（2026-11-03）

> 数据来源：`task_tasks` / `task_events`（task_id=178）、`logs/agents/agent_events.log`、当前提示词与工具配置。

## 结论先行

1. **TASK-178 是健康的一轮**：5 步全部 attempt=1、首判即过，580s、135 次模型调用、¥1.2542。比 177（923s 失败）已经好很多，但**仍有约 30% 的时间花在「找入口 / 猜日志关键词 / 重复标记」上**。
2. **给一份「详细测试步骤」会有帮助，但帮助不在于"步骤写得更细"，而在于三类信息**：入口锚点、页面结构、日志关键词。写成散文会被每轮重复计费，且 UI 一变就误导；应做成**结构化字段 + 应用短卡**。
3. **最大的一处是"该有却没有"的东西**：验收提示词明确写「系统提示词末尾附有日志关键词表（关键词 → 功能点）」，但仓里根本没有这份表（全仓无关键词目录资产），导致 TASK-178 的验收模型在 step2 连续盲猜 **13 次** `check_device_log`。
4. **成本最大的可控杠杆不是提示词，是上下文**：同一个 Agent 连跑 5 步，单次调用输入从 8.7K 涨到 28.7K；5 步共 239 万输入 token（¥0.98 全是输入）。**按步重置上下文**预计可把输入砍到 ~120 万、费用降到 ¥0.6 左右。

## 三、如果准备一份"定时功能详细步骤"文件，会不会更快？

会，但要看写什么。按收益排序：

### 3.1 最高性价比：补「日志关键词表」（本该存在）

验收提示词已承诺「系统提示词末尾附有日志关键词表（关键词 → 功能点）」，但：

- 仓里没有任何关键词目录资产（`engines/agents/config/data/` 下无关键词文件，`role_sys_prompts` 也没有注入它）；
- 结果就是上面 17 次盲猜。

做法：新增一份 `engines/agents/config/data/log_keywords/<SKU>.md`（或 yaml），按「功能点 → 关键词」列出（如 `定时设置成功 → timer_configs_set_success`、`唤醒设置 → awaken_configs_set_success`、`睡眠 → sleep_configs_set_success`），在 `role_sys_prompts` 里随 `app_info` 一起注入验收角色。
预期：step2 的 13 次 → 1~2 次，省 ~30s，且判决不再依赖"猜中"。

### 3.2 次高：把"步骤"写成**锚点**，而不是散文

现有 `app_info/govee_home.md`（1.4KB，约 400 token）已经有「导航与入口 / 交互约定 / 验收锚点」的结构，但**没有定时页**。建议按功能页扩写，内容只要四类：

| 类型 | 例子 |
|---|---|
| 入口 | 详情页「定时」按钮在左上（约 0.125,0.32）；定时页**没有新增按钮**，只能点已有任务行进入编辑 |
| 元素 | 任务行点击区域、时间行、滚轮列位置、右上角保存对勾 |
| 交互 | 滚轮按行滚动（每行 88px），分钟列要滚 30 行 → 直接用 `drag_ratio` 大位移，不要逐行点 |
| 证据 | 页面文案（「5:00 开 不重复」）+ 日志关键词 + 端口 7005 |

这一步直接消掉 2.1 与 2.2 的绕路，预计 step2 从 207s → 130s 左右。

### 3.3 更彻底：把"文件"变成结构化字段

比散装 Markdown 更稳的做法，是给用例 step 增加结构化字段并由 SOP 注入当步上下文：

```yaml
- action: 测试定时功能，成功设置一个预约定时任务；如果已有则重新设置不同的时间即可
  assert: 定时列表出现新时间且开关为开启
  anchor: {page: 定时页, entry: 详情页左上「定时」, target: 已有任务行}
  log: {sku: H6810, port: 7005, keyword: timer_configs_set_success}
```

好处：只注入**当前步**的锚点（几十 token），不污染历史；模型不用"读完全部步骤再找自己那步"。坏处：要改用例资产格式，且有 UI 变更时维护成本。

### 3.4 不建议：把整份操作手册塞进系统提示词

系统提示词每一轮都会重复计费。以 1.4KB 短卡为例每轮约 +400 token，135 次调用 ≈ 5.4 万 token（约 ¥0.02，尚可）；但如果写成 5KB 的"详细步骤"，就是每轮 +1500 token ≈ 20 万 token，且与"每步只看自己的锚点"相比是纯浪费。

## 四、与提示词无关、但收益更大的两项工程优化

### 4.1 按步重置上下文（成本减半）

现状：`platform_run._drive_real` **每条用例**建一次执行者，5 个步骤共用一个 Agent，历史持续累积：

| 步 | 平均输入/次 |
|---|---|
| 1 | 8.7K |
| 2 | 15.3K |
| 3 | 20.7K |
| 4 | 25.2K |
| 5 | 28.7K |

若每步新建执行者（或每步结束清空历史，只保留"当前页 + 上一步 handover"），输入预计从 239 万降到 ~120 万，**费用 ¥1.25 → ~¥0.6**，每步调用也会更快（上下文小 → 首 token 更快）。
风险：新实例不知道"当前停在哪个页面"，需多 1 次截图确认（约 +2s/步），净收益仍为正。

### 4.2 合并"标记 + 点击"，补"回桌面"动作

- `mark_dot` 35 次是纯预演：可以让 `click_ratio` 自带一次标注返回，或在同一轮里先标后点（现在是两轮、两次模型调用）。预计省 20~25 次调用、约 20s。
- 增加 `press_home` / `back_to_desktop` 原子工具：step5 从「2 次 stop_app + 4 次 BACK」变成 1 次调用，省 ~20s 并减少不确定性。

### 追加：`app_control` 启动/停止一直失败的根因（2026-11-04）

复盘「monkey 启动失败」时发现更底层的问题：被测应用短卡 `app_info/govee_home.md` 里把包名写成了 **`govee.home.com`**（`com.govee.home` 的段顺序反了）。设备上并不存在这个包，于是：

- `app_control start_app` 走 `monkey -p govee.home.com` → `** No activities found to run, monkey aborted.`，模型只能退回「上滑找图标再点」——这也解释了为什么每次第一步都要多花 10~50s。
- `app_control stop_app` 同样无效：`am force-stop` 对不存在的包也会返回成功，所以第 5 步出现「2 次 stop_app 都返回成功、但应用仍在前台」，只能用 4 次 BACK 兜底。

修复：短卡包名改为 `com.govee.home`；设备层 `app_start` 改为**先解析 LAUNCHER 组件**（`com.govee.home/.HomeActivity`）用 `am start -W -n` 启动，解析不到才退回 monkey；`app_stop` 先校验包已安装，包名错时直接报错并列出设备上名字相近的包，避免「表面成功」。
