# 分析：结构化步骤测试-定时功能测试-02（TASK-184）耗时构成

> 日期：2026-11-04｜数据源：`task_events`（TASK-184 共 740 条）＋ `task_tasks`｜设备：R5CT62RH88F
> 复算脚本：`temps/analyze_task184.py`（读 `temps/task184_events.tsv`）

## 一、结论

1. **界面上「2m06s」是这一步的墙钟，「模型 43s／8s」只是其中两次模型推理。** 第一步 125.9s = 执行模型 43s + 验收模型 8s + 工具 42.5s + 空档 32.4s。差的 75s 不在模型里。
2. **全案 645s 的构成**：模型 343s（53%）＋ 工具 172s（27%）＋ 空档 84s（13%）＋ 装配 44s（7%）。模型刚好过半，剩下 47% 与推理无关。
3. **真正的成本单位是「一次工具往返」而不是「一次动作」**：本用例只有 32 个实际设备动作，却产生 136 次工具调用 + 134 次模型调用，平均 **4.5s/往返、19s/动作**。想缩短墙钟，先减往返次数，而不是换更快的模型。
4. **两个实现级浪费**（占比大、可定点修）：
   - `mark_dot` 内部**自己截一次图**，而执行模型在 22 次里仍然先调了一次 `screenshot_page` —— 同一次核对截了两屏；
   - `check_device_log` 每次**把整份 8.5MB 日志全文读入并按行重解析**（`_capture_rows`），单次进程内即 1.56s，运行中实测 8.7–20.7s。

## 六、往返结构：32 个动作 → 136 次工具调用

相邻工具调用对（Top）：

| 前 → 后 | 次数 |
| --- | ---: |
| `screenshot_page` → `mark_dot` | 22 |
| `mark_dot` → `mark_dot` | 22 |
| `tap_screen` → `screenshot_page` | 13 |
| `mark_dot` → `tap_screen` | 12 |
| `mark_dot` → `click_ratio` | 10 |
| `click_ratio` → `screenshot_page` | 10 |

实际动作数 = `tap_screen` 13 + `click_ratio` 10 + `drag_ratio` 4 + `xpath_action` 5 = **32**；
工具调用 136 → **每个动作 4.25 次调用**；每次调用都要模型往返一次（均 2.56s）。

一个典型点击的链路：`screenshot_page`（0.79s）→ `mark_dot`（1.35s，内部再截一屏）→ `tap_screen`（0.24s）→ `screenshot_page`（0.79s），三到四趟模型往返 ≈ 12–16s。

## 十二、xpath 优先 + 锚点门槛实测（变更 xpath-first-anchor-gate）

同一份用例、同一台设备，改为「先按文案走 xpath → 命中点标在一张图上带序号 → 带 token 与 index 点击；xpath 未命中才用视觉估算」后重跑（standalone 直跑引擎，避开 dev server 自动重载）：

| 指标 | TASK-184（最初） | TASK-186（上次） | 本次（xpath 优先） |
| --- | ---: | ---: | ---: |
| 总耗时 | 645s | 354s | **356s** |
| 工具调用 | 136 | 98 | **60** |
| `mark_dot` | 49 | 33 | **8** |
| `screenshot_page` | 35 | 19 | 14 |
| `xpath_action` | 5 | 4 | **13** |
| `check_device_log` | 3 | 3 | 3 |
| 核对 / 动作 | 1.81 | 1.50 | **0.38** |
| 工具报错 | 0 | 0 | **0** |

关键验证：

1. **xpath 命中率 85%**（13 次里 11 次命中），超过 80% 的目标；其中两次是靠归一化匹配命中的（`睡眠` 与页面上的 `睡 眠`），一次是 `唤醒时间,7:53` 双候选一次读完。
2. **核对次数从 33 降到 8**：大部分点击直接用 xpath 返回的帧 token，不再额外 `mark_dot`。
3. **没有一次「缺 token」报错**：硬门槛没有挡住正常流程，说明提示词与工具的配合是通的。
4. 用例仍然 5 步全通过（`status: success`，`failed: []`）。

耗时没有继续下降的原因：工具往返少了 38 次，但本次 `drag_ratio` 从 4 次涨到 7 次（拖动重试），且 xpath 每次命中要多截一张标记图；两者相抵，墙钟与上次持平。下一步该看的是拖动为什么会重试。
