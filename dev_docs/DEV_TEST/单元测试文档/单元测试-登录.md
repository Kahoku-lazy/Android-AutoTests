## 一、鉴权拦截器层（`tests/login/p0/apiAuthInterceptors.spec.ts`，7 条）

> 被测对象：`frontend/src/shared/api-auth-interceptors.ts` 的 `createAuthInterceptors()`；生产由 `shared/api-client.ts` 挂到 axios 实例。本层全部通过注入假依赖（令牌读写、刷新请求、跳转、重试）来隔离网络。

#### TC-FE-LOGIN-001 请求拦截器：注入 Bearer token
- **业务功能**：已登录用户的业务请求自动携带身份凭证
- **测试目的**：验证主路径规则「本地持有访问令牌时，出站请求在被发出前已写入鉴权头」，使服务端能识别调用者
- **测试方法与步骤**：① 注入假令牌提供者（返回 `old-access`）；② 构造请求头为空的出站请求；③ 让请求经过请求拦截器；④ 读取拦截后请求的头字段
- **断言逻辑**：
  - 请求头 `Authorization == "Bearer old-access"`（`Bearer` + 半角空格 + 令牌原文，全等比较）

#### TC-FE-LOGIN-002 无 token 时：不写 Authorization
- **业务功能**：未登录 / 令牌缺失时不得伪造凭证
- **测试目的**：验证令牌为空串时不产生鉴权头，避免发出 `Bearer ` 这类空凭证请求
- **测试方法与步骤**：① 令令牌提供者返回空串；② 构造头为空的请求并过拦截器；③ 读取头字段
- **断言逻辑**：
  - `config.headers.Authorization` 为 `undefined`

#### TC-FE-LOGIN-003 401 后 refresh 成功：写新 token 并重试原请求
- **业务功能**：访问令牌过期后自动续期并续跑原请求（用户无感）
- **测试目的**：验证「401 → 用 refresh_token 换新令牌 → 以新令牌重试原请求」的完整链路，且过程中不把用户踢回登录页
- **测试方法与步骤**：① 打桩续期请求返回 `status=true` 与新 access；② 打桩重试请求返回成功；③ 构造带原请求信息的 401 错误交给错误拦截器；④ 观察各依赖调用与原请求头变化
- **断言逻辑**：
  - `refreshRequest` 调用 1 次，入参为 `{ refresh_token: "valid-refresh" }`
  - `setToken` 收到 `new-access`；原请求头被改写为 `Bearer new-access`
  - `retryRequest` 收到该原请求；错误拦截器的返回值即重试结果
  - `redirectToLogin` 未被调用

#### TC-FE-LOGIN-004 并发两个 401：只触发一次 refresh
- **业务功能**：多个请求同时过期时只续期一次，避免令牌轮换互相作废
- **测试目的**：验证并发 401 下续期被加锁合并 —— 同一时刻只发一次续期请求，其余请求共享其结果
- **测试方法与步骤**：① 打桩续期为一个悬挂未决的 Promise；② 同时把两个 401 交给错误拦截器；③ 观察 in-flight 锁状态与续期调用次数；④ 放行续期，等待两个请求收敛
- **断言逻辑**：
  - in-flight 期间 `hasInFlightRefresh()` 为 `true`；`refreshRequest` 仅 1 次
  - 放行后两个请求都完成重试（`retryRequest` 2 次）；`setToken` 收到共享的新令牌

#### TC-FE-LOGIN-005 refresh 失败：清 token 并跳转 /login
- **业务功能**：续期失败时退出到登录页
- **测试目的**：验证续期失败后清理凭证并跳转登录页（单账号下不再有「还有备用账号就留下」的分支），而不是无限重试
- **测试方法与步骤**：① 打桩续期失败；② 把 401 交给错误拦截器并捕获其拒绝
- **断言逻辑**：
  - 调用被拒绝（未吞错）；`clearToken` 被调用；`redirectToLogin` 被调用
  - `retryRequest` 未被调用

#### ~~TC-FE-LOGIN-006~~（已作废）
- **作废原因**：原用例验证「续期失败但池里仍有备用账号 → 不跳登录页」。账号池已随 `remove-multi-account-pool` 移除，该分支不再存在，行为合并进 TC-FE-LOGIN-005；编号保留以维持与 PRD 的对应关系。

#### TC-FE-LOGIN-007 无 refresh_token 时：直接拒绝，不跳转
- **业务功能**：缺少续期凭证时不应发出无效续期请求
- **测试目的**：验证 refresh_token 缺失时直接拒绝原请求，且不触发跳转（交由上层处理）
- **测试方法与步骤**：① 令 refresh_token 为空串；② 把 401 交给错误拦截器并捕获其拒绝
- **断言逻辑**：
  - `refreshRequest` 未被调用；`redirectToLogin` 未被调用

#### TC-FE-LOGIN-008 同一请求已 _retry 过：不再 refresh
- **业务功能**：防止「续期 → 重试 → 再次 401」形成刷新死循环
- **测试目的**：验证已被标记重试过的请求直接拒绝，不再触发续期
- **测试方法与步骤**：① 构造带 `_retry=true` 的原请求；② 把 401 交给错误拦截器并捕获其拒绝
- **断言逻辑**：
  - `refreshRequest` 未被调用

## 六、单账号会话存储层（`tests/login/p0/token-storage.spec.ts`，4 条）

> Vitest 复用 `frontend/vite.config.js` 的 `test.projects`，按「模块 / 优先级」分栏；下列命令均在 `frontend/` 目录下执行。

| 场景 | 命令 |
|------|------|

> ⚠️ `npx vitest run` 只把结果打到终端，**不产出报告文件**；要看报告请用 12.2。

### 12.2 生成测试报告（`tests/run.mjs`）

| 报告 | 命令 | 产物 |
|------|------|------|
| **HTML 报告**（推荐，浏览器直接打开） | `cd frontend && node tests/run.mjs html tests/login` | `frontend/tests/reports/html/index.html` |
| JUnit XML（接 CI / Jenkins） | `cd frontend && node tests/run.mjs junit tests/login` | `frontend/tests/reports/junit.xml` |
| JSON（二次统计 / 自己写脚本） | `cd frontend && node tests/run.mjs json tests/login` | `frontend/tests/reports/report.json` |
| 终端摘要 + JUnit + JSON | `cd frontend && node tests/run.mjs all tests/login` | 上面三个同时产出 |

- 命令末尾的 `tests/login` 是 Vitest 的路径过滤参数：换成 `tests/<模块>` 即可复用到其它模块，**不带则跑全量**。
- `node tests/run.mjs module login` 只跑登录模块、**不产报告**（只有终端输出），别用它找报告文件。
- 报告目录 `frontend/tests/reports/` 已在 `.gitignore:66` 中 —— 属可随时重新生成的产物，不入库。
