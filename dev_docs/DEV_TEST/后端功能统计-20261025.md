# 后端功能统计 — Android-AutoTests

> 统计时间：2026-10-25 · 基线：`Kahoku` 主干 · 口径：`backend/` + `engines/` + `utils/`，**不含** `migrations/`、`__pycache__`、`tests/`、`engines/agents/skills/`（第三方 skill 脚本）

---

## 一、结论

1. **后端是「9 个业务 App + 4 层引擎」的结构**，业务 App 共 **104 个文件 / 12,239 行**，对外 **65 个 HTTP 端点**，落 **19 张业务表**。
2. **真正吃代码量的是引擎层而不是接口层**：`engines/` 46 个文件 **5,694 行**，`utils/` 6 个文件 **2,282 行**；纯业务后端（App + config + gateway + shared）合计 **13,499 行**。
3. **`task_list` 是体量最大的模块**（25 文件 / 3,565 行 / 11 端点），其次是 `case_manager`（16 文件 / 2,763 行 / 11 端点）——两者占了业务代码的 **51.7%**。
4. **端点分布长尾很清楚**：11 个端点的模块 2 个、10 个的 2 个、5～7 个的 2 个、≤4 个的 3 个；平均 **7.2 个端点/App**。
5. **测试资产接近业务代码量**：`tests/` 107 个文件 / **12,612 行 / 536 个 test 函数**，约为后端纯业务代码（13,499 行）的 **0.93 倍**。
6. **发现 4 个与统计口径相关的实际问题**（详见第七节）：`utils/gen_arch_stats.py` 默认输出模式已跑不通、跨模块 import 前缀匹配已失效、架构文档的 per-App 端点数字与实际不符、`tool_ocr` 是保留但未装配的实现。

## 八、待决策

1. **要不要修 `gen_arch_stats.py`**？它是 `python run.py check` 之外唯一能产出「架构事实」的工具，也是架构文档漂移检测的唯一实现。修它 = 改 2 处路径/前缀（约 3 行），顺带能自动校正第七节的第 3 条。
2. **统计数据要什么载体**？当前是 Markdown。若需要给外部汇报（周报/评审），可再出 `.xlsx`（按 App / 按端点两张表）。
3. **`tool_ocr` 删除还是保留**？保留则 11 个已装配工具 + 1 个预留；删除则 `engines/vision` 整层失去调用方。
4. **统计口径要不要固化**？目前「有效行」= 去空行去注释；「端点」= 唯一路径、同路径多方法计 1、不含 schema/swagger/媒体直链。若后续要纳入 CI 门禁，需先把口径写进 `utils/`。
