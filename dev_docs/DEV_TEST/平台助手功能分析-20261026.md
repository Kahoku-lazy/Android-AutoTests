# 平台助手功能分析 — Android-AutoTests

> 分析时间：2026-10-26 · 基线：`Kahoku`（工作区含未提交改动，以当前文件内容为准）
> 范围：`frontend/src/modules/ai-assistant` · `backend/apps/ai_assistant` · `backend/apps/task_list` · `engines/agents`

---

## 一、结论

1. **平台助手不是"聊天助手"，是一台只做 UI 自动化的双角色执行机**：一个智能体（`ai_agents` 单行、超管拥有）带一条 `device_control` 线路，把「用例 YAML」翻译成「执行者点、验收者判」的逐步 SOP。
2. **对外只有 4 个动作**：看看板 → 改身份（名称/头像/标签/描述）→ 提交任务（YAML + 文档 + 设备）→ 看结果（时间线/报告/费用）。模型怎么配、工具怎么给，全都从界面拿掉了，改由代码与后台维护。
3. **执行链是「submit → 抢设备槽 → 后台线程 → 双角色 SOP → 事件入库 → 收尾」**，同设备串行、异设备并行；每条用例最多被驳回 2 次，整轮结束再关一次最近应用。
4. **能力其实压在引擎侧**：11 个已装配工具（执行者 10、验收者 2，其中 `screenshot_page` 双方共用）+ 两套系统提示词 + 上下文压缩/强制交卷开关，业务 App 只负责搬运。
5. **发现 6 处"配置还在、功能已死"的漂移**（详见第六节），其中 2 处有实际影响：**技能组指向不存在的目录**、~~同一笔用量存在两套计费口径~~（**已于 2026-10-26 收敛为单一口径**）。

## 二、能力地图

### 2.1 用户可见的 4 个动作

| # | 入口 | 能做什么 | 代码 |
|---|------|----------|------|
| 1 | `/ai-assistant/agents` 看板 | 看唯一一张身份卡：名称 · `职责：UI自动化` · 配置入口（仅超管可见） | `index.vue`、`helpers/assistant-cards.ts` |
| 2 | `/ai-assistant/agent/:id` 配置页 | 改名称 / 头像（base64 直传）/ 标签 / 描述；职责与工作流只读且写死 | `AgentDetail.vue`、`POST /api/ai/agents/{id}/update` |
| 3 | `/tasks` 任务发布 | 选用例 YAML(`config`) + 文档(`documents`) + 设备 + 用例标题 → 提交 | `TaskSubmitAPIView` |
| 4 | `/tasks/:id` 与 `/reports` | 事件时间线、逐用例结论、失败原因、token 与费用、截图媒体 | `task_reports.py`、`ai_usage.py` |

### 2.2 已经下线、不再存在的入口

- AI 聊天 / 会话面（SSE 流式对话）—— `constants.ts` 里仍留着 `SSE_WATCHDOG_MS`、`MODEL_STATUS_MAP` 等常量；
- AI 工具箱 / 装配台（平台工具开关、Skill 查看、工具调试）；
- 知识库、评测中心；
- 配置页里的模型选择、线路编辑、循环次数、模型校验按钮。

> 判据：`frontend/src/modules/ai-assistant/AGENTS.md` 明确写了三条下线项；后端对应迁移 `0053_retire_ai_chat_surface`、`0055_retire_ai_toolbox`。

## 三、端到端执行链路

```
POST /api/tasks/submit/            multipart: config(YAML) + documents + 表单
   │  校验：agent 存在 → sop_role_models(agent) 可装配（provider/模型名/key 齐备）
   ▼
api.create_task ──► task_tasks(PENDING) + task_attachments(config/documents)
   │
   ▼
api.dispatch_device(serial)        同 serial 至多一条 RUNNING：SELECT ... FOR UPDATE 抢槽
   │  冲突则排队；空闲则 start_task(RUNNING) 并 on_commit 起线程
   ▼
task_runner.spawn_task_thread      daemon 线程 ai-task-{id}
   │  close_old_connections → 取 agent/task → 解密线路密钥
   │  materialize_config_file：优先磁盘原件，否则用附件正文写临时 YAML
   │  bind_cancel / bind_sink(TaskEventSink) / bind_run_context
   ▼
platform_run.run_platform_sop      校验 YAML(唯一智能体 sop) → 按 case_title 过滤 → 逐用例
   ▼
AgentSOPWorkflow.run_workflow      每步 SOPStep(executor, verifier, max_attempts=2)
   │  engine.reply_stream(...) 边跑边把事件折叠上屏；_stamp_step 记录步序/尝试次数
   ▼
事件 / 媒体 / 用量                   task_events(UNIQUE(task,seq)) · task_media · task_usage_hourly
   ▼
api.finalize_task(COMPLETED/FAILED/CANCELLED) + 关闭最近应用（每用例收尾）
```

**关键取舍**（都能在代码里指到）：

| 取舍 | 位置 | 说明 |
|------|------|------|
| 执行者 60 轮 / 验收者 30 轮 | `platform_run.py:29,31` | 注释写明 30 轮会被试错吃满，收尾那次点击轮不到 |
| 每步最多 2 次尝试 | `ui_auto_workflow.py:33` | 驳回后把 `verdict.message` 原样回灌执行者 |
| 单条用例失败不中断整轮 | `platform_run.py:199-202` | 失败只进 `failed` 列表，其余继续 |
| 取消是"协作式" | `platform_run.py:47-57` | `threading.Event` + `loop.call_soon_threadsafe(task.cancel)` |
| 开场输入只喂设备串 | `api.build_sop_run_input` | 不拼目标与文档，避免把自然语言目标塞给执行者 |

## 四、角色分工与提示词契约

| 维度 | 执行者 executor | 验收者 verifier |
|------|----------------|----------------|
| 职责 | 看页面、按坐标操作设备、结构化交卷 | 只判当前这一步，不做操作、不改页面 |
| 工具 | 10 个（截图 / 标点 / 点击 / 滑动 / 拖动 / 输入 / 返回键 / xpath / 应用启停；截图与验收者共用） | 2 个（截图 / 日志关键词检查） |
| 轮次预算 | 60 | 30 |
| 硬约束 | 点击前必须 `mark_dot` 打红点核对坐标；handover 必带 `action_time` | 必须自己截图取证；UI 断言禁止查日志 |
| 禁止项 | 查日志、推测日志结论、交卷里写"未完成" | 要求执行者出示 base64/落盘路径/日志结果 |
| 结构化交付 | handover（做了什么 / 当前页面 / 每次操作时间 / 逐条达成情况） | `passed` + `message`（驳回说明会原样回灌） |

> 设计上把「日志证据」单独锁给验收者（`EXECUTOR_PROMPT` 第 14 条 + `VERIFIER_PROMPT` 第 4-5 条），这是这套 SOP 最有辨识度的一条规则：执行者只负责产出可核对的操作时间，日志真伪由另一个模型独立验证。

## 五、配置真值：执行链到底读什么

| 配置项 | 落库位置 | 执行链是否读取 | 结论 |
|--------|----------|:---:|------|
| `route_configs.device_control.executor` | JSON | ✅ | 执行模型（provider / model / key / base_url） |
| `route_configs.device_control.verifier` | JSON | ✅ | 验收模型 |
| `route_configs.device_control.planner` | JSON | ❌ | 仅 `AgentListSerializer` 展示与旧任务详情回退 |
| `route_configs.device_control.name/avatar` | JSON | ✅（展示） | 看板卡片与任务列表的显示源 |
| `vision_model_name` | 列 | ❌ | 无人读取 |
| `strong_model_name` / `strong_enabled` | 列 | ❌ | 无人读取 |
| `max_loops` | 列 | ❌ | SOP 重试实际由 `MAX_ATTEMPTS=2` 硬编码 |
| `agent_scope_id` | 列 | ❌ | 随聊天面退役，已是死字段 |
| `api_key` / `base_url`（Agent 级） | 列 | ❌ | 已被线路级 `route_configs.api_key` 取代 |

**装配期校验**（`engine_adapter._model_config`）：provider 必须在 `{deepseek, dashscope}`；模型名与密钥不能为空；密钥解密失败按空处理 → 任务提交阶段就会 400，不会等到跑起来才炸。

## 六、发现的问题

### P1-1 技能组空挂：`platform_business` 指向不存在的目录

`tools_config.py:123-125` 把 `engines/agents/skills/executor` 注册为执行者的技能来源，但该目录**不存在**（`engines/agents/skills/` 下只有 `common/` 和 `shared/`，且 `shared/` 只有一个 `.gitkeep`）。

`resolve_skill_dirs()` 只拼绝对路径、不校验存在性，所以不会报错，组会带着一个指向空路径的 `LocalSkillLoader` 继续装配——表现是"平台业务技能"静默为空。

> 影响面待确认：需要一次真实任务跑通后看执行者是否还能读到技能。若不能，等于该工具组形同虚设。

### P1-2 同一笔用量两套计费口径 —— 已收敛（2026-10-26）

| | 引擎侧（每条模型调用） | 业务侧（曾用于任务展示） |
|---|---|---|
| 实现 | `engines/agents/messaging/billing.py` | ~~`backend/apps/task_list/deepseek_billing.py`~~ |
| 精度 | 8 位小数 | ~~4 位小数~~ |
| 高峰判定 | 工作日 **+ 中国法定节假日**（`chinese_calendar`） | ~~仅按星期几~~ |
| 未登记模型 | 返回 0 | ~~回退 `deepseek-flash` 价~~ |

**修法**：业务侧删掉价目表与高峰判定，`task_deepseek_cost()` 换成只读的 `task_cost(task)`（返回 `task.cost_total`），任务列表/详情与仪表盘、任务报告从此同源。价目表与计算只剩 `engines/agents/messaging/billing.py` 一份；回归护栏见 `tests/graybox/unit/test_deepseek_billing.py`（含"task_list 下不得再出现价目表"的断言）。

> 收尾：只读访问器已迁至 `backend/apps/task_list/task_cost.py`（用例 `tests/graybox/unit/test_task_cost.py`）；`deepseek_billing.py` 与 `tests/graybox/unit/test_deepseek_billing.py` 已置为空占位，待 `git rm` 删除。

### P2-1 死配置 6 项

`vision_model_name`、`strong_model_name`、`strong_enabled`、`max_loops`、`agent_scope_id`、线路级 `planner` —— 模型字段、序列化器字段、迁移都在，执行链一项都不读。删掉界面时没有同步删数据面。

### P2-2 前端文案与常量漂移

- 页面标题写着「平台小助手 / 副标题：配置**两条**线路」，实际只渲染 **1** 张卡（`assistant-cards.ts` 的注释已改成"当前只有控制设备这一条"）；
- `constants.ts` 仍留着已下线聊天面的常量：`WORKSPACE_TOOL_NAMES`、`PLATFORM_TOOL_NAMES`、`SSE_WATCHDOG_MS`、`MODEL_STATUS_MAP`、`TOOL_SOURCE_LABELS`、`CONNECTION_MODE_LABELS`。

### P2-3 模型目录无调用方

`prompt_config.DEEPSEEK_MODELS` 与 `model_supports_image()` 没有任何调用点；注释里对拍的两个对象都已不存在——前端 `components/ModelConfigField.vue`、测试 `tests/graybox/unit/test_ai_deepseek_model_catalog.py`。

### P3-1 提交入参留着一套用不上的旧字段

`TaskSubmitInputSerializer` 仍校验 `attachment`（限 `.docx`/`.pdf`、≤20MB），但 `TaskSubmitAPIView.post` 只读 multipart 的 `config` / `documents`；`goal`、`assistant_route`（只接受 `device_control`）同样标着"仅兼容历史客户端"。读代码的人很容易以为附件走 `attachment`。

### P3-2 头像上传无约束

`POST /api/ai/upload-avatar/` 只校验"能 base64 解码"，不限大小与真实图片类型，直接拼成 `data:image/png;base64,...` 存进 `avatar`（TextField）。大图直接撑大 `ai_agents` 行。

## 七、权限与安全（现状是干净的）

| 面 | 现状 |
|----|------|
| 读 | 超管全量；普通用户 = 超管拥有的共享助手 ∪ 自己的（`filter_agents_for_user`） |
| 写 | 创建/更新/删除/揭示 Key **全部仅超管**（`check_can_*`），非超管 403 |
| 密钥 | 线路内 `api_key` 用 `SECRET_KEY` 派生 Fernet 加密；详情接口对非超管返回 `{}`，超管看到脱敏值 |
| 一次性揭示 | `key_revealed` 标记位，第二次只回脱敏值与"已过期"提示 |
| base_url | 生产必须 https + provider 主机白名单 + 禁本机地址（`provider_registry.validate_base_url`） |
| 提示注入面 | 执行者拿不到日志工具、验收者拿不到设备操作工具，两侧能力互斥 |

## 八、观测与成本

| 面 | 实现 |
|----|------|
| 事件时间线 | `task_events`（`UNIQUE(task,seq)`），`fold.py` 把增量事件折叠成一条可读记录 |

| 费用 | DeepSeek 两档价目 + 高峰 ×2；**dashscope 模型不计费** |
| 看板 | `dashboard/ai_usage.py`：用量趋势、当日分时、最近任务、活动时间线 |
