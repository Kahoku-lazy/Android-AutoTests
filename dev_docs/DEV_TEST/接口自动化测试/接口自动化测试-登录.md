## 一、公共执行机制（所有用例共用）

用例本身是 YAML 数据，运行时由 `tests/api/loader.py` 加载并执行，每条用例固定做**三级断言**；失败信息会带上「编号 + 测试标题 + 期望值 / 实际值」。

1. **HTTP 状态码** —— 来自用例的 `expect.status`
2. **响应结构（JSONSchema）** —— 来自 `expect.schema`，Schema 定义在 `tests/api/schemas.py`：
   - `auth_success`（登录成功）：`status=true`；`data.access_token` / `data.refresh_token` 为长度 ≥10 的字符串；`data.token_type=bearer`；`data.user` 含 `id` / `username`，且**不允许出现 schema 之外的字段**（`additionalProperties: false`）
   - `register_success`（注册成功）：同上，另加 `data.user.email`
   - `error`（失败）：`{status: false, message: 非空字符串}`，同样锁死结构（多一个字段即失败）
   - `refresh_success`（续期成功）：`status=true`；`data.access_token` 为长度 ≥10 的字符串；`data.token_type=bearer`
   - `me_success`（身份读取成功）：`status=true`；`data.user` 含 `id` / `username` / `is_superuser` 三项
   - `logout_success`（登出成功）：`status=true`；`data` 恰为空对象
3. **定点字段** —— 来自 `expect.check`，按点分路径取值比较（如 `data.user.username`）

环境与依赖：

- 被测地址 `base_url` 默认 `http://localhost:8766`，可用环境变量 `TEST_BASE_URL` 覆盖（`tests/conftest.py:16-22`）
- 凭据为开发环境种子账号 `admin` / `admin123`，直接写在 YAML 里（`tests/api/conftest.py`）
- `{{unique_username}}` 占位符由 `unique_username` fixture 生成 `test_<8位随机>`，保证注册类用例可重复执行、不撞已有账号
- 令牌类用例的输入来自 `{{admin_access_token}}` / `{{admin_refresh_token}}`，由 `admin_login` fixture **现场登录**签发 —— JWT 默认 1 小时过期，把令牌写死进 YAML 第二天就会红
- 用例可选字段：`auth`（`none` / `required`，决定用无令牌 session 还是带 Authorization 的 session，与 `test_devices.py` 同一约定）· `setup` · `concurrent`（后两者见第七节）
- 单请求用例的 GET 不带请求体（loader 只对非 GET 请求发送 JSON body）

## 二、登录接口（`tests/api/case/login.yaml`，13 条）

#### TC-LOGIN-001 正常登录
- **业务功能**：账号密码登录，签发访问 / 刷新令牌对
- **测试目的**：验证合法凭据能换取令牌对与用户信息，即登录主路径可用、响应结构符合契约
- **测试方法与步骤**：向 `POST /api/auth/login/` 发送 `{username: admin, password: admin123}`
- **断言逻辑**：
  - HTTP `200`
  - 响应满足 `auth_success`（`status=true`、两枚令牌 ≥10 字符、`token_type=bearer`、`user` 仅含 `id`/`username`）
  - 定点：`data.user.username == "admin"`

#### TC-LOGIN-003 用户名和密码均为空
- **业务功能**：登录必填校验（两者同时缺失）
- **测试目的**：验证两个必填项都为空时被后端统一拦截，返回合并提示而不是逐条报错
- **测试方法与步骤**：向 `POST /api/auth/login/` 发送 `{username: "", password: ""}`
- **断言逻辑**：
  - HTTP `400`；响应满足 `error` 结构
  - 定点：`message == "请输入用户名和密码"`

#### TC-LOGIN-004 用户名为空
- **业务功能**：登录必填校验（仅用户名缺失）
- **测试目的**：验证用户名单独缺失时提示准确到字段

- **断言逻辑**：

#### TC-LOGIN-005 密码为空

#### TC-LOGIN-006 用户名为纯空白

#### TC-LOGIN-007 用户名超过150字符

- **测试目的**：验证超长用户名被拦截（防止异常长度进入鉴权逻辑）

#### TC-LOGIN-013 密码错误
- **业务功能**：登录失败 —— 凭据错误
- **测试目的**：验证密码错误返回统一文案，**不泄露账号是否存在**（防用户名枚举）

#### TC-LOGIN-014 用户不存在
- **业务功能**：登录失败 —— 账号不存在
- **测试目的**：验证不存在的账号与「密码错误」返回完全相同的状态码与文案，不可区分
- **测试方法与步骤**：发送 `{username: "no_such_user", password: "pass123"}`
- **断言逻辑**：
  - HTTP `401`；响应满足 `error` 结构
  - 定点：`message == "用户名或密码错误"`（与 TC-LOGIN-013 一致）

#### TC-LOGIN-012 JSON 格式非法
- **业务功能**：请求体格式容错
- **测试目的**：验证请求体不是合法 JSON 时返回 400 业务提示，而不是 500 崩溃或抛框架堆栈
- **测试方法与步骤**：向 `POST /api/auth/login/` 发送原始文本 `not a json`（不走 JSON 序列化）
- **断言逻辑**：
  - HTTP `400`；响应满足 `error` 结构
  - 定点：`message == "请求格式错误"`

#### TC-LOGIN-015 账号前后带空格
- **业务功能**：登录账号的空白边界（账号不做 trim）
- **测试目的**：验证带首尾空格的账号按**原样**核对，不会匹配到 `admin` —— 守护 `LoginSerializer.username` 的 `trim_whitespace=False`
- **测试方法与步骤**：发送 `{username: "  admin  ", password: "admin123"}`
- **断言逻辑**：
  - HTTP `401`；响应满足 `error` 结构
  - 定点：`message == "用户名或密码错误"`

#### TC-LOGIN-016 密码前后带空格
- **业务功能**：登录密码的空白边界（密码被 trim）
- **测试目的**：验证密码首尾空格被去掉后仍能登录成功 —— 登录侧走 DRF CharField 默认 `trim_whitespace=True`，与注册侧显式 `strip()` 口径一致
- **测试方法与步骤**：发送 `{username: "admin", password: "  admin123  "}`
- **断言逻辑**：
  - HTTP `200`；响应满足 `auth_success`
  - 定点：`data.user.username == "admin"`
  - 备注：PRD 原设计写的是「401 / 密码不 trim」，与实现相反；已与需求方确认按**实测行为**记录，PRD 行同步修正

#### TC-LOGIN-017 请求体是 JSON 数组
- **业务功能**：请求体形态兜底（非对象）
- **测试目的**：验证请求体不是 JSON 对象时返回 400 而不是 500；文案由框架生成，不做逐字断言
- **测试方法与步骤**：以原始文本 `[1, 2]` 作为请求体提交（不走对象序列化）
- **断言逻辑**：
  - HTTP `400`；响应满足 `error` 结构（`message` 非空即可）

#### TC-LOGIN-018 公开端点不带 Authorization
- **业务功能**：公开端点的鉴权白名单
- **测试目的**：验证登录端点在**不带** `Authorization` 头时也可正常签发令牌（网关公开路径白名单生效，公开端点确实不要求令牌）
- **测试方法与步骤**：不带 `Authorization` 头发送 `{username: "admin", password: "admin123"}`
- **断言逻辑**：
  - HTTP `200`；响应满足 `auth_success`
  - 定点：`data.user.username == "admin"`

## 四、刷新接口（`tests/api/case/refresh.yaml`，5 条）

#### TC-REFRESH-001 正常续期
- **业务功能**：用刷新令牌换取新的访问令牌（会话续期）
- **测试目的**：验证有效刷新令牌能续期成功，且只返回该返回的字段（`access_token` + `token_type`）
- **测试方法与步骤**：取现场登录签发的刷新令牌，向 `POST /api/auth/refresh/` 发送 `{refresh_token: <admin 的 refresh>}`
- **断言逻辑**：
  - HTTP `200`；响应满足 `refresh_success`（`status=true`、`data.access_token` ≥10 字符、`data.token_type=bearer`、`data` 无多余字段）
  - 定点：`data.token_type == "bearer"`

#### TC-REFRESH-002 用访问令牌冒充刷新令牌
- **业务功能**：令牌类型校验（access 不能当 refresh 用）
- **测试目的**：验证类型不匹配被拒，且文案明确指向类型错误，而不是笼统的「无效」
- **测试方法与步骤**：把现场登录签发的 **access** 当作 `refresh_token` 提交给 `POST /api/auth/refresh/`
- **断言逻辑**：
  - HTTP `401`；响应满足 `error` 结构
  - 定点：`message == "令牌类型错误，需要刷新令牌"`

#### TC-REFRESH-003 刷新令牌是乱码
- **业务功能**：刷新令牌的签名 / 格式校验
- **测试目的**：验证非法令牌被拒，且文案与「类型错误」区分开（便于定位是伪造还是用错了令牌）
- **测试方法与步骤**：提交 `{refresh_token: "garbage.token.value"}`
- **断言逻辑**：
  - HTTP `401`；响应满足 `error` 结构
  - 定点：`message == "刷新令牌无效或已过期"`

#### TC-REFRESH-004 登出后再刷新
- **业务功能**：会话级吊销 —— 登出后刷新令牌立即失效

  - 定点：`message == "刷新令牌无效或已过期"`

#### TC-REFRESH-005 缺 refresh_token 字段
- **业务功能**：续期入参缺失时的兜底
- **测试目的**：验证空令牌走同一条拒绝路径，不出现 500

## 七、多请求用例的执行方式

39 条里有 5 条不是「一次请求一条用例」，但期望值同样写在 YAML 里，只有**步骤**由专门驱动完成：

| 标记 | 用例 | 驱动 | 执行方式 |
|------|------|------|----------|
| `setup: logout` | TC-LOGOUT-002 · TC-LOGOUT-003 · TC-REFRESH-004 · TC-ME-003 | `tests/api/test_auth_session_flow.py` | 现场登录 → 先调一次 `POST /api/auth/logout/` 吊销该会话 → 再用**同一份凭证**发用例里的请求并断言 |
| `concurrent: 2` | TC-REG-023 | `tests/api/test_auth_register_concurrency.py` | 两个线程并发提交同一用户名的注册请求 → 断言恰好一个 `200`、一个 `409`「用户名已存在」 |

- 为什么这么做：`tests/api/loader.py` 是单请求模型；为 5 条用例给它加一套通用步骤机不值当，而把期望值搬进 Python 又会与其它 34 条两处维护。于是**期望值留 YAML、步骤留驱动**。
- `test_login_page.py` 与 `test_auth_tokens.py` 会跳过带 `setup` / `concurrent` 标记的用例，不会重复执行或误判。
- 这两类用例依赖会话状态：登出只影响该用例现场登录的那个会话（`admin_login` 是 function 级 fixture），开发者浏览器里的登录态不受影响。
