# 认证模块商业标准评估

> 评估对象：[认证业务全景-20261026.md](认证业务全景-20261026.md) 描述的认证能力（注册 / 登录 / 续期 / 登出 / 当前用户）
> 评估日期：2026-10-26 · 基线：`Kahoku`
> 对标口径：OWASP ASVS 4.0 Level 2（商业 Web 应用基线）、NIST SP 800-63B（身份鉴别）、等保 2.0 三级（国内政企常见门槛）的公开要求
> 性质说明：本文是**产品/工程视角的差距评估**，不是渗透测试，也不构成合规认证结论。

---

## 0. 结论

**认证的「内核」是合格的，但它只完成了认证本身，没有完成商业产品需要的「账号运营 + 抗滥用 + 审计合规」三件事。按当前 PRD 的「内部单团队工具」定位可以上线；按「对外销售的商业产品」或「政企采购」定位，不达标。**

31 项商业能力中：**8 项达标、4 项部分达标、19 项缺失**。

| 使用场景 | 结论 | 说明 |
|----------|------|------|
| 内部单团队、内网使用（当前 PRD 定位） | ✅ **可用**，补 P0 六项即可生产 | 核心是登录限流、改密/重置、登录审计；另含传输加固、CSP、密码长度上限。约 1–2 周（不含改 Cookie） |
| 对外销售的 SaaS | ❌ **不达标** | 缺自助改密/找回、MFA、审计、会话管理、注册治理、隐私合规 |
| 政企采购 / 等保三级 | ❌ **不达标** | 缺双因素、登录失败处理、审计留存、密码复杂度策略、会话超时 |

### 最危险的三个组合风险

1. **开放注册 + 慢哈希 + 零限流 = CPU 打满**。每次登录/注册要跑 120 万次 PBKDF2（本机实测 **0.75 秒**），而接口没有任何限流；几十个并发就能拖垮服务。
2. **令牌存在 localStorage + 没有 CSP = 一次 XSS 接管 7 天**。refresh 有效期 7 天且不轮换，脚本读走即可长期冒用。
3. **禁用账号 / 管理员重置密码不会让已登录令牌失效**。事件响应时「改密踢人」这条最常用手段目前不成立，攻击者最多还能用 7 天。

## 1. 评估方法

从五个面看，而不是只看「能不能登录」：

| 面 | 要看什么 |
|----|----------|
| 功能完整 | 账号从注册到注销的全生命周期是否闭环 |
| 抗滥用 | 爆破、撞库、批量注册、资源消耗是否有刹车 |
| 会话安全 | 令牌怎么发、怎么存、怎么续、怎么撤、多久失效 |
| 可运维 | 出事后能否定位、能否踢人、能否轮换密钥 |
| 合规 | 隐私告知、数据删除、审计留存能否应对客户问卷 |

评分只分三档：✅ 达标（可直接商用）、⚠️ 部分（能用但有条件）、❌ 缺失（商业交付会被卡）。

## 2. 评分卡（31 项）

### A. 凭证安全（5 项）

| # | 能力 | 状态 | 现状与证据 | 商业影响 |
|---|------|:----:|------------|----------|
| A1 | 密码哈希强度 | ✅ | Django 默认 PBKDF2-SHA256，120 万次迭代（实测 0.75s/次），未自研加密 | 高于 OWASP 公开建议量级（60 万次） |
| A2 | 密码复杂度策略 | ❌ | 仅校验「≥6 位」（`serializers.py:68`），无大小写/数字/符号要求，无弱口令库 | 客户安全问卷第一题就卡 |
| A3 | 密码不回显、不落日志 | ✅ | 响应不含密码；前端不存密码；后端不记录请求体 | 合格 |
| A4 | 传输强制加密 | ⚠️ | 代码默认 `SECURE_SSL_REDIRECT=False`、`HSTS=0`，是否 HTTPS 取决于部署 | 若部署疏漏，密码与令牌明文可读 |
| A5 | 弱口令 / 泄露密码检测 | ❌ | 无 HaveIBeenPwned 类校验、无密码历史 | 撞库成功率显著偏高 |

### B. 账号生命周期（5 项）

| # | 能力 | 状态 | 现状与证据 | 商业影响 |
|---|------|:----:|------------|----------|
| B1 | 自助注册 | ✅ | `/api/auth/register/` 可用，注册即登录 | 有，但完全开放 |
| B2 | 注册治理 | ❌ | 无邀请码、无审批、无域名白名单、无频率限制 | 可被批量刷号，消耗算力与数据 |
| B3 | 邮箱验证 | ❌ | 邮箱只校验含 `@`，不唯一、不发验证信 | 无法证明邮箱归属，也堵死后续找回 |
| B4 | 自助修改密码 | ❌ | 5 个端点中无改密 | 商业产品的必备项 |
| B5 | 找回密码 | ⚠️ | 无自助找回；只能管理员进 Django Admin 手改 | 用户忘密码只能找运维，规模化后成本高 |

### C. 抗滥用（4 项）

| # | 能力 | 状态 | 现状与证据 | 商业影响 |
|---|------|:----:|------------|----------|
| C1 | 登录限流 / 失败锁定 | ❌ | `REST_FRAMEWORK` 无 throttle 配置，后端无失败计数 | 6 位密码可被在线爆破 |
| C2 | 注册限流 | ❌ | 同上，注册接口公开且无频控 | 批量注册 + 慢哈希 = 资源耗尽 |
| C3 | 人机校验 / 风控 | ❌ | 无 CAPTCHA、无设备指纹、无异常登录检测 | 自动化撞库无门槛 |
| C4 | 单请求成本上限 | ❌ | 密码字段无 `max_length`（`serializers.py:48`），请求体上限 16MB | 超长密码可放大 PBKDF2 计算 |

### D. 会话与令牌（6 项）

| # | 能力 | 状态 | 现状与证据 | 商业影响 |
|---|------|:----:|------------|----------|
| D1 | 令牌校验完整性 | ✅ | HS256 固定算法、校验 `type`/`exp`/`sub`，防算法混淆 | 设计正确 |
| D2 | 会话级吊销 | ✅ | 登出按 `sid` 同时作废 access + refresh（Redis，TTL 7d） | 单次登录可精确撤销 |
| D3 | 会话列表 / 全部登出 | ❌ | 无会话注册表，无「退出所有设备」 | 用户丢失设备后无法自救 |
| D4 | 空闲超时 | ⚠️ | 只有固定有效期（access 1h / refresh 7d），无「30 分钟无操作失效」 | 共用电脑/被盗设备窗口过大 |
| D5 | 令牌存储安全 | ❌ | access/refresh 均存 `localStorage`，代码内无 CSP | XSS 直接窃取 7 天凭证 |
| D6 | refresh 轮换 / 重放检测 | ❌ | 续期只发新 access，refresh 不变 | 被窃 refresh 可复用至过期 |

### E. 权限、审计与应急（6 项）

| # | 能力 | 状态 | 现状与证据 | 商业影响 |
|---|------|:----:|------------|----------|
| E1 | 角色模型 | ⚠️ | 只有 `is_superuser` 与普通用户两档；无管理员/操作员/只读等角色 | 团队协作只能「全给或全不给」 |
| E2 | MFA / 双因素 | ❌ | 无 TOTP、短信、WebAuthn | 超管账号一旦失守，平台全失守；等保三级通常要求 |
| E3 | 禁用/删除即时失效 | ❌ | 令牌校验不检查 `is_active`；禁用后旧令牌可用到 refresh 过期（≤7d） | 离职/封号无法立即止损 |
| E4 | 登录审计 | ❌ | 登录成败无日志；`auth_user.last_login` 始终为 NULL | 入侵无法追溯，客户审计问卷无法回答 |
| E5 | 敏感操作审计 | ❌ | 改密（后台）、禁用、权限变更均无审计记录 | 无法做责任认定 |
| E6 | 防账号枚举 | ✅ | 登录统一返回「用户名或密码错误」 | 合格（注册 409 会暴露用户名，可接受） |

### F. 工程与合规（5 项）

| # | 能力 | 状态 | 现状与证据 | 商业影响 |
|---|------|:----:|------------|----------|
| F1 | 前后端校验一致 | ✅ | 文案/阈值有专门的契约对拍测试 | 改一侧另一侧会红，防漂移 |
| F2 | 自动化测试覆盖 | ✅ | 前端 11 个登录单测 + 后端接口/并发/会话用例 + 4 个契约测试 | 回归有底 |
| F3 | 隐私政策 / 用户协议 / 同意 | ❌ | 登录页无任何协议与勾选（已确认无「隐私/条款/同意」文案） | 国内商业化（PIPL）与外销（GDPR）都会被卡 |
| F4 | 数据删除 / 留存策略 | ❌ | 无自助注销、无账号数据导出/删除流程 | 客户尽调常问 |
| F5 | 密钥轮换 / 依赖安全扫描 | ❌ | 单一 `SECRET_KEY` 签 JWT，无 `kid`；CI 有硬编码凭据扫描，但**无依赖漏洞扫描** | 密钥泄露只能全量重签；供应链风险无门禁 |

## 3. 差距清单与改造优先级

### P0 — 商业上线前必须做（约 1–2 周）

| 项 | 做什么 | 验收 |
|----|--------|------|
| 1 | 登录限流 + 失败锁定（IP + 账号双维度，如 5 次/15 分钟） | 脚本爆破 20 次被阻断 |
| 2 | 注册限流 + 密码 `max_length`（如 128） | 批量注册被限；16MB 密码被 400 |
| 3 | 自助改密 + 管理员重置，**重置后全端下线** | 改密后旧 access/refresh 立即 401 |
| 4 | 登录/登出/改密审计（账号、IP、UA、结果） | 能查「谁在何时从哪登录」 |
| 5 | 关掉 `localStorage` 风险：至少加 CSP；有条件的改 HttpOnly Cookie | 安全头扫描通过 |
| 6 | 部署强制 HTTPS + HSTS | HTTP 自动跳转，HSTS 生效 |

> 第 3 项的关键不是改密接口本身，而是「改密后让旧令牌失效」——需要在令牌里加用户级版本号（或 `password_changed_at` 与 `iat` 比较），这是当前架构没有的能力。

### P1 — 对外销售前应做（约 4–6 周）

| 项 | 说明 |
|----|------|
| 7 | 密码策略升级：≥8（建议 12）+ 弱口令库 + 禁止用户名/邮箱做密码 |
| 8 | 邮箱验证 + 注册治理（邀请码/审批/域名白名单，按客户类型选） |
| 9 | 会话管理：列出登录设备、单条撤销、全部登出、空闲超时 |
| 10 | refresh 轮换 + 重放检测 |
| 11 | RBAC：管理员 / 操作员 / 只读，替代「超管或普通人」 |
| 12 | 超管 MFA（TOTP 起步） |
| 13 | 隐私政策、用户协议、数据删除与留存说明 |
| 14 | 密钥轮换（`kid`）与 CI 依赖漏洞扫描 |

### P2 — 企业客户/规模化再做

- SSO（OIDC / SAML）与企业 IdP 对接；
- 多租户隔离（当前 PRD 明确不在本期）；
- 风险引擎（异地登录、设备指纹、异常行为）。

## 4. 商业交付路线（建议）

| 阶段 | 目标 | 内容 | 粗估工作量 |
|------|------|------|-----------|
| 阶段一 | 敢在内网生产用 | P0 六项 | 1–2 周（1 人） |
| 阶段二 | 敢卖给第一个外部客户 | P0 + P1（可先不做 SSO/多租户） | 再 4–6 周 |
| 阶段三 | 敢投政企标 | MFA、审计留存、等保整改、渗透测试报告 | 2–3 个月 + 第三方测评 |

**一个必须算的账：自研 vs 接 IdP。**
P1 里的「MFA + 找回 + 会话管理 + 审计」如果全自研，接近 2 个月；再把 P2 的 SSO 算上会更久。直接用 Keycloak / Authing / 云厂商 CIAM，通常 2–4 周能接完，且自带合规能力。若产品目标是「卖平台」而不是「卖认证」，建议评估接 IdP，把认证当基础设施而不是自研功能。

## 5. 已经做对、不要推翻的部分

1. **密码存储**：PBKDF2-SHA256 120 万次迭代，高于 OWASP 公开建议的 60 万次量级；不要为了「快」降迭代。
2. **令牌设计**：`sub`/`sid`/`jti`/`type`/`exp` 齐全，算法固定 HS256，防算法混淆；登出按会话而非单令牌。
3. **失效策略**：登出「Redis 不可用则拒绝」写进了规格（fail-closed）；令牌校验遇到 Redis 不可用时放行，代码注释里说明了取舍，不是遗漏。
4. **错误处理**：登录统一文案防枚举；响应信封统一；前后端文案有对拍测试。
5. **CSRF 姿态**：Bearer 头 + 显式豁免，Admin 仍受 CSRF 保护，方向正确。
6. **测试资产**：认证链路的单测、接口、并发、契约四层都有，改造时有安全网。
7. **CI 已有硬编码凭据扫描**（`security-scan` job，覆盖后端 Python 与前端源码）：方向对，但它只做模式匹配，后续补依赖漏洞扫描即可。

## 6. 不建议做的（避免过度设计）

- **不要强制 90 天改密**：NIST 800-63B 明确反对定期强制轮换，应改为「泄露/事件驱动」。**例外**：若目标市场是政企/等保，等保要求「定期更换」，此时需按客户类型二选一，并把冲突写进方案。
- **不要自研加密或自研 MFA**：用成熟库/IdP。
- **不要现在做多租户**：PRD 明确非本期，且会牵动全部数据模型。
- **不要为了「商业标准」把 JWT 换回 Session**：当前令牌设计没问题，问题在存储与治理，不在 JWT 本身。

## 7. 待决策

1. **产品定位确认**：这套认证是「内部工具」还是「要卖的产品」？这决定只做 P0，还是 P0+P1。
2. **自研还是接 IdP**：若目标是商业销售，是否接受用 Keycloak/Authing 换掉自研的 P1 部分？
3. **令牌存储路线**：短期加 CSP 接受 localStorage，还是直接改 HttpOnly Cookie（改动大但一步到位）？
4. **「改密/禁用即全端下线」是否作为硬要求**？若接受，需要给令牌加用户级版本号，属于架构级小改。
5. **合规范围**：只做国内（PIPL）还是也要面向海外（GDPR）？决定隐私文案与数据删除流程的深度。
