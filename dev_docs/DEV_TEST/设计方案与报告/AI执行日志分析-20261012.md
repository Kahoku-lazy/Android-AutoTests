## 四、平台侧缺陷（按影响排序）

### 4.1 [P0] 日志查询时间戳只接受带毫秒

`engines/agents/tools/tool_serial.py:37`

```python
LOG_AT_FORMATS = ("%Y-%m-%d %H:%M:%S.%f", "%H:%M:%S.%f")
```

两个格式都要求小数部分。executor 的 handover 里 `action_time` 112 次全部带毫秒，但 verifier 有 8 次只抄到秒（如 `2026-10-12 16:58:44`），工具直接抛 `时间点无法解析`，8 次调用全部作废（占全部日志查询的 8.7%），且每次都要多花一个模型轮次重发。

### 4.2 [P0] 「点 ON｜OFF 的 ON 半边」用例缺前置条件

- 现象：设备已开 → 点 ON 无状态变化 → 无 `switch_on` → 验收 FAIL → 重试 → 仍 FAIL。
- 影响：8 次尝试 6 次不通过；2 次整轮运行以该步失败收尾；这 4 个会话里该步骤合计花掉 **$1.218（占总成本 12.0%）**。
- 这是**用例设计问题**，模型行为完全正确（有截图 + 日志双证据、判 FAIL 并给出下一步建议）。

### 4.3 [P1] 日志空窗把整轮验收作废

`engines/agents/tools/tool_serial.py:259-260`：5 秒窗口内 0 行日志 → `raise ValueError(LOG_EMPTY)`，工作流把这一轮记成驳回、消耗一次重试。

已核对设备原始日志 `logs/H6810_7005.log`：**2026-10-12 17:17:00.774 → 17:17:18.713 无任何行**（设备侧 18.9 秒静默）。17:15:09 会话第 1 次「亮度设置大于70%」恰好落在这个空窗里，executor 已经做完动作（14 次调用、$0.197）却被整体作废重跑。

### 4.6 [P2] 其余观察

## 五、需要决策的点

> 按仓库规范，以下均需走 `OpenSpec` 流程（`/opsx:propose` → `/opsx:apply`），本次不做任何代码改动。

### 决策 1：是否放宽 `check_device_log` 的 `at` 解析（接受无毫秒）？

- **建议：做。** 改 `LOG_AT_FORMATS` 增加 `%Y-%m-%d %H:%M:%S` 与 `%H:%M:%S` 两个格式即可，收益是可量化的 8/92 = 8.7% 无效调用归零，且不改判定口径（缺毫秒等价于 `.000`）。
- 代价：一个函数、两条格式串，回归面小；需要同步 `openspec/specs/device-log-read-tool/spec.md` 的时间点契约。
- 若不做：模型侧要靠提示词反复强调「时间戳必须带毫秒」，属于用提示词兜住工具契约，历史上已经证明会漏。

### 决策 2：是否修 SOP 用例「点 ON｜OFF 的 ON 半边」的前置条件？

- **建议：做，且优先级高于决策 1。** 这是本次**唯一造成整轮运行失败**的原因（2/11 次运行、6/8 次尝试失败）。
- 两个可选口径：
  - a) 在 ON 之前插入「先点 OFF 半边，确认关闭态」一步，保证有状态变化；
  - b) 该步断言改成 UI 断言（ON 半边呈选中态），日志断言只挂在真正产生状态变化的那一次点击上。
- 推荐 a)：用例意图本来就是「验证开灯指令下发」，保留日志断言才有验证价值；b) 会把这个步骤弱化成纯 UI 断言。
- 若不做：每次运行的成败取决于上一轮遗留的设备状态，失败率会随运行次数波动，无法作为稳定回归用例。

### 决策 3：日志空窗是否降级处理？

- **建议：做。** 现在 5 秒窗内 0 行 → 抛异常 → 整轮作废并消耗一次重试。可改为返回 `FAIL` + 明确说明「窗口内无日志（设备静默）」，让 verifier 有机会用「延长窗口 / 换时间点」自救，而不是白烧一轮。
- 需要权衡：`openspec/specs/device-log-read-tool/spec.md:216` 现有口径是「工具中断本轮并说明日志为空，MUST NOT 返回成 FAIL」——**改动会推翻既有 spec**，必须在提案里显式声明并给出取舍理由（否则属于偷偷改口径）。
- 若不做：设备侧静默（本次实测 18.9 s）会持续造成随机整轮失败，观测到的代价是单轮 $0.197 + 一次重试。

### 决策 4：是否为 SOP 运行做上下文裁剪（截图/历史摘要）？

- **建议：先立小范围提案，不要一次做全。** 现在 executor 单次 input 均值 19,837、峰值 44,056，输入输出比 65:1，收尾的简单动作也在背全量历史。
- 最小可行口径：只保留「最近 N 步的截图 + 更早步骤的文字结论」，把历史截图换成文本摘要。
- 风险：验收依赖截图证据链，裁剪可能让 verifier 拿不到关键截图 —— 必须先明确「哪些是证据、必须留」。
- 收益估算：若把峰值 input 从 ~44K 压到 ~20K，按 856 次调用、缓存命中 75.5% 的现状，预计能省掉总成本的 20–30%（$2–3/11 次运行）。

### 决策 5：是否为重复文案的步骤加变体标识？

- **建议：做，成本极低。** 在步骤文案里加变体后缀（如「点分段控件『经典』（右半）」已经这样做了，可对齐），或在下发记录里带步骤序号。
- 理由：现在审计一次运行要人工比对时间轴才能判断「这两条同名步骤是设计重复还是重试」，日志可读性差；本次分析就为此多花了排查步骤。

### 决策 6：验收提示词是否明确「UI 断言不要查日志」？

- **建议：做（并入决策 2 的提案或独立小改）。** 本次 5 次探针式误查（`color_mode_start` ×2、`abstract_mode_start` ×3）全部 FAIL 但都不影响判定，属于纯噪声：既浪费调用，又让「FAIL」在日志里失去信号意义。
