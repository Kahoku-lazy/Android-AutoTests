## 一、结论先行

1. **任务层 5 条全部未通过**：1 条被服务重启打断（`interrupted`，21 分钟），4 条跑完整套后 `failed`；但**用例层 48 例次里 40 次通过（83.3%）**，失败高度集中，主因不是模型能力。
2. **「涂鸦」用例是确定性阻塞：4/4 轮、8/8 次尝试全败在同一处**。设备端每次都先收到涂鸦负载（`gra2d data size:21` → `Mode set: 8` → `gra2d_mode_start`），紧接着打印 **`png size error or front`**，然后**从不打印任何涂鸦设置成功事件**。这更像产品/固件缺陷（App 提示"应用成功"、设备端拒绝负载），而不是概率性抖动。
3. **「灵动卡片页」1/4 通过，且三次败在三个不同步骤**（141 亮度、142 应用、143 删除）：其中两次是"设备日志断言"不可达，一次是页面导航丢失。属于智能体长流程稳定性问题。
4. **日志关键词表与 H6810 固件不匹配，导致部分断言天然不可达**：67 个关键词中，H6810 近 4 天日志只出现过 12 个；固件实际打的是 `gra2d_mode_start` / `diy2d_mode_start`，表里是 `gra_mode_start` / `diy_mode_start`（`KeywordIndex` 为精确子串匹配），且 `graffiti_configs_set_success`、`diy_configs_set_success` 出现 **0 次**。
5. **平台行为本身正确**：重启打断记为「已中断」而非失败；141–143 在 22:32–22:37 提交后按同设备串行排队，在前一任务结束时依次启动（00:18 / 01:56）；失败用例不终止整批，符合既有口径。
6. **代价**：5 条约 **$60.80**、机器时长约 **7.4 小时**；已知必败的「涂鸦」每轮仍消耗约 15–25 分钟 / $1–2，四轮重复。

## 四、失败根因

### 4.1 涂鸦 · 第 6 步「应用涂鸦模式」——确定性失败

| 轮次 | 点击时间（action_time） | 设备端日志结果 |
|---|---|---|
| 140 | 19:16:45 / 19:17:18 | `png size error or front`；无成功事件 |
| 141 | 23:46:12 / 23:48:33 | 同上 |
| 142 | 01:27 / 01:28 / 01:29 | 同上（4 条 png 报错） |
| 143 | 03:20:53 / 03:21:23 | 同上 |

串口原文（143，`logs/serial_logs/H6810_7005.log`）：

```
03:20:53,754  gra2d data size:21
03:20:53,990  [base mode][I]: Mode set: 8
03:20:54,111  [base mode][I]: gra2d_mode_start
03:20:54,111  png size error or front
```

- 设备确实收到并切入了 2D 涂鸦模式，但随后明确报 `png size error or front`，**没有任何"涂鸦设置成功"事件**。
- 验收集要求的关键词 `graffiti_configs_set_success`，在 `H6810_7005.log` + `.log.1`（约 12 万行、10-20 至 10-23）中出现 **0 次**。
- 该关键词在 `backend/config/device_log_keywords.json:133` 的注释是「高阶模式下-颜色设置成功」，即**高阶（3D）模式**；而 H6810 是 20×12 点阵的 2D 涂鸦（固件日志 `graffiti_2d`、`gra2d_*`）。**关键字与设备能力不匹配。**
- 副证：执行者自称页面出现"应用成功"Toast，但验收截图看不到；若 Toast 确实存在，则属于 **UI 报成功、设备拒绝** 的失败路径未校验。
- 另：10-23 10:22:31 在无任务运行的情况下也出现过一次同样的 `png size error or front`，可用于人工复现对照。

**判定**：产品/固件侧问题（PNG 规格或 2D 涂鸦下发）与用例断言问题并存；无论哪一方，当前用例都**不可能通过**。

### 4.2 灵动卡片页 —— 3 次失败、3 个不同步骤

### 4.3 自动播放 · 第 4 步「删除灯效」（仅 141）

## 五、系统性缺陷：日志关键词表与 H6810 固件不一致

1. **精确子串匹配**：`engines/device/logbus.py` 的 `KeywordIndex.match` 用 `text.find(keyword)`，不模糊、不按型号分流。
2. **覆盖率低**：`device_log_keywords.json` 共 **67** 个关键词；H6810 近 4 天日志中出现过的只有 **12** 个（`switch_on/off`、`color/music/scene/timer/awaken/sleep_configs_set_success`、`lumi_set_success`、`*_mode_start` 等），其余 55 个 0 次。
3. **2D 模式命名错位**：

| 表里的关键词 | 固件实际打印 | 命中 |
|---|---|---|
| `gra_mode_start` | `[base mode][I]: gra2d_mode_start` | 0 |
| `diy_mode_start` | `[base mode][I]: diy2d_mode_start` | 0 |
| `graffiti_configs_set_success` | 无（仅 `png size error`） | 0 |
| `diy_configs_set_success` | 无 | 0 |

4. **验收侧看不到失败现场**：`check_device_log` 判负时只回「时间段内未抓到关键字」，丢弃 5 秒窗口内的其它行（`tool_serial.py:188`），所以验收模型无法发现 `png size error or front` 这类决定性证据，只能归因成"没下发"。

## 七、建议与待决策

### 建议

1. **涂鸦先定性**：人工复现一次「涂鸦 → 应用」，同时抓 App 日志与串口；确认 `png size error or front` 是 App 发送的 PNG 规格问题，还是固件缺陷。若是产品缺陷 → 提 Bug；若是断言问题 → 改用设备可实现的成功判据（如 `gra2d` 相关事件）。
2. **修正关键词表**：把 2D 模式条目改为固件实际输出（`gra2d_*` / `diy2d_*`），并按型号或固件版本拆表；对 55 个 0 命中词条逐条复核，避免"永远判不过"。
3. **让验收看得到现场**：`check_device_log` 判负时附带窗口内的原始行（或 ERROR 关键词行），至少回传末尾若干行，便于定位 `png size error` 这类问题。
4. **灵动拆短与复位**：11 步拆成 2–3 条用例；第 10 步前显式要求"回到灵动卡片页"并截图确认，或改为相对断言（删除后数量减一）。
5. **修 `by=sop` 兜底**：结构化输出缺失应在同一步重试，而不是直接判负。
6. **运行策略**：涂鸦修复前从夜间全量中摘除（或标记 skip），避免每轮 ~20 分钟 / ~$2 的必败消耗；同一套件不必连开 3 条任务。
