# 平台性能与安全风险分析

> 分析对象：Android-AutoTests（Django 6.0.6 + DRF + Daphne 单进程 + Vue 3 + AgentScope 2.0）
> 代码基线：`Kahoku` 主干 `369d102b`，并包含工作区未提交改动（`backend/apps/task_list/views.py`、`task_reports.py`、`backend/apps/report_generator/*` 等）。本文结论以当前工作区代码为准，不以已提交版本为准。
> 分析日期：2026-10-25
> 方法：静态代码审查 + 调用链/查询计数 + `python manage.py check --deploy`；未做压力测试、DAST、依赖 CVE 扫描，也未在生产数据上取数。
> 级别口径：**P0** = 默认配置且网络可达即可导致全量数据、控制权或验收结论失守；**P1** = 普通账号或内网可达即可造成实质损害；**P2** = 需要特定部署条件、较高权限或局部影响；**P3** = 加固项。性能级别按“当前单进程 + 轮询 + 多设备”场景下是否已可感知或随数据增长必然放大划分。

## 0. 结论先行

### 0.1 一句话结论

**平台在“单用户、可信本机”的前提下可以跑通业务；一旦按 README 的方式在局域网共享，安全边界并不成立；性能上它不是“模型慢”，而是每个请求、每个设备动作、每次验收都在重复支付固定开销。**

最危险的组合是四个默认事实的叠加：

1. 服务默认绑定 `0.0.0.0`，且当前 `.env` 为 `DEBUG=True`；
2. 注册接口公开，注册后即拥有几乎全部业务权限；
3. 任务、报告、截图、页面流没有归属，任何账号可读、可删；
4. 串口日志端口 `0.0.0.0:7005` 无任何认证，而它正是验收 PASS 的证据来源。

### 0.2 总体判断

| 维度 | 结论 | 关键依据 |
|---|---|---|
| 安全边界 | **不成立**（共享部署时） | 开放注册 + 无对象级授权 + 全局任务数据；见 SEC-02 |
| 验收可信度 | **可被网络侧伪造** | `:7005` 无认证，注入关键词即可让 `check_device_log` 返回 PASS；见 SEC-03 |
| 凭据与调试面 | **高暴露** | `DEBUG=True`、默认管理员口令、明文 HTTP、日志可下载；见 SEC-01/05 |
| 性能 | **单机小规模可用，扩容前必须改造** | 每请求新建线程/数据库连接、任务列表 N+1、设备动作多进程、验证器整文件读日志；见 PERF-01～09 |
| 可扩展性 | **只能单实例运行** | 启动恢复会误杀其它实例的 running 任务，取消/排空/当前设备指针均为进程内状态；见 SCALE-01 |
| 可运维性 | **一般** | 有统一启停、日志、门禁，但无指标、无队列、无分页、无缓存层 |

### 0.3 风险计数

| 类别 | P0 | P1 | P2 | P3 |
|---|---:|---:|---:|---:|
| 安全 | 3 | 4 | 3 | 8 |
| 性能/扩展性 | 0 | 10 | 7 | — |

> P0 均为“条件性 P0”：如果该实例只在本机、只由一个人使用，实际风险可降为 P2；但只要它能被第二个人访问（局域网、端口转发、共享开发机），就按 P0 处理。**这不是理论风险，默认启动方式即满足条件。**

### 0.4 如果只做六件事

| 顺序 | 动作 | 对应风险 | 预计工作量 |
|---|---|---|---|
| 1 | 关闭 `DEBUG`、默认绑定 `127.0.0.1`、改掉默认管理员口令、启用 TLS 或明确“仅本机” | SEC-01 | 0.5～1 天 |
| 2 | 关闭公开注册（或邀请/审批），并把 `clear/delete` 等破坏性操作收归超管 | SEC-02 | 0.5～1 天 |
| 3 | 串口日志端口改为回环或来源 IP 白名单，并加连接数上限 | SEC-03 | 0.5 天 |
| 4 | 报告下载只允许报告产物，原始运行日志仅超管可读 | SEC-05 | 0.5 天 |
| 5 | 任务列表 `prefetch_related` + `defer`，仪表盘一次解析 agents 并下传 | PERF-03/04 | 1～2 天 |
| 6 | 设备列表改为读缓存，设备动作复用会话、缓存屏幕尺寸 | PERF-05/07 | 3～5 天 |

### 0.5 适用前提

- 本文按“平台可能被第二个人访问”评估。若你确认它永远只在本机、只有你一个人用，SEC-01/02/03 的 P0 可下调，但 SEC-03 的“验收可伪造”仍是产品可信度问题。
- 本文不替代压测。所有查询数、耗时均为静态推导或框架行为推导，标注为“约/上限”的地方请在测试环境复核。

## 1. 评估范围与方法

### 1.1 代码基线

- 主干提交：`369d102b docs(openspec): 记录签名直链对 OpenAPI 前缀的影响`。
- 工作区有未提交改动，其中与本文直接相关的有：`backend/apps/task_list/views.py`、`backend/apps/task_list/task_reports.py`、`backend/apps/report_generator/views.py`、`backend/apps/report_generator/urls.py`。因此行号与行为以工作区为准。
- 未覆盖：`engines/agents/messaging/fold.py` 的逐事件格式化、`workflow/api_digest.py`、`serial_log/keywords.py`、`recent_apps.py` 等长尾模块；它们可能再增加 P2 项，但不改变主结论。

### 1.2 方法

1. **静态审查**：按请求入口 → 中间件 → View/ViewSet → `api.py` → ORM/引擎的调用链，逐段核对。
2. **查询计数**：按调用点手工累加，未运行 `CaptureQueriesContext`。仪表盘“约 40+N”、任务列表“约 101”是调用点数，不是实测值，误差约 ±2～3。
3. **框架行为核对**：对“每个请求新建线程/连接”一项，核对了本机安装的 Django 6.0.6 与 asgiref 3.11.1 源码，并用最小实验确认线程不复用；未在真实 MySQL 上观测 `SHOW PROCESSLIST` 增量。
4. **部署检查**：执行 `python manage.py check --deploy`，得到 5 条安全告警（见 SEC-01）。
5. **未做**：压力测试、并发测试、DAST、依赖漏洞扫描、生产数据取数。因此本文给出的是“风险清单 + 修复优先级”，不是“容量报告”。

### 1.3 威胁模型

| 角色 | 能力 | 最关心的问题 |
|---|---|---|
| 无账号的内网主机 | 能访问 `:8766`、`:5173`、`:7005` | 注册、登录爆破、日志注入、调试页 |
| 普通注册用户 | 有合法 JWT | 读别人的任务/截图/文档、删数据、用别人的模型 Key、刷任务 |
| 被盗令牌持有者 | 有 access/refresh | 在令牌过期/撤销前持续访问；禁用账号后仍可用 |
| 恶意用例/文档作者 | 能提交 YAML/Word/PDF | 让模型执行非预期动作、让验收误判 PASS |
| 粗心的运维 | 按 README 默认值部署 | `DEBUG`、默认口令、`0.0.0.0`、CORS 全开 |

### 1.4 性能模型

- 单 Daphne 进程，所有 HTTP 视图为同步函数；AI 任务在进程内 daemon 线程执行。
- 典型客户端行为：任务列表运行中每 5s 轮询；设备页每 30s 心跳；串口日志抽屉每 5s 刷新；任务详情页只在打开时拉一次报告（`useTaskDetail` 的 3s 轮询当前没有任何引用，见附录 C）。
- 典型任务：10～30 个步骤，每步 1 次截图 + 1～3 次动作 + 1 次日志检查；截图 1080p PNG 约 2～5MB。
- 典型数据：任务数百到数千；单任务事件数百到数万；串口当前文件上限 50MB。

### 1.5 局限

- 没有生产网络拓扑，无法确认是否在反向代理之后、是否对公网开放、是否改过默认口令。相关结论均标注“条件性”。
- 没有依赖漏洞扫描，不对具体 CVE 下结论；只评价“是否有 SCA/SAST 门禁”。
- 没有真实数据量，容量阈值是机制推导，不是压测结论。

## 3. 安全风险

### 3.1 P0

#### SEC-01 调试态、默认口令与明文暴露（条件性 P0）

**证据**

- `.env:7`：`DJANGO_DEBUG=True`。
- `backend/config/settings.py:29`：`DEBUG` 从环境变量读取；`:49-51` 在 DEBUG 下 `ALLOWED_HOSTS="*"`；`:134-146` 在 DEBUG 下 `CORS_ALLOW_ALL_ORIGINS=True` 且 `CORS_ALLOW_CREDENTIALS=True`；`:170-177` 在 DEBUG 下 Session/CSRF Cookie 非 Secure。
- `run.py:237-248` 以 `-b 0.0.0.0` 启动 Daphne；`run.py:353` 启动横幅打印 `Admin ... (admin/admin123)`。
- `README.md:117-123` 指导创建 `admin/admin123`。
- `frontend/vite.config.js:53-55` 开发服务器绑定 `0.0.0.0`。
- 实测 `python manage.py check --deploy` 输出 5 条告警：

```
(security.W004) You have not set a value for the SECURE_HSTS_SECONDS setting.
(security.W008) Your SECURE_SSL_REDIRECT setting is not set to True.
(security.W012) SESSION_COOKIE_SECURE is not set to True.
(security.W016) ... CSRF_COOKIE_SECURE is not set to True.
(security.W018) You should not have DEBUG set to True in deployment.
```

**攻击路径**

1. 同一局域网的主机访问 `http://<平台IP>:8766/admin/`，尝试 `admin/admin123`；若运维未改口令，直接进入超管。
2. 超管可调用 `POST /api/ai/agents/{id}/reveal-key/` 一次性揭示模型 Key（`backend/apps/ai_assistant/views_drf.py:145-152` → `api.py:107-125`），也可在 Admin 中修改设备/智能体。
3. 即使口令已改，`DEBUG` 错误页会泄露堆栈、局部配置、SQL 与文件路径；`CORS_ALLOW_ALL_ORIGINS + CORS_ALLOW_CREDENTIALS` 属于错误组合（库会回显 Origin 并允许凭证）。由于 API 用 `Authorization` 头、Session Cookie 默认 `SameSite=Lax`，该 CORS 组合当前的可利用性有限，但仍不应保留。
4. 明文 HTTP 下，JWT 与管理员会话可被同网段嗅探。

**影响**：平台控制权、模型 Key、设备控制权、全量数据。若实例只在本机，影响降为“本机信息泄露”。

**修复**

- 默认 `DJANGO_DEBUG=False`；开发需要时显式开启，且开发实例只绑 `127.0.0.1`。
- `DJANGO_ALLOWED_HOSTS` 显式列白名单；CORS 改为显式 Origin，且不要 `ALLOW_CREDENTIALS=True` + 通配。
- 首次部署生成随机管理员口令并强制修改；从 README 与 `run.py` 删除 `admin123` 字样。
- 共享部署必须 TLS 终止（反向代理或 Caddy/Nginx），并开启 `SECURE_SSL_REDIRECT`、HSTS、Secure Cookie。
- 把 `check --deploy` 纳入 CI，作为阻塞项；当前 CI 里它是 `|| true` 的非阻塞步骤。

**验收**：`check --deploy` 无 W004/W008/W012/W016/W018；`:8766` 默认不可从非本机访问；仓库中无 `admin123`；管理后台登录有失败次数限制。

#### SEC-02 开放注册 + 无对象级授权（P0）

**证据**

- `backend/apps/accounts/views.py:58-95`：`RegisterView` 为 `AllowAny`，注册成功直接签发 access/refresh。
- `backend/gateway/middleware.py:21-24`：`/api/auth/register` 在公开前缀内。
- 全局仅两档权限：`REST_FRAMEWORK` 默认 `IsAuthenticated`（`settings.py:309-323`）；只有智能体写操作/揭示 Key 与串口端口开关要求超管（`ai_assistant/views_drf.py:118-152`、`serial_log/views.py:50-51`）。
- 任务没有 owner 字段（`task_list/models.py:8-32`）；列表/删除/清空只按“平台唯一智能体”过滤（`task_list/views.py:101-194`）。
- 截图/报告的可见性通过 `filter_agents_for_user`，普通用户会命中“超管拥有的共享智能体”，因此能看到平台智能体的全部任务（`ai_assistant/api.py:36-49`、`task_list/api.py:492-531`、`task_reports.py:360-368`）。
- 页面流原型/目录/文档没有 owner（`workflow/models.py:6-104`），列表/删除/导入导出无用户过滤。
- 设备扫描/连接/删除/锁定对任意登录用户开放（`device_pool/views.py` 全部端点，仅全局 `IsAuthenticated`）。

**攻击路径（一个普通账号即可）**

1. `POST /api/auth/register/` 注册 `attacker/123456`，拿到令牌。
2. `GET /api/tasks/` 枚举最近 100 条任务；`GET /api/tasks/{id}/` 读取 YAML 正文、文档正文、设备序列号与结果；`GET /api/tasks/{id}/media/{mid}/` 读取他人截图。
3. `POST /api/tasks/clear/` 删除全平台任务及其截图目录；`POST /api/tasks/{id}/delete/` 删除单条；`DELETE /api/workflow/documents/{doc_id}/`（以及 prototypes/directories 的 `DELETE`）删除页面流。
4. `POST /api/devices/scan/` 连接/注册任意可达设备；`POST /api/devices/{serial}/disconnect/` 删除任意无线设备。
5. `POST /api/tasks/submit/` 用任意 `agent_id` 跑任务（见 SEC-04）。

**影响**：机密性（用例、文档、截图、设备串号、结果）、完整性（删除/覆盖）、成本（用他人模型 Key）、可用性（删设备、清任务）。即使“全员共享只读”是产品有意设计，**删除/清空/覆盖也不应开放给普通账号**。

**修复**

- 关闭公开注册，改为邀请码、管理员审批或 `is_staff` 才能创建账号；如需保留注册，至少加邮箱验证与注册频率限制。
- 引入最小角色：viewer（只读）、operator（提交/设备操作）、admin（配置/删除）。
- 给 `Task` 增加 `owner_id`（或 `created_by`），列表/详情/报告/截图/删除全部按 owner 或角色过滤；`clear/delete` 仅 admin。
- 给 `WorkflowPrototype` 增加 owner，导入时校验 doc_id 归属，`overwrite=1` 仅 admin。
- 所有破坏性操作写审计日志（谁、何时、对哪条数据）。

**验收**：非 owner 的 GET 返回 404/403；`clear/delete` 对普通用户 403；工作流导入不能覆盖他人 doc_id；注册在关闭状态下返回 403。

#### SEC-03 未认证日志通道可伪造验收 PASS（P0，产品可信度）

**证据**

- `backend/config/settings.py:273-274`：`DEVICE_LOG_TCP_HOST` 默认 `0.0.0.0`，`DEVICE_LOG_TCP_PORT` 默认 `7005`；`DEVICE_LOG_ENABLED` 默认开启，启动时 `serial_log` 会 `reconcile()` 拉起监听。
- `engines/uart_log/receiver.py:85-99`：直接 `bind/listen`，无认证、无来源白名单；`:109-119` 每个连接起一个线程，无连接数上限；`:147-151` 每行交给 `CaptureWriter.write`。
- `engines/uart_log/writer.py:16-18`：用 logging 写入 `logs/serial_logs/{SKU}_{port}.log`，每行带**服务器当前时间**。
- `engines/agents/tools/tool_serial.py:114-130`：每次检查读取整个文件、逐行正则；`:178-188` 在 `action_time` 之后 5 秒窗口内匹配关键词，命中即 `result=PASS`。
- `backend/apps/task_list/task_reports.py:390-420`：报告只从 `GenerateStructuredOutput` 的 `passed` 取判决，没有独立的第二证据源。

**攻击路径**

1. 任意 LAN 主机执行 `nc <平台IP> 7005`，持续发送包含目标关键词的行（如 `switch_off`）。
2. 服务端给每行打上真实当前时间；验收角色在动作后 5 秒窗口内查询时必然命中。
3. `check_device_log` 返回 PASS → verifier 输出 `passed=true` → 报告显示 PASS，而设备实际没执行。
4. 关键词可从任务详情（SEC-02）读取，也可按常见日志词猜。
5. 同一通道还可灌日志：每连接一个线程、每行一次磁盘 flush，配合 10MB×4 轮转可拖慢验收并占用磁盘。

**影响**：**验收结论不可信**，这是测试平台最核心的资产；其次是可用性（线程/磁盘耗尽）。

**修复**

- 监听地址默认改为 `127.0.0.1`；确需远程时使用来源 IP 白名单（串口盒固定 IP）。
- 增加连接数上限、每连接速率限制、单文件/总量磁盘配额。
- 采集端与平台之间加共享密钥/HMAC（每行带序列号与签名），或至少校验来源 IP 并记录 peer。
- 验收判定不要只看日志文本：要求截图/设备状态/日志三选二，或在报告中显式标记“日志来源不可信”。

**验收**：非白名单来源连接被拒绝；伪造关键词不能得到 PASS；1000 连接/持续灌日志时平台仍可响应。

### 3.2 P1

#### SEC-04 任务提交信任 `agent_id` 与 `device_serial`（P1）

**证据**

- `backend/apps/task_list/views.py:51-57`：`agent = agent_api.get_agent(data["agent_id"])`；`get_agent` 只按 id 查（`ai_assistant/api.py:143-148`），不校验 owner、可见性、`status=active`。
- `backend/apps/task_list/serializers.py:23-27,49-53`：`device_serial` 只要求非空字符串，不校验设备是否存在、是否可见、是否被锁。
- `views.py:96` → `api.py:237-267` → `task_runner.py:49-57` → `tool_device.py:73-79` → `android_device.py:126-131`：序列号含 `:` 时直接 `adb connect`。

**攻击路径**

- 普通用户提交 `agent_id` 指向另一个用户的私有/停用智能体：任务用该智能体的解密 Key 跑，消耗对方额度，结果写入对方任务历史（若可见性允许）。
- 提交 `device_serial="10.0.0.5:5555"`：服务端向任意内网地址发起 adb TCP 连接，可做端口探测/横向尝试，且不需要 `Device` 表存在。
- 提交已被他人锁定/占用的设备：任务仍会被派发，造成设备争用（`use_device` 只拦执行引擎前缀，不拦普通用户锁）。

**修复**：提交时要求 `check_agent_visible(user_id, agent_id)` 且 `status=active`；要求 `Device` 行存在、`is_device_visible`、未被他人锁定；`device_serial` 做格式/网段白名单；每用户并发与每日成本上限。

#### SEC-05 任意登录用户可下载运行日志（P1）

**证据**

- `backend/apps/report_generator/views.py:83-94`、`:105-142`：`settings.LOG_DIR / Path(filename).name`，只做了 basename 防穿越（这一点是正确的），但没有文件名白名单或 owner 校验。
- `backend/apps/report_generator/urls.py:13-16`：`<str:filename>` 可命中 `logs/` 根下的任意文件。
- 根目录日志包括 `backend.log`、`device.log`、`serial.log`、`frontend.log`、`redis.log`；`device.log` 记录 adb 命令与结果，`android_device.py:148-163` 还会把**配对码**写进日志。
- `backend/apps/serial_log/views.py:66-79`：`/api/serial-log/ports/<port>/lines/` 任意登录用户可读。
- 上传原件落在 `MEDIA_ROOT`（`task_list/upload_cleanup.py:13`），DEBUG 下 Django 直接服务 `/media/`（`config/urls.py:42-47`）；文件名带 UUID，猜测成本较高，但一旦 URL 泄露即无鉴权可读。

**影响**：内部拓扑、设备串号、操作文本、配对码、异常堆栈、上传文档泄露；与 SEC-02 组合后，新注册账号即可读取。

**修复**：报告下载只允许 `exports/` 或专用报告目录下的白名单扩展名（`.csv/.md`），并建立“报告文件 → 任务/用户”的索引；原始运行日志仅超管可读；`/media/` 的公开前缀改为签名 URL 或仅本机代理；日志中脱敏配对码、令牌、密码。

#### SEC-06 JWT 生命周期：撤销 fail-open、禁用用户仍有效、无登录限速（P1）

**证据**

- `backend/shared/auth/jwt_auth.py:91-117`：`_is_revoked` 在 Redis 异常时记录 error 并返回 `False`（放行 token）。
- `backend/gateway/middleware.py:86-96`：只验签并取 `sub`，不查用户是否存在/`is_active`。
- `backend/shared/auth/drf_auth.py:57-62`：只查 `User.objects.get`，不检查 `is_active`。
- `backend/apps/accounts/views.py:108-133`：刷新只校验 refresh 令牌，不查用户状态；refresh 不轮换。
- `backend/config/settings.py:263-264`：access 1h、refresh 7d。
- `frontend/src/shared/auth/token-storage.ts:20-40`：access/refresh 存 `localStorage`；前端无 CSP。
- 全仓库无 DRF throttle、无登录失败计数（`settings.py:309-323` 无 `DEFAULT_THROTTLE_CLASSES`）。

**攻击路径**

- 管理员把账号 `is_active=False`：该用户仍可用现有 access 直到过期，并可继续用 refresh 换新 access（DRF 只查存在性）。
- Redis 故障期间，已登出的 token 重新可用；`logout` 本身是 fail-closed 503（`accounts/views.py:156-160`），但读侧已经放行。
- 无登录限速：可对 `/api/auth/login/` 做在线爆破；无注册限速：可批量创建账号。
- 若发生 XSS（当前未发现 `v-html`/`innerHTML` 业务 sink，但不能排除依赖或未来改动），localStorage 中的 7 天 refresh 可被直接窃取。

**修复**：在认证路径查 `is_active`（短 TTL 缓存）；refresh 时校验用户存在且启用，并轮换 refresh；access TTL 缩到 15～30 分钟；登录/注册/刷新加 IP+账号双维度限流与锁定；登出/改密撤销全部会话；前端改 httpOnly Cookie 或至少加 CSP 与短期 access。

#### SEC-07 无速率限制与配额，重负载端点可被低成本刷（P1）

**证据**

- 无 throttle 配置（同上）；无队列/并发上限。
- `POST /api/tasks/submit/` 每次提交都 `threading.Thread` 起任务线程（`task_runner.py:98-105`）；`dispatch_device` 只限制“同 serial 一条 running”（`api.py:252`），因此用不同 fake serial 可无限起线程。
- `POST /api/tasks/upload-file/` 与提交附件在请求线程内做 Office/PDF 解析（`views_upload.py:115-159`、`attachments.py:39-78`），单文件 20MB，附件数量无上限。
- `GET /api/devices/` 与 `/heartbeat/` 在请求线程跑 `adb devices`（`device_pool/views.py:41,331-335`、`manager.py:75-91`）。
- `/api/schema/`、`/api/swagger/` 公开且无频率限制（`gateway/middleware.py:30-32`）；schema 生成是 CPU 操作。
- 模型调用没有看到平台显式配置的超时/重试上限；`platform_run.py:29-31` 只限制工具轮次（60/30）。

**影响**：一个账号即可让单进程平台进入高 CPU/高内存/高 API 花费状态；与 SEC-02 的开放注册叠加，攻击者不需要任何内部信息。

**修复**：DRF 限流（登录/注册/提交/上传分别配置）；每用户并发任务数与每日 token/费用上限；附件总大小/数量上限；解析超时与内存上限；`/api/schema/` 仅 staff 可访问并加缓存；给模型调用加 wall-clock 超时。

### 3.3 P2

#### SEC-08 密钥管理：派生、轮换与静默失败（P2）

- `ai_assistant/api.py:162-184`：Fernet Key = `SHA-256(DJANGO_SECRET_KEY)`；密钥与 JWT 签名、媒体直链 HMAC（`settings.py:267`）同源，无法单独轮换。

**修复**：独立的 `CREDENTIAL_ENCRYPTION_KEY`（支持版本号/轮换），启动时校验；解密失败要显式告警而非静默空串；Admin 对敏感 JSON 只读或自定义表单；密钥放系统密钥环/Secret Manager，`.env` 收紧 ACL；删除遗留变量。

#### SEC-09 证据可信度与提示词注入（P2）

- YAML 的 `action/assert` 文本会进入模型上下文，作为执行与验收指令（`engines/agents/workflow/case_file.py:68-72` → `platform_run.py:188-196`）。

- SEC-03 让日志证据可注入，进一步削弱“模型判决 + 日志”这一组合的独立性。

**修复**：把用例文本明确标注为“数据，不是指令”，用分隔符/结构化字段传入；对 `passed=true` 增加规则校验（断言必须有可观测证据、截图/日志双证据）；报告标注证据来源与可信级别；对导入的 YAML/文档做人工审核或来源标记。

#### SEC-10 供应链与 CI 安全门禁薄弱（P2）

- `.github/workflows/ci-phase1.yml` 的 `security-scan` 只做硬编码密码/Key 的正则 grep；`utils/check_gates.py:395-438` 同口径。

- `requirements.txt` 绝大多数是 `>=`（仅 Django 固定 `6.0.6`），Python 依赖不可复现；前端有 `package-lock.json` 且 CI 用 `npm ci`（这一点较好）。
- CI 的后端 `pytest` 只做 `--collect-only`，不跑用例；后端运行期回归无 CI 守护（前端 `npm test` 会跑）。

**修复**：加 `pip-audit`/`npm audit --audit-level=high`、Dependabot、`bandit` 或 `semgrep`；Python 用 `pip-tools`/`uv lock` 生成锁定文件；把关键 API/引擎测试纳入 CI，而不只是收集。

## 4. 性能风险

### 4.1 瓶颈排序（结论）

1. **设备 I/O**：每个工具调用新建连接/断开；每次坐标动作都跑 `adb shell wm size`；截图走原尺寸 PNG + base64。
2. **验收日志解析**：每次 `check_device_log` 读整个文件并逐行正则，文件上限 50MB。
3. **请求内查询放大**：任务列表每 5s 的 N+1、仪表盘约 40+N 查询、`filter_agents_for_user` 反复查。
4. **请求基础设施**：每请求新线程/新 MySQL 连接；双重 JWT 校验（4 次 Redis RTT + 4 次解码）。
5. **大对象内存**：报告全事件入内存 + 排序；`/api/reports/{file}/content` 整文件多次读；LocMem 缓存 raw+gzip。
6. **单实例架构**：不能横向扩容，重启即中断任务。

### 4.2 P1 详解

#### PERF-01 每个同步请求新建线程，`CONN_MAX_AGE` 实际失效（P1）

**证据**

- 单 Daphne 进程（`run.py:237-248`、`run_daphne.py:31-33`），所有视图是同步函数。
- Django 6 在 ASGI 下用 `sync_to_async(..., thread_sensitive=True)` 执行同步视图（本机 `django/core/handlers/asgi.py:169` 的 `ThreadSensitiveContext`；`django/core/handlers/base.py:250-252`）。
- asgiref 3.11 的 `ThreadSensitiveContext` 会为每个上下文创建 `ThreadPoolExecutor(max_workers=1)` 并在退出时关闭（本机 `asgiref/sync.py:460-471`）。
- Django 的 DB 连接是线程本地，`request_finished` 会关闭连接（`django/db/__init__.py`）；`settings.py:208` 的 `CONN_MAX_AGE=30` 因此只在单个请求内有效。
- `gateway/middleware.py:67` 还在每请求开头 `close_old_connections()`，进一步强化“每请求新连接”。

**影响**：每个有 DB 访问的请求至少一次 TCP+认证+`init_command` 的 MySQL 握手，外加线程创建/销毁；`CONN_MAX_AGE` 的调优完全不生效。低并发时是几毫秒的固定成本，高并发时是吞吐上限与 `max_connections` 风险。

**修复**：HTTP 改用 WSGI 线程池（waitress/gunicorn）并保留 Daphne 处理 WebSocket；或把热读接口改成 `async def` 并只在 ORM 处 `sync_to_async`；或加连接池代理。短期至少删除误导性的 `CONN_MAX_AGE` 与重复的 `close_old_connections`，并用 `SHOW PROCESSLIST` 验证。

#### PERF-02 每个请求双重 JWT 校验：4 次 Redis RTT + 4 次解码 + 用户查询（P1）

**证据**

- `gateway/middleware.py:89` 调 `verify_token`；`shared/auth/drf_auth.py:52` 又调一次，中间件没有把 payload 传给 DRF。
- `jwt_auth.py:217-229` 每次 `verify_token` 解码两次（先不验 exp 取 jti/sid，再验 exp）。
- `jwt_auth.py:109-112` → `_get_redis()` → `:63-66` 对缓存的 client 也执行 `ping()`，然后 `exists()`。
- 所以一个受保护的 DRF 请求：**4 次 HS256 解码 + 2 次 PING + 2 次 EXISTS + 1 次 `User.objects.get`**，之后才开始业务查询。

**影响**：这是所有接口的固定延迟下限；5s 轮询、30s 心跳、3s 详情（若未来启用）都会放大。Redis 抖动时所有接口一起变慢。

**修复**：中间件验一次，把 `request.jwt_payload` 与已解析用户传给 DRF；`JWTAuthentication` 直接复用；`verify_token` 只解码一次（PyJWT 在返回 claims 后再校验 exp）；去掉每次 `ping()`，用连接池的 `health_check_interval`；用户信息短 TTL 缓存。

#### PERF-03 任务列表 5s 轮询：约 101 条查询 + 全量 `result` 解析（P1）

**证据**

- `task_list/views.py:109`：`Task.objects.filter(agent=agent).select_related("agent").order_by("-id")[:100]`，没有 `prefetch_related`，也没有 `.only()/defer()`。
- `task_list/api.py:361`：`_attachment_names` 对每条任务取 `task.file_attachments.all()` → 每条 1 次查询。
- `task_list/models.py:20`：`result` 是 `TextField`，存整份过程 JSON；`api.py:346-357` 只为 120 字摘要就 `json.loads` 整份。
- 前端在任意任务非终态时每 5s 轮询（`frontend/src/modules/task-list/composables/useTaskList.ts:16,63`）。

**影响**：最多 100 条附件查询 + 100 份大 JSON 解析，每 5s 一次；任务越多、结果越长，越慢。这是“任务页越用越卡”的直接原因。

**修复**：`.prefetch_related("file_attachments")` + `.defer("result","model_usage","by_role","attachment")`；为列表存 `result_preview` 字段；改为 keyset 分页（`id < cursor`）而不是固定 100 条；给列表加 ETag/`If-None-Match`。

#### PERF-04 仪表盘一次约 40+N 查询，且把 7 天任务拉到 Python 分桶（P1）

**证据**

- `dashboard/views.py:105-139` 调用 9 个聚合函数；每个函数内部都重新 `_agents(user_id)`（`dashboard/ai_usage.py:19-25`）。
- `filter_agents_for_user` 每次 2 条查询（`is_superuser().exists()` + 超管 id 列表，`ai_assistant/api.py:41-49`），普通用户一次仪表盘会调用约 7～9 次。
- `case_manager/api_projects.py:42` 每个项目一次 `COUNT`，经 `dashboard/views.py:75` 进入 → N+1。
- `ai_task_daily_execution` 把 7 天内所有任务加载到 Python 再按天分桶（`ai_usage.py:302-324`）；`platform_activities` 各取 100 条再排序（`:381-419`）。

**影响**：一次只读页面约 40+N 次往返；任务/项目增长后线性变慢；无缓存，刷新即重算。

**修复**：请求级只解析一次 agents 并下传；用 `values("agent_id").annotate(Sum(...))` 合并聚合；项目列表用 `annotate(case_count=Count("testdefinition"))`；日期分桶用 `TruncDate` + `Count(filter=Q(...))`；对仪表盘加 30～60s 缓存。

#### PERF-05 设备列表/心跳在请求线程跑 adb，无线设备可阻塞十几秒（P1）

**证据**

- `device_pool/views.py:41` 每次列表都 `state_machine.update_device_status()`；`:331-335` 心跳也走同一同步。
- `manager.py:78` `subprocess.run(["adb","devices"], timeout=5)`。
- `manager.py:378-408` 对每个 adb 地址调用 `resolve_serial`；无线设备走 `fetch_serial_no`（`:130-148`）：最多 3 次 `adb -s ... getprop`，每次 timeout 5s，中间 `sleep(1)`。
- `manager.py:410-449` 每设备一次 `DeviceLock` 查询与若干 `save()`；`device_to_dict`（`:649-660`）对 BUSY 设备再查一次锁 → 第二个 N+1。
- 设备发布弹窗每 30s 轮询（`frontend/src/modules/task-list/composables/useTaskPublish.ts:100`）。

**影响**：一台无线设备异常时，单次列表请求可占线程 5～17s；多客户端同时刷新会耗尽请求线程池，表现为整站卡死。设备页与发布弹窗都会触发。

**修复**：列表只读 DB；把 adb 同步放到已有心跳后台循环（10～30s 一次），用内存快照供读；缓存 `ro.serialno`；`prefetch_related("locks")`；对 adb 调用加熔断/超时。

#### PERF-06 验证器每次整文件读取并逐行正则，文件上限 50MB（P1）

**证据**

- `tool_serial.py:114-130`：`path.read_text(...).splitlines()` 读整个文件，逐行正则、排序。
- `tool_serial.py:178`：每次检查都重新读。
- `settings.py:303`：单文件上限 50MB；`:305-306` 页面读 2000/20000 行。
- `check_device_log` 是 verifier 的常驻工具（`tools_config.py:117-120`），每个步骤可能调用多次。

**影响**：50MB 文件一次检查就是几十 MB 读取 + 数万行正则 + 排序；10 个步骤就是几百 MB～GB 级 I/O 与 CPU，且发生在任务线程内，直接拉长验收时间并抢占 Web CPU。

**修复**：按时间戳/字节偏移做尾部窗口读取（只读最近 N MB 或“动作时间前 30s 起”）；为每个文件维护“最后解析位置 + 行索引”，增量解析；用 mtime/size 缓存；硬上限 256KB/次。

#### PERF-07 每个设备动作新建连接/断开，坐标动作每次跑 `wm size`（P1）

**证据**

- `tool_device.py:72-79`：每次工具调用 `open_device(...)`，`finally` 断开。
- 无线设备：`android_device.py:128` `adb connect`、`:146` `adb disconnect`，即每个动作前后各一次子进程。
- `_to_pixel`（`:697`）、`swipe`（`:571`）、`click_img`/`long_click_img`/`drag` 都调用 `info.screen_size()` → `adb shell wm size`；没有缓存。
- `hierarchy_xml` 需要 `uiautomator dump` + `cat` 两次子进程（`:488-489`）。
- 截图走 `adb exec-out screencap -p`（`:649`），返回原尺寸 PNG。

**影响**：一次 `click_ratio` ≈ connect + `wm size` + `input tap` + disconnect = 4 个子进程；无线下每次 connect/disconnect 还可能重建 adb transport。按 20 步、每步 3 个动作估算，纯设备开销 10～40 秒，且每一步都在串行等待。

**修复**：按 `(task_id, serial)` 持有一次 `AndroidControl`，任务结束再断开；`screen_size()` 缓存在实例上（旋转时失效）；批量 shell 命令；无线设备只在任务开始时 `adb connect` 一次。

#### PERF-08 提交/上传在请求线程同步解析 Office/PDF，且没有总量上限（P1）

**证据**

- `task_list/views.py:71-97`：提交时同步 `collect_task_files`，内部 `MarkItDown().convert(path)`（`attachments.py:70`）。
- `task_list/views_upload.py:115-131`：先落盘、再 `read_bytes()` + `base64.b64encode`（5MB 图 → 6.7MB data URI）。
- `views_upload.py:150-159`：`docx` / `openpyxl.load_workbook` / `fitz` 同步解析 20MB 文件。
- 附件数量无上限（`attachments.py:124-130`）；前端 axios 超时 2 分钟（`api-client.ts:18`）。

**影响**：一个 20MB xlsx 可在请求线程里跑数秒并分配数百 MB；多附件提交叠加；与单进程架构叠加会拖慢所有用户；解析失败/超时还会留下半成品。

**修复**：提交只落元数据并返回 job id，解析放到有界 worker；流式解析，先限大小再解析；单次提交总大小/文件数上限；解析超时与内存上限；图片返回 URL 而非 data URI。

#### PERF-09 报告构建无上限、缓存策略粗糙、内容端整文件多次读（P1）

**证据**

- `task_reports.py:96-97`：取该任务**全部**事件行到 Python，再 `sort`；`_load_details` 再发一次 `seq__in` 查询。
- `task_list/views.py:214-223`：只有终态任务缓存；运行中每次重建；缓存 key 含 `max_seq`，每来一个新事件就是一个新 key。
- `views.py:36-39`：同时构造明文 bytes 与 `gzip.compress(raw)`；`settings.py` 没有 `CACHES`，默认 LocMem，默认 300 项上限，大 payload 会占满进程内存。
- `report_generator/views.py:111-117`：`read_text("utf-8-sig")` + 两次完整回退重读；`:132-142` 把整份 `content` 和逐行 CSV 结果一起返回。
- `task_reports.py:247-274`：`build_report_list` 遍历全部可见任务，无分页。

**影响**：长任务报告随事件数线性增长；打开报告可能几百 ms～数秒、几十 MB；LocMem 缓存会推高常驻内存；报告内容端点对 50MB 日志可做 3 次整读。

**修复**：SQL `ORDER BY seq` + 分页/增量尾部；终态报告缓存到 Redis 或文件，不在进程内；只 gzip 实际发送的变体；内容端点流式/限长；列表按时间范围分页。

#### SCALE-01 只能单实例运行（P1，扩展性）

**证据**

- 启动恢复把所有 `running` 任务改为 `interrupted`（`task_list/apps.py:34-46` → `api.py:64-86`），第二个实例启动会误杀第一个实例正在跑的任务。
- 排空标志 `_DRAINING`、取消表 `_cancel_events/_inflight` 都是进程内全局（`api.py:44`、`platform_run.py:33-34`）。
- 当前设备指针 `DevicePool.current_serial` 是进程内类属性（`device_pool/pool.py:8-23`）。
- 串口监听同一端口只能有一个进程（`receiver.py:91-95`）。
- 任务线程在 Web 进程内（`task_runner.py:98-105`），没有队列/租约。

**影响**：无法通过“再起一个 Daphne”扩容；重启即中断任务；任务归属与取消信号跨进程失效。容量只能纵向堆，且受单进程 GIL/内存限制。

**修复**：把任务执行移出 Web 进程（Celery/RQ/Arq/独立 worker），任务状态与取消用 DB/Redis 协调；启动恢复只处理“本实例租约”或带心跳超时的任务；设备指针与排空标志改为共享存储；串口采集单独进程。

### 4.4 性能预算与容量判断

| 区域 | 舒适区（当前代码） | 开始退化 | 不可用 |
|---|---|---|---|
| 并发用户 | 1～3 | 5+（轮询叠加线程/查询） | 10+ 同时开任务页/设备页 |
| 设备数 | 1～2（USB 或稳定无线） | 3～5（设备列表 adb 同步、动作串行） | 无线设备频繁重连/一台异常 |
| 任务数 | ≤500 | 1k+（列表 N+1、报告全量） | 1 万+ 事件的任务频繁打开 |
| 串口日志 | ≤10MB | 10～50MB（每次验收整读） | 50MB 且高频验收 |
| 报告/截图 | 单任务数百事件、少量截图 | 数千事件、几十张截图 | 数万事件、报告内容整读 50MB |

**结论**：当前形态适合“现场 1～2 台设备、1～3 个人、任务量不大”的试用；一旦要作为团队平台（5+ 用户、5+ 设备、长期任务历史），PERF-01/03/04/05/06/07 会同时出现，表现为“页面越来越慢、任务越跑越久、验收经常超时”。

**为什么不是模型慢**：模型调用本身有外部延迟，但每台设备串行、任务线程独立，模型等待不会直接阻塞 Web；真正拖慢全局的是截图/日志/解析/查询这些**同步 CPU 与 I/O**，以及每个请求的固定基础设施成本。

| ID | 级别 | 主题 | 主要成本 |

## 5. 交叉影响：安全风险会直接变成性能风险

| 组合 | 机制 | 结果 |
|---|---|---|
| 开放注册 + 无限流 + 任务线程 | 一个账号循环提交不同 fake serial，每次起线程 + 调模型 | 单进程 CPU/内存/API 花费被打满；正常用户接口超时 |
| `:7005` 无认证 | 任意主机持续灌日志 | 磁盘写满、验收线程变慢、日志文件变大后 PERF-06 更严重 |
| DEBUG + 日志可下载 | 攻击者先读日志了解设备/接口，再打 | 攻击成本降低；日志本身含配对码/命令 |
| 报告内容端点 + 50MB 日志 | 多个已登录用户同时打开大日志 | 单进程内存峰值叠加，可能 OOM |
| 单实例 + 任务线程 | 重启/崩溃即中断任务，启动恢复又把 running 全改 interrupted | 长任务不可靠，用户重跑进一步放大负载 |

### 6.2 2 周：低成本高收益

1. **认证只做一次**：中间件存 payload，DRF 复用；单次解码；去掉每次 `ping()`。
2. **查询预算**：给任务列表、仪表盘、设备列表、报告分别加 `assertNumQueries` 测试，防止回退。
3. **报告/日志读取**：`ORDER BY seq` + 分页；`check_device_log` 改尾部窗口/增量索引；内容端点流式/限长。
4. **上传/提交异步化**：解析移出请求线程；返回 job id；加解析超时。
5. **设备会话复用**：按 `(task, serial)` 缓存 `AndroidControl`；缓存 `screen_size()`；无线只在任务开始 `connect`。
6. **分页统一**：DRF 默认分页 + 列表接口 keyset；报告列表限时间范围。
7. **CI 安全门禁**：`pip-audit`、`npm audit`、`bandit`/`semgrep`、依赖锁定；`check --deploy` 阻塞。
8. **密钥治理**：独立加密 Key、解密失败显式告警、Admin 敏感字段只读、轮换 `.env`。

### 6.3 1～2 月：结构改造

1. **任务执行移出 Web 进程**：队列 + 有界 worker + 租约/心跳；取消与排空跨进程协调；启动恢复只处理本实例/超时租约。
2. **HTTP 服务模型**：WSGI 线程池或 async 视图 + 连接池；Daphne 仅保留 WebSocket。
3. **权限模型**：`owner_id` + 角色（viewer/operator/admin）+ 审计日志；任务/报告/工作流/设备全部对象级过滤。
4. **观测性**：每接口 p50/p95/p99、SQL 查询数、Redis/MySQL 连接数、任务队列深度、验收日志解析耗时、单任务事件量。
5. **对象存储**：截图/上传从本地磁盘迁到对象存储（或至少独立目录 + 生命周期），报告与素材分离。
6. **压测基线**：用 k6/Locust 模拟 10 用户、5 设备、1000 任务、50MB 日志，验证 6.4 的 SLO。

### B. 建议的复现/固化方法

1. **部署检查**：`python manage.py check --deploy`，把 W004/W008/W012/W016/W018 作为 CI 阻塞项。
2. **查询预算**：在测试里用 `django.test.utils.CaptureQueriesContext` 或 `assertNumQueries` 包住 `GET /api/tasks/`、`/api/dashboard/stats/`、`/api/devices/`，把本文的“约 101 / 约 40+N”变成硬断言。
3. **认证复用**：在中间件与 DRF 认证各打一条 debug 计数，确认每请求只发生一次 `verify_token`。
4. **数据库连接**：用 `SHOW PROCESSLIST` 或 MySQL 的 `Connections` 状态观察 100 次顺序请求前后的增量，验证 PERF-01。
5. **日志解析**：用 1MB/10MB/50MB 三档文件跑 `check_device_log`，记录耗时与 RSS。
6. **设备动作**：在无线设备上统计一次 `click_ratio` 的 adb 子进程数与耗时（Windows 可用 Process Monitor / 包装 `adb` 脚本计数）。
7. **压测**：k6/Locust 模拟 5 用户轮询任务列表 + 2 个并发任务，观察 API p95 与任务单步耗时。
