7. 这是一个很好的问题。我从架构、代码、样式、数据、质量保障五个维度来谈。

  ---
  一、架构维度

  1. 目录结构即文档

  新人打开项目，5 分钟内应该能猜到某个东西放在哪。当前项目这块做得不错：

  modules/{domain}/        ← 按业务域拆分，不是按技术类型
    index.vue              ← 入口一眼可见
    components/            ← 模块私有组件
    composables/           ← 模块私有逻辑
    api.js                 ← 模块 API 收敛
    routes.js              ← 子路由独立管理
  shared/                  ← 跨模块共享（不放业务逻辑）
    styles/tokens.css      ← 设计令牌单一真相源

  关键原则：一个模块能独立删掉而不影响其他模块，才算解耦到位。

  2. 分层清晰，避免网状依赖

  视图层 (components/)  ← 只负责渲染 + 事件 emit
    ↓ 调用
  逻辑层 (composables/) ← 状态 + 业务逻辑 + API 调用
    ↓ 调用
  数据层 (api.js)       ← 纯粹的 HTTP 请求封装

  红线：组件里不直接调 axios/fetch，composable 里不操作 DOM，api.js 里不处理业务状态。当前项目 api.js → api-client.js
  两层分离已经做到了这一点。

  3. 路由设计

  - 子路由定义在模块内部（routes.js），router.js 只做汇总
  - 路由守卫只做认证判断，不做业务逻辑
  - 懒加载默认开启（() => import(...)），无需手写

  ---
  二、代码维度

  1. 命名一致性

  当前项目已经定好规范，核心是前后端字段名映射：

  ┌─────────────┬───────────┐
  │ 后端 (JSON) │ 前端 (JS) │
  ├─────────────┼───────────┤
  │ snake_case  │ camelCase │
  └─────────────┴───────────┘

  这个转换应该在 api-client 拦截器或 API 层统一处理，不要让每个组件自己转。

  2. 组件粒度

  一个好的组件拆分标准：

  ❌ 过早拆分：3 个 prop、20 行模板就拆 → 碎片化
  ❌ 过晚拆分：一个文件 500+ 行 → 难以维护
  ✅ 信号：出现以下任一就该拆——
     - 状态变量超过 6 个 ref/reactive
     - 模板超过 ~150 行
     - 有独立的"区域"（面板、列表、表单）
     - 多个开发者会同时改同一个文件

  当前项目的 500 行上限是一个硬止损线，但不应等到 500 行才拆——200-300 行是最佳拆分点。

  3. composable 是核心抽象

  // ❌ 组件内直接操作 API
  const agents = ref([])
  onMounted(async () => {
    const { data } = await apiClient.get('/ai/agents')
    if (data.ok) agents.value = data.agents
  })

  // ✅ composable 封装
  // useAgents.js
  export function useAgents() {
    const agents = ref([])
    const loading = ref(false)
    const error = ref(null)

    async function fetch() {
      loading.value = true
      try {
        const { data } = await client.get('/ai/agents')
        if (data.ok) agents.value = data.agents
      } catch (e) {
        error.value = e
      } finally {
        loading.value = false
      }
    }

    return { agents, loading, error, fetch }
  }

  好处：组件只渲染，逻辑可独立测试、复用、替换。

  ---
  三、样式维度

  1. 设计令牌（Design Tokens）是基石

  当前项目 tokens.css 已经做对了——所有视觉参数集中管理：

  :root {
    --app-text: #4a4e69;           /* 改一个，全局生效 */
    --app-radius-md: 20px;
    --app-glass-blur: 20px;
    --el-color-primary: var(--app-green-deep);  /* 覆盖组件库变量 */
  }

  这块当前项目做得很好，保持住。

  2. 组件库选型的代价

  当前项目已从 animal-island-vue 迁移回纯 Element Plus。这说明了两个真理：

  - 第三方主题库的维护成本往往高于其美观收益。animal-island-vue 的 API 差异（danger 是布尔属性而非 type
  值等）是持续的认知负担
  - 覆盖 CSS 变量 > 封装组件。通过 --el-* 变量控制 Element Plus 外观，比在代码里到处用自定义组件更轻量、更可持续

  3. CSS 作用域策略

  全局 tokens.css      ← 只放变量定义，不放选择器
  全局 style.css       ← 通用布局（.doc-page / .doc-body）+ Element Plus 覆盖
  模块 <style scoped>  ← 业务样式，不污染全局

  scoped 样式不够用时，用 :deep() 穿透，不要轻易写全局选择器。

  ---
  四、数据维度

  1. 单一数据流向

  API 响应 → composable/ref → 组件渲染
  用户操作 → emit/composable 函数 → API 调用 → 更新 ref → 重新渲染

  不要出现两条路：组件既从 props 读数据，又自己在 onMounted 里请求同样的数据。

  2. 错误处理分三层

  ┌────────┬────────────────────┬──────────────────────────────────────────────┐
  │  层级  │      处理什么      │                     工具                     │
  ├────────┼────────────────────┼──────────────────────────────────────────────┤
  │ 网络层 │ 401/超时/网络断开  │ api-client 拦截器统一处理                    │
  ├────────┼────────────────────┼──────────────────────────────────────────────┤
  │ 业务层 │ API 返回 ok:false  │ composable 中判断 + ElMessage                │
  ├────────┼────────────────────┼──────────────────────────────────────────────┤
  │ 视图层 │ 空态/加载态/错误态 │ 组件中的 v-if="loading" v-if="!items.length" │
  └────────┴────────────────────┴──────────────────────────────────────────────┘

  当前项目的规则已经覆盖了这些，但可以进一步强化：每个列表组件必须处理 loading / empty / error 三种状态。

  3. 状态管理选择

  ┌──────────────┬────────────────────────────┐
  │     场景     │            工具            │
  ├──────────────┼────────────────────────────┤
  │ 组件内部状态 │ ref / reactive             │
  ├──────────────┼────────────────────────────┤
  │ 父子通信     │ props down, events up      │
  ├──────────────┼────────────────────────────┤
  │ 跨组件共享   │ composable（推荐）或 Pinia │
  ├──────────────┼────────────────────────────┤
  │ 跨路由持久化 │ Pinia + localStorage       │
  └──────────────┴────────────────────────────┘

  原则：能用 ref 就不用 Pinia，能用 composable 就不用 event bus。当前项目的 mitt
  事件总线适合通知类场景（"数据已更新，重新加载"），不适合做数据传递。

  ---
  五、质量保障维度

  1. 编译检查是第一道防线

  当前项目的 npx vite build 检查已经是一个好习惯。可以加强：

  # 提交前跑这个
  npx vite build --mode development 2>&1 | grep -i "error\|warning"

  2. 样式检查

  当前项目没有 CSS 相关的自动化检查。建议补充：

  # 检查是否有 scoped 泄漏的全局样式
  grep -rn "!important" frontend/src/modules/ | wc -l
  # 数量应该控制，越多说明样式优先级大战越严重

  # 检查硬编码颜色（应该用 CSS 变量）
  grep -rnP "color:\s*#[0-9a-fA-F]{3,6}" frontend/src/modules/ --include="*.vue"
  # 模块内的硬编码色值应该尽量少

  3. 文档同步

  规则文件（.claude/rules/frontend.md）必须随代码演进持续更新。之前 animal-island-vue
  已移除但规则文件还写了一个多月就是反面案例。

  ---
  总结：易维护前端的三个判断标准

  如果你半年后回来看这个项目，能否：

  1. 10 分钟加一个简单的 CRUD 页面？→ 目录结构 + API 封装模式一致
  2. 改一个颜色，全局生效？→ 设计令牌驱动
  3. 删掉一个模块，其他模块不受影响？→ 模块边界清晰，无网状依赖

  这三条能做到，就是一个好维护的前端项目。当前项目在（1）和（2）上已经有很好的基础，（3）取决于后续新功能会不会打破边界

1. 几轮修改的根因回顾：

问题不是遗漏了一次，而是每次都没看到同一层
四轮修改做了什么
轮次	改了	没改
R1	背景、卡片框、工具栏按钮	表格内部的 el-tag、el-button
R2	KPI 条、双视图、卡片分组	同上
R3	边框颜色 #2d2d2d → 模块色、拆组件	同上
R4	布局重排、:deep() 覆盖	这次才覆盖到
根因：CSS 穿透层数被忽略
表格单元格的渲染路径是 4 层嵌套：


index.vue (scoped)           ← 我的 CSS 写在这里
 → AppTable (shared)         ← 透一层
  → el-table (Element Plus)  ← 透两层
   → slot 模板               ← 透三层
    → el-tag / el-button     ← 目标元素，必须 :deep() 才能穿透
早期轮次我写的：


.lock-btn { border-color: #A78BFA !important; }
这个选择器能命中 .lock-btn class，但 el-button 组件内部还有自己的 .el-button--primary、.is-plain 等 class，它们的优先级更高，!important 不够用。

正确写法是：


.action-btns :deep(.el-button--primary.is-plain) {
  background: #E8DDF8 !important;
  border-color: #A78BFA !important;
}
:deep() 穿透 scoped 边界 + 精确匹配 Element Plus 内部 class。

认知盲区
每次修改前，我的注意力去了"新增的东西"——KPI 条、卡片视图、彩色边框。表格是"旧的东西"，默认它已经被改好了。但改没改好不是靠感觉判断的，而是要看渲染结果。我四轮都没去浏览器里点开表格单元格检查 el-tag 实际渲染成什么颜色、el-button 的边框是什么色。

这不是 CSS 技术问题，是验证习惯问题：改完不检查渲染结果，只依赖构建通过 + grep 残留。构建通过只能证明语法对，不能证明视觉对。
