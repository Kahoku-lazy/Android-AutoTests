# IoT 智能设备测试用例设计方法论 V2.0

> **基于**: H717D 文档库 V1.0 评估改进
> **核心改进**: 从"方法驱动的选择性覆盖" → "需求驱动的全覆盖追溯"
> **日期**: 2026-07-23

---

## V1.0 → V2.0 核心变化

| 维度 | V1.0（原方案） | V2.0（改进方案） |
|------|:--:|:--:|
| 驱动模式 | 方法驱动（先选方法再套需求） | **需求驱动**（先拆需求再配方法） |
| 覆盖追踪 | 手动标注，无强制矩阵 | **需求追溯矩阵**（逐条需求→用例映射，必填） |
| 集成场景 | 无 E2E 用例 | **E2E 用户旅程**（跨模块，≥3条/项目） |
| 优先级 | 按功能重要性主观判断 | **安全→功能→体验** 三级校准 |
| 需求冲突 | 发现但未处理 | **冲突登记表** + 用例标记"待确认" |
| 执行追踪 | 无 | **每条用例必须记录执行状态** |
| 方法应用 | "五法组合"标签化 | **按 L1~L4 强制选法，不可跳过** |

---

## 一、设计流程 SOP（5 阶段）

```
阶段1: 需求全量拆解 → 阶段2: 逐条方法匹配 → 阶段3: 优先级校准
        ↓                                               ↓
阶段4: 跨模块 E2E 补充 ←──────────────────────────── 冲突检测与登记
        ↓
阶段5: 用例执行 + 结果校验 + 缺陷闭环
```

### 阶段 1：需求全量拆解（强制穷举）

**目标**：将需求文档的每一个独立功能点拆为不可再分的"需求原子"。

```
输入: 需求文档 (.md / PRD)
输出: 需求原子表

拆分规则:
- 一个按键操作 = 1 个原子
- 一个指示灯状态 = 1 个原子
- 一个传感器触发条件 = 1 个原子
- 一个定时器超时行为 = 1 个原子
- 一组冲突/互斥规则 = 1 个原子
- 一个数据存储/展示规则 = 1 个原子
```

**需求原子表模板**：

| ID | 来源章节 | 需求原子 | 类型 | 用户可感知 | 物理依赖 |
|:--:|:--:|------|:--:|:--:|:--:|
| REQ-001 | 6.4 | 待机状态下单击 POWER → 开机并恢复上次模式 | 按键 | ✅ | 无 |
| REQ-002 | 6.4 | 开机状态下单击 POWER → 进入待机 | 按键 | ✅ | 无 |
| REQ-003 | 6.4 | 配网验证时单击 POWER → 验证通过 | 按键+协议 | ✅ | 蓝牙 |
| REQ-004 | 6.4 | 长按 POWER 3s → 进入网络待机模式 | 按键+定时 | ✅ | 无 |
| REQ-005 | 7.1 §16 | 上电检测 NTC 开路 → L/M/S 三灯持续闪烁 | 传感器 | ✅ | NTC 传感器 |
| REQ-006 | 7.1 §17 | 电磁阀控制脱冰 → 计为 1 轮制冰 | 硬件自闭环 | ❌ | 电磁阀+压缩机 |

> **铁律**：不允许跳过任何需求原子，包括"看起来不可测"的。不可测的也要登记，标注原因。

---

### 阶段 2：逐条方法匹配（强制覆盖）

**目标**：为每个需求原子匹配至少一种测试方法，不允许任何需求原子处于"未分配"状态。

**方法选择矩阵（改进版）**：

| 方法 | 适用信号 | 不适用信号 | 典型需求原子类型 |
|------|---------|-----------|---------|
| **场景流法** | 用户操作 → 反馈 → 状态变化 | 无用户触发、内部闭环 | 按键、模式切换、状态转换 |
| **判定表法** | ≥2 个条件组合影响结果 | 单条件、线性流程 | 状态×事件冲突、传感器并发 |
| **边界值+等价类** | 有数值阈值（时间/次数/电压） | 无量化参数 | 长按阈值、超时、重试次数、电压范围 |
| **正交排列法** | ≥4 个独立因子，全组合≥20 种 | 因子＜3或全组合＜10 | 多状态×多事件×多模式 |
| **错误推测法** | 有异步操作/竞态/边界 | 纯同步确定性系统 | 断电竞态、快速连击、并发操作 |
| **硬件注入法** | 传感器触发/硬件保护 | 纯 UI/协议 | NTC 故障注入、压缩机过载 |
| **协议测试法** | 蓝牙/WiFi/OTA/网关 | 本地按键/传感器 | 配网、断网重连、抢配、OTA |
| **CRUD 数据法** | 日志记录/图表/持久化 | 实时控制 | 轮次统计、日志、图表、记忆功能 |

**方法匹配规则（强制）**：

```
L1（≤2个因子，无物理依赖）→ 场景流法 + 边界值 即可
L2（3-5个因子或有物理依赖）→ 场景流 + 判定表 + 边界值，至少 3 种
L3（≥6个因子或多种驱动混合）→ 场景流 + 判定表 + 正交排列 + 边界值 + 错误推测，至少 4 种
L4（跨系统/协议/硬件）→ 全部 8 种方法按需选用，必须正交剪枝
```

**逐条分配表**：

| 需求原子 ID | 复杂度 | 推荐方法 | 用例编号 | 用例标题 | 备注 |
|:--|:--:|------|:--:|------|------|
| REQ-001 | L1 | 场景流+边界 | TC-XXX-001 | 待机→开机状态转换 | |
| REQ-005 | L2 | 场景流+硬件注入+判定表 | TC-XXX-015 | NTC 开路→三灯闪烁验证 | 灯效可软件测；接线需硬件注入 |
| REQ-006 | L2 | 硬件注入+CRUD | TC-XXX-022 | 脱冰触发=1轮计数 | 电磁阀触发可模拟；压缩机制冷不可测 |

> **铁律**：需求原子表 + 方法分配表 = 不可跳过的设计产物。两者合起来就是需求追溯矩阵。

### 阶段 3：优先级校准（安全→功能→体验）

**原方案问题**：优先级按"功能重要性"划分，导致安全相关用例（缺水不提醒→压缩机损坏）和体验用例（冰篮灯颜色好不好看）混在一起。

**V2.0 优先级校准规则**：

```
P0（必测，阻塞发版）:
  - 设备安全相关（缺水保护、满冰停止、压缩机过载保护）
  - 用户数据安全相关（WiFi 密码存储、配网安全验证）
  - 核心功能不可逆损坏风险（NTC 故障不停止制冰）
  - 出厂默认配置验证

P1（应测，发版前尽量完成）:
  - 主要功能正向流程（按键、模式切换、配网）
  - 主要异常处理（超时、断网、缺水恢复）
  - 状态冲突矩阵（按键×状态、指示灯×状态）
  - 跨模块交互（预约→制冰→满冰→取冰）

P2（可测，时间允许时覆盖）:
  - 数值边界（长按 2.9s vs 3.0s）
  - 性能指标（指示灯亮度衰减）
  - 罕见场景（10 个预约时间表全满）
  - UI 体验细节（颜色是否好看）
```

**校准检查清单**：

```
[ ] 所有"传感器异常+硬件损坏风险"场景是否 P0？
[ ] 所有"出厂状态/恢复出厂设置"是否 P0？
[ ] 是否有 P2 用例被错误标为 P0？（如冰篮灯颜色 → 应为 P1/P2）
[ ] 是否有安全相关用例被错误标为 P1？（如缺水不提醒 → 应为 P0）
```

### 阶段 4：跨模块 E2E 补充 + 冲突登记

**4a. E2E 用户旅程（每个项目至少 3 条）**

E2E 用例覆盖完整的用户使用路径，验证模块交接处的行为：

| E2E 编号 | 用户旅程 | 涉及模块 | 关键验证点 |
|:--:|------|------|------|
| E2E-001 | 首次开机 → 蓝牙配网 → WiFi 连接 → 选择 Medium → 制冰 → 满冰提醒 → 取冰 → 继续制冰 → 缺水 → 加水恢复 | 按键+配网+指示灯+缺水满冰 | 配网→制冰切换点；缺水恢复后模式记忆；满冰→取冰→继续制冰切换 |
| E2E-002 | 预约(明天 8:00) → 断电 → 上电 → WiFi 重连 → 预约是否恢复？→ 8:00 启动制冰 | 预约+断电记忆+WiFi重连 | 断电是否取消单次预约；预约定时是否记忆恢复；到点触发是否准确 |
| E2E-003 | 制冰中 → 手机蓝牙断连 → WiFi 断网 → 设备继续制冰 → 满冰停止 → 重连 → 数据同步 | 蓝牙+WiFi+制冰+数据记录 | 离线制冰是否继续；满冰是否正常停止；重连后数据是否补推 |

> **E2E 用例不需要多（3-5 条足够），但必须覆盖"完整用户从开机到关机的全路径"。**

## 二、用例结果校验步骤（完整流程）

### 2.1 校验分层架构

```
层级 1: 即时结果校验（每条用例执行时）
    ↓
层级 2: 批量回归校验（每次跑全量用例集）
    ↓
层级 3: 需求追溯校验（发版前确认覆盖率）
    ↓
层级 4: 缺陷→用例反哺（bug 发现后补充用例）
```

---

### 2.2 层级 1：单条用例执行校验（执行时必做）

每条用例执行后，按以下流程校验结果：

```
执行用例 → 收集实际结果 → 与预期结果对比 → 判定 → 记录
```

**判定标准**：

| 判定 | 条件 | 后续动作 |
|:--:|------|------|
| ✅ PASS | 实际结果 = 预期结果，量化指标全部达标 | 记录执行时间、设备信息 |
| ❌ FAIL | 实际结果 ≠ 预期结果 | 截图/录屏 → 提 Bug → 标记阻塞用例 |
| ⚠️ SKIP | 前置条件不满足（如硬件不可用） | 记录跳过原因、所需硬件 |
| 🔄 BLOCKED | 被其他 FAIL 用例阻塞 | 标记阻塞链，等阻塞解除后重跑 |
| ❓ UNCERTAIN | 需求本身矛盾或预期不明确 | 标记冲突 ID，提需求澄清 |

**校验清单（执行时逐项检查）**：

```
视觉类（指示灯/颜色/闪烁）:
  [ ] 颜色是否正确？（对比标准色卡/APP 色值）
  [ ] 闪烁频率是否在容差内？（1s亮1s灭 → 0.9~1.1s）
  [ ] 亮度是否符合预期？（暗光环境下目视 + 照度计）
  [ ] 过渡动画是否平滑？（无闪烁/无跳变/无错色）

时序类（超时/延迟/持续时间）:
  [ ] 触发到响应的时间 ≤ 预期上限？
  [ ] 超时时间是否准确？（用秒表或自动化计时）
  [ ] 持续时间是否符合规格？

功能类（按键/状态转换/模式切换）:
  [ ] 状态是否正确转换？（对照状态机图）
  [ ] 互斥条件是否生效？（A 状态下 B 按键应无效）
  [ ] 记忆功能是否生效？（断电→上电→恢复上次状态）

传感器类（缺水/满冰/NTC/压缩机）:
  [ ] 触发阈值是否准确？（如满冰红外检测距离）
  [ ] 保护动作是否正确执行？（停止制冰/蜂鸣/指示灯）
  [ ] 恢复后是否正常回到原状态？

协议类（蓝牙/WiFi）:
  [ ] 连接超时是否在规格内？
  [ ] 断网重连周期是否正确？
  [ ] 指示灯与连接状态是否一致？
```

### 2.3 层级 2：批量回归校验（每次跑全量）

**目标**：确认新改动没有破坏已有功能。

```
1. 确认用例集基线（本次回归跑哪些用例？全部 P0+P1 还是全量？）
2. 按模块分组执行
3. 统计 PASS/FAIL/SKIP/BLOCKED
4. 对比上次回归结果 → 新出现的 FAIL 是回归缺陷
5. 更新用例执行状态表
```

**回归结果表模板**：

| 回归批次 | 日期 | 总用例 | PASS | FAIL | SKIP | 通过率 | 新增 FAIL | 相比上次 |
|:--|:--:|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| R1 | 07-20 | 239 | 195 | 18 | 26 | 81.6% | — | 基线 |
| R2 | 07-22 | 239 | 201 | 12 | 26 | 84.0% | 0 | ✅ 修复 6 条，无新 FAIL |
| R3 | 07-23 | 239 | 198 | 22 | 19 | 82.8% | 10 | ❌ 新引入 10 条 FAIL → 排查 |

**回归触发条件**：
- 固件版本变更
- APP 版本变更
- 硬件改版
- 每周例行回归（即使无变更）

---

### 2.4 层级 3：需求追溯校验（发版前必做）

**目标**：确认所有需求原子都已被测试覆盖且通过。

```
需求原子总数: N
  ├── 已覆盖且全部 PASS: X  → 覆盖率 = X/N
  ├── 已覆盖但有 FAIL:    Y  → 阻塞发版
  ├── 已覆盖但有 SKIP:    Z  → 评估风险，记录原因
  └── 未覆盖:             W  → 必须补充或标记"不可测"
```

**发版门禁**：
```
✅ 可以发版:
  - P0 覆盖率 = 100%（全部 PASS）
  - P1 覆盖率 ≥ 90%
  - P2 覆盖率 ≥ 70%
  - 无未解决的 FAIL（P0/P1）

❌ 阻塞发版:
  - 任一条 P0 FAIL 未修复
  - P1 FAIL > 3 条未修复
  - 新增回归缺陷未解决
  - 需求冲突（UNCERTAIN）未澄清
```

---

### 2.5 层级 4：缺陷→用例反哺闭环

**这个闭环是 V1.0 完全不存在的机制。**

```
线上/测试发现 Bug
      ↓
Step 1: 在用例库中搜索 → 是否有已有用例覆盖这个场景？
      ├── 有 → 为什么没拦住？→ 检查校验步骤是否漏检
      └── 没有 → Step 2: 用例库有空白 → 补充新用例
      ↓
Step 2: 补充用例 → 归入对应需求原子 → 标记"Bug 反哺"
      ↓
Step 3: 新用例在下次回归中纳入 → 确认不会再漏
```

**Bug→用例反哺表**：

| Bug ID | 来源 | 遗漏的需求场景 | 新增用例编号 | 新增用例标题 | 原用例库是否覆盖 |
|:--|:--|------|:--:|------|:--:|
| BUG-042 | 用户反馈 | 断电瞬间恰好预约到点 → 设备无法恢复 | TC-SCH-029 | 竞态: 断电瞬间恰好到点触发 | ❌ 原用例库未覆盖 |

## 四、用例生成优先级排序（执行顺序）

**不再按"模块序号"生成用例，而是按依赖关系排优先级**：

```
第1批: 出厂状态 + 恢复出厂设置（一切测试的起点）
    ↓
第2批: 按键功能（最基础的用户交互）
    ↓
第3批: 制冰核心流程（按键→制冰→满冰，核心业务闭环）
    ↓
第4批: 指示灯交互（依赖按键和制冰的状态变化）
    ↓
第5批: 缺水/满冰保护（依赖制冰流程，安全关键）
    ↓
第6批: 蓝牙配网 + WiFi 连接（通信层，依赖设备基础功能正常）
    ↓
第7批: 预约定时（依赖配网+制冰）
    ↓
第8批: 数据记录 → 图表 → 日志（依赖制冰流程）
    ↓
第9批: NTC/压缩机/脱冰（硬件层，需台架）
    ↓
第10批: E2E 集成用例（所有模块就绪后）
```

## 五、用例结果校验 Checklist（执行前逐项确认）

执行任何用例前，先通过以下检查：

```
环境校验:
  [ ] 设备固件版本 = 被测版本？
  [ ] APP 版本 = 被测版本？
  [ ] 测试环境与生产环境的差异已记录？
  [ ] 所需硬件/工具已就位？（照度计/秒表/色卡/台架）

用例校验:
  [ ] 用例的前置条件已满足？
  [ ] 预期结果是明确的（不是"待确认"）？
  [ ] 量化指标的测量工具已校准？

执行中校验:
  [ ] 每步操作后等待足够时间观察反馈？
  [ ] 异常状态是否截图/录屏？
  [ ] 实际结果与预期结果有差异时立即记录，不等跑完？

执行后校验:
  [ ] 用例状态已更新（PASS/FAIL/SKIP/BLOCKED/UNCERTAIN）？
  [ ] FAIL 用例是否已关联 Bug ID？
  [ ] 执行证据（截图/日志/录屏）已存档？
  [ ] 设备是否恢复到初始状态？（不影响下一条用例）
```

## 六、V1.0 → V2.0 迁移路径

```
Step 1: 补全需求原子表（从 4 份需求文档拆解）
Step 2: 现有 239 条用例 → 逐条标注追溯需求 ID
Step 3: 识别出"0 用例覆盖的需求原子" → 优先级排序 → 逐批补充
Step 4: 补 3-5 条 E2E 用例
Step 5: 建立需求冲突登记表，标记 UNCERTAIN
Step 6: 下一轮回归执行 → 每条用例填充执行状态
Step 7: Bug 反哺闭环启动
```

- 首轮执行 + 状态填充：3-5 人天（取决于设备可用性）
