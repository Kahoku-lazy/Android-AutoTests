## Context

- 体例真相源：`frontend/AGENTS.md` 既有的 L0/L1 速查，均为六段式（① 元素链 ② 代码范围 ③ 能写什么 ④ 不能写什么 ⑤ 运行时/契约 ⑥ 破约如何被发现）。
- 行为真相源：`openspec/specs/frontend-l2-page-region/spec.md`（9 条契约）。
- 插入位置：L1 速查结束（现 `AGENTS.md:166`）与 `### 跨模块共享文件：shared/`（现 `:168`）之间。

## Goals / Non-Goals

**Goals:**

- 让接手者在同一份文档里读到 L2 的边界：页面根怎么写、页头唯一实现是谁、内边距与验收判据是什么。
- L0/L1/L2 三层速查体例一致，读者不需要为 L2 学新格式。

**Non-Goals:**

- 不改任何代码、行为、接口；不新增规则。
- 不修当前 `AGENTS.md` 里失效的「规则唯一真相源」引用（另议）。
- 不把 L2 速查写进 spec：契约已在 spec 里，本节只是接手入口。

## Decisions

**D1 插入位置：L1 速查之后、`shared/` 之前。**
备选：放在文档末尾——会与「区域与归属」的主题脱节，读者按 L0→L1→L2 顺序阅读时断档。

**D2 体例：复用 L0/L1 的六段式。**
备选：写成紧凑表格清单——信息密度高，但缺少「元素链」与「破约如何被发现」两段，而这两段正是 L0/L1 速查最有价值的部分。

**D3 内容来源：只复述契约与实施落点，并在节首写明真相源指向 spec。**
理由：避免文档成为第二份会漂移的规则集；数值判据（96px / 24px / 四个色值）直接取自已归档变更的实测记录。

**D4 记录 3 条已知缺口。**
理由：这正是 L0/L1 速查的既有做法（两节都有「已知缺口」段），让接手者不踩坑；这三条都已在前一份报告里核实。

## 模块防火墙自检

纯文档变更，无代码：

- **跨 App import**：无。
- **禁止跨 App import service/runner/consumer/state_machine**：不涉及。
- **所有写库收敛到 api.py**：不涉及，无任何写库或 HTTP 改动。
- **前端不直连数据库**：不涉及。
- **仪表盘不做写操作**：不涉及。
- 结论：无新依赖，无需走 `api.py`。

## Risks / Trade-offs

- [文档与 spec 双份描述可能漂移] → 本节只写判据与落点、不复制契约的规范性措辞（SHALL/MUST 留在 spec），并在节首写明真相源。
- [新增一节会让 `AGENTS.md` 变长] → 控制在约 60 行，与 L0/L1 同量级。
- [文中引用的路径/类名可能随代码演进失效] → 在 tasks 里加一条逐条 grep 自检，并在 ⑥ 说明「静态可查」的命令。
