## Context

- 现状根因：DRF router（默认 `trailing_slash=True`）与手写 `path()` 并存，导致 App 内混用
- 前一变更加了双向容错中间件；本变更**反向**取舍：删中间件、钉死约定
- `APPEND_SLASH` 当前使用 Django 默认 `True` → `CommonMiddleware` 会对缺失斜杠的请求发 **301**
- 301 的三个已知危害：部分客户端丢 `Authorization` 头（真机发现 #1）、可能把 POST 降级为 GET（RFC 7231）、被浏览器长期缓存
- 无 `re_path`，111 条待改路径全为 `path()`，改写可机械化

## Goals / Non-Goals

**Goals**：`/api/` 路径只有一种正确写法；网关不再"猜"调用方的意图；约定可被一条测试断言守住。

**Non-Goals**：不改路由层级/命名；不保留任何重定向过渡；不动 router 配置。

## Decisions

**D1：先加斜杠，最后删中间件（实施顺序，非终态差异）。**

| 顺序 | 中间件 | 老调用方 | 说明 |
|---|---|---|---|
| ① 路由补 `/` | 暂留 | 仍可用（中间件补斜杠） | **非破坏**，可独立验证 |
| ② 关 `APPEND_SLASH` | 暂留 | 仍可用（中间件在 301 之前改写） | 显式关闭有害路径 |
| ③ 调用方补 `/` | 暂留 | 正常 | 逐个面收敛 |
| ④ 删中间件 | 删除 | **缺失斜杠即 404** | 终态生效 |

**D2：`APPEND_SLASH = False` 是必需的，不是可选项。**

只删中间件而不关 `APPEND_SLASH`，缺失斜杠的请求会落到 `CommonMiddleware` 的 301 —— 那正是本变更要消除的路径。关掉它之后缺失斜杠才是**确定的 404**，语义可判定。

**D3：连同 `api-path-normalization` 规格一起移除该能力。**

中间件删除后，原规格的「双向容错」需求不再成立。规格必须随之 `REMOVED`，否则文档会宣称一个不存在的能力。

**D4：端点资产目录（`seed_api_endpoints.py`）视为调用方。**

该目录是平台自身的 API 端点资产（`el_` 表），路径若与实际路由不符，用它发起的接口调用会 404。故与前端、用例同列更新。

## Risks / Trade-offs

- [外部调用方] 任何未随本变更更新的第三方调用方会立即 404。**这是本变更有意承担的代价**，须在接口文档显眼处声明"路径必须带尾斜杠"
- [文档量] `dev_docs` 约 502 处引用需同步；漏改不导致运行时故障，但会让文档失真
- [数据] `el_` 表中已种入的端点路径需要重新 `seed` 或迁移，否则目录与实际路由不符
- [回滚] 回滚需同时还原 111 条路由、settings、中间件与调用方，不可只回滚一部分

## Migration Plan

按 D1 的四步顺序实施，每步可独立验证。回滚 = `git revert` 本变更的提交（不可部分回滚）。

## Open Questions

1. `el_` 表中已有的端点路径数据是否需要一次性数据迁移（而非重新 seed）？
2. 是否需要一个过渡期（同时接受两种写法并打 deprecation 日志）？本变更选择不加过渡，理由见 D2/Non-Goals。
