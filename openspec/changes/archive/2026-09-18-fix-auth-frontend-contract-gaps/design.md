## Context

动机与证据见 `proposal.md`。方案需要的当前状态：

- 前端没有测试运行器（`frontend/src` 下无 spec/test 文件），因此对拍必须在 Python 侧做 —— 沿用
  `tests/AGENTS.md` §契约对拍测试 已确立的范式与四条边界（只读、只做一致性断言、零外部依赖、跨行扫描）。
- 后端事实可直接从源码测出：`apps/accounts/views.py` 的 `Response({...})` 顶层 key 可由 AST 读出；
  `gateway/middleware.py` 的 `PUBLIC_PREFIXES` 可直接 import。
- 前端 DTO 目前 3 个：`AuthTokenData`（登录/注册共用）、`AuthRefreshData`（刷新）、`MeUser`（身份，在 `api/auth.ts`）。
- 实测：`AuthTokenData.user` 在前端**无任何读取点**（`useAuthFlow` 只取 access/refresh token）。

## Goals / Non-Goals

**Goals:**

- 让"前端声明了后端不返回的字段"变成默认门禁里的失败。
- 让"公开端点清单"在前端与网关之间不可能各自漂移。
- 让公开端点的 401 不再白走一次刷新、不再误清本地令牌。

**Non-Goals:**

- 不建共享常量源、不让前端运行时拉规则（与 `auth-form-validation` 同一取舍）。
- 不为 `user` 补一套按端点区分的类型（无消费者，YAGNI）。
- 不改后端。
- 不覆盖嵌套字段的形状差异（见 D3）。

## Decisions

### D1 删除未被消费的 `user?`，而不是补一套按端点的类型

后端两个端点返回的 `user` 形状不同（`login` 无 `email`、`register` 有），而前端**没有消费者**。
补 `LoginData` / `RegisterData` 两个类型只是给未来加负担；删掉这个说谎的可选字段是最小且诚实的修法。
将来真要用，按端点声明准确形状即可，顶层字段由本能力的守护验证。

### D2 豁免清单写在前端常量里，由 Python 侧对拍网关

不引入共享常量（前端 ↔ Python 没有共享模块机制，为三个字符串新建一套是过度设计）。
改为：前端写常量、测试 import 网关的 `PUBLIC_PREFIXES` 并对拍两者 —— 漂移会失败，成本一次断言。

### D3 对拍只覆盖顶层字段；嵌套形状差异用"删除"解决，机制上不覆盖

`AuthTokenData` 被两个端点共用，而它的嵌套 `user` 形状不同。要机械检测这一点，
必须让类型按端点分开声明（D1 已否决）。因此：

- 顶层字段子集断言覆盖 `AuthTokenData` / `AuthRefreshData` / `MeUser`
- 嵌套差异通过删除该字段消除；**若将来重新加入嵌套字段，本守护不会检测其形状差异** —— 已记录为已知限制

### D4 前端断言用"完整路径清单相等"，而不是"包含"

拦截器豁免清单与网关公开清单必须**逐项相等**（不是"网关是前端的超集"）。
网关的公开清单还包含 `/admin/`、`/static/`、`/media/`、`/api/schema/`、`/api/swagger/`、`/api/ai/tools/`，
这些**不该**进前端拦截器的豁免（它们不是前端会调用的认证端点）；
因此断言取网关清单中 `/api/auth/` 前缀的子集与前端清单比较。

### D5 红验证用"注入一个假项"，而不是"删掉真项"

本变更同时修代码与加守护，若只跑绿无法证明守护有效。实施时注入**假数据**证明它会失败：

- DTO 里加一个后端不返回的 `nickname?: string` → 子集断言必须失败
- 豁免清单里加一个不存在的 `/auth/foo` → 清单相等断言必须失败

然后还原。这比"删掉真项"更安全（不会中途留下真实缺陷）。

## 模块防火墙自检

- **跨 App import**：无新增。改动在 `frontend/src`（无 import 变化）与 `tests/`（不属于任何 App，
  只 import 网关中间件的公开常量用于对拍）。
- **禁止跨 App import service/runner/consumer/state_machine**：无。
- **写库收敛**：不触碰任何 INSERT/UPDATE/DELETE。
- **前端不直连数据库**：改的是类型声明与拦截器判断，未新增任何 HTTP 出口。
- **结论**：不触碰任何红线。

## Risks / Trade-offs

- **[删除 `user` 字段可能让将来需要它的人少一条线索]** → 后端确实返回；需要时按端点声明准确形状，
  顶层字段由守护验证。当前没有消费者，保留只会误导。
- **[豁免清单硬编码在前端]** → 由 D2 的对拍钉死与网关一致。
- **[前缀匹配可能误豁免同前缀路径]**（如 `/auth/login/other`）→ 三个前缀都是端点根，
  且清单由 D4 的相等断言约束；误加前缀会失败。
- **[对拍只覆盖顶层字段]** → 见 D3；这是有意识的取舍，不假装覆盖了嵌套。
- **[改 401 分支可能影响既有刷新重试]** → 只对三个公开端点短路；受保护端点的行为由规格明写不得改变，
  且既有 E2E 登录链路可回归。

## Migration Plan

1. 删除 `AuthTokenData.user?`；拦截器加公开端点豁免。
2. 新增对拍守护并跑绿。
3. 注入假项证明守护会失败，再还原。
4. 更新 `tests/AGENTS.md`；跑门禁（含 E2E 登录链路回归）。

**回滚**：改动为两个前端文件与一个新增测试模块，`git revert` 即可；无数据、迁移、依赖影响。

## Open Questions

- 是否把"顶层字段子集"对拍推广到其他模块的前端 DTO —— 独立评估。
- 是否值得为 `login` / `register` 分别声明响应类型以覆盖嵌套形状 —— 当前无消费者，暂不做。
