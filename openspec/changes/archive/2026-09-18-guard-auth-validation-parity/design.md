## Context

动机与实测数据见 `proposal.md`。方案需要的当前状态：

- 两侧文案：前端 13 条、后端 12 条、共有 **10** 条；差异为前端独有 1 条、后端独有 2 条。
- 两侧阈值：`{(<,3), (<,6), (>,150), (>,20)}` —— **当前完全相同**。因此本变更预期零产品代码改动。
- 前端没有测试运行器（`frontend/src` 下无 spec/test 文件），后端有 pytest。
- `tests/AGENTS.md` §契约对拍测试已确立"测试读源码做契约对拍"这一范式与四条边界
  （只读、只做一致性断言、零外部依赖、跨行扫描），本变更沿用并新增第三个断言。

## Goals / Non-Goals

**Goals:**

- 让"两侧用户看到同一句话、同一个数字"成为**被断言**的不变量。
- 让例外**可见、带理由、进 diff**，而不是变成沉默的忽略列表。
- 失败信息要能直接指出两侧差异，使同步成本一眼可见。

**Non-Goals:**

- 不合并两份实现（前端要即时反馈，后端是唯一权威）。
- 不建共享常量源、不让后端下发规则、不引入 i18n（会把即时反馈变成网络往返，并把文案变成运行时依赖）。
- 不做字段归属对拍（见 D1）。
- 不推广到其他模块的表单。

## Decisions

### D1 只对拍"文案集合 + 数值阈值集合"，不做字段归属

后端 `ValidationError` 在 `validate()` 里以对象级抛出，**不带字段信息**；
前端 `errs.<field> = ...` 有字段，但两侧无法对齐。强行做字段对拍只能靠人工维护一张映射表，
那张表本身就是新的漂移源。

- 代价（已记录）：若某条文案在前端被挂到**错误的字段**上（例如把密码文案挂到 `errs.email`），
  本守护不会发现。这属于前端内部的错误，由前端自身的评审覆盖，不在本能力的范围内。

### D2 差异用"两侧各自的例外集合"声明，而不是忽略列表

断言形式是 `实际差异 == 声明的例外`。这比"忽略某些差异"强：忽略列表允许新增差异被静默吞掉，
而等式会立刻失败。例外条目带理由文本，且测试会校验理由非空。

### D3 数值阈值用集合相等，而不是逐条登记

登记 `用户名上限=150` 这类句子等于把源码抄进测试，抄本会跟着源码一起腐化。
改为提取两侧所有 `.length <op> N`（前端）与 `len(...) <op> N`（后端）构成两个集合，
断言集合相等 —— 任何一侧新增/修改/删除阈值都会改变集合。

- 代价：若将来在 `useLoginForm.ts` 里出现与表单校验无关的 `.length > N` 判断，守护会失败并指出该条。
  这是**显式成本**，比静默漏掉一条真实阈值便宜。

### D4 放 Python 侧，沿用既有契约对拍范式

与 `test_api_path_callers.py` 同理：前端没有运行器；且"两侧是否一致"需要一个能同时读到两侧源码的位置。
边界沿用 `tests/AGENTS.md` 已写明的四条（只读、只做一致性断言、零外部依赖、跨行扫描）。

### D5 用"临时改一条文案"证明守护有效

本变更预期不产生任何产品代码 diff，因此无法靠"先跑红"证明守护有效。
改为在实施时**手工**改一条前端文案，确认守护失败并列出差异，然后还原（列入 tasks 的验证项）。
没有这一步，交付的只是一个"总是绿"的测试。

## 模块防火墙自检

- **跨 App import**：无新增。改动仅在 `tests/`（不属于任何 App）与 `tests/AGENTS.md`。
- **禁止跨 App import service/runner/consumer/state_machine**：无。
- **写库收敛**：不触碰任何 INSERT/UPDATE/DELETE，无 Model 改动，无迁移。
- **前端不直连数据库**：不改前端产品代码。
- **结论**：不触碰任何红线。

## Risks / Trade-offs

- **[文案对拍天然脆]**（改文案要同步改测试）→ 这是设计意图：两侧用户看到同一句话本就是硬约束；
  失败信息会直接给出两侧差异，同步成本可见。
- **[测试可能"总是绿"而无人知道它有效]** → D5 的手工红验证 + 例外等式（D2）使"静默忽略"不可行。
- **[误把非表单的 `.length` 判断纳入]** → 见 D3 的显式成本说明；失败信息会指出具体条目。
- **[例外集合腐化]** → 每条强制带理由；且例外必须是**当前真实存在的差异**（多一条少一条都会失败）。
- **[与 `auth-registration` 的边界混淆]** → 后者的规格只管用户名唯一性与 409；本能力只管输入格式校验，
  两者不重叠（409 的文案「用户名已存在」不在本守护的文案集合内，因为它是写口错误而非输入格式校验）。

## Migration Plan

1. 新增对拍守护并运行 —— 预期绿（两侧当前一致）。
2. 手工改一条前端文案，确认守护失败并列出差异，然后还原。
3. 更新 `tests/AGENTS.md`。
4. 跑门禁。

**回滚**：改动仅为一个新增测试模块与一处文档；`git revert` 即可，无产品代码影响。
