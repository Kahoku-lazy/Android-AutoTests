## Context

- 死代码的来源是明确的：上一组变更删除了 18 条被 router 遮蔽的 legacy 路由，而它们的视图模块没有一起删。
  所以本变更是**清理自己造成的混乱**，不是顺手改相邻代码。
- 「无引用」的判定必须排除同名不同物：`apps/element_locator/api.py` 里存在同名的写原语
  （`create_web_element` / `delete_flow` / `batch_import_web_elements` / `create_api_endpoint`），
  `views_drf.py` 调用的是 `api.create_web_element(...)`。若只按符号名 grep 会误判为"仍被引用"。
- 两个模块（`views_web_groups` / `views_api_assets`）看起来"有人用"，实际只是被护栏测试 import 着，
  而那个测试断言的是**这些符号不存在** —— 测试本身就是"该模块已无实质消费者"的证据。

## Goals / Non-Goals

**Goals**：删掉方案 B 遗留的全部死视图代码，让"唯一实现"这个事实在文件层面也成立。

**Non-Goals**：改路由、改行为、动仍在用的视图模块。

## Decisions

**D1：四个模块一起删，而不是只删用户点到的那两个。**

判定标准是同一个（删除 legacy 路由后无引用者），四者都满足；只删两个会留下同性质的不一致。
另两个所需的额外工作仅是调整一个护栏用例的断言方式（从"符号不存在"改为"模块不存在"，断言更强）。

**D2：护栏用例改为断言模块不存在。**

原用例 import 模块并检查 `not hasattr(module, name)`。模块删除后 import 即失败，
故改为 `importlib.util.find_spec` 判定模块不存在 + 保留 `api.__all__` 中写原语的断言。
这样护栏的强度不降反升：它同时守住"模块不再回来"。

**D3：接口文档的修正是必需的，不是附加项。**

`API-元素定位.md` 现在同时陈述三件已经不成立的事（legacy 路由存在、两种信封可共存、靠中间件保证）。
留着会让后来者据文档写出错误调用。

## Risks / Trade-offs

- [误删仍在用的代码] 已逐个符号排除自身定义后核实引用数为 0；`views_drf.py` 的调用点是 `api.*` 而非模块内函数
- [护栏变弱] D2 使断言更强（模块级），不存在变弱
- [文档改动范围] 只改与该死代码直接相关的两处（信封说明与尾斜杠说明），不重写整篇接口文档

## Migration Plan

无需迁移。删除的代码在删除前已不可达（无路由、无 import）。回滚 = 还原 4 个文件与 1 处函数。
