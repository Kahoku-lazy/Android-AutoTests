## Context

现状：密码的首尾空白由**接口层**去掉（登录密码字段沿用字段默认行为），注册侧另有**显式去掉**，前端登录出口**不自行去掉**、注册出口会去掉。三处实现分布在前后端，彼此没有代码级联系；「两侧最终口径一致」目前只是巧合，没有任何默认测试守护。动机与范围见 `proposal.md`。

约束：

- **行为已被测试定格** —— TC-LOGIN-016 按实测行为断言「密码前后带空格 → 200」。本次不得改变任何运行时行为。
- **守护必须零外部依赖** —— `tests/AGENTS.md` 要求契约对拍测试不启服务、不连库、不联网，留在默认单元套件内。
- **既有范式** —— 同目录已有 `test_auth_validation_parity.py`（文案与阈值对拍，读源码）、`test_auth_frontend_contract.py`（网关公开路径 + 前端 DTO，读源码 + import 项目代码）。本设计的守护应当沿用这两个范式，不自创第三种。

## Goals / Non-Goals

**Goals:**

- 让「密码首尾空白在两侧都被去掉」成为被默认单元测试断言的规格不变量。
- 让注释与规格不再陈述与代码相反的事实。
- 明确记录「账号口径两侧有意不同」及其理由，使这条不对称不再像疏漏。

**Non-Goals:**

- 不改运行时行为、接口形状、状态码、DB 与缓存写入。
- 不统一账号的空白口径。
- 不覆盖密码复杂度、哈希、限流等其它安全面（限流已单列为已知缺口）。
- 不在本设计里处理审查中发现的其它问题（错误码靠文案判定、`data.data` 未判空等）。

## Decisions

### D1 — 扩展既有对拍文件，不新建

守护落在 `tests/graybox/unit/test_auth_validation_parity.py`。该文件已是「登录/注册校验口径对拍」的登记处，规格也指向它；另开文件会让同一契约有两个家，读者容易漏看其中一个。

备选：新建 `test_password_normalization.py` —— 否决，理由是分散登记。

### D2 — 后端侧断言真实对象，前端侧沿用读源码

两侧的可达性不同，用不同手段，但都不依赖运行中的服务：

- **后端侧**：直接 import `LoginSerializer` / `RegisterSerializer`，断言
  1. 登录密码字段的首尾空白去除处于开启状态、账号字段处于关闭状态（即账号原样）；
  2. 登录密码字段对带首尾空白的输入，返回的是去掉后的值；且**内部空白原样保留**（含制表符、换行）；
  3. 注册侧对密码的去除仍然生效（对同一份带首尾空白的入参，产出已去空白）。
- **前端侧**：沿用既有的读源码方式，断言登录出口不自行去除密码、注册出口会去除 —— 前端是 TS，Python 侧只能读源码，这正是 `test_auth_frontend_contract.py` 已确立的范式。

理由：后端可 import，就断言**真实行为**而不是源码字面量 —— 有人把字段换成自定义 Field 并自行处理空白时，行为断言仍成立，正则断言会失效。前端没有 Python 侧运行入口，只能读源码。

备选：两侧都用读源码正则 —— 否决，后端侧会把「实现方式」当成契约，重构即误报。

### D3 — 规格落在 `auth-form-validation`

该能力的定位正是「两侧必须保持一致的部分、允许不同的部分及其理由」。空白归一化属于其中一类，与既有「文案与数值阈值一致」要求同源。

备选：放进 `auth-session` —— 否决，该能力只讲会话与令牌生命周期，不涉及表单输入归一化；放进去会让后来者去错地方找。

### D4 — 注释改为陈述分工，而不是陈述「一致」

原注释的问题是它用「与后端一致」来解释前端为什么不 trim，而后端实际会 trim，方向相反。改后只陈述分工：前端不 trim，去空白由接口统一负责，与注册侧最终口径一致。避免再次把「谁在什么时候 trim」写成一句含糊的等价声明。

## 模块防火墙自检

- **跨 App import**：无新增。改动只落在前端 composable 的注释、`tests/graybox/unit` 与规格；`apps/accounts` **零改动**。
- **写库收敛**：本设计不含任何 INSERT / UPDATE / DELETE，也不触碰 `api.py`。
- **前端不直连数据库**：不涉及。
- **新跨模块依赖**：无。测试侧新增的 import 是 `apps/accounts/serializers.py`，属既有被测对象，不构成新的运行期依赖。

## Risks / Trade-offs

- [规格把「账号不 trim」一并钉住，将来产品若想统一成 trim 会先撞测试] → 这正是意图：口径变更必须走一次显式评审，而不是被顺手改平。
- [前端侧读源码断言对文件改名、函数搬迁敏感] → 沿用既有做法：设提取量下限，提取不足即失败，而不是静默通过（两个空集合对比也会「相等」）。
- [后端侧断言真实对象，若有人换成自定义字段并自行处理空白] → 行为断言仍会通过（因为断言的是行为而非实现），符合设计意图。
- [两条路径都是「读源码/读对象」，无法覆盖真实 HTTP 链路] → 真实链路由 `tests/api` 的 TC-LOGIN-016 与 TC-REG-021/022 覆盖，本守护只负责「口径是否漂移」，两者分工互补。

## Migration Plan

无 —— 不涉及数据、接口或部署变更，回滚即放弃本变更的文档与测试改动。
