## Context

- 今日采集编排（`apps/device_inspector/service.py:84-135`）只把**展示裁剪后**的 elements 与 actionable 返回；`api.py:73` 存入 `dump_json`，未裁剪层级用完即丢。
- 快照详情（`api.py:391-411`）把 `dump_json.elements` 原样返回（含 XPath 候选），前端与「保存到元素定位」都消费它。
- 展示裁剪的唯一实现在 `algorithms/xpath.py:204-232`（`trim_hierarchy`），本单不改。
- 分层规则由前置变更落在 `algorithms/element_layers.py`（纯函数）；本单只调用，不重复实现判据。
- 体积实测（示例页 140 节点 / 保留 95）：全量节点不含候选 **58.5 KB**、含主定位 75.0 KB、含全部候选 134.6 KB。
- 存量数据：309 条历史快照（both 231 / dump 67 / ocr 11）没有全量索引，原始 XML 未落盘，无法回溯补齐。

## Goals / Non-Goals

**Goals:**

- 让「被展示裁剪丢弃的元素」在后端可见：快照落全量节点索引。
- 提供分层查询端点与筛减/分页能力，使前端只需渲染。
- 历史快照可读不报错，并如实标注数据完整度。

**Non-Goals:**

- 不改展示裁剪规则、不改 6 层分区端点与其前端消费。
- 不把分层结果落库（避免两处真相源）。
- 不做历史快照回溯补齐。
- 本单不含前端改动。

## Decisions

**D1 全量索引作为快照的独立字段，而非塞进 `dump_json`。** `dump_json` 已被快照详情、前端渲染与「保存到元素定位」多处消费，把未裁剪节点混进去会迫使所有消费方自行过滤。备选：塞进 `dump_json.nodes` → 否决（污染既有契约）；备选：新建一对一表 → 否决（只带来 join 与级联维护成本，无查询收益）。

**D2 索引不含定位候选。** 候选是节点集合的纯函数输出（`gen_xpath_candidates`），查询时重算即可；含候选体积为 2.3 倍。备选：连候选一起落库换查询速度 → 否决（体积换来的收益不足以抵消「两处可漂移的数据」）。

**D3 分层即时计算、不落库。** 分组与主定位都可由索引重算；落库会形成第二处真相源。备选：落 `layers_json` → 否决。

**D4 筛减同时支持服务端与前端本地，但判据必须同源。** 服务端参数作为深链接与大页面的兜底，前端本地筛保证切分组零延迟；两侧的分组、细类、稳定性判据 MUST 全部来自算法层，MUST NOT 在 Django 侧重写一套。

**D5 历史快照降级并标注来源。** 无索引的快照按「仅保留集」返回，响应标注数据来源为降级集；MUST NOT 伪造「被裁元素」（索引缺失时无法得知）。备选：对无索引快照返回 404 → 否决（会让 309 条存量快照不可用）。

**D6 端点沿用现有 inspector 路由风格。** `GET /api/inspector/snapshots/{id}/layers/`，与既有 `…/analyze/`、`…/save-elements/` 同构；归属过滤沿用 `created_by`（与详情、分区端点一致）。

**D7 分层响应只回「主定位」，MUST NOT 回候选全量；候选按需单独查询。** 理由有三：① 候选全量使响应从 82.8 KB 涨到 134.6 KB（实测同一页 140 元素）；② 更关键的是**消除第二处主定位规则**——页面当前自己在一堆候选里挑（`StructureAnalysisPanel.vue:188-197` 的 `XPATH_PRIORITY` 与 `bestXPath()`），与算法层的口径不一致（顺序不同，且会把位置型候选当作最佳），响应只给一条算好的主定位即可让判据回到单一真相源；③ 保存到元素定位**不需要**前端传候选——既有实现是后端从快照的节点数据里取（`api.py:284-296`），前端只传元素下标与别名。备选：保留候选全量以省一次按需请求 → 否决（体积与两套规则的成本高于偶尔一次按需请求）。按需候选端点不在本单范围，待出现「界面上挑候选」的需求再开。

**D8 既有快照详情端点本单不动。** 它仍返回带候选的元素集；其前端消费者在后续前端变更中改为消费分层端点，之后该端点的去留另议（见 Open Questions）。

## 模块防火墙自检

- **写库**：仅 `apps/device_inspector/api.py` 写本模块自有表 `di_snapshots`；无跨 App 写。
- **跨 App 读写**：本单不新增跨 App 依赖（不需要读元素定位的任何表）。
- **分层 View**：只解析入参与封装信封，编排下沉 `api.py` / `service.py`。
- **算法层调用**：`apps/` 调 `algorithms/element_layers` 是合法方向（上层调下层纯函数）；反向依赖不存在。
- **前端**：本单无改动，无新增 HTTP 出口。

## Risks / Trade-offs

- [每条快照体积上升约 58.5 KB] → 已是最小可用形态（不含候选）；若后续需要，可对索引做字段裁剪或分片存储。
- [主定位需要候选，导致每次查询重算候选；`gen_xpath_candidates` 对每个元素都重建一次索引，整体是 O(n²)] → 当前页面规模（百量级节点）为毫秒级；节点数上到千量级时需改为「只对筛减后的结果算主定位」或缓存索引，任务里已按「先筛减、后算主定位」的顺序实现。
- [历史快照与新增快照的数据完整度不同，前端可能误判] → 响应显式带来源标记与是否含被裁元素；前端按标记提示。
- [索引与展示集不一致（索引全量、dump_json 仍为裁剪集）] → 两者职责写进 spec 与模型注释；分层查询只读索引，详情端点只读 dump_json，互不推断。

## Migration Plan

- 新增字段可空且默认空列表，迁移无需数据回填，可在线上直接执行。
- 发布顺序：先落索引（采集端写入）→ 再暴露分层端点；端点上线前不依赖索引存在（有降级路径）。
- 回滚：下线端点（前端回退到既有详情端点）+ 反向迁移删除字段；采集端回退到只写展示集。
