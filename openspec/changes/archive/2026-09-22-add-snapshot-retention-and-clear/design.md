## Context

- 现状（真机库）：快照 314 条 / 5 个 `created_by`（`'1'` 276、`''` 31、`'2'` 5、`'331'` 1、`'layers-acceptance'` 1）；媒体目录 `shots` 1341 文件、`thumbs` 32117 文件 / 317 目录。
- 列表接口：`api.list_snapshots(user_id, offset, limit)` 按 `-created_at` 倒序；视图把 `limit` 钳到 100；前端 `store.fetchSnapshots` 传 `(0, 100)`，抽屉在「总数 > 已拉取数」时提示「已显示最近 N 条」。
- 删除单条的媒体保全逻辑已在 `api.delete_snapshot`（判定 `_media_referenced` → 被引用则保留文件 → 删记录），并有 6 条集成用例守着（`tests/graybox/integration/test_inspector_snapshot_media.py`）。
- `element_locator` 侧保存页面时已把媒体**复制**到自有目录（`locator/pages/<id>/`），页面的 `snapshot_id` 只是普通整数字段、无外键；但历史页面里仍有 2 个页面、16 个元素指向 `inspector/` 路径 —— 因此淘汰与清空必须走「被引用则保留文件」的判定。
- `created_at` 为 `auto_now_add`；同一毫秒内的多条靠 ID 兜底排序。

## Goals / Non-Goals

**Goals:**

- 每个用户的快照记录收敛到最多 10 条，且「最多十条」在接口层也成立（列表不会返回超过 10 条）。
- 提供一键清空入口，语义与单条删除一致（归属隔离 + 媒体保全），并可一次删除全部。
- 存量按用户选择一次性清空，减少记录与孤儿媒体。

**Non-Goals:**

- 不做按时间过期（如「保留 7 天」）、不做按设备/包名分组保留、不做容量配额。
- 不改单条删除的既有语义与媒体判定。
- 不清理与任何快照记录都无关的历史孤儿媒体（本次只删「记录所属」的媒体）。
- 不动元素定位侧的记录与副本。

## Decisions

**D1 保留上限落在「采集成功后淘汰」，而不是查询时过滤。** 用户要的是「自动删除时间最早的一条」；查询时过滤只会隐藏数据、磁盘照样涨。备选：只在列表侧封顶 → 否决（记录与媒体仍无限增长）。

**D2 列表接口同时封顶为上限。** 存量尚未清理、或历史用户数据尚未回落时，「最多显示近十条」必须在接口层成立，不能只靠删除。封顶值取同一个常量，避免两处口径。

**D3 淘汰与清空必须复用 `delete_snapshot` 的媒体判定。** 把「判定 + 删文件 + 删记录」抽成一个内部帮手，`delete_snapshot` / 淘汰 / 清空 三处共用；MUST NOT 在淘汰路径上直接 `queryset.delete()`（会绕过引用判定，删掉仍被引用的媒体）。

**D4 清空用独立路径 `DELETE /api/inspector/snapshots/clear/`。** Django 的 `path()` 不按方法分发，若与列表共用 `snapshots/` 会让 GET 视图吞掉 DELETE（405）。同路径双视图不可行，故沿用本模块既有的动作后缀风格（`/delete/`、`/save-elements/`）。备选：把列表视图改成 `["GET", "DELETE"]` 双方法 → 否决（一个视图承担两种语义，且与「View 只分发」的单一职责相悖）。

**D5 清空返回删除条数。** 「清空了几条」是用户唯一能核对的反馈；空列表返回 0 而不报错（幂等）。

**D6 前端不做逐条删除循环。** 一键清空 MUST 调一次清空端点：逐条循环会让 N 条记录产生 N 次请求、N 次列表刷新，且中途失败会留下「删了一半」的状态。

**D7 抽屉里「已显示最近 N 条」提示随封顶移除。** 列表最多 10 条、总数也 ≤ 10，该分支恒不成立；留着就是死代码与误导。这是本变更造成的后果，故一并清理。

**D8 存量一次性清空按用户逐个走清空端点。** 复用刚被测过的路径，而不是写一条 `queryset.delete()` 或数据迁移：媒体判定与归属隔离直接复用，且清理结果可被同一批用例覆盖。

**D9 淘汰失败只告警、不回滚采集。** 采集已经落库成功之后，淘汰只是附带的维护动作；若引用判定或文件清理抛错并向上传播，前端会看到「获取失败」而记录其实已经存在（界面状态与库不一致）。故淘汰包在 try/except 中、以 `logger.exception` 留痕。代价：极端情况下会短暂多留几条快照，等下次采集再收敛。备选：让异常向上传播 → 否决（把一次成功的采集报成失败）。

## 模块防火墙自检

- **写库**：淘汰与清空都经 `apps/device_inspector/api.py` 写本模块自有表 `di_snapshots`；无跨 App 写。
- **跨 App 读**：`_media_referenced` 只读 `element_locator` 的 `Page` / `Element`（既有允许方向），本次不扩大。
- **View**：新增清空视图只解析身份 → 调 `api` → 封信封；不直接 ORM。
- **算法 / 引擎**：不涉及。
- **前端**：新增一次 `DELETE` 调用，仍经 `api.ts` → `shared/api-client`（唯一 HTTP 出口）。

## Risks / Trade-offs

- [存量一次性清空不可逆，会删除 314 条记录与其中未被引用的媒体] → 用户已明确「全部清掉」；被元素定位引用的 2 个页面 / 16 个元素的媒体按既有判定保留，页面回看不 404。清理前记录条数与文件数，事后可核对。
- [淘汰发生在采集成功之后，用户「正在查看」的历史快照可能已被淘汰] → 采集后前端本来就会刷新列表与分层数据；被淘汰的快照若仍在展示，界面状态由下一次刷新覆盖。
- [列表封顶 10 条后，`total` 与 `items` 的关系在存量未清理时会出现「total 276 / items 10」的反常组合] → 正是需要一次性清理的理由；清理后两者一致，且「截断提示」不再需要。
- [每个用户保留 10 条，会让同一设备的历史对比变短] → 用户明确要「最多近十条」，若后续需要更长历史再调常量。

## Migration Plan

- 无 schema 变更、无迁移文件：保留上限是运行时策略（常量），清空是新增端点。
- 发布顺序：先落后端（淘汰 + 封顶 + 清空端点）并跑通门禁 → 再落前端入口 → 最后执行存量一次性清空。
- 回滚：把保留上限常量调大或改为不淘汰 + 前端保留单条删除即可；已清空的存量不可恢复（用户已确认）。

## Open Questions

- 是否需要把「保留条数」做成可配置项（当前按用户给定值硬编码为常量 10）。
- 是否需要定期清理「无任何快照记录指向」的历史孤儿媒体（本次不做）。
