## Context

动机与范围见 proposal.md，此处只写方案所需的现状与约束。

现状（2026-09-23 盘点，均为查证事实）：

- `.github/workflows/ci-phase1.yml` 现有步骤：Django system check、ruff format --check、ruff lint、Vitest P0+P1、Vite build、Prettier check、硬编码凭据扫描、模块边界检查、Vue 文件体积检查、硬编码假数据检查、大段内联样式检查。
- 该 workflow 中 `eslint`、`vue-tsc`、`typecheck` 出现次数均为 **0**；`frontend/package.json` 中这两个命令存在但无人执行。
- Prettier 的 CI 检查范围为 `src/**/*.{vue,js,css}`，不含 `.ts`；而本地 `npm run format` 的 glob 含 `.ts`。
- ruff 的 CI 范围为 `apps/ config/ gateway/ shared/ models/`，不含 `engines/`。
- 约束一：存量代码未经这四道检查，直接拦截会让 CI 长期红。历史教训见已归档变更 `2026-09-15-restore-repo-lint-gate`——命令常年红灯等于门禁形同虚设。
- 约束二：CI 原只监听 `main` / `Kahoku` / `Aaron` / `feat/*` / `fix/*`，本变更把 `eevog` 纳入该名单（见决策 6），否则新增检查在当前工作分支上无法被观察。

## Goals / Non-Goals

**Goals:**

- 让四道缺口检查在 CI 中**被执行并可见**，从而拿到存量问题的准确基线。
- 接入过程对既有拦截型检查零影响：现有绿灯/红灯判定不变。

**Non-Goals:**

- 不把任何检查转为拦截（转拦截是后续独立变更）。
- 不清理存量违规（不在本变更范围）。
- 不修改 eslint / prettier / tsconfig / ruff 的规则内容本身。
- 不改动 PR 的目标分支名单（仅改 `push` 分支名单）。

## Decisions

### 决策 1：以「仅警告不拦截」接入，而非直接拦截

步骤内捕获失败输出并输出摘要，步骤自身以退出码 0 结束，同时在日志中打 `::warning::` 注解；不使用 `continue-on-error` 单独承载。

- 理由：GitHub Actions 的 `continue-on-error: true` 会让步骤在 UI 上显示为失败但作业继续，容易被误读为「CI 坏了」；显式 `|| echo "::warning::..."` 让步骤保持绿色、告警进入注解区，语义更准确。
- 备选一：直接拦截。被否——存量未清，会造成 CI 长期红，重演 `2026-09-15-restore-repo-lint-gate` 记录的问题。
- 备选二：不接 CI，只在本地按需运行。被否——无人执行正是本次要解决的问题。

### 决策 2：四道检查一次性全接入

- 理由：一次运行即可得到完整基线，避免分批接入导致基线口径前后不一致。
- 备选：按风险分批。被否——四者均为只读检查，一次接入无额外风险。

### 决策 3：告警需带可统计的信息

步骤在失败时输出命令名称与输出末尾若干行，便于从日志中读出「哪一类问题、多少条」。

- 理由：转拦截的决策依赖基线数字，只输出「失败」而不输出规模无法支撑决策。
- 备选：仅打印原始全量输出。被否——日志过长会淹没信息，反而降低可读性。

### 决策 4：不触碰现有步骤的判定语义

现有 ruff format / ruff lint / prettier check / vitest / vite build 与 4 个自定义门禁保持原样。

- 理由：本次只**扩大可见范围**，不改变门禁强度；混入判定变更会使基线不可比。

### 决策 5（实现期补充）：扩大范围以「新增独立警告步骤」落地，而非改动既有步骤

实施中发现 tasks 2.3 / 2.4 的字面写法（把既有步骤的 glob / 作用域直接扩大并改为告警形式）与决策 4 冲突：既有 Prettier check（vue/js/css）与 ruff 步骤是**拦截型**，一旦改成告警形式，等于把已生效的门禁降级；而若保持拦截又只扩大范围，则 `.ts` 与 `engines/` 的存量问题会立刻阻断构建——正是本变更要避免的。

因此落地方式为：**既有拦截型步骤一字不动**（glob、作用域、判定全部保持），新增 4 个独立的告警型步骤承接扩大后的范围：

- `Ruff format check engines (warning only)`、`Ruff lint engines (warning only)`
- `ESLint (warning only)`、`TypeScript check (warning only)`、`Prettier check ts (warning only)`

- 结果等价：`engines/`、`.ts`、eslint、vue-tsc 均被 CI 覆盖且只警告；既有门禁强度零变化。
- 依据：决策 4「不触碰现有步骤的判定语义」，以及 tasks 3.1「确认无任何既有步骤由绿变红或由红变绿」。

### 决策 6：把 `eevog` 纳入 CI 的 push 触发名单

- 理由：`eevog` 是当前实际工作分支，此前不在名单内（该分支历史 CI 运行次数为 0），导致本次新增的检查在该分支上永远无法执行，「已接入」无法被验证，问题只能靠本地手跑。纳入名单后，推送即自动执行，验证路径与日常路径一致。
- 代价：`eevog` 每次推送都会触发一次 workflow（约数分钟）。由于新增步骤均为告警态，结论仍由既有拦截型检查决定。
- 备选一：临时建 `feat/*` 验证分支后删除。被否——验证路径与日常路径不一致，且每次改动都要重复这套仪式。
- 备选二：保持名单不变、仅本地手跑。被否——这正是本变更要解决的「规则存在但无人执行」。
- 边界：仅改 `push` 的 `branches`，`pull_request` 的目标分支名单保持 `main` / `Kahoku` 不变。

### 决策 7（实现期补充）：验证载体由临时分支改为直接推送 `eevog`

- 理由：决策 6 生效后，推送 `eevog` 即可触发并观察全部检查，不再需要临时分支与随后的删除动作。
- 影响：tasks 第 4 组的验证载体由 `feat/ci-warning-gates` 改为 `eevog`，不再产生需要清理的临时远端分支。

### 决策 8（实现期补充）：建议性检查独立成 job

- 触发原因：本地实测发现**既有拦截型 `Prettier check` 在当前分支已失败**（109 个 vue/js/css 文件不符合格式）。GitHub Actions 在步骤失败后会**跳过同一 job 内的后续步骤**——把告警步骤放在拦截型步骤之后，恰好在最需要它们的时候（拦截门禁变红时）被跳过，可见性归零。
- 结论：5 道建议性检查移入独立 job `advisory-checks`，与拦截型 job 并行、互不影响；该 job 内所有步骤退出码恒为 0，因此其结论恒为绿。
- 备选：给告警步骤加 `if: always()`。被否——仍与拦截型 job 耦合（作业整体依旧显示失败），且无法独立重跑。
- 附带收益：与拦截型 job 并行，不叠加其耗时。
- 记录：既有拦截型 Prettier check 当前为红属**存量事实**（109 个文件），不在本变更范围内（本变更不修存量）。

## 模块防火墙自检

本变更只改 CI workflow 文件，不涉及任何 Python / 前端业务代码：

- 跨 App import：不涉及。
- 跨 App import service / runner / consumer / state_machine：不涉及。
- INSERT / UPDATE / DELETE 收敛到 api.py：不涉及（无任何写库行为）。
- 前端不直连数据库、仪表盘不做写操作：不涉及。

无新增跨模块依赖。

## Risks / Trade-offs

- [仅警告的检查长期无人处理] → 在 tasks 中记录首次运行的基线数字，并在 design 与 proposal 中明确「转拦截」为后续独立变更，避免警告永久静默。
- [新增 2 个步骤拖长 CI] → job 超时为 10 分钟，eslint 与 vue-tsc 为增量耗时；若逼近超时，可将两者拆到并行 job（属于后续优化，不在本变更）。
- [vue-tsc 在非严格配置下仍可能报出大量既有错误] → 正是「仅警告」模式要度量的对象；基线出来后由后续变更决定收敛路径。
- [ruff 范围扩到 engines/ 后暴露既有问题] → 该目录 2026-09-23 全量本地检查为通过，预计无新增噪音；若非空，同样只警告。

## Migration Plan

- 生效条件：改动进入被 CI 监听的分支（`main` / `Kahoku` / `Aaron` / `feat/*` / `fix/*`）后自动生效，无需其他部署步骤。
- 验证方式：在匹配 `feat/*` 的临时分支上推送，观察 4 道新增步骤出现在运行记录中且作业结论不受其影响。
- 回滚：删除新增步骤即可，单文件纯增删，无状态残留。

## Open Questions

- 四道检查何时转为拦截：取决于首次基线的规模，属后续独立变更的决策，不影响本变更的设计与任务拆分。
- CI 侧的实际执行验证：因账号付款问题导致作业未分配到运行器（`steps=0`），无法在 CI 侧确认；已改由本地门禁（变更 `2026-09-23-add-local-gate-runner`）验证同一批检查的执行与结论。账号恢复后推送一次即可补齐，属运维动作，不需要改动本变更的代码。
