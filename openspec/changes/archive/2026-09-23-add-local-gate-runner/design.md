## Context

动机与范围见 proposal.md，此处只写方案所需的现状与约束（均为 2026-09-23 本地实测）。

- `run.py` 现状：380 行 argparse CLI，命令表为 `{"start" / "stop" / "restart" / "status" / "logs"}` 的字典分发；已有 `_run()` 辅助函数（`subprocess.run`，`timeout=5` 硬编码，面向短命令如 `netstat`）。
- `tools/` 目录**不是** Python 包（无 `__init__.py`），现有脚本以 `python tools/xxx.py` 方式调用。
- 可复用的既有检查实现：
  - `python tools/gen_arch_stats.py --check-boundaries` → 本地实跑通过（退出码 0）
  - `python tools/gen_arch_stats.py --check-frontend` → 本地实跑失败（`CaseBreakdown.vue` 528 行 > 500）
- 工具可用性：`python -m ruff`（0.15.20）、`node`（v24）、`npm`（11.6）均在位；`frontend/package.json` 已有 `lint` / `typecheck` / `test` / `format` 脚本可直接复用。
- 约束：CI 的检查项散落在 workflow 的内联 shell 与内联 Python 中，本地无共享实现；本次要把它们收敛到一处。

## Goals / Non-Goals

**Goals:**

- 一条命令在本地跑完全部检查，结论与 CI 同源、可比对。
- 检查内容有唯一真相源，后续新增检查只改一处。
- 阻塞 / 告警分级与 CI 一致，避免本地比 CI 更严或更松。

**Non-Goals:**

- 不做自动修复（`--fix`）：本变更只负责"发现问题并如实报告"。
- 不改动 CI workflow，不让 CI 改调本脚本（后续独立变更）。
- 不清理任何存量违规（prettier 109 文件、`CaseBreakdown.vue` 超限等）。
- 不引入第三方依赖、不做并行执行与结果缓存。

## Decisions

### 决策 1：检查逻辑放 `tools/check_gates.py`，`run.py check` 委托执行

- 理由：`run.py` 已是 380 行的进程/端口管理器，检查逻辑塞进去会同时伤害两者的可读性；且检查清单需要被 CI 复用，独立脚本才有复用价值。
- 落地方式：`run.py` 的 `check` 分支以子进程方式调用 `sys.executable tools/check_gates.py`，把退出码原样传出。`tools/` 非包，故不走 import。
- 备选一：全部写进 `run.py`。被否——单文件超 500 行，且与"检查内容唯一真相源可被 CI 复用"冲突。
- 备选二：放进 `shared/`。被否——`shared/` 是运行期共享代码，检查脚本属开发期工具，`tools/` 才是既有归属。

### 决策 2：检查清单以数据结构声明，执行器统一

每项检查声明为：名称 · 命令 · 工作目录 · 级别（阻塞/告警）· 失败时输出的摘要行数。执行器遍历清单统一处理输出与退出码。

- 理由：十余项检查如果各写一段流程，必然出现重复的错误处理与输出格式；声明式清单让"新增一项检查"变成加一行数据。
- 备选：每项写一个函数。被否——重复代码多，且与"最少代码"冲突。

### 决策 3：环境缺失（命令不存在）判为失败，不静默跳过

若 `npm` / `ruff` / `node` 不存在，该项标记 FAIL 并输出明确原因（如"未找到 npm"），而非 SKIP 后继续。

- 理由：`AGENTS.md` 代码规范要求"错误不许静默忽略"；而"静默跳过"恰好会制造"检查都过了"的假象——这正是本变更要解决的病根（CI 里步骤从未执行却显示为一次运行）。
- 备选：缺失即 SKIP。被否——会重演"看起来有门禁、实际没跑"的问题。

### 决策 4：内联在 CI 里的三段脚本按原规则在 Python 内重写，不改判定口径

- 涉及：硬编码凭据扫描（CI 内联 bash `grep` 五条规则）、硬编码假数据检查（CI 内联 `grep -rnE`）、内联样式体积检查（CI 内联 `python3 -c`，阈值 120 行）。
- 理由：这三项目前只存在于 workflow 文本中，本地无法复用；重写为等价 Python 是让"本地 = CI"成立的必要代价。
- 约束：**逐条对齐原规则的正则与阈值**，不放宽也不收紧；实现时把 CI 原文作为对照，任何差异都要在 tasks 中显式记录。
- 备选：本地不实现这三项，只实现工具链检查。被否——会在本地留下与 CI 不对等的空洞。

### 决策 5：输出格式固定为「一行一项 + 失败摘要 + 结尾汇总」

- 理由：十余项检查的全量输出会淹没关键信息；固定格式便于扫读，也便于后续让 CI 复用同一输出。
- 备选：直接透传各工具原始输出。被否——无法一眼看出"哪几项没过"。

### 决策 6：退出码只由阻塞项决定

- 理由：与 CI 的阻塞/告警分级保持同一语义；告警项若参与退出码，就成了变相拦截，与本变更的"仅报告"定位矛盾。

## 模块防火墙自检

本变更只新增开发期工具脚本与一个 CLI 子命令，不涉及业务代码：

- 跨 App import：不涉及（新脚本不 import `apps/`）。
- 跨 App import service / runner / consumer / state_machine：不涉及。
- INSERT / UPDATE / DELETE 收敛到 api.py：不涉及（无任何写库行为）。
- 前端不直连数据库、仪表盘不做写操作：不涉及。

无新增跨模块依赖。

## Risks / Trade-offs

- [本地检查与 CI 可能随时间长歪] → 检查清单集中在一处，且每项注明对应的 CI job；后续让 CI 调用同一脚本即可消除（Non-Goal，另立变更）。
- [首次运行红灯会被误读为本变更引入的问题] → 在 proposal 的 Impact 与脚本结尾汇总中明确区分"阻塞项失败"与"存量红灯"，并列出已知存量项。
- [重写三段内联脚本时判定口径漂移] → tasks 要求逐条对照 CI 原文并逐条记录；执行时以 CI 原文为准。
- [全量执行耗时较长（含 `npm test`、`vite build`）] → 不做并行与缓存（Non-Goal），耗时换实现简单；必要时后续再加。

## Migration Plan

- 生效方式：合并后即可使用，无需部署步骤。
- 验证：`python run.py check` 能跑完并给出与 proposal 中记录一致的基线结论。
- 回滚：删除 `tools/check_gates.py` 与 `run.py` 的 `check` 分支即可，无状态残留。
