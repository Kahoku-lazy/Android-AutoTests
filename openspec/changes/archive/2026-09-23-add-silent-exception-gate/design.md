## Context

动机见 proposal.md。现状与约束（2026-09-23 实测）：

- 全仓扫描 179 个 `.py`（`apps/ config/ gateway/ shared/ engines/`，排除缓存与迁移）：处理器体为空的有 **18 处**——供应商产物 `skill-creator` 10 处、历史迁移 1 处、**项目自有 8 处**。
- 若把判定放宽到「无 raise、无日志、无注释」的全部处理器，命中 **183 处**——其中绝大多数是**合法的错误处理**：把异常转成 4xx/5xx 响应（`return JsonResponse(..., status=409)`）在 AST 上看既无 raise 也无日志调用。该口径不可用。
- 再收一层为「+ 直接返回默认空值」，命中 49 处（其中 31 处为 `return None/False/{}/set()` 形态）。
- 工具侧现状：`tools/check_gates.py` 已具备自定义门禁能力（`inline_style_gate` 即先例），且 `Gate` 支持 `blocking=False` 的告警级别。
- 约束：`ruff.toml` 明确排除供应商产物，理由写明"改了会在下次 skill 更新时丢失"——本检查必须沿用同一排除，否则会把不可维护的文件判为违规。

## Goals / Non-Goals

**Goals:**

- 让「错误不应默默忽略」成为可机械验证的检查：违规 = 处理器什么都不做且未说明理由。
- 项目自有违规清零，使该门禁具备转拦截的条件。

**Non-Goals:**

- 不改造「把异常转成 HTTP 错误响应」的合法处理（那是已处理，不是吞掉）。
- 不要求 `except X: return <默认值>` 逐处加注释（见决策 2）。
- 不改动供应商产物与历史迁移。
- 不在本变更内把门禁转为拦截（后续独立变更）。

## Decisions

### 决策 1：违规判定取「处理器体只有 pass/continue/break」这一最窄口径

- 理由：183 处 → 49 处 → 18 处的逐层收紧表明，只有"体为空"这一档不存在误报——它既没抛出、也没记录、也没有任何其它动作，是"默默忽略"的字面含义。
- 备选一：AST 上看"无 raise 且无日志"（183 处）。被否——会把 `return JsonResponse(status=409)` 这类合法错误处理全部误报。
- 备选二：再加"直接返回默认值"（49 处）。被否——见决策 2。

### 决策 2：「直接返回默认值」不判违规，作为已知未覆盖类别记录

- 事实：31 处 `except X: return None/False/{}/set()` 中，绝大多数是**契约化的未命中**（`DoesNotExist → None`、`Device.DoesNotExist → False`），调用方依赖该返回值分支，不是吞错。
- 代价评估：若判违规，需要为 31 处各加一行纯注释——注释不会改变任何行为，只是让检查变绿，价值低而噪音大。
- 处理：在 proposal 的 Impact 与本文档显式记录该类别**未被覆盖**，并留作后续独立变更的候选（若要做，正确路径是要求"返回值分支需有 docstring 或类型说明"，而非逐处注释）。
- 备选：先判违规再逐处清理。被否——与"规范只写可机械验证、且值得遵守的要求"取向不符。

### 决策 3：注释即"明确地选择忽略"的标记

- 理由：原则原文即"除非**明确地**选择忽略"；在代码里，注释是唯一能表达"这是有意为之"且不产生运行期成本的手段。日志与注释二选一即可通过，把"要不要留痕"的判断留给作者。
- 备选：必须写日志。被否——会污染热路径（如逐文件 `getsize`、adb 重试循环）且这些场景本就不需要运行期日志。

### 决策 4：排除供应商产物与迁移，与 `ruff.toml` 的分界保持一致

- 理由：一处排除规则在同一仓库内应只有一份定义；供应商产物的排除理由已在 `ruff.toml` 写明。历史迁移改了会破坏已应用的迁移记录。
- 备选：把 `skill-creator` 的 10 处也补注释。被否——下次 skill 更新即丢失，属无效功。

### 决策 5：先以告警级别接入

- 理由：与既有告警项（eslint / vue-tsc / prettier .ts / ruff engines）保持同一节奏，转拦截统一在后续变更中执行，避免逐个门禁单独切换导致状态难以追踪。

## 模块防火墙自检

本变更新增一个开发期检查并为 8 处异常处理器补注释：

- 跨 App import：不涉及（新增检查只做 AST 解析，不 import 业务模块）。
- 跨 App import service / runner / consumer / state_machine：不涉及。
- INSERT / UPDATE / DELETE 收敛到 api.py：不涉及（无写库行为）。
- 前端不直连数据库、仪表盘不做写操作：不涉及。

无新增跨模块依赖。

## Risks / Trade-offs

- [仅告警级，长期无人处理] → 存量已清零，门禁当前为绿；后续转拦截变更会将其变为强制。
- [注释沦为"为了让检查过"的形式] → 8 处注释均写明具体理由（幂等删除、可选元数据、重试后由调用方处理等），可被 review 判断真伪。
- [口径过窄，漏掉真正的吞错] → 31 处"返回默认值"确实未被覆盖，已显式记录；若后续发现真实吞错案例，按决策 2 的路径扩展规则。
- [AST 解析失败的文件被静默跳过] → 实现上把 `SyntaxError` 作为一条违规输出，不跳过。

## Migration Plan

- 生效方式：合并后 `python run.py check` 即包含该门禁（告警级），无部署步骤。
- 验证：单独运行该门禁 → 0 命中；`ruff check` / `ruff format --check` 覆盖被改文件；`python manage.py check` 通过。
- 回滚：删除门禁函数与其在清单中的登记即可，8 处注释可保留（无害）。
