## Context

`scanDeclarations(css)` 被两处消费：批 2（T0 主 token 的声明集合与逐条判定）与批 3（全仓自定义属性声明落点）。它的返回值是 `{ line, name, value }`，其中 `line` 是**块内相对行号**，批 3 用 `b.startLine + d.line - 1` 换算成文件行号——所以行号语义不能变。

原实现逐物理行匹配 `/--name\s*:\s*([^;}]+)/`，并要求匹配前缀（同一行 `--name` 之前的内容）为空或以 `{` / `;` 结尾（防 BEM 修饰符 `.x--danger:hover` 被误当声明）。

## Goals / Non-Goals

- Goals：跨行声明能进 `declared` 集合；行号语义不变；判定规则与阈值一字不改；门禁由红转绿。
- Non-Goals：不动 `tokens.css`；不新增/收紧任何规则；不把 `lint:styles` 接进总门禁或 CI；不重构脚本其余部分。

## Decisions

### D1：折叠跨行声明，而不是改令牌写法

把 `--font-body` 压成一行确实能让门禁变绿，但那行是 **104 字符**，超过 `frontend/.prettierrc` 的 `printWidth: 100` —— prettier 的 CSS 覆盖是拦截型门禁，下一次格式化就会把它打回多行，红点复发。所以修扫描器。

实现：逐行累积 buffer，遇到 `;`、`{`、`}` 收尾即视为一条逻辑行并 flush（选择器块、单行声明都自然断开），flush 时记录**起始行号**；对逻辑行跑原有正则与前缀规则。

### D2：注释收尾也必须断开

只做 D1 会让情况**更糟**：`tokens.css` 里大量声明前面跟着注释行，注释行不以 `;`/`{`/`}` 结尾，会被拼进下一条声明的 buffer；此时匹配前缀是注释文本，末尾既不是 `{` 也不是 `;` → 前缀规则把这条声明判成"非声明位置"而**漏登记**。实测一次性冒出 30+ 条 `--color-*` 假报"未声明"。

因此把 `*/` 作为第三种断开点（注释行不携带声明，收尾即 flush）。这与批 4 已有的做法一致——批 4 就是先把行内注释 strip 掉再判定，本单只是让批 2 的扫描器同样不被注释污染。

### D3：值语义变化的边界

折叠后跨行声明的 `value` 变成拼接文本（如字体族栈）。逐条核对会不会引发别的判定：

- G1：只对 `--color-*` 判色值，跨行声明里没有 `--color-*`（颜色原子全是单行）。
- G2 / G2b：`EMBEDDED_COLOR_RE` 只认字面量颜色；`tokens.css` 的跨行值（字体栈、`color-mix(...)`）不含字面量颜色 → 复合值登记数不变（仍 3 条）。
- G3：`MODULE_PREFIX_RE` 命中的模块前缀令牌都是单行 `var(...)` 组合，不受影响。
- 批 3：逻辑行只是把原本漏掉的声明补进来（**超集**），只会多抓不会漏抓；实测 0 违规。

### D4：用计数守恒验证"只多不少"

修复前后跑同一脚本对比批 2 计数：声明 339 → 340，颜色原子 98 → 98，复合值登记 3 → 3。差值恰好是 `--font-body` 一条，证明没有声明被折叠逻辑漏掉。

## Risks / Trade-offs

- 折叠算法对"值里出现 `;` 的字符串"无能为力（原实现同样如此），`tokens.css` 当前无此写法；若将来出现，会表现为该声明值被截断——属于已知边界，未在本单扩大处理。
- 批 3 / 批 4 首次真正跑完，理论上可能暴露此前不可见的存量违规（实测没有：批 3 0 违规、批 4 全通过）。若未来它们转红，属**新暴露的真问题**，不应回退本修复。

## Migration Plan

无迁移。脚本改动即时生效；`npm run lint:styles` 由红色转绿。
