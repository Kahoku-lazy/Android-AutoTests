## Context

- 页面流画布的节点实例上限声明在前端工作流模块的节点注册表里（`NODE_REGISTRY`，每类节点一个 `maxInstances`）：页面 10、起点 1、终点 5、弹窗 `Infinity`。上限判定集中在 store 的 `createNode`：按「画布上同类节点已有数量 ≥ 上限」拒绝，并把原因写进 `statusMessage`。
- 画布一次只承载一篇文档的图，节点是浏览器内存里的 JSON（与服务端 `config_json` 同构），因此上限是**每篇文档、前端单点**的约束，服务端不做节点数校验。
- 工具栏已有三处反馈惯例：起点、终点按钮在创建失败时把 `statusMessage`（或兜底文案）写进工具栏状态行；「+ 页面」缺了这一分支，顶格时点按钮没有任何可见变化 —— 这正是本次上报的观感来源。
- AI 侧读取页面流时另有截断（语义摘要最多 10 条跳转路径、深度 32），与本上限各自独立：提高画布上限不会自动提高 AI 的可见路径数。

## Goals / Non-Goals

**Goals:**

- 页面节点上限从 10 提升到 50，并把「顶格」这件事在界面上说清楚。
- 把四条节点容量边界（起点 1 / 页面 50 / 终点 5 / 弹窗不限）写成可测的契约，防止以后被顺手改动。
- 保证上限只拦「新增」，不影响存量文档的打开、显示与保存。

**Non-Goals:**

- 不在服务端加节点数校验（见 Decisions 2）。
- 不改 AI 语义摘要的路径条数与深度上限。
- 不改画布渲染方式（不做节点虚拟化）；50 个页面节点仍在同一张画布上直接渲染。
- 不改终点上限（保持 5）与起点上限（保持 1）。

## Decisions

1. **上限值取 50。** 由需求方拍板。备选：保持 10（现状，已被真实资产撞上，否决）；完全取消上限（画布节点数无界，自动保存 payload 与渲染开销无预警上限，否决）。50 相对当前最大真实资产（10）留出 5 倍余量，又不至于让单篇文档无界增长。

2. **上限仍只在前端注册表声明，服务端不校验。** 理由：上限是画布交互约束，不是数据契约。服务端若按 50 校验 `config_json`，会立刻打断两条既有写入路径 —— 导入 JSON 与 AI 生成页面流（写图工具直接编译节点，不经过画布）—— 把「画布装不下」变成「接口 400」。备选：服务端同步校验（导入/AI 生成的历史文档会写不进去，否决）。
   代价是绕过 UI 的写入仍可超过 50，因此配套需求「存量超限文档仍可打开与编辑」把超限状态定义为**只读放行、禁止再加**：加载不截断，新增才拦。

3. **提示走工具栏状态行，不新增弹窗或 toast。** 与起点、终点的失败反馈保持同一形态（同一行文案、同一位置），用户不必学两套反馈；同时零新增依赖。备选：ElMessage toast（与其他创建失败反馈不一致，且创建节点属高频操作，弹窗噪音大，否决）。

4. **上限判定继续统一走 `createNode`，不在按钮层各写一份。** 按钮只负责把失败原因显示出来；数量真相源保持在注册表 + store，避免出现「按钮说能加、store 说不能」的双口径。

## 模块防火墙自检

- 本变更**只动前端工作流模块内部**（节点注册表 + 画布工具栏组件 + 该模块的前端用例），不新增任何跨 App import。
- 后端零改动：不新增/修改 `api.py`、Model、Serializer、URL 或 Consumer；无写库路径变化。
- 前端不直连数据库、不绕过 HTTP 唯一出口：本变更不新增任何 HTTP 调用。
- 无跨模块新依赖：不引入新的共享件，不改 `shared/`。

## Risks / Trade-offs

- [上限提高后单篇文档变大，自动保存 payload 与画布渲染开销上升] → 自动保存已有 500ms 防抖与「空图不覆盖」保护；50 作为软上限本身就是节流阀；若后续真实流在 50 附近出现明显卡顿，再单独立项评估画布虚拟化（本次不做）。
- [AI 读到的跳转路径仍只有前 10 条，50 个节点的流在 AI 侧可见性不足] → 本次不改，作为已知限制记录在 proposal「Impact」；如需提高，另立变更改语义摘要的路径上限。
- [服务端不校验导致导入/AI 生成可越过 50] → 由需求「存量超限文档仍可打开与编辑」兜住：超限文档能看能改能存，只是不能再加节点；界面提示仍会说明上限数值。
- [上限数值将来再次调整时四处口径漂移] → 上限只在注册表声明一处，用例直接断言注册表数值与第 50/51 个节点的行为，改值必须同时改用例。
