## Context

`planner_input` 的取值链路（皆为现状，本单不动）：

```
build_planner_user_input(task)  →  json.dumps({四键}, ensure_ascii=False)   # 紧凑单行
        ├─ 引擎装配：作为规划模型 user 输入原文
        └─ 详情接口 serialize_agent_task_detail → TaskDetail.planner_input
                                                   → TaskInputPanel <pre>
```

既有验收标准要求「详情取到的文本 == 引擎入模文本」（同源同函数）。因此**格式化必须发生在前端展示层，且必须只在渲染时派生**：一旦在后端或 DTO 层改写文本，「展示即入模」的断言即失效。

## Goals / Non-Goals

- Goals：四键结构一眼可读；字符串内的换行（尤其附件正文）按真实换行呈现；历史脏数据不白屏。
- Non-Goals：语法高亮、折叠子节点、复制按钮、附件区块改造、接口字段变更、新增第三方依赖。

## Decisions

### D1：格式化落在纯函数，不在组件里

`frontend/AGENTS.md` 禁止组件内写解析逻辑。新增纯函数放在既有 `helpers/task-detail.ts`（已是任务详情的纯函数归集处），组件只做 `computed` 取值：

```
formatPlannerInputText(raw?: string): string
```

- 空 / 全空白 → 返回空串（沿用既有空态文案「本条任务没有规划输入记录」）。
- `JSON.parse` 成功 → 按 D2 序列化。
- `JSON.parse` 失败 → **原样返回入参**（trim 后），保证脏数据可读、不丢内容。

### D2：自写序列化，而不用 `JSON.stringify(v, null, 2)`

`JSON.stringify` 的缩进能力只作用于结构，字符串值内部的换行仍会被转义为 `\n` 两个字面字符——这正是当前不可读的根因。因此自写递归序列化：

| 规则 | 取值 |
| --- | --- |
| 缩进 | 2 空格 |
| 键顺序 | 保持 `Object.entries` 原序（四键顺序即后端 `json.dumps` 顺序） |
| 字符串值内的 `\n` / `\r\n` / `\r` | 转真实换行，续行缩进到「该值起始所在层级」 |
| 字符串转义 | `\` → `\\`；`"` → `\"`；`\t` 及其它控制字符 → `\t` / `\uXXXX`（**换行除外**） |
| 数值 / 布尔 / null | 直接 JSON 字面量 |
| 空对象 / 空数组 | `{}` / `[]` |
| 顶层非对象（字符串 / 数组 / 数字） | 同样支持，不特判崩溃 |

副作用与取舍：字符串内换行真实化后，**展示文本不再是合法 JSON**（不可直接复制去 `JSON.parse`）。这是需求明确要求的效果（「回车行字符串要回车」）；需要原文时以后端字段为准，本单不改该字段。

### D3：不改视觉与外层结构

`<pre class="ti-pre">` 的代码块皮肤（等宽字体、虚线边框、定高等宽滚动、`white-space: pre-wrap`）沿用既有令牌与规则，不新增样式令牌、不改字号。仅把绑定值由原始字符串换成格式化结果。

## Risks / Trade-offs

- 附件正文很长时，格式化后行数显著变多 → 由既有 `max-height: 240px` 内部滚动兜底，不撑破页面。
- 展示文本不再可解析为 JSON（见 D2 取舍），在区块语义上仍标注为「原文」的**可读视图**，字段本身未变。
- 用户若已依赖单行形态复制整段文本，行为会变；这是本次需求的目标形态。

## Migration Plan

无数据迁移：不落库、不改接口。前端发布即生效，历史任务详情同样受益（格式化在渲染时进行，与数据新旧无关）。
