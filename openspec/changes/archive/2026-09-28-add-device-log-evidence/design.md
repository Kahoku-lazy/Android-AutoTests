## Context

设备控制链路已是 planner → executor ↔ verifier 三角色工作流（`engines/ai/agentscope/workflow.py`）。当前 verifier 的输入只有「断言 + 执行结果 + 截图」，工具子集为 `VERIFIER_TOOLS = ["screenshot_page"]`；因此「页面变了」可判，「设备日志层面响应了没有」不可判。

设备日志的现状与约束：

- 设备通过 TCP 端口（现场为 7005）主动连入，另有串口一条链路；平台侧**目前没有任何采集能力**，只有 `temps/` 下的临时调试脚本（已实测能收到真机日志）。
- 真机日志内容**不含时间字段**（实测行：`ram free heap size: 11636, psram free heap size: 1186528`），所以时间只能取采集层收到该行的时刻。
- 引擎分层：串口 / TCP 句柄只能出现在 `engines/device`；`engines/ai` 目前不 import `engines/device`，且要求零 `apps.*`。
- 注入先例：`TaskRequest.on_progress` 与 `tools` 都是 Django 侧注入的纯标准库对象，引擎只经协议调用。
- 单进程假设：本地由 `python run.py start` 起单个 daphne 进程，采集可由该进程常驻持有。
- Windows + Python 3.13：`zoneinfo("Asia/Shanghai")` 需要额外 `tzdata` 依赖；北京时间无夏令时。
- 端口 / 串口独占：Windows 允许两个进程绑同一端口，会造成「看起来在采集、其实一条都收不到」；串口一个 COM 口只能被一个进程打开。

## Goals / Non-Goals

**Goals:**

- 平台常驻采集设备日志（TCP 端口 + 串口），每条日志带北京时间毫秒时间戳，按设备隔离缓冲
- 在步骤交给执行模型**之前**开窗，动作发出时刻随截图一起进入验收阶段
- 验收前由脚本按「动作发出时刻 + 5 秒」筛选窗口日志，逐条标注证据等级，连同原始日志交给验收模型
- 关键词表（关键词 → 功能模块 / 功能点）数据驱动，改表不改代码
- 采集缺失或窗口为空时优雅降级：任务照常完成，验收标注「无日志证据」

**Non-Goals:**

- 不给验收模型增加自主查询工具：`VERIFIER_TOOLS` 保持 `["screenshot_page"]`，避免牵动 `ai-device-planner-tools`、`ai-model-debug` 的验收工具子集契约与前端调试页展示
- 不做日志全量落库、长期留存、报告页与前端 UI
- 不做独立采集进程、多 worker / 多实例部署下的采集协调
- 不改规划 / 执行提示词口径，不做关键词表的后台维护界面

## Decisions

### D1 采集落点与生命周期

新增 `engines/device/logbus.py`（设备日志总线：采集线程 + 按设备缓冲 + 窗口），由 Django 侧在启动时拉起单例常驻。

- 理由：串口 / TCP 句柄属设备侧 I/O，必须在引擎层；apps → engines 是允许方向，Django 侧只做装配与注入。
- 备选：独立采集进程 + 本地 socket —— 引入新通信通道，违反通道收敛；apps 层直接开串口 —— 违反引擎边界且句柄跨层泄漏。
- 采集**不随动作开关**：动作与读取之间到达的日志必须已被收下。

### D2 时间戳实现

固定 UTC+8 偏移生成北京时间（`datetime.now(timezone(timedelta(hours=8)))`），格式 `YYYY-MM-DD HH:MM:SS.mmm`，由采集层在收到该行时生成。

- 理由：不引入 `tzdata` 依赖；北京时间无夏令时，固定偏移与 `zoneinfo` 等价。
- 备选：`zoneinfo("Asia/Shanghai")` —— Windows 无系统时区库，需新增依赖，收益为零。

### D3 开窗 / 读窗放在引擎侧、实现经注入

`TaskRequest` 新增 `log_evidence`（协议对象：`open_window` / `read_window`），由 Django 装配时注入；工作流在 `_execute_step` 之前开窗，在 `_verify_step` 之前读窗并把证据块并入验收输入。

- 理由：只有工作流知道「步骤何时交给执行模型」，但引擎不能碰设备句柄；注入与既有 `on_progress` 同构。
- 备选：`engines/ai` 直接 import `engines/device.logbus` —— 新增引擎横向依赖；由验收模型自己调工具取日志 —— 要改 `VERIFIER_TOOLS`，牵动既有能力与前端调试页。

### D4 动作发出时间的采集点

动作类工具在**真正调用设备之前**取时刻，写入工具结果（`action_time`）；工作流从本步工具轨迹中取**最早一次产生副作用的动作**的 `action_time` 作为基准；读取类动作（如读取当前前台）不记录。

- 理由：设备可能在调用瞬间就开始响应，用返回时刻会切掉动作执行期间的日志；一步内多次动作取最早，覆盖响应起点。
- 备选：由工作流在调用 executor 前统一记时刻 —— 会把执行模型自己找元素 / 截图的耗时计入窗口，起点偏早、噪声大；本设计只把它用于**开窗**（窗口起点），基准仍取动作发出时刻。

### D5 窗口筛选与证据等级

取证窗 = 本步**每一次**副作用动作的 `[动作, 动作 + 5 秒]`（默认阈值，可配置）的**并集**；动作前基线窗口默认取「本步首次动作」之前 30 秒。等级四值：

| 等级 | 判定 |
|---|---|
| 强证据 | 落在取证窗内，且基线窗口内未出现同一关键词 |
| 疑似周期 | 落在取证窗内，但基线窗口内已出现同一关键词 |
| 动作前 | 时间早于本步首次动作（作为上下文返回） |
| 超窗 | 时间晚于「本步最后一次动作 + 5 秒」（不作为本次证据，但在结果中说明） |

落在本步内、但不在任何一次动作响应窗内的行不进等级列表，仍原样出现在交付给模型的原始日志里。

> **真机验证修正（2026-09-28）**：原设计取「本步最早一次动作 + 5 秒」单一窗口。真机跑（任务 #99）显示执行模型一步内会点 4~13 次，灯的真实响应分别落在最后一次/倒数第二次点击后 **0.61s / 0.67s**，却被单一窗口判成「超窗 +14.3s / +22.4s」= 白采。因此改为并集窗口；同一批验证还修掉了「上下文累积导致基准取到上一步动作时间」的缺陷。

周期性日志**不自动剔除**，连同动作前的同名日志一起交给模型判断；但采信**默认从严**：疑似周期证据不得单独作为通过依据，窗口内唯一命中为疑似周期时必须由截图证据同时成立才判通过（需求方口径）。命中全部返回，并给出同一关键词的出现次数与各次时间戳。

### D6 关键词表数据源

库内数据文件 `config/device_log_keywords.json`（由 `dev_docs/1.txt` 经转换工具生成），路径经 settings `DEVICE_LOG_KEYWORD_FILE` 传入引擎侧加载器；启动加载并在文件 mtime 变化时热加载。

- 理由：无新表、无迁移，满足「改表不改代码」。
- 备选：新建数据表 + 后台维护界面 —— 需要迁移 / 接口 / 前端，本期非目标。

### D7 交付形态与留痕

证据块以文本（结构化 JSON）注入验收模型的用户消息，与截图并列；同时把证据块写入该步骤的任务过程记录，供报告与事后排查。

- 理由：验收模型是视觉模型，长文本作为独立内容块易喧宾夺主；文本注入与既有 `assert` / `exec 结果` 注入方式一致。
- 备选：独立 DataBlock —— 需要动内容块拼装，收益不明显。

### D8 资源互斥与失败可见

采集启动时对监听端口做占用探测（探测到已有监听即报可读错误并提示排查命令），串口打开失败记录可读错误且不影响网络来源；平台上线后**独占** 7005 与串口，`temps/` 下的调试脚本降级为离线工具，不同时运行。

### D9 通道以被测设备 SKU 命名

TCP 7005 这条来源对应的是**被测灯具**（APP 里显示的 SKU 为 `H6810`），而不是被 AI 操作的安卓手机；一个端口只为一种 SKU 服务，因此把通道名直接取为该 SKU（`DEVICE_LOG_SOURCE_SKU`，默认 `H6810`），并在证据里标出「来源 H6810」。

- 理由：日志归属无法从连接本身识别（设备只说自己是 TCP 客户端），用配置固化「这条来源是谁」最诚实；手机 serial → 通道的解析仍走 `resolve_channel()`，将来多 SKU 时按 SKU 配端口 / 串口即可，无需改判定逻辑。
- 备选：通道固定为共享名 `*`（多 SKU 时无法隔离，证据里也看不出日志来自哪台设备）；按手机 serial 分通道（与物理事实不符：手机不产生这些日志）。
- 未配 SKU 时退回共享通道 `*`，不报错。

## 模块防火墙自检

- **跨 App import**：不新增跨 App 内部 import。日志证据提供者的 Django 侧实现与装配放在 `apps/ai_assistant/`，只经 `engines/device/logbus.py` 的公开函数访问采集。
- **写库收敛**：本变更不新增表、不新增写操作；证据写入既有任务过程记录，沿用 `task_runner` 既有落库路径。
- **引擎边界**：串口 / TCP 句柄只出现在 `engines/device/logbus.py`；`engines/ai` 不 import `engines.device`，只接收注入的协议对象；`apps` 不 import `airtest` / `uiautomator2`。
- **通信通道**：不新增 WS 生产点、不新增前端 HTTP 出口；AI 工具仍经既有工具装配注入。
- **前端**：本变更无前端改动，前端唯一出口约束不受影响。

## Risks / Trade-offs

- [5 秒阈值与设备上报延迟不匹配，慢模组会被判「无响应」] → 阈值可配置（settings 默认 5 秒），证据中明确标注「超窗」，并在验收输入里说明阈值取值，避免把「上报慢」当作「设备没动」
- [周期性日志造成稳定误判成功] → 不自动剔除，改为基线比对 + 「疑似周期」标注 + 附动作前同名日志，交由模型结合截图判断
- [两进程绑同一端口导致静默收不到数据] → 启动做占用探测，占用时记录可读错误并给出排查命令；文档明确平台独占端口与串口
- [单进程假设：多 worker / 多实例部署会重复绑定端口] → 本期只在单进程部署生效；启动检测到重复实例时报警；独立采集进程列入后续
- [关键词表与真机日志不同步，导致漏判] → 关键词只作「命中提示」，无命中时仍交付窗口内原始日志，失败判定不依赖关键词是否齐全
- [缓冲内存占用] → 保留时长（默认 10 分钟）与单设备最大行数双上限，超出 FIFO 淘汰

## Migration Plan

- 无数据迁移、无新表；新增 settings 项：日志监听端口、串口 / 波特率（默认空）、缓冲保留时长、默认阈值与基线窗口、关键词表路径
- 默认开启采集、但串口默认空 → 只采网络来源；关闭采集开关即回退为「仅截图」判定，`log_evidence` 为空且验收标注「无日志证据」
- 回滚：关闭开关 + 停止采集线程，无残留数据需要清理
