## Context

上一次变更（`archive/2026-09-28-add-device-log-evidence`）已交付：引擎层常驻采集（`engines/device/logbus.py`）、按设备 SKU 命名的通道与环形缓冲、验收前由编排层注入日志证据。见 proposal.md - Why 了解本次动机，此处只记实现所需的现状：

- 日志缓冲按**通道**（现场 = 被测 SKU `H6810`）隔离，行记录时间戳（北京时间毫秒）、来源（`tcp` / `serial`）与原始文本；**未记录来源端口**，因此「按端口查询」目前无法区分。
- 采集来源由 `settings` 决定（`DEVICE_LOG_TCP_PORT` 默认 7005、`DEVICE_LOG_SOURCE_SKU` 默认 H6810），单端口单通道。
- 工具注册面有两处：`apps/ai_assistant/tools.py`（`TOOLS` / `TOOL_META` / `TOOL_CATEGORIES`，供工具箱展示与 HTTP 网关）与各角色的工具子集常量（`engines/ai/agentscope/config.py` 的 `VISION_TOOLS` / `VERIFIER_TOOLS`）。
- 验收模型「仅截图工具」是既有契约（`ai-device-planner-tools`、`ai-model-debug` 有对应断言），本次不得改动。
- 既有经验：工具箱展示的是「AI 能调用的业务工具」，采集与证据注入不在其中——本次正是要把「查日志」变成一个可调用工具。

## Goals / Non-Goals

**Goals:**

- 一个只读工具 `read_device_log`：按时间点（或最近一段）+ 端口 + 可选关键词读日志
- 工具箱出现「设备日志」分类，可整类启停、标记只读
- 装配进执行模型，让它能自查「设备到底响应了没有」
- 失败口径明确：未配置端口 / 非法时间 / 无日志，三种情况都给可读结论，不冒充成功

**Non-Goals:**

- 不给验收模型加工具（既有「仅截图」契约不变）
- 不做临时连接任意端口（只读工具不建立新连接；多端口靠配置，不靠调用时新开）
- 不做日志落库、分页、导出与前端页面改造
- 不做「按时间点重放/回放」设备状态

## Decisions

### D1 查询复用常驻缓冲，不新开连接

工具从 `LogBus` 已采集的按通道缓冲里取数；端口只用于**选择通道**，不会去连该端口。

- 理由：只读工具若临时连端口，既可能与设备争抢连接，也绕过了「常驻采集不漏日志」的设计前提。
- 备选：调用时临时连端口抓一段 → 抢连接、漏首行、必须同步等待，与只读定位冲突。
- 备选：把查询做成常驻采集进程的 RPC → 需要新通信通道，违反通道收敛。

### D2 日志行补记来源端口，端口 → 通道由配置决定

`LogLine` 增加来源端口字段；`LogBusConfig` 增加「端口 → 通道」的来源登记（现场为 `7005 → H6810`），工具按端口反查通道。

- 理由：没有端口维度，「指定端口」无法落地；登记表同时为将来多 SKU / 多端口铺路。
- 备选：只接受一个端口并在代码里写死 7005 → 换端口要改代码，且无法表达「两个灯同时采」。
- 备选：让工具接受通道名而非端口 → 与需求方口径（指定端口）不符。

### D3 时间点语义：该时刻之后一个跨度

给定 `at` 时返回 `[at, at + 跨度]`（含 `at`）；不给定则返回最近 `跨度`。跨度默认 30 秒，入参可覆盖并设上限 300 秒（保护模型上下文）。

- 理由（需求方口径）：典型用法是「我动作发出后这一段设备打了什么」，取该时刻之后即可；之前的状态排查时另调一次即可，避免把无关的历史一起塞进上下文。
- 备选：`at ± 跨度/2`（前后各半）→ 上下文里混入前因，且「跨度」含义变模糊，需求方未选。
- 备选：只给绝对起止时间 → 模型每次要自己算两个时间点，容易算错。

### D4 关键词过滤复用既有关键词表

`keyword` 入参做忽略大小写的子串匹配，并用既有「关键词 → 功能点」索引还原命中的功能模块 / 功能点；不给关键词时返回全部行。

- 理由：排查时最常见的两个问题是「这句日志对应哪个功能点」和「这个功能点到底打印了没有」，一次调用就能回答。
- 备选：只返回裸日志、让模型自己去对表 → 关键词表在平台侧，模型看不到。

### D5 三种失败口径必须显式，且都走「可读结论」而不是报错

未配置端口、非法时间点、范围内无日志，三种都返回**可读结论**（实际查询范围 / 期望时间格式 / 端口未配置），不返回空对象。

- 未配置端口（需求方口径）：**不报错**，正常返回 `note=「端口 X 未配置为日志来源」`、`conclusion=port_not_configured`、行数 0 —— 端口写错是可预期输入，让 AI/调用方拿到结论自行换端口比抛错更有用，也避免调试页显示成红色失败。
- 非法时间点：仍按调用错误处理（格式错误属于真正用错用法），错误文案给出期望格式。
- 范围内无日志：正常返回行数 0 + 「该时间范围内无日志」。

### D7 端口只在已登记来源里解析，绝不临时连接

未登记端口直接给结论，不去连它：既避免与设备抢连接，也避免把「端口写错」伪装成「设备没打日志」。

- 备选：调用时按传入端口临时连一次抓日志 → 抢连接、必须同步等待、还绕过了常驻采集的前提。

### D8 同一时刻的日志合并为一条，且最新在上

按「时间戳 + 来源」合并：同一条记录内 `text` 用换行连接该时刻的所有原始行；时间戳或来源不同不合并。列表按时间戳**倒序**（最新在最上面），**同一条内部保持原始先后**。工具输出与验收证据两处都按此口径展示，并保留合并前的原始行数（`raw_line_count` / `window_line_count`）。

- 理由（需求方口径）：设备一次事件常在同一毫秒打出一串日志（实测 `request → start → switch_off` 三行同为 `15:47:41.466`），逐行摊开既长又难读；合并后读起来就是"那一刻发生了什么"。倒序则是日志查看的通用习惯——最新的一条最关心，不用滚到底。
- 关键取舍：**同一条内部不倒序**。合并条代表"那一刻"，其内部顺序是事件发生顺序（`request → start → switch_off`），倒过来读会变成"先关灯再收到请求"，语义就错了。
- 关键取舍：合并与排序**只做展示**，不改判定——关键词命中仍按原始行逐行匹配（不会漏判），原始行数照旧给出。
- 备选：保持正序（时间从早到晚）→ 需要滚动到底看最新，与查看习惯相反；需求方明确要求最新在上。
- 备选：合并到只剩最后一行 → 丢信息，事后无法复盘那一刻的完整经过。

### D6 只装配进执行模型

工具名加入 `VISION_TOOLS`（执行模型），不加进 `VERIFIER_TOOLS`。

- 理由：验收模型「仅截图」是既有契约，验收阶段的日志证据已经由编排层注入，无需它自己查；执行模型主动查日志对排查最有用。
- 备选：同时给验收模型 → 要改两处既有契约与模型调试页展示，收益不抵成本。

## 模块防火墙自检

- **跨 App import**：工具写在 `apps/ai_assistant/tools.py`，只调 `engines/device/logbus.py` 的公开函数（apps → engines 是允许方向），不 import 其它 App 内部实现。
- **写库收敛**：本变更零写库、零新表；查询只读内存缓冲。
- **引擎边界**：串口 / TCP 句柄仍只在 `engines/device/logbus.py`；`engines/ai` 只通过工具名与注入协议接触日志，不新增对 `engines.device` 的 import。
- **通信通道**：不新增 WS 生产点、不新增前端 HTTP 出口；工具经既有工具装配与 HTTP 网关暴露。
- **前端**：本变更不改前端页面（工具在工具箱里按既有分类机制自动出现）。

## Risks / Trade-offs

- [缓冲只保留最近 10 分钟，查更早的时间点会得到「无日志」] → 失败口径里注明「可能已超出缓冲保留时长」，避免被误解为设备没打过日志
- [时间点解析依赖「当天」假设，跨零点查询会解析到错误日期] → 结果回显解析后的完整起止时间，跨零点场景可被立即发现；需要时允许传完整日期
- [执行模型拿到工具后可能频繁调用、拉长上下文] → 跨度设上限、默认 30 秒，且工具描述里明确「排查用，不要每步都调」
- [端口 → 通道映射写错会导致查不到日志] → 未配置端口时直接报错并列出已配置端口，不做静默兜底
- [工具箱新增分类会让「交给助手」总闸多一个开关，误关会导致 AI 查不到日志] → 工具是只读且非必需（验收证据不依赖它），误关只影响主动排查能力

## Migration Plan

- 无数据迁移、无新表；新增 settings 仅为「端口 → 通道」登记（默认 `7005 → H6810`，与现状一致，不配也能跑）
- 回滚：移除工具注册与分类即恢复现状；既有验收证据链路完全不受影响（二者互不依赖）
