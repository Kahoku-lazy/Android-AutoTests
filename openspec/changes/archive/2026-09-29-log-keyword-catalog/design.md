## Context

见 `proposal.md - Why`。与本设计相关的现状约束（代码事实）：

- 对照表是**数据文件**：`config/device_log_keywords.json`，结构 `{source, description, feature_count, keyword_count, keywords: {关键词: [{id, module, feature}, …]}}`（现场 67 个关键词 / 56 个功能点），由 `tools/gen_device_log_keywords.py` 从需求文档生成。
- 引擎侧 `engines/device/logbus.py` 的 `KeywordIndex` 负责加载与最长匹配消解：`from_file()` 在文件缺失 / 不可解析时返回空索引并记可读错误；`mapping` 暴露原始对照；**总线是进程内单例**（`get_or_create_log_bus`），关键词在**构造时加载一次**，文件改了不会自动重载（要重建总线，即重启平台）。
- 工具箱来源范式已成型：`ASSEMBLY_SOURCES`（5 项，其中「设备提示词 / 无线端口 / 模型调试」为无总闸来源，各自带 `meta` 副标题）；`ToolboxPanel` 在 `prompt` / `port` 两个来源上渲染专用面板（`DevicePromptPanel` / `WifiPortPanel`），面板内部复用装配台的 `tb-cat-head` / `tb-cat-body` 与共享空错态组件。
- 权限先例：`GET /api/ai/log-ports/`（端口列表）**登录可读**，开关才是超管；只读查询工具 `read_device_log` 也从同一张表还原功能点。

## Goals / Non-Goals

**Goals:**

- 一眼看到「当前支持筛选的日志关键词」及其功能模块 / 功能点归属，并能按关键词 / 模块 / 功能点搜索。
- 与判定所用的那张表**同源**，且「表改完什么时候生效」如实说明。
- 零写操作、零新通道：只多一个只读端点与一个来源面板。

**Non-Goals:**

- 不提供关键词表的在线编辑 / 导入 / 上传（改表仍是文件 + 重启）。
- 不改关键词表内容、不改证据等级与 5 秒窗口、不改只读日志查询工具、不改端口监听语义。
- 不在本面板做日志正文浏览（那是「无线端口」面板的日志抽屉）。

## Decisions

**决策 1：新增只读端点 `GET /api/ai/log-keywords/`，登录可读，不经内部工具网关。**

- 理由：与 `GET /api/ai/log-ports/` 同权限口径（文档性质的只读目录，谁都能看；有写能力的开关才限超管）；工具网关是给智能体调工具用的内部面，展示用数据不该走那里。
- 备选：复用 `read_device_log` 的 schema 拿关键词——那是查询工具，返回的是日志行而非对照表，语义不对。不取。

**决策 2：取值优先级「运行中的采集索引 > 直接读配置文件」，并如实回传来源。**

- 做法：`get_log_bus()` 有总线时取其 `keywords.mapping`（`origin="runtime"`，即判定真正在用的索引）；没有总线（从未启动过采集）时用 `KeywordIndex.from_file(settings.DEVICE_LOG_KEYWORD_FILE)` 直读（`origin="file"`）；两者都拿不到时 `keywords` 为空并给可读 `note`。响应同时带 `keyword_file` 与文件 `updated_at`。
- 理由：面板的用途是「当前支持什么」，因此优先给正在用于判定的那份；只在采集尚未创建时退化为读文件，而不是让面板空着。
- 备选：只读文件——文件改完未重启时，面板会展示一份「判定其实还没用上」的表，且与 `origin` 无法区分。只读运行索引——采集没跑时面板空白。均不取。

**决策 3：后端只下发原始对照，表格行与搜索放前端纯函数。**

- 做法：响应里 `keywords: [{keyword, features: [{id, module, feature}]}]` 保持**表内顺序**；前端 `helpers/log-keyword-rows.ts` 把它拍成表格行（一行一个「关键词 × 功能点」，`key = 关键词|模块|编号|名称`）并做搜索过滤，行序**与表内逐行一致**（不重排、不合并）。
- 理由：拍平与过滤是展示派生，本仓既有做法就是「后端给事实、前端做展示派生」（任务详情分组、日志证据渲染、来源行副标题皆然）；放前端还能让搜索做到即时无请求。行序照搬表内顺序，排查时行序与数据文件一致才便于对照。
- 备选：① 后端直接下发拍平后的行——等于为一种展示形态造 API，换列或换序就要改后端与契约；② 一行一个关键词、多功能点合并进一格——单元格会长到读不动，且「一个功能点一行」的对照关系被藏进文本里。均不取。

**决策 4：来源 key 取 `keywords`，面板复用装配台的页头 / 空错态范式。**

- 做法：`AssemblySourceKey` 增 `"keywords"`；来源定义 `{key:"keywords", name:"日志关键词", desc:"关键词 → 功能模块 / 功能点（只读）", gateKey:"", meta:"关键词 → 功能模块 / 功能点 · 只读"}`；`ToolboxPanel` 在 `activeSource === "keywords"` 时渲染 `LogKeywordPanel`。
- 理由：无总闸来源必须带 `meta`（上一轮已把这条规则写进类型与用例），否则会掉进「n/m 生效」计数分支——本次沿用该规则，并由既有用例自动守住。

**决策 5：只读 + 如实标注生效时机。**

- 做法：表格区不提供任何写控件，操作只有页头「刷新」与搜索框；页头副标题与表格上方说明写明「改表后需重启平台才用于判定」，并展示取值来源与文件更新时间。
- 理由：引擎在进程内单例构造时只加载一次关键词表（代码事实），若不明说，用户改完文件发现判定没变会以为面板骗人。

**决策 6：权限沿用登录可读，不新增角色判断。**

- 理由：对照表内容不含密钥、不含设备标识，只是判定口径的文档化；与端口列表同口径，避免「能看不给看」的不一致。

## 模块防火墙自检

- 跨 App import：无。改动在 `apps/ai_assistant` 内部，只读消费 `engines/device` 的 `KeywordIndex`（引擎层，允许方向）。
- 写库收敛：不新增任何写库路径（本变更纯读，不改 `api.py`，不改任何表）。
- 引擎边界：不新增引擎行为，不加引擎依赖；前端不直连数据库。
- 通信通道：只新增一个 HTTP 只读端点（前端唯一出口 `api/toolbox.ts` 内调用），不新增 WS 事件、不走工具网关。

## Risks / Trade-offs

- [运行中的索引与磁盘文件不一致（改表未重启）] → 响应带 `origin` 与文件 `updated_at`，页面如实标注该差异与生效时机，不假装一致。
- [对照表较大导致一次渲染 DOM 偏多（现场 67 关键词 → 约 70 行）] → 70 行远低于需要虚拟滚动的量级；搜索在前端过滤，不额外请求。
- [表里同一功能点编号出现在多个模块下] → 行标识与功能点计数都以 `(module, id, feature)` 三元组为口径，不假设编号全局唯一；用例覆盖「同编号不同模块」。
- [文件缺失 / 解析失败时面板空白] → 端点返回可读 `note` 与空列表，面板渲染空态而不是错误页、也不是空表格；用例覆盖。
- [新增来源被误当成可装配来源] → 由既有「无总闸来源的副标题不含计数」用例与新增来源注册用例共同守住。
