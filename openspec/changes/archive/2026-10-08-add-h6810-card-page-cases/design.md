# 设计：H6810 经典 / 灵动卡片页功能测试用例

## Context

- **源材料**：`logs/01/H6810自动化测试点.md`（19 行，`logs/` 被 `.gitignore` 覆盖）。两组测试点各 3 条，差别在"选择经典 / 灵动"这一模式选择与检查对象；两组都含"**开关 OFF/ON + 日志断言**"与"**WIFI&蓝牙图标显示正确**"。
- **现有用例资产**：`tests/ai_planner/cases/planner.yaml` = 正式口径（单步 / 多步，`input: text`）；`extended.yaml` = 5 条按需跑的难场景（其中 `with-attachment` 已覆盖"测试点来自附件"这条输入路径，但内容是我编的占位文本）。
- **输入契约**：四键 JSON（任务标题 / 任务目标 / 附件文本内容 / 设备ID）是规划模型的正式输入形态（引擎协议规格）；生产经 `api.build_planner_user_input` 组装，附件来自 Word/PDF 解析后的 Markdown。
- **判据现状**：硬性 5 项（契约 / 关键词 / 步骤数区间 / 页面流工具 / `log_check` 区分度）+ 疑似 3 项。
- **设备现状**：设备池当前**无在线设备**（实测 `get_online_devices()` 为空）。

## Goals / Non-Goals

**Goals:**

- 把这份真实测试点文档变成**两条可复现的评测用例**，且用例自包含（内容入库，不依赖被忽略的 `logs/`）。
- 测到"**给一份多测试点文档 → 能否规划出覆盖全部测试点的步骤**"这条真实链路，含日志断言与页面断言的区分。
- 期望尽量用不可能被同义改写的硬事实，避免假红。

**Non-Goals:**

- 不改评测工具、判据、主用例集（正式口径仍是单步 / 多步）。
- 不把整份 `H6810 基础测试用例.md`（294 行、详情页/设置页等）纳入本单——本次只按用户指定的那份 19 行测试点文档拆两条。
- 不跑执行链路（无在线设备；规划也不需要设备）。
- 不追求"步骤数精确匹配"——那会与模型正常波动冲突。

## Decisions

**D1 放扩展集，不动正式口径。**

用户此前已定正式口径＝单步 + 多步两条；这两条属"更难的业务场景"，进 `extended.yaml` 按需跑（`--cases tests/ai_planner/cases/extended.yaml`）。若日后要提升为正式口径，单独改主文件即可（守卫用例会随之被要求同步）。

**D2 测试点原文放「附件文本内容」，任务目标写一句话。**

生产消费测试点文档的方式就是把解析后的 Markdown 放进附件键；把三条测试点塞进"任务目标"一句话里既不符合真实用法，也会人为提高难度。故：`input: json` + `attach` = 三条测试点原文（逐字，含编号），`goal` = 一句话目标（"按附件中的测试点，完成 H6810 设备卡片页『经典页面』的功能测试"）。

**D3 关键词只取不会改写的硬事实。**

`must_contain` 取 `["H6810", "经典", "开关"]`（灵动那条换 `灵动`）。**不放** `WIFI` / `蓝牙`——写法可能被改写（Wi-Fi / wifi / 蓝牙图标），且模型可能用"无线图标"等同义表达；也**不放**"图标显示正确"这类句子。
步骤数区间放宽为 `3 ~ 12`：3 条测试点至少要 3 步（漏掉就是真错），上界给"长按→选择→保存"这类子动作与弹窗处理留空间。

**D4 开启 `log_check` 区分度判据——这正是它的用武之地。**

这组测试点**天然混合两类断言**：开关 OFF/ON 明确要求"**日志断言**"，图标检查是**页面级断言**。所以一条合格的计划必须出现 `log_check` 的不同取值；若模型一律填 true 或一律 false，就说明它没有按提示词区分两类断言——这比现有那两条正式用例更能检验该判据。

**D5 设备 ID 留空，并登记原因。**

实测设备池无在线设备；且规划阶段不需要设备（设备只在执行链路用）。MUST NOT 编造 serial —— 编一个不存在的设备串会污染用例语义（规划提示词要求"不要改写成其它设备"，一个假 serial 反而可能误导）。

**D6 源材料不入库，内容内联并在用例里标注来源。**

`logs/` 被 gitignore，故测试点原文**逐字内联**进 `attach`；用例注释注明来源路径（`logs/01/H6810自动化测试点.md`）以便追溯。这样用例自包含、可复现，且不依赖被忽略的目录。

**D7 期望必须校准，不能只靠推断。**

三条测试点的难度高于现有用例，期望的步骤数区间与关键词属**待校准**值：实施时先只跑这两条（临时用例文件，不跑整份扩展集），据真实输出核对关键词是否命中、步骤数是否落在区间；若某关键词确实只出现在被改写的表达里，则**删除该关键词**（而不是放宽到无意义）。

## 模块防火墙自检

- 跨 App import：无（只改测试数据文件）。
- 写库路径：零写库；`planner_eval` 本就不建任务、不占设备池。
- 前端 / 接口 / 数据库 / 引擎：零改动。
- 测试隔离：新增用例默认不参与任何自动套件（仅在显式 `--cases` 时执行），故不产生 CI 费用。

## Risks / Trade-offs

- [关键词被同义改写导致假红] → D3 只取硬事实 + D7 校准；实测若命中不了就删词。
- [步骤数区间过窄] → 区间取 3~12，只拦"漏掉测试点"与"粒度失控"。
- [用例内容与源文档漂移] → 内容内联并标注来源路径；源文档更新时需同步用例（属预期的人工同步，与"测试点即资产"一致）。
- [跑这两条产生费用] → 只在校准时跑这两条（约两分钱量级），不跑整份扩展集。
- [误把它当成正式口径] → 用例文件头与本文档都写明：正式口径仍是单步 / 多步；扩展集按需跑。

## Migration Plan

1. 在 `extended.yaml` 追加两条用例（内容内联，附来源注释）。
2. 用临时用例文件只跑这两条做**校准**；据此调整期望（关键词 / 区间），必要时记录调整原因。
3. 跑既有守卫用例（扩展集 ≥5 条）与静态检查。
4. 归档并提交。
5. 回滚：删除两条用例即可，无数据与代码变更。
