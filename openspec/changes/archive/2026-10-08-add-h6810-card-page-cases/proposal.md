# 新增两条真实业务用例：H6810 卡片页的经典 / 灵动功能测试

## Why

用户提供了一份真实测试点文档（`logs/01/H6810自动化测试点.md`，19 行），内容是 **H6810 设备卡片页列表页**的界面功能测试点，按两种卡片页风格分成两组：

- **经典页面功能测试**：① 长按卡片 → 选择经典 → 保存成功；② 点击经典卡片页上的开关 OFF/ON，**日志断言**是否开关成功；③ 检查经典卡片页上 **WIFI&蓝牙图标**显示正确。
- **灵动页面功能测试**：① 长按卡片 → 选择灵动 → 保存成功；② 检查灵动卡片页上 WIFI&蓝牙图标显示正确；③ 点击灵动卡片页上的开关 OFF/ON，**日志断言**是否开关成功。

要求：把这份测试点**作为输入条件**，拆成**两条评测用例**（经典 / 灵动）。它比现有用例更接近真实业务：一份多测试点的文档 + 同时含"日志断言"与"页面级断言"两类验收。

**关键约束**：该文档位于 `logs/` 下，而 `logs/` 已被 `.gitignore` 覆盖——**用例必须内联测试点原文才能入库留存**，不能只写一个路径引用（否则仓库里的用例失去可读性与可复现性）。

## What Changes

- 在 `tests/ai_planner/cases/extended.yaml` 新增两条用例：`classic-page-functions`（经典）与 `dynamic-page-functions`（灵动）。
- **输入形态**：用四键 JSON 的「附件文本内容」承载测试点原文（生产正是这样消费 Word/PDF 测试点文档的），「任务目标」写一句话目标——这样测的是"**给一份测试点文档 → 能不能规划出步骤**"这条真实链路，而不是把测试点塞进一句话里。
- **期望口径**（机械可判）：关键词只取不可能被改写的硬事实（`H6810` / `经典` / `灵动` / `开关`）；步骤数区间放宽（3 条测试点 → 3~12 步）；要求先读页面流工具；并**开启 `log_check` 区分度判据**——这组测试点天然同时含"日志断言"（开关）与"页面级断言"（图标），正好检验模型会不会把两种断言标成不同取值。
- 设备 ID 留空：当前无在线设备，且**规划阶段不需要设备**（要跑执行链路时才需要），不编造 serial。
