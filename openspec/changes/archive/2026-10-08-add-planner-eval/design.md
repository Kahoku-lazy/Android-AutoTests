# 设计：规划模型能力评测入口

## Context

- **被测对象**：planner 角色（`engines/ai/agents/planner.py`）。输入是用户需求（或 Django 侧的四键 JSON：任务标题 / 任务目标 / 附件文本内容 / 设备ID），输出是 `{"plan": {"goal", "steps": [{"action", "assert", "log_check"}]}}`。
- **生产同源装配**：`apps/ai_assistant/model_debug.build_device_models_for_agent(agent)` 已被 `model_test` 与模型调试台共用（避免两处装配漂移）。评测必须走它——否则测的不是生产实际那份提示词与工具子集。
- **规划角色的工具**：`DEVICE_PLANNER_TOOLS = [list_page_flows, get_page_flow]`（读页面流文档）；提示词明确要求"规划前先用 `list_page_flows` 查看平台有哪些页面流文档"。上一轮实测该链路可用（真实调用返回了 1 篇页面流文档）。
- **现状入口与其边界**：`model_test planner` 单次、无校验、无重复、无对比、无成本统计。
- **产物落盘约定**：仓库 `tests/AGENTS.md` 规定"测试报告统一输出到 `reports/`"（实际目录 `tests/reports/`）；`tests/api/case/*.yaml` 是既有的 YAML 用例范式。
- **依赖**：PyYAML 可用（6.0.3）；`tests/reports/` 已存在。

## Goals / Non-Goals

**Goals:**

- 一条命令批量评测规划能力，输出**可复现的客观指标**：契约、粒度、断言、日志标记、工具使用、覆盖、稳定性、成本。
- 支持**同批用例换模型对比**（选型 / 回归）。
- 报告落盘可追溯（含每条用例的原始 plan 与工具轨迹）。
- 与生产同源装配，不改生产。

**Non-Goals:**

- 不做主观质量评分（用户已定：只做机械校验）；不引入裁判模型。
- 不评测执行 / 验收角色（需设备或截图，属另一单）。
- 不改提示词、不改工具子集、不动任务链路与前端。
- 不把评测接入 CI 门禁（它是按需运行、要花模型费用的工具）。

## Decisions

**D1 复用生产同源装配，只取 planner 角色。**

命令内调用 `build_device_models_for_agent(agent)` 后只使用 `planner`（另两个角色对象构造出来即弃——它们不发起调用，无副作用）。这样"评测用的提示词与工具子集"与生产完全一致。

**D2 用例集为 YAML，入库并版本化；`--cases` 必填。**

每条用例字段：
- `id`：用例标识（报告里引用）
- `title`：短标题
- `goal`：需求文本（或四键 JSON 的"任务目标"）
- `input`（可选）：`text`（默认，直接喂需求）或 `json`（按 Django 侧四键 JSON 构造，可带 `attach` 附件文本 / `device` 设备ID）
- `expect`（可选，全部机械可判）：
  - `must_contain`：必须出现的关键词（设备名 / 页面名 / 入口名）
  - `steps_min` / `steps_max`：步骤数区间
  - `require_flow_tool`：是否要求调用页面流工具（默认 true，与提示词一致）
  - `expect_mixed_log_check`：是否要求 `log_check` 出现混合取值（用于检验它没有一律填同一值）
- `repeat`（可选）：该用例的重复次数覆盖（默认取命令参数）

**D3 指标分两级：硬性项（判失败）+ 疑似提示（只提示、不判失败）。**

机械判据若过于激进会给出假失败，故明确分级：
- **硬性**：① JSON 可解析且 `plan.steps` 非空、每步 `action`/`assert` 非空字符串；② `must_contain` 关键词全部命中；③ 步骤数落在区间；④ `require_flow_tool` 时工具轨迹里出现 `list_page_flows`（与提示词要求一致）；⑤ `expect_mixed_log_check` 时 `log_check` 不是单一取值。
- **疑似提示**（进报告，不计入失败）：⑥ action 里出现"多副作用动作 + 并列连接词"（如同时点击与输入）；⑦ assert 命中"空话表"（操作成功 / 执行成功 / 正常 / 没有问题 等）；⑧ 结构指纹在重复之间不稳定。
  理由：这三类无法机械定论（提示词本身规定的"先找到元素，再点击"句式合法），把它们当失败会制造假红；如实标为"疑似，需人看"。

**D4 结构指纹用于稳定性。**

每次重复取"步骤数 + 每步副作用动作序列"作为指纹；重复 N 次后统计众数占比（`稳定性 = 众数次数 / 总次数`），报告里给百分比并列出各次指纹。

**D5 成本复用既有计价，不另写算法。**

每次调用取 `RoleResult.usage`（输入/输出/缓存命中）与 `RoleResult.cost`（引擎侧已按 `billing` 的价目算好）；命令内累加，报告给"总花费 + 单次均值 + 按用例拆分"。

**D6 报告落 `tests/reports/planner_eval/<标签>-<时间戳>.md`；控制台同时给总表。**

`--tag` 由调用方给（如模型名或提示词版本），用于同批对比时区分文件；报告包含：运行参数（模型名、用例数、重复次数）、汇总（硬性通过率、平均稳定性、总费用、总耗时）、逐用例明细（各项 ✓/✗、疑似提示、plan 原文、工具轨迹、token/费用）。

**D7 不写库、不建任务、不用设备。**

命令只在进程内装配角色并调用模型；不触碰 `ai_tasks`、不占用设备池。执行期用 `--dry-run`？——不需要：**不做**"先干跑一次"这类子模式，避免半成品（真实调用即是评测本身）。

**D8 退出码语义：硬性失败不影响退出码（评测不是门禁）。**

命令始终以 0 退出（除非参数错 / 装配失败），失败项体现在报告里。理由：它是按需评测工具，不是门禁——避免被误接进 CI 造成"模型波动即红灯"。

## 模块防火墙自检

- 跨 App import：命令在 `apps/ai_assistant` 内，只 import 本 App 的 `model_debug` / `api` 与引擎公开入口；无新增跨模块依赖。
- 写库路径：**零写库**（不建任务、不写进度）；用例集是文件，报告写 `tests/reports/`。
- 前端：零改动（不新增接口）。
- 引擎边界：经引擎包级公开入口取角色类；不 import 引擎内部实现细节以外的私有符号（`RoleResult` 属 `engines.ai.messaging` 公开导出）。
- 测试隔离：命令不写入生产数据库（只读装配），可在任何环境按需运行。

## Risks / Trade-offs

- [评测口径与生产漂移] → 复用 `build_device_models_for_agent`（D1），与 `model_test`、调试台同一装配；若将来装配入口变更，本命令随之。
- [机械判据误判（假红/假绿）] → 三级处理：硬性项只取"无歧义"的五条（D3 ①~⑤），其余降为"疑似提示"；报告如实标注口径，不冒充质量评分。
- [真实调用产生费用] → 报告给总花费与单次均值；用例集控制在 6~8 条、默认重复 1 次，重复次数由 `--repeat` 显式控制。
- [把评测误当门禁] → D8：始终退出 0；文档写明"按需运行、不入 CI"。
- [报告目录被误提交大量产物] → 报告写 `tests/reports/planner_eval/`；关单时确认该目录是否被 `.gitignore` 覆盖，若未覆盖则在任务里明确"是否入库"由使用者决定（默认不提交评测产物，只在汇报里给路径）。
- [用例期望写错导致假失败] → 用例集随本单一起交付并在任务中逐条自测（先对已知可控用例跑一次，确认期望与真实输出对齐再计入）。

## Migration Plan

1. 新增 `planner_eval` 命令（用例加载 + 装配 + 调用 + 校验 + 报告）。
2. 新增用例集（6~8 条，含单步 / 多步 / 指定设备名 / 带附件 / 模糊需求 / 需日志核对 / 页面流依赖场景）。
3. 自测：先用 1~2 条用例实跑，校正用例期望与报告字段；再跑全量一遍作为交付证据（会产生真实费用，属预期）。
4. 回滚：新增文件删除即可，无迁移、无数据变更。
