# 设计：修复模型配置页被误判为登录表单

## Context

现状（已逐条核实，见 proposal.md - Why）：

- `ModelConfigField.vue` 的 API Key 输入是 `el-input type="password"`，**没有任何 `autocomplete` 声明**；
- Element Plus 的 `el-input` 把 `autocomplete` 声明为**属性**（`input.mjs:86`）且默认值为 `"off"`（`input.mjs:227`），所以该密码框当前 DOM 上其实是 `autocomplete="off"`；
- `el-form` 渲染的是**真正的 `<form>`**（`form.vue_…mjs:191` 的 `createElementBlock("form", …)`）；
- 该表单内密码框的正上方就是"模型名"下拉（内部为文本输入框），构成浏览器识别登录表单的"文本 + 密码"组合；
- 全前端 `src/` 对 `autocomplete` 零命中 —— 登录页（账号 / 密码）与注册页（邮箱 / 两个密码）也都没声明。

## Goals / Non-Goals

**Goals:**

- 让浏览器不再把模型配置表单当成登录表单（不再提示保存/填充凭据）。
- 顺带让登录 / 注册页的密码管理器行为规范（该填的填、该存的存、不该混的不混）。
- 用自动化钉住"组件把正确的提示属性交给了输入框"，防止后续改动静默移除。

**Non-Goals:**

- 不改 API Key 的**可见性机制**（仍用原生密码框 +"显示/隐藏"切换）；不改任何校验、提交、接口契约。
- 不为登录 / 注册页重新设计表单结构。
- 不做浏览器兼容的兜底分支（如按 UA 分支）——提示属性是标准机制，无需运行时判断。

## Decisions

**D1 采用 `autocomplete="new-password"` 这一最小改（用户已选）。**

语义正是我们要的："这是**新**凭据，不要用已有密码来填充"。相对 `off`（Chrome 对密码框忽略）与 `current-password`（会主动找已保存密码来填），它是唯一既保留原生密码框体验、又能阻止"当登录密码处理"的取值。
备选：不用密码框类型、改文本框 + CSS 掩码 —— 提示必然消失，但 Firefox 不支持该掩码样式，需要回退方案（显明文或另造掩码），改动面与风险都更大；本次不做，若仍有残留提示再评估。

**D2 属性经 Element Plus 的声明式 prop 落到原生 input。**

我们写在 `<el-input autocomplete="new-password">` 上的是它的**声明式属性**（不是 `$attrs` 透传），Element Plus 会把它渲染到内部原生 `<input>` 上。这一点已核实其属性定义与默认值，故自动化只需断言"组件给输入框传了该值"，最终 DOM 行为由框架保证。

**D3 登录 / 注册页按语义分别标注。**

登录页：账号 `username`、密码 `current-password`（允许/建议填充已保存凭据）；注册页：邮箱 `email`、两个密码 `new-password`（都是新凭据，且避免与登录页凭据混淆——这也顺带降低"注册页被当成登录页"的误判）。

**D4 验证口径要诚实：浏览器气泡自动化断言不了。**

密码管理器的提示是**浏览器原生 UI**（不在 DOM 里），Playwright/vitest 都读不到。因此本单的自动化只做两件事：① 钉住组件到输入框的属性传递；② 保证不破坏既有交互用例。**最终确认必须由使用者在真实浏览器里肉眼复核**（打开配置页 → 选模型名 → 看是否还弹提示），这一点写进任务清单并如实汇报。

## 模块防火墙自检

- 跨 App import：无（纯前端改动）。
- 写库路径：零改动。
- 前端 HTTP 出口：零改动（不新增请求、不改 api 层）。
- 引擎 / 后端 / 数据库 / 通道：零改动。

## Risks / Trade-offs

- [Chrome 某些版本仍可能弹"保存密码"气泡] → `new-password` 已阻止"用已有凭据填充"；保存气泡由浏览器策略决定，无法从页面完全控制。若仍出现，按 D1 的备选（去密码框类型 + 掩码）再改一单。
- [属性加错位置（加到包装层而非输入框）] → 用 Element Plus 的声明式属性（D2）而非自定义包装；用例断言到组件接收值这一层。
- [修改登录 / 注册页影响既有认证用例] → 认证用例的输入框桩需同步透传该属性；改完跑 `tests/login/` 相关用例（按文件跑，不发起全量前端测试）。
- [测试桩掩盖真实 DOM] → 用例只证明"传值正确"，不声称"DOM 一定正确"；DOM 侧由框架行为 + 使用者的浏览器复核兜底（D4）。

## Migration Plan

1. 四个前端文件加属性（配置页 API Key；登录页账号/密码；注册页邮箱/两个密码）。
2. 扩展/新增用例钉住属性传递。
3. 验证：相关 vitest 用例（按文件）、`npm run typecheck`、eslint、prettier；随后请使用者在浏览器复核。
4. 回滚：纯属性改动，`git revert` 单次提交即可。
