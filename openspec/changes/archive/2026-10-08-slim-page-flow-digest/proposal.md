# 规划读取的页面流摘要只给「页面与节点关系」

## Why

规划模型读页面流的出口叫「语义摘要」（`get_page_flow` → `apps/workflow/semantics.py` 的 `build_graph_digest`），但它实际返回**全量图谱**。实测平台唯一那篇页面流文档（17 节点 / 16 连线）：

| 项 | 实测 |
| --- | --- |
| 摘要全文 | **27,473 字符** |
| 去掉元素清单后 | **12,722 字符**（**省 54%**） |
| 页面元素条目 | **74 条** |
| 其中 xpath 非空的 | **0 条** |

两个问题：

1. **费钱且无用**：元素清单占一半以上体积，而 **xpath 全是空的**——既不能定位，又会诱导模型在计划里引用"页面流元素"。
2. **实现漂移**：这个出口的名字与规格口径都是「语义摘要」，返回全量元素属于实现超出本意。规划真正需要的是「从哪一页、点哪个入口、到哪一页」——该信息在**连线**上（触发口名称实测非空，如「设备主页入口」）与路径文本里，**不在元素清单里**。

**顺带发现（一并收口）**：执行模型的提示词写着「优先使用页面流里的元素 xpath 定位」「按页面流的跳转边逐页推进」，但执行角色的工具子集里**没有任何页面流工具**，它根本读不到页面流；即便读到，那些 xpath 也是空的。这是三处**空指令**，留着会误导模型、也会诱导将来把元素塞回摘要。

## What Changes

- **摘要瘦身**：节点条目不再输出 `elements` 与 `navigation_entries`；保留节点（页面身份 / 起点 / 弹窗）、连线（含触发口名称）、路径与出入关系。
- **不牺牲诊断**：原由元素收集顺带产生的「连线端口槽位不可解析」告警，改在连线遍历处产生（去重），`parse_warnings` 能力不退化。
- **清理死代码**：`_collect_elements` 与其专用辅助 `_element_source` 随之下线（`_resolve_port_targets` 仍被弹窗逻辑使用，保留）。
- **执行提示词收口**：`VISION_PROMPT` 中三处"页面流"表述改为与它实际能力一致——**视觉定位优先；元素 xpath 仅在步骤里明确给出时使用；推进按步骤而非"按页面流跳转边"**。
- **评测口径收敛（用户指定）**：正式测试**只用 `deepseek-flash`**、只跑**单步与多步**两条用例；其余 5 条（四键 JSON / 附件 / 指定设备名 / 需日志核对 / 模糊需求）移入**扩展用例文件**保留资产、默认不跑。

## 关联文档

- 关联能力：`ai-device-planner-tools`（规划读到的页面流摘要口径）。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `ai-device-planner-tools`：**新增**一条需求——规划读取的页面流摘要 MUST 只含页面与节点关系（节点 / 连线 / 路径 / 出入关系），MUST NOT 输出页面元素清单。既有两条需求（planner 装配页面流工具、提示词指引先列后读）不受影响、原文保留。

## Impact

- 后端（工作流域）：`apps/workflow/semantics.py`（摘要构造、告警位置、死代码下线）。
- 引擎：`engines/ai/agents/config.py` 的 `VISION_PROMPT`（执行提示词三处表述）。
- 评测：`tests/ai_planner/cases/planner.yaml` 收敛为 2 条；新增 `tests/ai_planner/cases/extended.yaml`（5 条）。
- 测试：新增页面流摘要形状用例（**此前该摘要零测试覆盖**，属既有缺口）；评测单测补"主用例集恰为 2 条"的口径守卫。
- **不受影响**：前端（该摘要不经 HTTP 下发，仅 AI 工具读取）、任务链路、数据库、元素定位域（元素的真相源在元素定位域，不在页面流摘要）。
- **成本影响**：规划每次读取的输入体积减半，费用随之下降。
