## Context

- 现状（上一单落地）：模型图 = 原始帧 → 最长边 1280 → JPEG 85 → base64（实测单张约 65 KB）；本地图 = 原始帧 → 全分辨率 JPEG 90（约 180 KB）。
- 用户要求：**给模型的图不压缩**（模型需要看到原始细节，压缩与缩放会影响小控件、选中态识别）。
- 实测参考：同一张原始帧编码为 PNG 后 base64 约 800 KB（约为 JPEG 档的 12 倍）。

## Goals / Non-Goals

**Goals:**

- 模型图无损、原尺寸（PNG），媒体类型如实为 `image/png`。
- 本地图与其余链路不受影响（仍是全分辨率 JPEG 90、毫秒命名、相对路径形状不变）。

**Non-Goals:**

- 不改本地图格式与命名。
- 不改截图工具的参数表与返回字段（仍只有路径与文件名）。
- 不为"省 token"再做任何自动降采样（若成本不可接受，按数据另行决策）。

## Decisions

**D1 模型图用 PNG（无损）而不是"不编码"或 BMP。**
理由：base64 需要一份确定的字节流；PNG 是无损压缩（像素不失真），体积远小于 BMP，且是模型供应商普遍支持的图片格式。备选：BMP（无损但巨大）、JPEG 100（仍是有损）。

**D2 不缩放、不设上限。**
理由：用户口径是"不压缩"；缩放同样会丢小控件细节。风险（体积、延迟）如实记录在案，不用隐藏的默认值兜。

**D3 本地图仍用 JPEG 90。**
理由：本地图是给人看的证据，体积可控；"不压缩"的要求只针对给模型的图。

## 模块防火墙自检

- 只改引擎设备动作层与测试，依赖标准库 + Pillow（既有依赖）。
- 不改落点注入、不 import 平台模块、无写库路径、前端不涉及。

## Risks / Trade-offs

- [单张给模型的图由约 65 KB 涨到约 800 KB（约 12 倍），视觉 token 与延迟上升] → 如实记录；若识别质量提升明显但成本过高，再按数据决定是否分档（例如"小图无损、大图分块"）。**不做**隐藏的自动缩放。
- [部分模型供应商对单张图片有体积上限或服务端会自行缩放] → 实测我方档位远低于常见上限；若某供应商限制更严，报错如实回传，不静默降级。
- [上下文里图片数量上限不变（5 张），无损图会更快占满] → 现有上限照旧生效；真机回归观察是否出现"图片被挤出上下文"导致判断退化。

## Migration Plan

1. 设备动作层：模型图编码改为无损 PNG、去掉模型侧缩放与质量档位；媒体类型随之。
2. 测试：截图链路单测改为断言"模型图为 PNG、尺寸等于原始帧、与原始帧像素一致"。
3. 真机验证一次（记录新的 base64 体积与图片尺寸）；门禁与归档。

回滚：还原模型图编码档位即可；本地图与其它链路不受影响。
