## Context

- 旧链路：设备控制层的 `screenshot()` 先用 Pillow 压成 JPEG 质量 55 返回字节；截图动作把这份字节写盘（文件名 `capture_<微秒>.png`，内容其实是 JPEG）；工具层再用 Pillow 缩到最长边 1280、压 JPEG 85、转 base64 给模型。**两次有损 + 命名与格式不一致。**
- 平台侧还有一条快照链路用同一个 `screenshot()`（设备检查器保存快照），因此不能直接改它的语义。
- 工具返回的图片数据形状必须保持框架可识别的约定：`{"image": {"base64", "media_type"}, "summary": {…}}`（框架据此装箱成图片块给模型）。

## Goals / Non-Goals

**Goals:**

- 从原始帧只编一次：模型图与本地图共用同一份无损来源。
- 本地图毫秒命名、全分辨率、扩展名与格式一致。
- 工具同时返回模型图与本地图信息；不落盘分支仍给模型图。

**Non-Goals:**

- 不改平台快照链路（既有 `screenshot()` 语义与产物保持不变）。
- 不改模型图档位（仍 1280 / JPEG 85）；档位对照实验另议。
- 不改截图工具的参数表与工具说明（仍是 `serial` + `keep_local`）。
- 不改历史文件的命名（存量仍为旧 `.png`）。

## Decisions

**D1 新增"取原始帧"能力，而不是改既有 `screenshot()`。**
理由：平台快照链路依赖既有 JPEG 产物；改它会影响设备检查器的存储体积与页面。新增一个无损取帧入口，只有引擎的截图动作使用。备选：直接改 `screenshot()` 为无损（影响面超出本单）。

**D2 编码与落盘都收口在设备动作层（`Screenshot`），工具层只做适配。**
理由：动作层本来负责"在设备上做事"，编码档位与命名属于同一处口径；工具层此前那次重复编码随之删除。备选：把编码留在工具层（会出现两处编码口径，正是本次要消除的问题）。

**D3 本地图用 JPEG 90 全分辨率，而不是无损 PNG。**
理由：同一张 1080×2340 的图，PNG 约 0.8MB、JPEG 90 约 0.18MB（实测）；证据图给人看，90 档肉眼无损，磁盘占用可控。备选：PNG（更纯净但体积约 4 倍）。

**D4 时间戳取毫秒三位（`%f` 前三位），不加序号后缀。**
理由：用户口径明确；一次截图耗时远大于 1ms，碰撞概率可忽略。若日后真出现同毫秒碰撞，再考虑后补序号。

## 模块防火墙自检

- 只改引擎（设备动作层与工具层）与测试，依赖标准库 + Pillow（既有依赖）。
- 不 import 平台模块；不改落盘根目录的注入方式（仍由调用方给出）。
- 无跨 App 依赖、无写库路径、前端不涉及。

## Risks / Trade-offs

- [原始帧比 JPEG 大（约 0.8MB），采集与两次编码的内存瞬时占用上升] → 单张量级、逐张释放；不缓冲、不排队。
- [平台快照链路与引擎截图从此用不同档位] → 属预期：平台快照要体积小、模型图要清晰；两者都在文档里写明各自档位。
- [毫秒命名在同毫秒内可能重名] → 实测一次截图远超 1ms；真出现则后补序号（已记在 D4）。
- [前端/报告消费方仍按 `.png` 找图] → 相对路径形状未变、前端按路径渲染；只有"按扩展名硬筛"的脚本会受影响，本单实施时全仓 grep 确认无此类消费方。

## Migration Plan

1. 设备动作层：新增取原始帧契约方法 + Android 实现；重写截图动作（一次编码 + 毫秒命名落盘）。
2. 工具层：改用一次编码结果，删除重复编码函数与无用导入。
3. 测试：新增截图链路单测；真机验证一次（本地图全分辨率、模型图档位、毫秒命名）。
4. 回归：设备与工具相关单测、ruff、架构边界。

回滚：还原截图动作的编码与命名实现即可；存量文件不受影响。
