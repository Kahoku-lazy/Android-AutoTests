## Context

动机与范围见 `proposal.md`。方案需要知道的当前状态：

- `engines/agents` 是独立脚手架（当前 git 未跟踪），已有执行角色与验收角色，两者都是「同步门面 + 私有异步实现」：对外只有「给一句话、拿一条消息」的同步入口，异步细节藏在私有方法里。
- 角色就绪时才创建智能体，且智能体只在就绪那一步创建一次；过程日志、计费、消息记录都挂在这套角色上。
- AgentScope 2.0.9 提供实验模块 `agentscope.sop`（`SOP` / `SOPStep` / `SOPEngine` / `SOPRunState`）。它的步骤契约是：一次调用一次尝试，执行者以结构化「交接说明」交付、验收者以结构化「是否通过 + 驳回说明」结案；驳回原因原样回灌给执行者重做。
- 框架的结构化输出由内置工具 `GenerateStructuredOutput` 实现，工具描述要求模型「必须以调用该工具结束回复」；脚手架既有的执行/验收提示词要求「最终回答只输出一个 JSON 字符串」，两者直接冲突。
- 框架的事件流已经是可用的事实来源：每次模型调用结束都会发一个带输入/输出/缓存命中 token 的事件，事件自带时刻；模型调用开始事件自带模型名。

## Goals / Non-Goals

**Goals:**

- 让「多步设备检查」在脚手架内一次跑完：按里程碑逐个执行、逐个验收、驳回重做。
- 让整次运行的用量与费用可核对，且费用口径经得起跨高峰时段的检验。
- 让 SOP 路径下的思考与工具调用照样进过程日志，并能按「角色 × 步骤 × 第几次尝试」定位。

**Non-Goals:**

- 不改平台引擎（`engines/ai`）与其对外行为，不并入平台用量统计。
- 不实现平台侧的步骤证据装配（点击前时间戳、设备日志关键词、验收截图落盘）——那是平台工作流的职责。
- 不新增自定义步骤类型（例如不经模型的确定性检查）；本次只用「执行 + 验收」这一种步骤形态。
- 不做运行状态的持久化落盘策略；只提供导出与重建的接口，落到哪里由调用方决定。

## Decisions

### 决策 1：编排用框架的 SOP 模块，不自研步骤循环

用 `agentscope.sop` 的定义、步骤与引擎；脚手架只负责装配、驱动与可观测。

- **理由**：驳回回灌、重试上限、结构化交付/结论、运行状态可序列化都是框架已实现且已文档化的行为；自研等于重写一遍这些语义。
- **备选**：像平台工作流那样自研步骤循环（自管阶段与重试）。平台这么做是因为它要接自己的证据装配与日志窗口；脚手架没有这些约束，自研只会多出一份需要维护的状态机。

### 决策 2：把框架步骤的执行者/验收者接到「角色内已创建的智能体」，而不是角色对象

装配时取角色上已就绪的智能体实例交给步骤。

- **理由**：框架要求的能力是「可被要求以结构化输出结束的一次流式回复」，而角色的对外面是同步门面（无此能力）；角色内已创建的智能体天然满足该能力，无需改角色的对外接口。
- **备选一**：给角色补一个符合框架要求的流式入口，让角色自己满足契约。生产侧走的是适配器路线；这条会把角色的职责从「同步门面」扩成「同步门面 + 框架管道」，改动面更大。
- **备选二**：单独写一层适配器（生产侧 `workflow/sop_step.py` 的做法），把「角色怎么跑」与「框架要什么」隔开。这是最终更干净的方向，但需要新增一个编排层；本次先用最小改动落地，代价记在风险里。

### 决策 3：SOP 用独立提示词，不复用既有 JSON 契约提示词

新增 SOP 专用执行/验收提示词，并让角色构造时支持覆盖系统提示词与角色名。

- **理由**：结构化输出由内置工具产出，与「只输出一个 JSON 字符串」互斥；混用会让模型按旧契约输出，框架收不到结构化交付，步骤被记为「没有交付」并消耗重试次数。
- **备选一**：改既有提示词适配结构化输出。会把非 SOP 场景的行为一起改掉，且平台侧 `engines/ai` 的提示词与之一字不差地对应，容易两边漂移。
- **备选二**：让适配层忽略框架 schema、由代码自己造结构化输出（生产侧做法）。那样交付内容就不再由模型决定，SOP 的「执行者自己写交接说明」这一语义会丢。

### 决策 4：费用按每次调用分别计费后求和

在模型调用结束事件上，用**该次调用的时刻与模型名**算三项费用并累加。

- **理由**：计费器按调用时刻判高峰（工作日 9–12、14–18 双倍），且每项金额各取 4 位小数；先合并 token 再算一次，会把高峰与空闲两段的单价抹平成一段。模型名同样只能按次取——跨角色可能不是同一个模型。
- **备选**：先累计 token，运行结束算一次。实现更短，但跨高峰边界时误差可达一倍，且日志里已有的逐次 token 行无法对账。

### 决策 5：汇总只留内存与过程日志，不写平台用量统计

运行器在内存累计，并在每次推进结束时往过程日志写一条汇总记录。

- **理由**：脚手架不属于平台，平台用量统计的口径、去重与归属规则都在平台侧；把脚手架的数字塞进去会污染平台看板。
- **备选**：写进平台用量表。需要新增落库与归属逻辑，且本次非目标。

### 决策 6：SOP 路径的过程日志由运行器消费事件流

运行器按「回复开始事件」切换角色、按「步骤起止事件」切换阶段标识，把事件交给同一份过程日志写入器。

- **理由**：框架引擎直接驱动智能体，绕过了角色的同步门面，角色侧那套「上屏 + 记日志」不会被触发；事件流是唯一的共同来源。
- **备选**：让角色在 SOP 路径也自己记日志。需要在角色与运行器之间传递「当前是哪个步骤」，耦合更紧，且步骤名只有运行器知道。

## 模块防火墙自检

- 跨 App import：本变更不新增任何跨 App import，也不改动 `apps/` 下任何代码。
- 写库收敛：本变更不产生任何 INSERT / UPDATE / DELETE，不接触 ORM 与数据库。
- 前端：不涉及前端代码，前端不直连数据库的红线不受影响。
- 新跨模块依赖：新增的依赖都在 `engines/agents` 包内（计费、过程日志、消息记录）与第三方框架 `agentscope.sop`；没有任何一项需要走 `api.py`。
- 平台引擎：`engines/ai` 零改动，因此不触及引擎边界与通信通道边界。

## Risks / Trade-offs

- [SOP 路径下角色就绪时的日志开关不起作用，日志其实由运行器沿用那个日志对象写入] → 本次在文档与代码注释层说明「SOP 模式沿用执行角色那份日志」；后续变更可把开关与落点归位到运行器，使两条路径语义一致。
- [用量与费用不随运行状态持久化，跨进程续跑只统计新进程] → 规格里已如实声明该边界；后续变更再补一份随运行落盘的用量文件。
- [多个步骤共享同一个智能体，步骤越多上下文越长] → 依赖既有的上下文压缩配置（触发比例、保留最近图片数）；若仍超限，可改为每步重建角色。
- [步骤描述写成「检查某状态」会让驳回原地打转（重做的是检查本身）] → 用法约定要求描述写成「要达成的状态」；默认步骤列表按此口径编写。
- [框架 SOP 模块处于实验阶段，接口可能变动] → 引用面收敛在装配与驱动两处；升级框架时按一次独立变更处理。
- [过程日志会同时被角色路径与 SOP 路径写入同一文件] → 记录里带角色名与阶段标识，两种路径的记录可按第 4 列区分。

## Open Questions

- 非 DeepSeek 提供商何时接入计费：当前口径是只统计用量、费用为 0，与既有单轮计费一致；接新提供商时是否需要独立变更。
- 过程日志第 3 列的模型名是否改成取「模型调用开始事件」自带的模型名：当前用的是运行器构造时传入的单一模型名，执行与验收用不同模型时该列会与实际不符；不影响本次规格（规格只要求记录带模型名）。
