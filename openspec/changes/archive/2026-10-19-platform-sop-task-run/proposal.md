## Why

平台小助手的新建任务仍把一份 Word/PDF 交给规划模型生成步骤，和已经能按 YAML 跑起来的 SOP 是两条执行链。控制设备任务应只负责启动和关闭这一条 SOP：标题与目标保持不变，配置与文档分开上传，格式检查和文档解析留在后端，智能体只接收检查通过的 YAML 文件和已经解析好的 Markdown。

## What Changes

- 控制设备任务的执行改为启动 / 关闭 `engines/agents` 中已有的 SOP。不再由规划模型从目标生成步骤。
- Agent 的工具以 `engines/agents` 代码为准。后端启动任务时不传入、不筛选、不替换工具清单。装配台「交给助手」不作用于这次 SOP。
- 新建任务的标题、目标、设备选择保持必填口径不变。
- **BREAKING** 任务附件改为两类，且都可以多份上传：
  - 配置：界面列出 csv、yaml、json；csv 与 json 标明暂不可用且不能选择；只有 YAML 可提交。一次任务只收一份 YAML。
  - 文件：markdown、Word、PDF。后端用 MarkItDown 解析为 Markdown 并写入数据库。
- 新建任务弹窗提供助手下拉。选项与平台小助手卡片当前展示的助手一致，当前只有控制设备这一条；只有一条时默认选中，且必须选择后才能提交。所选助手决定本次执行与验收模型。
- YAML 不必写 `agent`。未写时按 `sop` 跑。若写了 `agent`，全文件必须相同且等于 `sop`。后端先做格式检查；执行前再读该文件，通过则任务显示「配置加载成功」，不通过则显示「加载失败」且不跑步骤。
- 同一份 YAML 里的多条用例按文件顺序在同一次任务中跑完。任务目标与设备序列号作为开场说明，不拿来挑选用例标题。
- 磁盘上的原始上传文件保留 7 天后删除。数据库中的 Markdown 与 YAML 正文保留；原件过期后，启动时用库内正文重新落成临时文件再交给智能体。
- 用户关闭运行中的任务后，该任务进入终态，并按既有排队拉起同一设备上的下一条。
- 失败任务「重新执行」复制全部附件（含 YAML 正文与文档 Markdown）。

## 关联文档

PRD-08。本单收窄的是该 PRD 中「设备操控」任务的提交与执行方式，无单独子编号。

## Capabilities

### New Capabilities

- `sop-task-run`: 控制设备任务如何启动和关闭 SOP，助手如何在新建任务弹窗选择，YAML 如何在不写 `agent` 时仍按 `sop` 跑，工具如何只来自引擎代码，以及执行前如何报告配置加载成功或失败。

### Modified Capabilities

- `ai-task-publishing`: 附件从「至多一份 Word/PDF、交给规划模型」改为「一份 YAML + 多份文档」；详情不再展示规划入参，改为展示配置加载结论、开场说明与文档 Markdown。
- `ai-task-device-dispatch`: 用户关闭运行中的任务与完成、失败一样释放该设备槽位，并拉起下一条排队任务。

## Impact

- 后端：`apps/ai_assistant` 的任务提交、附件解析、任务详情、关闭任务与 `task_runner`；新增 MarkItDown 依赖；上传清理继续使用现有 7 天策略，任务附件必须落在该上传目录。
- 引擎：`engines/agents` 的 SOP 入口接收平台传入的 YAML 路径、开场说明、文档 Markdown，以及控制设备线路上的执行 / 验收模型。工具由 `tools_config.py` 与 `tools/tool_*.py` 装配，入口不接收工具清单。不在引擎内做 MarkItDown 或上传校验。`engines/ai` 的规划工作流不再被控制设备任务调用。本单不删除 `engines/ai`。
- 前端：新建任务弹窗的助手下拉与附件区、任务卡片上的附件名、任务详情中的加载结论与附件正文；运行中任务提供关闭。助手下拉与平台小助手卡片使用同一份展示列表。
- 数据：任务附件从单字段扩展为可多条；任务状态增加关闭终态。
- 测试：任务提交、YAML 校验、文档解析、同设备排队、关闭后拉起下一条、重新执行复制附件。不跑全量回归。
