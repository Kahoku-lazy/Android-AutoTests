## Context

平台在 `run_platform_sop` 里按 YAML 逐条跑用例。一条用例是一份 SOP，返回后才决定下一条还是结束任务。设备侧已有按包名 `am force-stop` 的 `app_stop`，以及从 `dumpsys window` 解析当前前台的 `_parse_current_app`。当前前台只有一个包，读不到最近任务里其余应用。见 proposal.md - Why。

## Goals / Non-Goals

**Goals:**

- 每条已经开始的用例在步骤结束之后，由引擎关闭最近任务里的非桌面应用并回到桌面。
- 收尾失败只记日志，不改通过、失败或取消。
- 解析最近任务包名可以不连设备单测。

**Non-Goals:**

- 不把收尾写成 YAML 步骤，也不新增模型工具。
- 不删除已有用例里的关闭步骤。
- 不改本地调试入口 `ui_auto_workflow.run_workflow`。它没有独立的设备序列号参数，平台入口才有。
- 不改「前一条失败则不跑后一条」的顺序。

## Decisions

1. 收尾挂在 `run_platform_sop` 的每条用例之后，放进该条的 `finally`。通过、失败、执行中抛出的取消都会走到这里。循环开头发现取消标记已置位、本条还没开始时直接返回，不收尾。备选是只在通过后收尾，失败时设备会留在被测应用里。
2. 平台入口增加设备序列号，由 `task_runner` 传入任务上的 `device_serial`。序列号为空则跳过收尾并记日志。备选是从开场说明里拆序列号，模板一变就会关错设备。
3. 收尾函数可注入。缺省实现才连设备。现有用替身跑用例的测试不传序列号，因此不会连设备。新测试传入假收尾，断言调用次数与判决不变。
4. 最近任务用 `dumpsys activity recents` 的原文解析。包名取 `realActivity=` 与 `cmp=` 里 `/` 前的一段，按出现顺序去重。桌面包名用 `cmd package resolve-activity` 解析 HOME，并固定跳过 `com.android.systemui`。解析不到桌面时，再跳过一组常见桌面包名，避免把桌面停掉。备选是只停当前前台，最近任务里退到后台的应用会留下。
5. 停应用沿用已有的 `app_stop`，全部停完后再按 Home。一次收尾只开一次设备连接。成功与失败都写一条事件日志，写明停了哪些包或失败原因。不写入步骤清单。

## 模块防火墙自检

- 收尾在引擎内完成，引擎不导入 apps。
- `task_runner` 只多传设备序列号，不新增写库。
- 前端与仪表盘不参与。

## Risks / Trade-offs

- [最近任务输出格式因系统版本不同而解析不到包名] → 解析函数用固定样例单测；解析结果为空时仍按 Home，并记日志。
- [桌面解析失败导致停掉桌面] → 固定跳过系统界面，并备一份常见桌面包名。
- [收尾本身抛错] → 调用处接住异常，只记日志，判决用步骤已经返回的阶段。
- [用例 YAML 里仍有关闭应用步骤] → 该步骤仍由模型执行，可能先把用例判失败；引擎收尾发生在判决之后，不把失败改成通过。

## Migration Plan

- 无数据迁移。回退时去掉用例 `finally` 里的收尾调用即可，步骤判决不受影响。
