## Context

见 proposal.md - Why。小时用量已经按智能体、角色、模型、统计日写入。仪表盘原先读任务上的 token 列，并用四位小数重算费用。

## Goals / Non-Goals

**Goals:**

- 五张用量卡、智能体卡、近 12 日 Token 与费用曲线共用小时用量合计。
- 一个智能体一份数字，角色和模型只作为加总来源。

**Non-Goals:**

- 不改角色计费函数，不改任务卡上的费用。
- 不改任务数量的数据源。
- 不把角色芯片收成一张。

## Decisions

1. 读小时用量表，按当前用户可见智能体的标识过滤。今日用统计日等于当天，不用任务创建时间。备选是继续读任务 token 列，但那些列与小时表已经分叉。
2. 智能体卡按智能体标识分组求和。显示名用现有助手名称解析。费用用 8 位十进制字符串，避免浮点把末位吃掉。备选是按角色各出一张卡，与「作为一个整体」相反。
3. 任务数仍数可见任务。平均每任务 Token 用小时表的输入加输出，再除以这个任务数。
4. 近 12 日曲线按统计日分桶，与卡片同一合计。

## 模块防火墙自检

- 仪表盘只读智能体、任务、小时用量三张表，不写库。
- 助手名称解析走 `apps/ai_assistant/api.py` 的既有只读函数。
- 前端只消费既有仪表盘统计接口，不新增请求，不直连数据库。

## Risks / Trade-offs

- [任务 token 列与小时表不一致] → 卡片以小时表为准，任务列留给任务卡，两处数字可以不同。
- [平均每任务混用两张表] → 任务数保持原口径，Token 与费用跟卡片一致。
- [可见智能体很多时卡片变长] → 只列出当前用户可见的智能体，零用量也保留，避免漏掉新建助手。
