# 设计：事件流信息完整性与运行预算

## Context

事件流只有一条落地路径，中间没有独立的事件接口：

```
AgentScope 事件 → fold.step() → EventRecord → TaskEventSink.emit() → task_events
                                                                        ↓
                              GET /api/tasks/{id}/report/ → task_reports → 前端 rounds
```

- `fold.step` 是纯函数：只按事件类型名分派，产出日志行与结构化记录，不写库、不依赖应用层。它只认 11 种事件，其余（含 `CustomEvent`、`HintBlockEvent`、`ExceedMaxItersEvent`）落到空结果。
- SOP 的步骤边界由框架以 `CustomEvent(name="SOP_STEP_STARTED"|"SOP_STEP_ENDED")` 发出；「推理轮次用尽」由 `ExceedMaxItersEvent` 发出；运行时注入提醒由 `HintBlockEvent` 发出。三者都在既有事件流里，只是被折叠层忽略。
- `RunContext` 是 `ContextVar` 上的可变 dataclass。工作线程通过 asgiref 的 `copy_context()` 进入，复制的是上下文映射、值仍是同一个对象引用，因此工作线程改字段、主线程立即可见——这也是既有 `set_step_context` 能工作的原因。
- 前端不读 `event_type`，只渲染后端给出的 `label` 与 `detail`，新增事件类型无需改前端。

## Goals / Non-Goals

**Goals:**

- 事件表能独立回答两件事：这次运行跑到了哪一步；这一轮为什么停。
- 一个任务里的每条用例在事件表里可区分（用例标题、步骤号从 1 重启）。
- 运行有次数与时长兜底，超限时以可预期的方式停止，且不丢已落库事件。
- 写库容错：一行写不进去不拖累同批其余行，长载荷不会把整批顶穿。

**Non-Goals:**

- 不把流式增量原文落库（保持现有「增量折叠成计数」的设计）。
- 不引入任务级费用上限（费用由调用次数间接约束，口径仍只由计费模块决定）。
- 不新增列、不写迁移、不改接口形状与信封。
- 不处理人工确认/外部执行（`RequireUserConfirmEvent` 等）——当前工具全部自动放行，触发不到；此处只登记为潜在缺口。
- 不修改既有「某条用例失败后是否继续下一条」的行为（见 Open Questions）。

## Decisions

### D1 用例名用 `set_case_title` 刷新，不重新绑定运行上下文

- 理由：与既有 `set_step_context` 完全对称，不需要额外的 token/reset 作用域管理；跨线程可见性由同一机制保证。
- 备选：每条用例重新 `bind_run_context` + `reset`——多一个令牌要管，异常路径容易漏 reset；在写库层读任务表——写库层拿不到「当前正在跑哪条用例」。

### D2 只落步骤起点，不落步骤终点

- 理由：终点等于下一个起点或整次运行结束，信息冗余；更关键的是落终点会与步骤号的打点逻辑错位——该步结束时可能已是 `completed`，按「第一个未结束的步骤」匹配会算到下一步。
- 备选：起点终点都落 → 需要维护额外的「当前步骤游标」，与框架状态重复。

### D3 预算挂在运行上下文，中断用内置 `RuntimeError`，终止判定用标志位

- 理由：项目规范禁止新增自定义异常类，只能抛内置类型；调用方靠标志位而非异常类型判断是否预算触发，避免字符串匹配。
- 备选：自定义异常（规范禁止）；只在用例之间检查（用例内部打断不了，一次用例就能把预算吃穿）。

### D4 计数点放事件展示层，不放进接收方

- 理由：每一轮事件都经过展示层，能在用例内部即时打断；接收方只该负责写库，不该决定运行生命周期。
- 备选：在接收方的 `emit` 里计数——写库失败会连带影响预算判定，职责也混。

### D5 批量写入先把行摘出缓冲，再决定成败

- 理由：原实现失败后整批仍留在缓冲，下一条事件追加即再次整批重试，一路失败到收尾，最后收尾抛错把剩余事件全丢。先摘出、失败降级逐行，可以让坏行只丢自己。

### D6 分片按字节上限，不只按行数

- 理由：一条长载荷（例如整段设备日志）能让 50 行的批直接撑到几十 MB，只按行数分批挡不住。

### D7 每条用例新建角色

- 理由：`sop-task-run` 既有要求已写明「后一条用例 MUST NOT 复用前一条的角色对话」，此前实现是整任务一个实例，属于实现与规范不一致；本次顺手对齐，同时抹平手工入口与生产路径的差异。
- 备选：共享实例 + 每用例清理上下文——要动框架内部状态，且并发任务下同一个实例不能同时被两条任务使用。

## 模块防火墙自检

- 引擎侧新增依赖只在同层：`fold` 只用已导入的 `EventRecord`；`messages` 只用同层的 `event_sink` 与 `fold`。**未**引入 `apps.*` 或 `django.*`。
- 后端写库仍只经 `api.insert_task_events`；`event_store` 不直接写 ORM 的 INSERT。
- 新增 `utils.logs` 依赖与既有 `task_runner` 一致，属日志工具而非跨 App 内部实现。
- 无新的跨 App import；前端零改动。

## Risks / Trade-offs

- [每条用例重建角色有毫秒级开销（会扫技能目录）] → 已实测可接受；若成为瓶颈，可缓存目录扫描结果但不可共享 toolkit 实例。
- [步骤起点让事件行每步每次尝试 +1] → 相对被折叠的增量行数可忽略（<1%）。
- [预算按次数计，不直接等价于费用] → 默认给到典型用量的 6 倍余量，且 0 可关闭；费用口径仍由计费模块单一决定。
- [`SOP_MAX_MODEL_CALLS` 设得过小会截断正常长任务] → 任务以可读原因失败且保留已完成用例与事件，便于判断是否调大。
- [坏行被丢弃且只记警告] → 警告带任务号、序号与事件类型名，可追查；不静默。
- [步骤起点行的角色与模型为空] → 报告的分轮逻辑对空角色已有兜底（存量轮次不渲染徽章），不会出现空徽章。

## Open Questions

- 「某条用例失败后是否继续下一条」：`sop-task-run` 写明 MUST NOT 开始后续用例，当前实现仍在失败后继续。需要产品口径确认后单独变更，本次不改。
- 「启动时组装执行与验收模型」仍描述从助手配置读取模型，而当前实现已把模型写死在引擎侧。属另一处规范与实现偏差，单独变更处理。
- 是否为正文/思考块补「块起始行」：可降低中断后整块文本无痕的比例，但每轮多两行。先观察一个迭代再定。
