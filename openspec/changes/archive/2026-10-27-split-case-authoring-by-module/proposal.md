# 用例编写按模块拆分并检测输出截断

## Why

一份大 PRD（110~157 个需求原子）要求编写角色在**一次 handover** 里写完整七节文档。2026-10-27 的六个失败任务里，四个的编写输出顶到 65,535/65,536 token 后被截断：文档停在用例表中间，第五~七节缺失，验收必然不通过；其中一个重写稿在 `<submission>` 之前就用完额度，交付为空。每次失败约 11~19 分钟、1.2~1.4 元，且重写仍从零开始，下一次照样截断。

另一半失败来自完整稿的质量问题（自造阈值、方法数、统计不符），但 `CASE_MAX_ATTEMPTS=2` 只给一次重写。截断和“最后一次机会”叠在一起，使大 PRD 几乎不可能通过。

## What Changes

- **先规划模块**：新增模块规划角色与提示词，读入带行号的需求正文，输出 2~12 个模块的行号区间（`start_line`/`end_line`），每个模块约 10~18 个需求原子；区间不重叠、按原文顺序、覆盖全部需求。规划输出只有几十行，不受文档长度影响。规划失败时按空行/标题/固定行数回退切块。
- **逐模块编写与验收**：每个模块单独跑一次「编写 + 验收」，需求正文只给该模块的行区间；不同模块使用不同的原子编号区段（`REQ-001`、`REQ-101`……）与模块缩写，避免 ID 冲突。任一模块通过验收才算该模块通过；整任务只有全部模块通过才 `completed`。
- **输出截断检测**：编写步骤记录每次模型调用的输出 token；达到 60,000 或交付缺少第六/七节、handover 为空时标记 `truncated`。截断的模块**不再重写、不再送验收**，直接把区间一分为二重新生成（最多递归两层）；切到单块仍截断才判失败，并在结果与摘要里写明 `OUTPUT_TRUNCATED`。
- **重试策略**：每个模块最多两次尝试（首稿 + 一次按验收意见重写）；截断不消耗第二次尝试。多模块的判决按模块前缀汇总，任务结果新增模块清单（键、名称、行区间、通过标记、截断标记）。
- **结果文档**：`Task.result.document` 为按模块拼接的完整 Markdown（带模块标题与验收结论）；每个模块仍是自包含的七节文档。
- **提示词**：编写提示词新增「模块化交付」小节（只处理片段、原子编号区段、E2E 编号带模块前缀）；验收提示词保持逐条判卷口径，SOP 步骤说明会告诉它本次是模块范围。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `appliance-case-authoring`：从「一步 SOP 全量交付」改为「模块规划 + 逐模块编写验收 + 截断拆分」。
- `appliance-case-authoring-task`：后台执行改为模块化流水线，任务结果新增模块清单与截断标记。

## Impact

- 引擎：新增 `prompts/case_module_planner_prompt.py`、`role/case_roles.build_case_planner`、`workflow/case_module_plan.py`；改写 `workflow/case_authoring_workflow.py` 与 `prompts/case_writer_prompt.py`。
- 后端：`task_runner._run_case_authoring` 调用模块化流水线；`Task.result` 增加 `modules`、`truncated`。
- 测试：新增模块规划/拆分/截断单测；更新提示词纪律断言与任务 runner 映射测试。
- 无数据库迁移；报告接口字段向后兼容（新增字段不破坏原 `document` / `verdicts`）。
- 成本：每个任务多一次规划调用（约 0.02~0.05 元）；大 PRD 从「一次 65K 截断 + 一次重写」变成「多块各自 15~25K 输出」，总 token 略增但成功率显著提高。
