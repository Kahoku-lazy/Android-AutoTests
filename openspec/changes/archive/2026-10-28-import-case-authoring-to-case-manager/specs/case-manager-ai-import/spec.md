## Purpose

定义 Agent-02 验收通过的测试用例如何从任务结果进入平台用例管理：落到哪个项目与文件、每条用例与每个步骤如何映射、来源如何追溯、重复导入如何幂等，以及导入失败时任务结论如何保持不变。

## ADDED Requirements

### Requirement: 验收通过的用例写入当前用户的专用项目

系统 SHALL 为每个用户维护一个名为「AI 生成用例」的用例项目，并在该项目下为每个 Agent-02 任务创建一个用例文件。项目与文件 MUST 归属于任务发起人，MUST NOT 归属于 Agent-02 的 owner。一个任务 MUST 只创建一个用例文件，该任务产出的全部模块用例 MUST 放在同一个文件内；MUST NOT 为每个模块拆出独立文件。

#### Scenario: 首次导入创建项目与文件

- **WHEN** 用户第一次有一个验收通过的 Agent-02 任务完成
- **THEN** 系统创建（或复用）该用户的「AI 生成用例」项目
- **AND** 在该项目下创建一个以任务标题命名的用例文件，并把该任务的全部用例写入这个文件

#### Scenario: 后续任务复用项目但新建文件

- **WHEN** 同一用户第二个验收通过的 Agent-02 任务完成
- **THEN** 系统复用「AI 生成用例」项目
- **AND** 为新任务创建一个新的用例文件，MUST NOT 覆盖第一个任务的文件

#### Scenario: 未通过验收不写入

- **WHEN** 任务终态为 `failed`、`cancelled` 或 `interrupted`
- **THEN** 系统 MUST NOT 创建用例项目、用例文件或用例行

### Requirement: 用例与步骤按固定字段映射

每条 Markdown 用例行 MUST 映射为一条平台用例，MUST 写入标题、优先级、系统、类型、业务类型、模块、前置条件与步骤。系统 MUST 固定为 `ANDROID`，类型 MUST 固定为 `FUNC`，业务类型 MUST 固定为 `appliance`。优先级 MUST 只接受 `P0` / `P1` / `P2`，无法识别时 MUST 回退为 `P1`。模块 MUST 取该用例所属模块标题；没有模块标题时 MAY 为空。平台用例编号 MUST 继续由平台按 `TC-YYYYMMDD-NNNN` 分配，MUST NOT 直接复用源文档的用例编号。

测试步骤与预期结果 MUST 按 `<br>` 分隔并按出现顺序一一配对为 `CaseStep.action` 与 `CaseStep.assertion`，MUST 去掉 `1)`、`1.` 这类序号前缀。两侧条目数不一致时，系统 MUST 退化为一条步骤：动作取完整测试步骤、断言取完整预期结果，MUST NOT 猜测缺失的对应关系。标题为空、动作或断言为空的行 MUST 被跳过并计数，MUST NOT 让整批导入失败。

#### Scenario: 三步用例拆成三条步骤

- **WHEN** 一条用例的测试步骤为 `1) 上电<br>2) 单击 POWER<br>3) 等待 3s`，预期结果同样有三段
- **THEN** 平台用例包含 3 条按原顺序排列的步骤
- **AND** 每条步骤的动作与断言分别来自对应段，序号前缀被去掉

#### Scenario: 步骤与预期数量不一致

- **WHEN** 测试步骤有 3 段而预期结果只有 2 段
- **THEN** 平台用例只有 1 条步骤
- **AND** 该步动作为完整测试步骤、断言为完整预期结果

#### Scenario: 缺少标题的行被跳过

- **WHEN** 某条用例的测试标题为空但步骤非空
- **THEN** 该行不写入平台用例
- **AND** 导入结果记录跳过条数与原因，其余用例仍正常写入

### Requirement: 用例保留来源追溯

平台用例 MUST 记录源文档用例编号与来源任务编号，供报告跳转后核对来源。来源字段 MUST 与平台用例编号分离：平台编号仍按平台规则生成，来源编号 MUST NOT 覆盖或改写平台编号。来源任务编号 MUST 能定位到唯一任务。

#### Scenario: 导入后可按来源任务查询

- **WHEN** 用户查看某个任务导入的用例
- **THEN** 每条用例都能给出源文档用例编号与来源任务编号
- **AND** 平台用例编号仍为 `TC-YYYYMMDD-NNNN` 格式

### Requirement: 同一任务重复导入保持幂等

同一任务的结果 MUST 只导入一次；重复导入 MUST 复用已存在的项目与文件，MUST NOT 新增重复用例、重复文件或重复项目。一次导入 MUST 在单个事务内完成：任一步骤失败 MUST 整体回滚，MUST NOT 留下部分用例。导入结果 MUST 给出项目编号、文件编号、用例条数与跳过条数。

#### Scenario: 同一任务重试导入

- **WHEN** 对已经成功导入的任务再次执行导入
- **THEN** 系统返回原项目与原文件
- **AND** 该文件下的用例条数不变，不产生重复行

#### Scenario: 中途失败整体回滚

- **WHEN** 导入第 5 条用例时数据库写入失败
- **THEN** 前 4 条用例 MUST NOT 留在库中
- **AND** 导入结果标记失败并给出原因

### Requirement: 导入失败不改变任务验收结论

导入是可降级的后处理：导入失败 MUST NOT 把已通过验收的任务改成失败，MUST NOT 删除任务结果中的 Markdown 文档。任务结果 MUST 记录导入状态（`imported` / `skipped` / `failed`）、项目与文件编号（成功时）、用例与跳过条数，以及失败原因（失败时）。报告 MUST 只在状态为 `imported` 时给出可点击的用例管理地址；其它状态 MUST 给出可读提示。

#### Scenario: 导入异常但任务仍完成

- **WHEN** 用例已通过验收，但写用例库时数据库异常
- **THEN** 任务状态仍为 `completed`
- **AND** 任务结果标记 `case_import.status=failed` 并写明原因
- **AND** 报告不给出失效的跳转地址

#### Scenario: 跳过全部用例

- **WHEN** 文档中没有任何可写入的合法用例行
- **THEN** 任务结果标记 `case_import.status=skipped`
- **AND** 报告提示「没有可写入的用例」而不是给出空文件地址
