## Context

现状见 proposal.md - Why。要动的只有三个工具模块与一句提示词，约束如下：

- `xpath_action` 当前只回文本与中心坐标，命中多个时返回带下标的 `items`，但模型看不到这些点在屏幕上的位置，只能按坐标大小猜。
- `mark_dot` 已能签发帧 token、点击类工具已能凭 token 复用该帧（变更 `trim-tool-roundtrips`），本次把同一条链路扩展到 xpath 命中点。
- 设备侧一次 UI 树读取约 0.5 秒（`xpath_action` 实测均值 0.54s），一次截图约 0.8 秒；OCR 单张 4.5 秒，不可用于每次点击，因此页面识别只用 UI 树。
- 图片标注已在 `tool_img_b64.py` 内实现，Pillow 13 支持 `ImageFont.load_default(size=…)`，不需要系统字体。

## Goals / Non-Goals

**Goals:**

- xpath 命中多个时，模型能在**一张图**上看到每个命中点的位置与序号，并按序号点击。
- 文本匹配容忍 App 的空格/全角写法，且多候选择只读一次 UI 树。
- "没核对就不许点"由工具强制，而不是只写在提示词里。

**Non-Goals:**

- 不引入 OCR 或页面指纹（延迟不可接受）。
- 不改 `drag_ratio` / `swipe_screen` / `app_control` 的门槛（无单一目标点或结果由日志判定）。
- 不改日志检查、报告、前端、数据库。
- 不做坐标吸附（另案）。

## Decisions

**D1 多点标在一张图上，序号按 (纵坐标, 横坐标) 升序编号。**

同一帧内编号可复现，模型说“第 2 个”时含义稳定。标签画在点右上角、白底描边、字号取图片短边的 3%，保证缩略到模型输入尺寸后仍可读。

**D2 帧缓存从「一个点」扩成「按序号的点列表」，`mark_dot` 存 1 个点。**

`Frame.points` 是 `tuple[(x, y), ...]`，序号 = 下标 + 1。`mark_dot` 走同一结构（长度 1），点击时 `index` 缺省取 1，避免两条路径出现两套语义。

**D3 `token` 从可选改必填，只对「有单一目标点」的点击类工具生效。**

`click_ratio` / `tap_screen` 缺 token 直接返回 error 且不碰设备；`drag_ratio` / `swipe_screen` / `app_control` 不强制，避免误伤由日志判定的步骤。这一步令「未确认锚点不得操作」成为工具硬约束，而不是纪律条款。

**D4 归一化匹配：去全部空白 + NFKC + casefold，候选最多 3 个。**

精确匹配优先，未命中再走归一化；同一批候选只读一次 UI 树。去空格会放大「多命中」的概率，但多命中已由编号图消歧，可接受。

**D5 0 命中不截图。**

命中才需要标记图；未命中时截一张图没有信息量，纯属多花 0.8 秒。

**D6 提示词与工具双保险。**

提示词写清「先 xpath 再视觉、多命中看编号图、无核对不操作」，工具侧同时硬拒绝，防止模型只读提示词就绕过。

## 模块防火墙自检

- 跨 App import：本次只改 `engines/agents/tools/**` 与提示词数据，无后端、无前端、无跨 App 依赖。
- 写操作：工具不写库、不落盘（标记图只在内存与帧缓存里）。
- engines 边界：帧缓存仍是进程内结构，不 import `apps.*` / `django.*`。

## Risks / Trade-offs

- [模型忘传 token 导致整条链路报错] → error 文案给出下一步动作（"先调用 mark_dot 或 xpath_action 的 confirm"），提示词写死；真机验证先看报错次数。
- [编号标签在缩略图里看不清] → 字号随短边比例放大 + 白底描边；真机跑一轮看模型是否能正确挑序号。
- [归一化后多命中更多，模型挑错] → 编号图给出文本与坐标对照，按序号点击可回溯；越界直接报错不点。
- [同一帧内 `index` 与 `items` 顺序不一致] → 顺序只由帧缓存决定，`items` 与图上的序号同源，单测锁死。

## Migration Plan

无数据迁移。回滚只需还原三个工具文件与提示词：帧缓存不持久化，没有残留状态；旧调用方（不带 token 的点击）会被新规则拒绝，属预期破坏性变更，回滚即恢复。
