## Context

见 proposal.md - Why。用户管理今天只有单条停用、启用、重置密码、授予运营。停用只改 `is_active`。网关只验令牌，不看账号是否启用；续期也不看。吊销表 `acc_token_revocations` 只有会话（`sid`）和单令牌（`jti`）两档，令牌里没有「账号世代」，无法按账号一次作废历史令牌。

业务数据（项目、任务、缺陷、设备锁）用字符串记创建者，不挂用户外键。删账号不会级联删这些行，也不会自动清掉创建者字段。

`ops-user-console` 尚未归档。本变更废止其中「不提供删除」和「停用后旧令牌自然过期」两条，归档时要和 `add-ops-user-console`、`grant-operator-role` 一起合并，不能单独归档覆盖掉授予运营。

## Goals / Non-Goals

**Goals:**

- 当前页勾选后，一次请求完成批量停用或批量注销。
- 停用立即作废该账号停用前的全部令牌；启用不恢复这些令牌。
- 在线用户在下一次受保护请求看到固定文案，10 秒后被前端清出会话。
- 注销只删账号行及其组、权限关系，业务行不动。

**Non-Goals:**

- 不新建 WebSocket，不补「停用瞬间推送」。
- 不新增软删除字段，不改业务表，不扫 `created_by`。
- 不提供跨页全选。
- 不改单条停用的权限边界，只补它缺失的吊销。

## Decisions

### 1. 停用吊销用账号世代，不逐条吊销 sid

停用时在吊销表增加第三档 `kind=user`，`ref` 为账号主键，`expires_at` 取 `JWT_REFRESH_TTL`（与会话吊销同一理由：要盖住 refresh 的最长寿命）。`verify_token` 在既有 `jti` / `sid` 检查之外，再查该账号是否有未过期的 user 档记录。

启用时删除该账号的 user 档记录，使**启用之后新签发**的令牌可用。停用前的令牌靠 `iat` 与记录的 `created_at` 比较：`iat` 早于这次停用的，仍然拒绝。因此启用不恢复旧会话。

重复停用覆盖同一行（与会话吊销的 `update_or_create` 同一写法），不堆记录。

备选：停用时查出该用户全部 sid 再逐条吊销。否决，因为平台不存「账号 → sid」索引，做不到。备选：停用后每次请求查 `is_active`。单独用它满足不了「启用后旧令牌仍无效」，所以世代记录是必需的，`is_active` 只负责登录与专用文案。

### 2. 专用拒绝走 403 + `code`，不走 401

网关在令牌验签通过、且未被吊销之后，若账号 `is_active` 为假，返回：

```json
{"status": false, "message": "你的账号已被超管停用，10 秒后将退出登录", "code": "account_disabled"}
```

HTTP 403。前端拦截器只在 `code === "account_disabled"` 时进入倒计时，不走 401 续期。其它 401 行为不变。

倒计时放在 `shared/`，不放在运营页：被停用的人可能停在任意页。10 秒用常量，不从接口下发。同一时刻只展示一层，重复响应不重置倒计时。

备选：继续返回 401，靠文案区分。否决，因为现有拦截器见 401 且有 refresh 就会续期，文案区分挡不住。

### 3. 续期在签发前拒绝停用账号

`/api/auth/refresh/` 验过 refresh 之后，若 `sub` 对应账号不存在或 `is_active` 为假，返回 401，不签发 access。存在 user 档吊销且 refresh 的 `iat` 早于该记录时，同样 401。这样倒计时期间不能换新令牌续命，启用后旧 refresh 也不能用。

### 4. 两个批量端点，语义分开

- `POST /api/ops/users/disable/`，请求体 `{ "user_ids": [1, 2] }`。运营可调用。逐行结果，部分成功。
- `POST /api/ops/users/purge/`，请求体同样。仅超管。任一目标不可注销则整批 403，不删任何行。

路径带尾斜杠。成功响应走既有 `{status, data}`。`user_ids` 去重后为空、超过 100、或含非正整数，整批 400，不写库。

停用逐行 `outcome`：`disabled` / `skipped` / `rejected`。注销成功只返回已删除的主键列表；失败不返回部分删除。

不复用 `POST /api/ops/users/<id>/disable/` 在前端循环。一次往返才能给出整批计数，也避免中途失败留下操作者看不到的半批。

### 5. 注销只删账号，整批一个事务

`accounts.api` 新增 `purge_users(user_ids)`：在一个事务里对每个目标 `user.delete()`。Django 会连带删掉组关系、权限关系。不碰其它 App 的表。

调用前 `ops_console` 先做完超管校验与「不含自己、不含其他超管、目标都存在」。校验失败不进写口。写口本身不再判权限。

注销前不额外做停用。账号行删除后，旧令牌的 `sub` 对不上任何用户；网关对「验签通过但账号不存在」返回同一个专用拒绝，避免注销用户还要等令牌自然过期。不写 user 档吊销，避免删号后留下孤儿记录。

### 6. 勾选只活在当前页

列表用现有 `AppTable`，加一列复选框，不改共享表格的选择模型。勾选集合放在页面状态，翻页、改筛选、改每页条数时清空。不可管理的行复选框禁用，不进提交名单。批量注销按钮仅 `isSuperuser` 为真时渲染。

注销确认用输入框，要求与「注销 N 个账号」全字匹配，N 为当前勾选人数。停用沿用现有二次确认，不要求输入。

### 7. 规则文档与规格的落地顺序

实现前先改两份模块 `AGENTS.md` 的红线，再写代码。改动范围只限「允许批量停用；允许仅超管注销且只删账号」。不放宽「不能动自己 / 不能动超管 / 运营不能动其他运营」。

`ops-user-console` 的主规格还不在 `openspec/specs/`。本变更的 delta 用 ADDED 与 REMOVED，不写 MODIFIED，避免归档时按标题对不上未归档正文。归档本变更之前，须先归档 `add-ops-user-console` 与 `grant-operator-role`，否则 REMOVED 没有可删的主规格条目。

## 模块防火墙自检

- 跨 App 写库：`ops_console` 只调 `accounts.api` 的 `set_user_active` 与新的 `purge_users`。不 import `accounts` 的 views / serializers / jwt_auth。
- 读：`ops_console` 继续只读 `auth.User` 做列表与身份判断，与现有列表相同。
- 吊销写入留在 `accounts.api`。`jwt_auth` 已惰性调用 `accounts.api`，本变更只扩展它已有的 `is_revoked` 读口，不新增跨 App 依赖。
- 网关不写库。它只读账号是否存在、是否启用，用来决定 403 文案。
- 前端不直连数据库。仪表盘无写操作。
- 不新增自定义异常类。批量失败沿用 `PermissionError` / `LookupError` / `ValueError`，由 View 映射 403 / 404 / 400。

## Risks / Trade-offs

- [没有推送，倒计时从下一次请求起算] → 规格已按此承诺。停用瞬间人可以继续看已打开的页面，直到他发下一个请求。不在本期补通道。
- [网关每条受保护请求多一次账号存在性读取] → 只取 `is_active`，命中主键。不在网关做组查询。
- [吊销表查询失败今天是放行] → user 档沿用同一 fail-open，避免吊销库抖动把全员踢下线。停用后的登录阻断不依赖这张表，`authenticate` 已拒绝 `is_active=false`。
- [注销后业务行的 `created_by` 变成死 id] → 需求方明确不删这些行。列表若按创建者显示用户名，可能显示空或原始 id。本期不改那些页面。
- [未归档规格互相覆盖] → 归档顺序写进 tasks。单独归档本变更会丢「授予运营」。
- [启用与停用的世代比较依赖时钟] → `iat` 与 `created_at` 都来自本机。不引入外部时钟。重复停用覆盖 `created_at`，以最后一次停用为准。

## Migration Plan

1. 先改两份模块 `AGENTS.md` 红线（需求方已在本变更确认范围内同意放宽删除与批量）。
2. 扩吊销表：新增 `user` 档。`kind` 是普通字符串加 choices，无数据迁移；已有行保持 `session` / `token`。
3. 上线后，停用即写 user 档。上线前已经停用、且令牌未过期的账号，靠网关的 `is_active` 检查进入 10 秒退出，不依赖历史吊销行。
4. 回退：去掉两个批量端点与勾选列，网关恢复为只验令牌，续期不再看 `is_active`。已注销的账号不能靠回退代码恢复。user 档记录可留在表里，旧代码不读它，不阻断回退。
