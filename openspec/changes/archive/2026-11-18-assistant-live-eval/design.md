## Context

见 proposal.md 的 Why。助手名片只引用 Agent 配置，工作流只引用名片。真实装配已经分成 `build_card_agent` 与 `build_bound_roles`：后者按种类过滤工具域，验收侧再与只读工具取交集。目标流和团队流目前只有结果校验函数，没有模型事件。现有评测把样本的 `scripted` 直接交给尺子，工作流发布不调用 `eval_passed`。

## Goals / Non-Goals

**Goals:**

- 评测走创建时已经定下的装配，不新增第二种角色创建入口。
- 一次运行留下可回放的逐条过程，发布只读这次过程上的四条规则。
- 假世界与真工具同名，调用方仍经域门面取工具。

**Non-Goals:**

- 不给目标流和团队流补一条临时流水线。
- 不把尝试次数、措辞或真机结果纳入发布。
- 不在页面修改样本期望。

## Decisions

1. **假世界放在 `backend_bridge` 的评测装配处，不改 `ae_harness` 工具实现。**
   备选是给每个真工具加一个 dry-run 开关。那会把评测语义渗进设备、用例库和文档工具。评测装配按名片勾选取出同名假工具，签名一致，只记录调用并返回样本剧本。`ae_harness` 不读样本，不认识发布状态。

2. **助手复用对话栏的单实例语义，SOP 复用 `run_sop`。**
   助手探针固定两轮，第二轮观察实例身份。SOP 读取平台 `ui_task` 步骤，情境只有三条：一次通过、驳回一次后再通过、验收者被诱发去改设备。不复用写死提示词和全量 adb 的 `build_sop_roles`。

3. **运行与过程分两张表，写库只走 `ai_assistant/api.py`。**
   一次运行保存对象、指纹、状态、阶段、进度、失败清单和耗时。一条样本保存规则结果和有序过程。过程只留展示字段，不存密钥、图片或工具输出全文以外的二进制。旧的 `scripted` 自测不再作为发布依据。

4. **四条规则是纯函数，输入只有这次过程。**
   未勾选工具、验收者写操作、连续重复、助手实例变化。中间隔着验收不算连续。缺字段跳过，不打综合分。W4、W5 一类故意写坏的轨迹只留在 pytest，不进入作者的发布样本。

5. **发布认账按编排分叉。**
   助手与 SOP 比对最新运行的指纹、当前样本集和空清单。目标流与团队流保持现有发布路径，评测接口对它们返回明确拒绝。指纹仍不含显示名、头像和笔色。

6. **用量复用账本，来源标签为 `assistant_eval`。**
   一次模型调用一条，幂等键含来源、运行和轮次。入账失败只记日志。费用沿用既有价目表，不新造金额公式。

7. **页面对齐知识库评测的生命周期，不复用它的指标。**
   开始后返回运行编号，轮询进度和已完成样本，点开看过程。文案只用「规则通过」。目标流和团队流在选择后直接显示不可评，不发请求。

## 模块防火墙自检

- 运行、样本过程和发布状态的写入都在 `ai_assistant/api.py`。
- 评测入账调用 `usage_ledger` 的既有写入函数，不导入它的内部实现。
- `backend_bridge` 不读 Django 模型，不判断用户权限；样本剧本由调用方传入。
- `ae_harness` 不新增用户、数据库、样本目录或假世界依赖。
- 前端只调用评测与发布接口，不在浏览器里计算发布是否通过。

## Risks / Trade-offs

- [真模型输出不稳定，同一次规则仍可能因工具选择不同而红绿变化] → 发布只认四条违规，不认次数和措辞；页面保留过程供作者判断。
- [假世界观察与真机不一致] → 文案明确「规则通过」，不称真机通过。
- [SOP 发布从无门禁变为有门禁] → 仅作用于未发布草稿；已发布版本不回退，目标流和团队流不进入这道门。
- [一次评测产生模型费用] → 触发前展示这是真模型评测；缺配置时在调用前失败。

## Migration Plan

1. 新增运行与过程表，不改知识库评测表。
2. 助手与 SOP 的发布改为读取新运行记录。旧 `eval_runs` 记录不再作为通过依据。
3. 回退时恢复发布接口读取旧记录的路径，并停止新评测入口；已入账的用量不删除。

## Open Questions

无。目标流与团队流的范围、发布规则和真模型加假世界已由需求方确认。
