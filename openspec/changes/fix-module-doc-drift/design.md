# Design: fix-module-doc-drift

## Context

结构外置已完成（`align-backend-docs-with-code` 5/6 组）。外置时约定「只迁移、不改语义」，
于是 14 处旧失真被原样搬进 `.agents/docs/**`；另查出 3 处 `engines/agents` 退役后遗留的指路漂移，
按同一口径一并收口（共 17 处，A/B/C 三组）。现在这些文档是模块级约束的载体，失真即误导。

约束：本变更**只改文本**，不改代码、不重排结构；红线措辞变更需单独批准。

## Goals / Non-Goals

**Goals**
- 17 处说法与代码/仓库实际一致；每条都有可复查的复核命令与结论。

**Non-Goals**
- 不批量重写文档、不合并篇章、不补写新章节；
- 不改任何代码或配置；
- 不改代码、不改 `.gitignore`、不改 `.agents/rules/` 的其它条款（只修 C1 那几处失效指路）。

## Decisions

### D1 一条一任务，先复核后动笔
每条任务都带「复核命令 + 期望」；复核结果与审计结论不一致时，**以复核为准**并记录差异。
理由：审计是 2026-11-23 的快照，代码在动（工作区还有 10+ 个在途变更），拿旧结论改文档等于制造新漂移。

### D2 真相源是代码，不是「看起来更合理的说法」
例如 B2 的 `events/`：不臆测它「应该存在」，按实际目录树写；A1 的设备检查器：不确定是否退役就不删行，先查。

### D3 红线措辞单列，未批不动
B7 改的是红线句子本身。虽只是把「子 AGENTS」换成「模块文档」，但按根 `AGENTS.md` 第 4 条仍属红线改动，
先提交变更申请、获批后执行；未获批则在 tasks 里标记 skipped 并说明原因，不留半改状态。

### D4 与前置变更的时序（需求方裁定）
需求方 2026-11-23 指定：**`align-backend-docs-with-code` 合并后再跑本变更**。
理由是两单改同一批 `.agents/docs/**` 文件——前置未合并时改文本，等于在未定稿的文件上叠加第二版差异，
冲突只能靠人工消解，且破坏前置变更「只迁移不改语义」的可复核性。

因此 `tasks.md` 0.1 是**硬门控**：前置没合并、没归档，本变更一行不写。
不设「前置搁置则独立执行」的例外——真要绕过，先改这一条，别在执行时临时决定。

## Risks / Trade-offs

- [改完仍失真：代码在变] → 每条都留复核命令，下次可重跑；不追求「一次到位」，追求「可复查」。
- [A5/A6 涉及前端设施现状] → 前端测试栈在演进（vitest + `frontend/tests/`），只描述现状并给出处，不写死数量。

## Migration Plan

纯文档，无部署动作。回退 = 还原文档提交。
