## Context

`TaskEventSink.emit` 目前每收到一条记录就追加一行，每 50 行 flush 一次；`_row` 为每条记录生成 `seq`。报告侧 `_spans` 在读取时按「同类型 + 同步骤 + 同尝试」把连续增量合并成一条，并用合并条数作为 `count`。

## Goals / Non-Goals

**Goals:**

- 让数据库里的增量事件一行代表一段，行数下降 90% 以上，报告输出完全不变。
- 实时显示与引擎事件流保持不变。

**Non-Goals:**

- 不改实时事件推送与前端渲染。
- 不回溯折叠历史任务事件（`delta_count` 默认 1，读取时仍按原逻辑合并）。
- 不改计费、判决、用例切分逻辑。

## Decisions

**1. 在平台接收方折叠，而不是引擎。**

`fold.py` 逐片段产生记录是为了实时显示；落库是平台侧职责。`TaskEventSink` 保留一条「未结束的增量行」：同类型/同步骤/同尝试就累加 `delta_count` 与结束时间；类型、步骤或尝试变化时把它写入 `_rows`，再处理新记录。批量 flush 不包含未结束行，因此不会从中间切断一段。

**2. 序号在段结束时分配。**

`seq` 仍从已有最大值连续递增，但只在一条记录真正落行时占用。这样折叠后没有空洞，报告按 `seq` 排序仍保持事件顺序。

**3. 展示时刻取段内第一条增量。**

报告用 `ended_at or started_at or called_at` 作为展示时刻。折叠行把 `ended_at` 保留为**第一条**增量的时刻，另用 `duration_ms` 记录整段耗时；这样 `×N` 那行的时间与折叠前完全一致。

**4. 报告对 `delta_count` 求和。**

`_spans` 仍按原规则切段，`_grouped` 把段内各行的 `delta_count` 相加作为 `count`。旧数据每行都是 1，结果等于段长度；新数据一行 `delta_count=N`，结果也是 N。

## 模块防火墙自检

- 只改 `task_list` 内部写库与报告聚合；无跨 App import。
- 事件写库仍经 `api.insert_task_events`，引擎不碰数据库。

## Risks / Trade-offs

- [段中途崩溃丢失未落库的增量] → `close()` 会先收尾；进程被强杀时该段丢失，与当前批量 flush 丢失尾部窗口同级。可接受。
- [混合新旧数据] → `_grouped` 求和同时兼容 1 与 N，已覆盖单测。
- [展示时间语义] → 明确取段内第一条；`duration_ms` 保留整段耗时，便于需要时排查。
- [历史数据不折叠] → 旧任务仍按多行读取，行数不下降；本次不回溯。
