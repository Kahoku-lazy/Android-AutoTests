## Context

`doodle-craft/references/page-layout.md` 的「左树 + 右预览」一节（第 115–123 行）是一张版式规格表，共 5 行：版式、左栏可拖动、右栏职责、姊妹模块、行皮肤与工具栏。其中：

- 第 115 行：`由用例管理工作台（/cases/projects/:id）确立，姊妹模块可照抄` —— 「确立」暗示当前有页面在跑这套版式。
- 第 120 行：`两栏之间 MUST 有 SplitHandle（共享件）` —— 无条件 MUST。

代码事实：
- `case-manager/routes.ts` 的 `/cases/projects/:projectId` → `ProjectSheet.vue`（用例表），该模块无 tree / pane / preview 代码。
- `SplitHandle.vue` 零引用（上一单三次核验：路径匹配、模板标签、纯文本点名）。

因此技能处于「描述一个不存在的版式 + 对不存在的用法下 MUST」的状态。

## Goals / Non-Goals

**Goals:**

1. 让「使用 `SplitHandle`」变成**条件式**要求：采用可拖动分栏时必须用，不采用时不要求；这样组件作为共享件保留、规则不再空转。
2. 纠正「由用例管理工作台确立」这句失实描述，避免后来者去 `/cases/projects/:id` 找分栏却只看到用例表。

**Non-Goals:**

- 不改 `SplitHandle.vue` 一行代码（组件本身是好的共享件）。
- 不把 `/cases/projects/:id` 改成左树 + 右预览（那是一次功能改版，需要单独的版式方案与需求确认）。
- 不改 `standalone-html.md` 的「照抄 `SplitHandle.vue`」指引——它说的是交互规格来源，仍然成立。

## Decisions

**D1：把 MUST 改成条件式，而不是删掉整行。**
交互细则（拖动范围 220px ~ min(560px, 容器宽 − 360px)、← / → 16px、Shift 48px、Home/End 到两端、双击复位、`app-split-<mod>-tree-w` 记忆、窄屏不渲染、不得另画第二条分隔线）是有价值的实现规格，删掉会让下次做分栏时从零摸索。收窄条件即可让规则与现状一致。

**D2：「确立」改「可选」，并如实写出当前状态。**
文档要回答「现在是什么样」，不是「曾经计划过什么」。用一句「当前无页面采用（用例管理工作台现为用例表）」把事实钉住，避免后来者反查代码后怀疑文档。

**D3：保留组件，不做「零引用即删除」。**
上一单的判据是「零引用 + 无规格/技能点名」才算死代码；本单把技能点名改为条件式后，它仍是「采用分栏时的唯一实现」，属设计系统零件库存，不是死代码。这条边界写进本单，避免下次有人再来删它。

**D4：不设 `skip_specs` 之外的任何规格动作。**
`openspec/specs/` 下没有任何能力描述「前端分栏版式」，技能文档不在规格体系内，故 `skip_specs: true`，且不虚构需求。

## 模块防火墙自检

- **跨 App import**：不涉及。
- **禁跨层依赖**：不涉及（文档单）。
- **写库收敛**：不涉及。
- **前端不直连数据库**：维持。
- **仪表盘只读**：不涉及。

## Risks / Trade-offs

- **[收窄 MUST 后，将来做分栏时可能有人不用 SplitHandle 自造手柄]** → D1 保留「采用可拖动分栏 MUST 使用」的强制语义 + 全部交互细则，条件成立时规则依旧硬。
- **[有人把「可选」读成「SplitHandle 已废弃」]** → D2 明确写出「组件保留、采用分栏时必须使用」，并在 D3 记录「不要因零引用删除」。
- **[文档与代码仍不同步（技能描述的可选版式仍无实现）]** → 本单只承诺「描述不撒谎」，不承诺「版式落地」；版式落地属功能改版，另案。
