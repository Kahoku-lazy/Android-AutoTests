## Purpose

规定一份「与 AgentScope 官方语义对齐」的运行记录：把一次运行的产物按 `Msg` → 内容块 → 事件三层组织落盘，折叠交给框架提供的能力，使下游（报告渲染、排障、回放）只依赖一套结构，而不是各写一套折叠。

## ADDED Requirements

### Requirement: 运行记录按官方消息结构组织

一次运行的记录 SHALL 是一个带版本标识的 JSON 文档，包含六段：运行信封（角色、智能体名、模型、密钥环境变量名、设备或线程标识）、输入条件（system prompt、工具 schema、用户消息）、回复列表、观测列表、运行汇总、事件列表。

记录 MUST 带 `schema` 版本标识，使读取方能在结构变化时识别版本；MUST NOT 依赖文件名推断结构。

#### Scenario: 单角色运行产出一份记录

- **WHEN** 一次运行结束
- **THEN** 记录文件包含六段且 `schema` 非空
- **AND** 运行信封含角色、智能体名与模型名

#### Scenario: 读取方可按版本识别结构

- **WHEN** 读取方打开一份记录
- **THEN** 它先读到 `schema`，再按该版本决定如何解析其余各段

### Requirement: 回复的折叠 MUST 使用框架提供的折叠能力

回复列表中的每条回复 SHALL 由该次运行的全部事件通过框架的折叠接口累积成一条消息对象，MUST NOT 由本仓库另写一套块装配规则。

消息对象 MUST 含有序内容块列表与累计用量；单条事件折叠失败时 MUST 记录该事件的类型名到该条回复的降级清单，MUST NOT 使整份记录写入失败或丢弃其它事件。

#### Scenario: 块顺序由事件顺序决定

- **WHEN** 一次运行依次产生思考、文本、工具调用、工具结果的事件
- **THEN** 折叠后的消息内容块顺序与事件顺序一致
- **AND** 累计用量与运行汇总的 token 数字一致

#### Scenario: 单条事件无法折叠

- **WHEN** 某条事件无法被折叠接口接受
- **THEN** 该事件类型出现在这条回复的降级清单里
- **AND** 其余事件仍被折叠，记录仍写盘成功

### Requirement: 多回复 MUST 按回复标识分组

记录 MUST 按回复标识把所有事件分成若干条回复，MUST NOT 把不同角色的回复合并成一条。事件携带的智能体名 SHALL 作为该条回复的发送方名称；缺失回复标识的事件 MUST 单独计数，MUST NOT 混入任何一条回复。

#### Scenario: 双角色编排产出两条回复

- **WHEN** 执行者与验收者在同一次运行中各产出一次回复
- **THEN** 记录里有两条回复，各自带自己的回复标识与智能体名

#### Scenario: 无回复标识的事件

- **WHEN** 事件流里出现不携带回复标识的事件
- **THEN** 它们只体现在单独的计数上，不出现在任何一条回复的内容块里

### Requirement: 二进制媒体 MUST 旁路存放并保持事件可校验

图片、音频等二进制 MUST 写入记录同级的媒体目录，事件里的二进制字段 MUST 换成指向该文件的 URL 源或置空；记录 MUST NOT 内联 base64。

事件 MUST 保持可被框架事件 schema 重新校验：读取方把记录里的事件再次解析时 MUST 成功，MUST NOT 因脱敏产出的自定义结构而校验失败。

#### Scenario: 截图事件脱敏后仍可解析

- **WHEN** 一条携带截图的工具结果事件被写入记录
- **THEN** 记录里该事件的二进制字段为空且带指向媒体文件的 URL
- **AND** 该事件可被框架事件 schema 重新解析

#### Scenario: 记录不含内联二进制

- **WHEN** 检查记录文件文本
- **THEN** 其中不出现 base64 图片数据

### Requirement: 观测与派生信息 MUST NOT 混入事件流

中间件采样得到的观测记录、以及运行汇总等派生信息，MUST 各自单独成段，MUST NOT 作为事件混入事件列表；事件列表 MUST 只含框架事件。

#### Scenario: 观测单独成段

- **WHEN** 运行中产生 system prompt、上下文压缩与模型调用的观测
- **THEN** 它们只出现在观测段，事件段的事件条数不受影响

### Requirement: 观测 MUST 记录实际发送的 payload 并与框架消息对账

每次模型调用的观测 MUST 记录框架消息里的图片数量；当该通道的格式化器接受图片时，MUST 另记一份「实际发送的 payload 摘要」（每条消息的角色与内容类型，图片只记长度与媒体类型，不落 base64）。

框架消息里有图片、而实际发送里没有图片时，该次观测 MUST 标注「图片被通道丢弃」，MUST NOT 让读取方误以为模型看到了图片。

#### Scenario: 通道支持图片

- **WHEN** 使用声明支持图片的模型（如 `deepseek-flash`）且工具返回截图
- **THEN** 观测里框架图片数与实际发送数一致，且不出现丢弃标记

#### Scenario: 通道不支持图片

- **WHEN** 使用只声明文本输入的模型且工具返回截图
- **THEN** 观测里标注图片被丢弃，模型侧只收到文字

### Requirement: 观测 MUST 覆盖框架提供的全部可观测位置

观测段 MUST 覆盖框架中间件提供的全部可观测位置，至少包括：整轮回复的开始与结束、每轮推理的开始与结束、每次工具执行、每次权限判定、每次模型调用与其返回、每次 system prompt 组装、每次上下文压缩判定。

每轮推理的观测 MUST 附带当时的状态快照：上下文条数、计划任务清单、压缩摘要长度、权限模式。

#### Scenario: 一轮 ReAct 的链路可回放

- **WHEN** 一次回复经历两轮推理、一次工具调用与一次权限判定
- **THEN** 观测段里能按顺序找到：回复开始 → 推理开始 → 模型调用 → 模型返回 → 权限判定 → 工具执行 → 推理开始（第二轮）→ 回复结束

#### Scenario: 状态快照随推理记录

- **WHEN** 智能体维护了计划任务
- **THEN** 该轮推理的观测里带任务清单与上下文条数
