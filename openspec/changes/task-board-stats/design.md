## Context

见 [proposal.md](./proposal.md) - Why。两条既有约束决定了实现形状：

1. `GET /api/tasks/` 只返回最近 100 条（`order_by("-id")[:100]`），所以「总任务数」不能由前端列表求和。
2. 任务清单页已有 10 秒运行态轮询（`useTaskList.schedulePoll`），统计必须跟着这套节奏走，不再开第二个定时器。

## Goals / Non-Goals

**Goals**

- 总数/成功率/执行中三个数字在任何数据量下都正确，且与列表刷新同步。
- 统计接口开销与任务条数无关（一次 `GROUP BY status`）。
- 图表复用既有 ECharts 封装与 Doodle Craft 卡片族，不自造第二套视觉。

**Non-Goals**

- 不做时间维度（近 7 天趋势、按型号分组）——那是仪表盘与报告页的事。
- 不做点击下钻筛选；统计区只读。
- 不缓存统计结果；每次随列表请求重取。

## Decisions

### D1 统计在服务端一次聚合，而不是前端数列表

`GET /api/tasks/stats/` 用 `values("status").annotate(Count("id"))` 一次拿全部分组；SQL 恒为 2 条（智能体范围 + 聚合）。备选是前端对 100 条求和——数据一多总数就错，且分页上限变化时会静默失真。

### D2 成功率口径 = 成功 ÷ 已结束

`已结束 = 总数 − 执行中 − 待执行`。这样执行中的任务不会把成功率压低；暂停/stopped 等历史状态也会自然落入分母。没有已结束任务时前端显示「—」，避免用 0% 误导。备选是「成功 ÷ 总数」，会在长任务运行期间给出偏低的读数。

### D3 占比图四类固定，不合并「失败 + 中断」

产品口径把失败与中断都算「不过」，但两者处置完全不同（失败要查原因，中断是外部打断）。图例并排展示，谁要合并一眼能加总。备选是三类（失败+中断合并），信息量更低。

### D4 统计跟着列表刷新走，不新增轮询

`useTaskList.load()` 成功后顺带刷新统计（同一个 await 周期，静默失败不阻塞列表）。列表轮询只在有运行中任务时存在，统计也就只在有意义的时候变。

### D5 视觉：KpiCard × 3 + AppCard 包 ECharts 环形图

按 Doodle Craft 选型表：单个指标用 `KpiCard`（kpi 变体，形状/微倾按序号轮转），可复用数据块用 `AppCard`。图表色沿用八支彩笔的语义映射（成功=`--c-device`、失败=`--c-runner`、中断=`--c-report`、取消=`--c-ai` 之外的灰紫档），ECharts 画布内保留色值字面量并注明 token 对照（既有约定）。不自造统计卡、不自绘 SVG 环。

## Risks / Trade-offs

- [统计与列表两次请求可能短暂不一致] → 同一轮刷新里先列表后统计，差异只存在毫秒级；统计失败时保留上一次数值，不显示 0。
- [状态取值漂移（新增状态）导致漏计] → 分母用「总数 − 执行中 − 待执行」推导，未知状态自动进入分母；占比图只认四类，新增状态最多不进扇区，不会把成功率算错。
- [ECharts 画布与令牌脱节] → 只在组件内写同值字面量并注明 token 对照，沿用 `SeriesBarChart` / `TodayUsageChart` 的既有做法。

## Migration Plan

- 无数据库变更；新接口为只读，旧前端不受影响。
- 上线后若统计接口异常，任务清单仍按原逻辑展示列表与错误态，统计区显示占位。
