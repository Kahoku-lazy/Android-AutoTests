# agent-task-event-store Specification

## Purpose

把一次平台任务里已经折好的智能体事件写入数据库，同时保存缩略图和按小时累计的 8 位费用。任务流程报告读取这些事件。

## Requirements

### Requirement: 平台任务写入结构化事件
有任务号的平台运行 MUST 把交给接收方的结构化记录写入该任务的事件表。同一任务内序号 MUST 从已有最大序号之后连续递增，且任务与序号的组合 MUST 唯一。连续且同类型、同步骤、同尝试次数的流式增量 MUST 合并写成一行，并用 `delta_count` 记录该段的增量条数；这一行的展示时刻 MUST 取该段第一条增量的时刻。每条记录 MUST 带上**当前正在执行的用例**标题：一个任务按序跑多条用例时，每进入一条用例 MUST 刷新该标题，MUST NOT 让整任务的所有行共用一个值；没有用例标题时 MUST 写空串。有当前步骤时 MUST 带上从 1 起的步骤序号和该步的尝试次数，没有当前步骤时这两项 MUST 为空。费用 MUST 保留小数点后 8 位。文本日志 MUST 仍然写出。任务号为 0 或未绑定运行上下文时 MUST NOT 写入事件、图片或小时用量。

#### Scenario: 三条记录按序落在同一任务下
- **WHEN** 一次任务依次交出回复结束、模型调用结束和工具返回结束
- **THEN** 事件表有序号 1、2、3 的三行，且都带该任务的用例标题

#### Scenario: 一个任务里两条用例各有自己的标题
- **WHEN** 同一任务先跑标题为「甲」的用例，再跑标题为「乙」的用例，两条用例各自交出记录
- **THEN** 「甲」产生的行用例标题为「甲」，「乙」产生的行用例标题为「乙」，后半段行的步骤序号从 1 重新开始

#### Scenario: 当前步骤被盖到记录上
- **WHEN** 交出记录时，流程正处于第 2 步的第 1 次尝试
- **THEN** 该行的步骤序号为 2，尝试次数为 1

#### Scenario: 没有任务号时不写库
- **WHEN** 任务号为 0 时交出一条模型调用结束
- **THEN** 事件表、图片表和小时用量表都没有新增行，文本日志仍可写出

#### Scenario: 连续增量合并成一行
- **WHEN** 同一类型、同一步骤、同一尝试次数连续交出 17,447 条工具参数增量
- **THEN** 事件表只为该段写一行，`delta_count` 为 17,447，序号在段结束时分配

### Requirement: 模型调用结束累加小时用量
模型调用结束 MUST 先写入逐次账。小时用量表 MUST NOT 再作为仪表盘、趋势或任务费用的数据源。已有小时行 MUST 保留为切换点之前的归档，本变更 MUST NOT 删除这些行，也 MUST NOT 用它们回写任务费用。

#### Scenario: 一次模型调用写入对应小时
- **WHEN** 一条模型调用结束的时刻是北京时间 2026-10-20 10:00，且成功写入逐次账
- **THEN** 仪表盘该日 10 时的账本分桶包含该笔
- **AND** 不依赖小时表新增行

#### Scenario: 回复结束不计入小时用量
- **WHEN** 同一任务只交出回复结束，没有模型调用结束
- **THEN** 逐次账没有新增模型调用行，费用合计不增加

#### Scenario: 旧小时行不参与新账单
- **WHEN** 小时表中存在切换点之前的费用行
- **THEN** 这些行不进入切换点之后的平台费用合计

### Requirement: 任务费用只汇总模型调用结束
任务收口时 MUST 按该任务的执行 ID 汇总逐次账中模型调用行的人民币费用，并写回任务费用列。合计 MUST 等于这些已计价行之和。未计价行 MUST NOT 计入费用，任务详情 MUST 能看出存在未计价调用。回复结束行携带的轮次费用 MUST NOT 再参与求和。任务收口 MUST NOT 自行按价目表重算。逐次账暂时不可写时，任务终态仍 MUST 可写入，费用列保持可随后按执行 ID 补汇总。

#### Scenario: 回复结束的费用不重复计入
- **WHEN** 一条模型调用结束已入账 0.00006000 元，同一次运行的回复结束也带有该金额
- **THEN** 任务费用只计入这一笔 0.00006000 元，不把回复结束再加一次

#### Scenario: 收尾时刷出尚未写入的记录
- **WHEN** 运行结束时还有未入账的模型调用
- **THEN** 这些调用先写入逐次账，再按执行 ID 回写任务费用

#### Scenario: 任务费用等于逐次账
- **WHEN** 一个任务有两笔已计价调用，费用分别为 0.10000000 元与 0.02000000 元
- **THEN** 任务费用合计为 0.12000000 元

#### Scenario: 缺模型名的调用不把整单算成已计价
- **WHEN** 一个任务的逐次账中有一笔计价状态为未计价
- **THEN** 任务费用只含其余已计价行
- **AND** 任务详情标出存在未计价调用

#### Scenario: 收口不再按结束时刻重算
- **WHEN** 任务在空闲时段结束，但其中一笔调用的起点处于高峰
- **THEN** 任务费用仍包含该笔按高峰基数算出的金额

### Requirement: 图片只存缩略图并按内容去重
带图片的记录 MUST 把原图压成长边不超过 720 的 WebP（质量 75）后写入任务媒体目录下的本地文件，MUST NOT 保存原图，MUST NOT 把图片字节写进数据库。文件路径 MUST 为 `<任务媒体目录>/<task_id>/<sha256>.webp`。同一任务内内容相同的原图 MUST 只占一行图片与一个文件，后续记录 MUST 指向这一行。系统 MUST NOT 按张数设置采集上限：任意数量的不同图片 MUST 都能新增图片行和文件，对应事件 MUST 拿到该图片的引用。无法解码的图片 MUST 跳过图片保存，事件行本身 MUST 仍然写入，且该行的载荷 MUST 带上表示编码失败的标记，使「这一步没有截图」与「截图存不下来」在事后可区分；同时 MUST 留下可读警告日志，含任务号、序号与角色名。删除任务时，该任务的事件、图片行与图片文件 MUST 一并删除。

#### Scenario: 坏图在行上留痕
- **WHEN** 一条记录携带的 base64 无法解码成图片
- **THEN** 该行照常写入、图片引用为空，载荷带编码失败标记，并留下含任务号与序号的警告日志

#### Scenario: 同一张图只存一行
- **WHEN** 同一任务的两条工具返回结束携带同一张原图
- **THEN** 图片表只有一行、任务目录下只有一个 `.webp` 文件，两行事件指向同一张缩略图

#### Scenario: 数据库不存图片字节
- **WHEN** 写入一张新截图
- **THEN** `task_media` 行的 `thumb_b64` 为空，`storage_key` 指向存在的 WebP 文件

#### Scenario: 超过三百张后继续保存
- **WHEN** 某任务已经有 300 张不同图片，又出现第 301 张新的不同图片
- **THEN** 图片表新增一行、目录新增一个文件，该事件的图片引用不为空

#### Scenario: 多用例任务全程都有图
- **WHEN** 一个任务的截图总数达到 785 张（跨 12 条用例）
- **THEN** 每张不同画面都占一行图片和一个文件，任意一次截图事件都能拿到图片引用

#### Scenario: 删除任务带走事件和图片
- **WHEN** 删除一个已有事件和图片的任务
- **THEN** 该任务的事件行、图片行与图片目录都不再存在

### Requirement: 单批按字节上限分片
接收方 MUST 按累计字节数提前结束一批，MUST NOT 只按行数分批。单批累计字节数达到上限时 MUST 立即写入，不等凑满行数。上限 MUST 显著小于数据库单次语句允许的最大包长，以免一条长载荷把整批顶穿。

#### Scenario: 长载荷触发提前写入
- **WHEN** 单批字节上限为 100，先收到一行短行，再收到一行带 200 字节载荷的行
- **THEN** 两行进同一批并立即写入，不等凑满常规行数

#### Scenario: 短行仍按行数分批
- **WHEN** 每行都很短，累计字节数远低于上限
- **THEN** 仍按常规行数上限分批写入

### Requirement: 写入失败保留待写行并重试

接收方按批写入事件时，整批失败 MUST NOT 使这一批行被永久丢弃：待写行 MUST 留在缓冲里，并在下一次写入时重试；写得进去的行 MUST 落库，写不进去的行 MUST 继续保留。缓冲 MUST 有行数上限，超过上限时 MUST 只保留最新的行并留下含任务号与行数的告警，MUST NOT 无限增长。任务收尾时 MUST 再尝试一次；只有收尾仍写不进去的行才允许丢弃，且 MUST 留下含任务号、序号与事件类型名的警告。降级之后小时用量 MUST 只按真正落库的行累加，MUST NOT 重复累加。

事件写入 MUST 在同步上下文执行。调用方处在事件循环里（异步上下文）时，MUST 通过线程转交执行，MUST NOT 直接访问 ORM；因此产生的 `SynchronousOnlyOperation` MUST NOT 造成任何事件丢失。

#### Scenario: 整批失败后下次写入补齐

- **WHEN** 一批三行整批写入失败，随后连接恢复
- **THEN** 这三行在下次写入时被重试并落库，序号连续；小时用量只按真正落库的行累加一次

#### Scenario: 收尾仍失败才丢弃

- **WHEN** 某几行到任务收尾时仍写不进去
- **THEN** 丢弃这几行并写一条含任务号与序号的告警，其余事件照常保留

#### Scenario: 缓冲超过上限只留最新行

- **WHEN** 写入持续失败，待写行数超过上限
- **THEN** 只保留最新的若干行，并留下含任务号与行数的告警

#### Scenario: 异步上下文里不丢行

- **WHEN** 工作流在事件循环里记录一条事件，而写入需要访问 ORM
- **THEN** 写入经线程转交执行并成功落库，不出现 `SynchronousOnlyOperation`，也不因它丢事件

### Requirement: 成品记录直交接收方

已经是成品记录的条目（例如步骤中断事件）MUST 直接交给接收方，MUST NOT 送进按 AgentScope 事件类型分派的折叠：折叠对认不出的类型返回空结果，既不入库也不报错。

#### Scenario: 成品记录不被折叠吞掉

- **WHEN** 工作流写入一条已构造好的步骤中断记录
- **THEN** 接收方收到该记录并入库；MUST NOT 因它不属于事件流类型而被静默丢弃

### Requirement: 异常收口也写逐次账与任务用量

运行内以失败结束的 SOP 任务 MUST 与成功收口一样，把该次运行已经结束的模型调用写入逐次账（来源 `task`，执行 ID 为任务号），并按执行 ID 汇总回写任务的输入、输出、缓存命中 token 与逐项费用。回写 MUST 使用整次运行的累计值，MUST NOT 使用增量累加，重复收口 MUST NOT 让任务用量翻倍。逐次账写入失败 MUST NOT 阻止任务终态落库；此时任务用量与费用 MUST 保持可随后按执行 ID 补汇总。回写用量与费用 MUST NOT 改写任务状态、失败原因、失败步骤清单或已完成清单。经 `goal` / `team` 编排的任务不适用本条（其成功收口当前也不写逐次账，另开变更）；进程退出或预算超限导致的中断、以及用户主动取消同样不适用，按各自既有口径处理。

#### Scenario: 失败任务仍回写用量与费用

- **WHEN** 一次运行已完成 25 次模型调用，随后在交卷轮失败
- **THEN** 该任务的输入、输出与缓存命中 token 均大于 0
- **AND** 任务费用等于逐次账中该执行 ID 已计价行之和
- **AND** 逐次账中该执行 ID 的调用行数与实际调用次数一致

#### Scenario: 账本暂不可写不阻断失败收口

- **WHEN** 失败收口时逐次账暂时不可写
- **THEN** 任务仍以 `failed` 落库，失败原因与失败步骤清单保持不变
- **AND** 任务费用列保持可随后按执行 ID 补汇总

#### Scenario: 重复收口不重复计入

- **WHEN** 同一次失败运行的用量回写被触发两次
- **THEN** 逐次账中同一「执行 ID + 轮次」仍只有一行
- **AND** 任务费用仍等于逐次账之和，不翻倍
