# appliance-case-authoring Specification

## Purpose
把家电测试用例的编写与验收拆成两个独立角色，让「按需求原子产出 13 字段用例」和「按同一份需求逐条判卷」由不同模型承担，产出可追溯、可执行、可判定。

## Requirements

### Requirement: 用例编写角色按需求原子产出完整用例文档

编写角色的系统提示词 SHALL 声明五阶段工作流（需求全量拆解、逐条方法匹配、优先级校准、跨模块 E2E 与冲突登记、用例编写与自检），并 MUST 要求交付固定七节文档：需求原子表、方法分配表、需求冲突登记表、13 字段测试用例、E2E 用户旅程、覆盖与门禁自检、待确认问题。

每条用例 MUST 回指一个存在于原子表的原子 ID，MUST 包含 13 个字段；预期结果 MUST 量化（可观察对象 + 阈值/容差），MUST NOT 使用「正常」「稳定」「良好」「符合预期」等不可判定措辞。输入没有给出的阈值、颜色、灯效、时长 MUST 登记为待确认问题，MUST NOT 编造。

#### Scenario: 输入一份固件规格书

- **WHEN** 调用方把需求正文、项目代号与版本号交给编写角色
- **THEN** 编写角色在交付文档中给出需求原子表、方法分配表、13 字段用例表、至少 3 条 E2E 与自检统计，且每条用例的追溯 ID 都能在原子表中找到

#### Scenario: 需求存在缺口

- **WHEN** 需求正文没有写清某个灯效的颜色或时长
- **THEN** 编写角色把该点登记进「待确认问题」并把相关原子标记为 UNCERTAIN，MUST NOT 自行补一个数值

#### Scenario: 增量编写

- **WHEN** 调用方提供了已有用例索引
- **THEN** 编写角色先对比原子与已有用例的追溯 ID，只为本批未覆盖的原子生成新用例，并列出需要随需求更新的已有用例

### Requirement: 用例验收角色独立判卷

用例验收角色 SHALL 只依据需求正文、SOP 步骤要求与作者提交的文档判卷，MUST NOT 采信作者的自述；判定 MUST 覆盖需求覆盖、原子质量、方法匹配、优先级、13 字段完整性、预期可判定、E2E 与冲突、一致性与统计八组清单。结论 MUST 以结构化输出的 `passed` 与 `message` 给出。

`passed=true` MUST 同时满足：需求覆盖、13 字段、预期可判定三组无阻断问题；原子质量、方法匹配、优先级、E2E 与冲突、一致性五组无严重问题；P0 原子覆盖率 100%、P1 ≥90%、P2 ≥70% 或缺口已登记。

#### Scenario: 覆盖不全

- **WHEN** 需求原子表中的某个原子既没有用例也没有不可测登记
- **THEN** 验收角色判 `passed=false`，并在 `message` 里给出 `[阻断]` 问题、位置与必须怎么改

#### Scenario: 用例可执行且覆盖完整

- **WHEN** 原子全部有用例、13 字段齐全、预期全部量化、E2E 不少于 3 条且冲突已登记
- **THEN** 验收角色判 `passed=true`，并在 `message` 里写原子数、用例数、各优先级覆盖率与剩余风险

#### Scenario: 提交只有摘要

- **WHEN** 作者提交的内容只有目录、摘要或文件路径，没有完整用例文档
- **THEN** 验收角色直接判 `passed=false`，不得因为「结构看起来完整」而通过

### Requirement: 编写与验收成对运行

引擎 SHALL 先按模块切分需求，再为每个模块单独运行一次 GoalPipeline：编写角色只拿本模块的需求片段与原子编号区段，把完整七节文档保存到模块存储，最终 `report` 只写摘要；验收角色从模块存储读取实际文档，只按该片段判卷并给出 `result` / `message`。单个模块不通过时把驳回说明与上一版文档拼进下一轮输入，最多三轮；一个模块通过后继续下一个模块，MUST NOT 因前一个模块通过而跳过后续模块。全部模块通过时整轮运行才标记完成；任一模块达到三轮仍未通过时整轮标记失败，并保留该模块的最后文档与历次判决。

#### Scenario: 第一次驳回后重写

- **WHEN** 某个模块的验收角色第一次给出 `result=fail`
- **THEN** 该模块的编写角色收到驳回说明与上一版文档并定点重写，其它模块不受影响；后续任一轮 `result=pass` 则该模块完成

#### Scenario: 尝试次数用尽

- **WHEN** 某个模块第三轮仍为 `result=fail`
- **THEN** 该模块标记失败，整轮运行阶段为 failed，结果里保留该模块的最后文档与历次判决说明

#### Scenario: 全部模块通过

- **WHEN** 每个模块的验收角色都给 `result=pass`
- **THEN** 整轮运行阶段为 completed，结果文档按模块顺序拼接且每个模块带验收结论

### Requirement: 需求按模块切分

引擎 SHALL 在编写前把需求正文切成 2~12 个模块，每个模块带 3~4 个大写字母的模块 KEY、中文名与原文行号区间。切分 MUST 按原文顺序、区间不重叠、并覆盖全部有实质内容的行；每个模块的工作量 SHOULD 约 10~18 个需求原子。需求非空行不足 80 行时 MAY 只切一个模块，MUST NOT 为此调用规划模型。

规划 MUST 由独立角色完成，其输出 MUST 是结构化模块列表。规划失败、输出为空或区间覆盖率低于 60% 时，引擎 MUST 回退到确定性切块：有至少 6 个章节标题时按标题分组，否则按固定行数切块；MUST NOT 因为规划失败退回「整份一次生成」。

#### Scenario: 大 PRD 被切成多块

- **WHEN** 需求正文有 110 个以上需求原子、非空行超过 80 行
- **THEN** 规划角色返回至少 2 个模块区间，每个模块带 KEY、名称与起止行号
- **AND** 各区间按原文顺序排列且互不重叠

#### Scenario: 规划输出漏段

- **WHEN** 规划角色给出的区间只覆盖不到 60% 的非空行
- **THEN** 引擎丢弃该规划结果并按章节标题或固定行数回退切块
- **AND** 回退后的模块仍覆盖全部需求内容

#### Scenario: 小需求不调用规划

- **WHEN** 需求正文的非空行不超过 80 行
- **THEN** 引擎直接按一个模块运行，不发起规划模型调用

### Requirement: 输出截断检测与拆分

编写步骤 MUST 记录每次模型调用的输出 token。任一次编写输出达到 60,000 token、或 handover 为空时，该模块 MUST 标记为截断（truncated），MUST NOT 再调用验收角色，MUST NOT 在原区间上重写。引擎 MUST 把该模块的行号区间一分为二后分别重新生成，最多递归两层；拆到最小块仍截断时该模块判失败，并在模块摘要中写明 `OUTPUT_TRUNCATED`。

交付缺少「覆盖与门禁自检」或「待确认问题」两节但输出 token 未达上限时 MUST NOT 按截断处理，仍按普通验收不通过进入重写。

#### Scenario: 输出顶到上限

- **WHEN** 某模块的编写调用输出 60,000 token 以上且 handover 在用例表中途结束
- **THEN** 该模块标记 `truncated=true`，不调用验收角色
- **AND** 引擎把该模块区间一分为二，分别生成两个更小的模块

#### Scenario: 拆分后通过

- **WHEN** 截断模块被拆成两个子模块，两个子模块均通过验收
- **THEN** 整轮运行不因这次截断判失败，结果文档包含两个子模块的完整内容

#### Scenario: 最小块仍截断

- **WHEN** 模块已递归拆到最小块，编写输出仍达到上限
- **THEN** 该模块判失败，任务结果含 `truncated=true`，摘要含 `OUTPUT_TRUNCATED`

### Requirement: 模块化结果拼装

引擎 MUST 把各模块的交付文档按原文模块顺序拼成一份 Markdown，MUST 在每个模块前写明模块名、模块 KEY 与验收结论（PASS / FAIL），MUST 用分隔线与上一模块隔开。每个模块文档 MUST 仍是自包含的七节结构；MUST NOT 把一个模块的第六节统计与另一个模块混算。

引擎 MUST 在运行结果中给出每个模块的 KEY、名称、起止行号、是否通过、是否截断与文档长度。判决列表 MUST 按模块加前缀，使用户能区分哪条意见属于哪个模块。

#### Scenario: 拼接两份模块文档

- **WHEN** 两个模块都通过验收
- **THEN** 结果文档先出现项目标题与模块数量说明，再按顺序出现两个模块标题与各自的七节文档
- **AND** 每个模块标题后带 `验收 PASS`

#### Scenario: 模块判决可区分

- **WHEN** 模块 BTN 被驳回、模块 IND 通过
- **THEN** 判决列表里 BTN 的意见带 `[模块 BTN]` 前缀，IND 的意见带 `[模块 IND]` 前缀

### Requirement: 模块文档存储

系统 SHALL 为一次用例编写任务提供任务级模块存储，按模块 KEY 保存完整 Markdown 文档与编写报告。编写角色 MUST 通过 `save_case_module_document` 保存完整七节文档；验收角色 MUST 通过 `read_case_module_document` 读取实际文档，MUST NOT 只依据 `report` 自述判卷。

保存工具 MUST 只写入当前模块 KEY，MUST NOT 允许模型跨模块覆盖。存储内容缺失或短于 200 字符时 MUST 视为空交付，按截断处理并进入模块拆分。最终结果文档 MUST 从存储内容拼装，MUST NOT 依赖 `report` 里的摘要。

#### Scenario: 保存后验收读取

- **WHEN** 编写角色调用 `save_case_module_document` 保存 20K 字符的七节文档
- **THEN** 验收角色的 `read_case_module_document` 能读到同一份全文
- **AND** 最终 `Task.result.document` 使用这份存储内容，而不是 `report` 摘要

#### Scenario: 未保存文档

- **WHEN** 编写轮次结束但模块存储里没有该 KEY 的文档
- **THEN** 该模块标记 `truncated=true`，不进入最终拼装，并按截断路径拆分/失败

### Requirement: 确定性校验

平台 MUST 在每轮 GoalPipeline 写完后，用代码解析模块文档并核对：七节是否齐全、原子/用例 ID 是否唯一、每条追溯 ID 是否存在于原子表、原子是否被覆盖、13 字段是否为空或占位符、执行状态是否合法、复杂度与最少方法数是否达标、P0 用例占比是否 ≤30%、E2E 是否 ≥3、预期结果是否含模糊词。

存在任一确定性问题时，该轮 MUST NOT 判定为通过。平台 MUST 追加一条 `[确定性问题]` 判决，把问题清单并入下一轮重写输入；没有剩余轮次时该模块判失败。

平台 MUST 用表格实际数据重写第六节「覆盖与门禁自检」，至少给出需求原子数、用例数、P0/P1/P2 用例数及占比、已判定覆盖率、已登记覆盖率、方法使用统计与 E2E 条数。重写结果 MUST 回写模块存储，验收角色读到的是修正后的统计。

#### Scenario: 统计与表格不一致

- **WHEN** 编写角色在第六节写「用例数 30」，但用例表实际只有 28 行
- **THEN** 平台把第六节重写为用例数 28
- **AND** 其余确定性问题（如有）作为 `[确定性问题]` 判决进入下一轮

#### Scenario: 追溯 ID 不在原子表

- **WHEN** 某条用例追溯 `REQ-999`，而原子表没有该 ID
- **THEN** 该轮标记确定性问题，MUST NOT 通过验收
- **AND** 下一轮输入包含「REQ-999 不在原子表」的明确要求

#### Scenario: 方法数不足

- **WHEN** 一条 L2 用例的方法列只有「场景流+判定表」两种
- **THEN** 该轮标记确定性问题，要求补足到三种或下调复杂度

#### Scenario: 确定性问题已修复

- **WHEN** 下一轮文档通过全部确定性校验且验收 `result=pass`
- **THEN** 该模块通过，最终文档使用代码重写后的第六节

### Requirement: 编写角色用计划模式跟踪五阶段

用例编写角色 SHALL 装配 AgentScope 计划模式工具 `TaskCreate`、`TaskGet`、`TaskList`、`TaskUpdate`，并 MUST 在开始拆解需求前创建计划任务。计划任务 MUST 覆盖至少四个阶段：需求原子拆解、方法匹配与优先级、13 字段用例编写、E2E 与自检；每进入一个阶段 MUST 用 `TaskUpdate` 标记 `in_progress`，完成时 MUST 标记 `completed`。交付七节文档前 MUST 用 `TaskList` 确认没有遗留的 `pending` / `in_progress` 任务。

计划清单只是过程管理，MUST NOT 替代七节文档：最终交付仍 MUST 是完整 Markdown（GoalPipeline 下还必须先保存到模块存储），MUST NOT 用计划摘要、任务列表或“已完成”当作交付正文。

规划角色与验收角色 MUST NOT 装配计划工具；验收角色仍只读文档与模块存储，MUST NOT 修改计划清单。

#### Scenario: 编写角色拿到计划工具

- **WHEN** 创建一个用例编写角色（含 SOP 与 GoalPipeline 两种装配）
- **THEN** 其工具包包含 `TaskCreate`、`TaskGet`、`TaskList`、`TaskUpdate`
- **AND** 规划角色与验收角色的工具包不包含这四个工具

#### Scenario: 编写前先建计划

- **WHEN** 编写角色收到一个模块的需求片段
- **THEN** 在输出需求原子表之前先调用 `TaskCreate` 建立阶段任务
- **AND** 阶段推进时调用 `TaskUpdate` 更新状态
- **AND** 最终交付仍是完整七节 Markdown

#### Scenario: 计划不能当交付

- **WHEN** 编写角色只创建了计划任务、没有产出七节文档
- **THEN** 验收角色按“没有完整用例文档”判不通过
- **AND** 计划清单不得被当作 handover 或模块存储文档

#### Scenario: 验收角色不改计划

- **WHEN** 验收角色判卷
- **THEN** 它没有 `TaskCreate` / `TaskUpdate` 等计划工具
- **AND** 只能读取模块存储文档并给出 `result` / `message`
