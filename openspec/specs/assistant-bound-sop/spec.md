# assistant-bound-sop Specification

## Purpose

让用户像新建助手一样登记一条 SOP：绑定两张助手名片，运行时读当前名片，并用里程碑 YAML 跑现有的执行加验收流程。

## Requirements

### Requirement: SOP 工作流只保存名称与两张名片引用

系统 SHALL 只允许助手作者创建一条 SOP 工作流。不是作者的已登录用户 MUST 被拒绝且不产生记录。记录 MUST 保存非空名称、执行助手编号与验收助手编号。编号 MUST 是已存在的助手名片 `assistant_id`。系统 MUST NOT 把名片的显示名、系统提示词、模型连接参数或工具勾选复制进工作流记录。两张名片可以是同一张。任一编号不存在时，创建 MUST 拒绝并返回可读原因。

#### Scenario: 绑定两张已有名片

- **WHEN** 助手作者提交名称，以及两张已存在的助手名片编号
- **THEN** 系统创建工作流，记录只含名称与这两个编号

#### Scenario: 同一张名片同时担任两侧

- **WHEN** 助手作者把同一张助手名片同时选为执行助手与验收助手
- **THEN** 系统创建工作流

#### Scenario: 名片不存在时拒绝创建

- **WHEN** 执行助手或验收助手编号不对应任何名片
- **THEN** 系统拒绝创建，并说明哪一侧的名片不存在

#### Scenario: 非作者不能创建

- **WHEN** 不是助手作者的已登录用户提交合法名称和两张已存在的名片编号
- **THEN** 系统返回 403
- **AND** 不产生工作流记录

### Requirement: 运行时现读当前名片

系统 SHALL 在工作流任务开跑和重跑时读取该任务已记下的冻结版本，MUST NOT 读取两侧名片的当前内容。版本中的系统提示词、模型与工具勾选 MUST 作为本次两侧角色的运行内容。任务没有版本时 MUST 失败，且 MUST NOT 开始第一步。名片在任务记下版本后被修改、退回草稿或删除，MUST NOT 改变该任务的运行内容。

#### Scenario: 改名片后下次运行使用新内容

- **WHEN** 工作流发布后，作者修改执行名片的系统提示词并再次发布，用户随后提交一条新任务
- **THEN** 新任务使用新版本的系统提示词
- **AND** 发布前已记下旧版本的任务仍使用旧提示词

#### Scenario: 名片已删除时不开始步骤

- **WHEN** 任务已经记下版本，但其中一侧的运行内容在版本中缺失
- **THEN** 运行失败，详情说明缺失的一侧，且不产生步骤执行

#### Scenario: Agent 配置已删除时不开始步骤

- **WHEN** 任务所记版本无法解析出一侧的模型或提示词
- **THEN** 运行失败，并且不开始第一步

### Requirement: 运行输入是里程碑 YAML

本要求只适用于 `sop + ui_automation`。系统 SHALL 在启动该组合时接收一份 YAML。顶层 MUST 含非空 `name` 与非空 `steps`。每一步 MUST 含非空 `subject` 与非空 `description`。`max_attempts` 缺省为 3，写出时 MUST 是正整数。`task` 与 `description` 可选。YAML MUST NOT 作为角色来源；其中出现的角色、模型或工具字段 MUST 被忽略。用例格式（根节点为用例列表，或步骤使用 `action` 与 `assert`）MUST 被拒绝，并且 MUST NOT 进入执行。一次运行 MUST 只有一份该 YAML。Goal 与 Team MUST NOT 要求这份 YAML。

#### Scenario: 合法里程碑可以启动

- **WHEN** 用户为 UI 自动化工作流提交一份含两个步骤的 YAML，每步都有非空 `subject` 与 `description`，且两张名片都可解析
- **THEN** 系统按文件顺序执行这两步

#### Scenario: 用例格式被拒绝

- **WHEN** 用户为 UI 自动化工作流提交的 YAML 用 `title`、`action`、`assert` 描述用例
- **THEN** 系统拒绝本次运行，并说明需要里程碑格式

#### Scenario: YAML 里的角色字段不生效

- **WHEN** 里程碑 YAML 另外写了执行者或验收者编号
- **THEN** 系统仍使用工作流绑定的两张名片

### Requirement: 整份流程只使用一对角色

本要求只适用于 `sop` 与 `goal`。一次运行 MUST 只装配一个执行角色实例与一个验收角色实例，并在该次运行中复用这一对。系统 MUST NOT 为每一步新建角色，也 MUST NOT 让两侧共用同一个运行实例。执行角色 MUST 只挂载其名片勾选与该种类允许工具的交集。验收角色 MUST 再去掉写操作工具。未知工具名 MUST 使运行失败，并且 MUST NOT 开始第一步。`team` MUST NOT 适用本要求。

#### Scenario: 步骤之间复用同一对实例

- **WHEN** UI 自动化 YAML 含两步，且第一步已经执行
- **THEN** 第二步仍由同一次运行里的那一个执行实例与那一个验收实例处理

#### Scenario: 验收侧丢掉写工具

- **WHEN** 验收名片勾选了只读工具和写操作工具
- **THEN** 验收角色只挂载其中的只读工具

#### Scenario: 未知工具名拒绝启动

- **WHEN** 执行名片的工具勾选含目录中不存在的名字
- **THEN** 运行失败，并且不开始第一步

### Requirement: 新入口不改变既有控制设备任务

本工作流 MUST 使用独立入口启动。既有控制设备任务 MUST 继续使用其现有步骤来源、角色装配与用例 YAML 校验。本变更 MUST NOT 要求控制设备任务改为里程碑 YAML，也 MUST NOT 把本工作流的名片绑定写入控制设备任务。

#### Scenario: 旧任务仍按原入口运行

- **WHEN** 用户按现有方式提交一条控制设备任务
- **THEN** 该任务不读取 SOP 工作流绑定，也不按里程碑 YAML 校验其配置附件

### Requirement: 设备不是本工作流的必填项

设备是否必填 MUST 由种类决定。`ui_automation` 启动时 MUST 选择一台设备，设备为空时 MUST 拒绝创建任务。`case_authoring` 与 `requirement_breakdown` MUST NOT 要求设备；提交设备时系统 MUST 忽略该设备，并且 MUST NOT 因此占用设备槽。

#### Scenario: UI 自动化缺少设备被拒绝

- **WHEN** 用户启动一条 UI 自动化工作流，且未选择设备
- **THEN** 系统拒绝创建任务，并提示需要选择设备

#### Scenario: 用例编写不因缺少设备被拒绝

- **WHEN** 用户启动一条绑定合法的用例编写工作流，且未提供设备
- **THEN** 系统不因缺少设备而拒绝本次运行

### Requirement: 工作流可以由用户编辑与删除

系统 SHALL 只允许助手作者编辑或删除一条已有工作流。编辑 MUST 只改名称与两侧名片编号，并 MUST 沿用创建时的校验：名称非空、两侧名片都存在、两侧可以是同一张。校验失败时 MUST 拒绝并说明是哪一侧，且 MUST NOT 留下任何被改动的字段。删除 MUST 只删该工作流记录，MUST NOT 删除两张助手名片、它们引用的 Agent 配置，或任何历史任务。不是作者的请求 MUST 返回 403，且 MUST NOT 改动记录。

#### Scenario: 改名后卡片同步

- **WHEN** 助手作者点某工作流卡片的「配置」，把名称改掉并保存
- **THEN** 同一张卡片显示新名称
- **AND** 记录里仍是原来的两个名片编号

#### Scenario: 换执行助手后按新名片运行

- **WHEN** 助手作者把执行助手换成另一张名片并保存，随后启动该工作流
- **THEN** 本次执行角色使用新名片的提示词、模型与工具勾选

#### Scenario: 编辑时名片不存在

- **WHEN** 助手作者提交的两侧名片中有一侧已在别处被删除
- **THEN** 保存被拒绝，并说明是哪一侧的名片不存在
- **AND** 工作流记录保持编辑前的名称与编号

#### Scenario: 删除工作流不动名片与任务

- **WHEN** 助手作者删除一条已经跑过任务的工作流
- **THEN** 该工作流记录消失
- **AND** 两张助手名片与历史任务仍然存在

#### Scenario: 非作者不能编辑或删除

- **WHEN** 不是助手作者的已登录用户请求修改或删除一条工作流
- **THEN** 系统返回 403
- **AND** 工作流记录保持原样

### Requirement: 页面按助手在上、工作流在下分区呈现

助手入口页 SHALL 分成两个区块：助手区块 MUST 在上，工作流区块 MUST 在下。两个区块都 MUST 用卡片网格展示。普通用户的两个区块 MUST 只展示已发布记录。作者与超级管理员 MUST 同时看见自己可见的草稿，并标明草稿。工作流 MUST NOT 再以页内常驻表单呈现。两个区块之间 MUST 有一条分区虚线。工作流卡片 MUST 显示名称，并按编排显示绑定：`sop` 与 `goal` 显示执行者与验收者，`team` 显示队长与成员数量。卡片 MUST 保持便签卡形态：顶部半透明笔色胶带、浅墨虚线外框，底部「配置」「任务」与一块不可交互的占位块。只有助手作者的工作流区块 MUST 提供「新建工作流」入口，新建时 MUST 先选择允许的编排与种类，并保存为草稿。

#### Scenario: 打开页面先看到助手再看工作流

- **WHEN** 用户打开助手入口页
- **THEN** 助手卡片网格排在页面上方
- **AND** 工作流卡片网格排在其下方，两块之间有一条虚线

#### Scenario: Team 卡片显示队长与成员数

- **WHEN** 用户查看一条含一名队长和三名成员的需求拆解工作流
- **THEN** 卡片显示队长名称与成员数量 3
- **AND** 不显示验收者

#### Scenario: 没有助手时新建被拦住

- **WHEN** 平台上还没有任何助手名片，助手作者点「新建工作流」
- **THEN** 弹窗说明需要先新建助手
- **AND** 保存不可用

#### Scenario: 普通用户看不到草稿

- **WHEN** 作者有一条草稿工作流，普通用户打开助手入口页
- **THEN** 该草稿不在工作流区块中

### Requirement: 工作流卡片只有配置与任务两个动作

每张工作流卡片 MUST 只有「配置」与「任务」两个动作，MUST NOT 提供第三个动作入口。点「配置」MUST 打开预填了该工作流名称与绑定的弹窗，并且 MUST NOT 允许改编排或种类。点「任务」MUST 打开该工作流种类对应的运行弹窗。卡片 MUST NOT 显示工具清单、模型名或工作流编号。

#### Scenario: 卡片上只有两个按钮

- **WHEN** 用户查看任意一张工作流卡片
- **THEN** 卡片动作只有「配置」与「任务」

#### Scenario: 配置不能改种类

- **WHEN** 用户点一条 UI 自动化工作流的「配置」
- **THEN** 弹窗预填当前名称与绑定
- **AND** 编排与种类可见但不可修改

#### Scenario: 任务由卡片带入工作流

- **WHEN** 用户点某张卡片的「任务」
- **THEN** 弹窗打开，并且不要求再选一次工作流

### Requirement: 运行弹窗只提交工作流编号、里程碑 YAML 与可选设备

运行弹窗 MUST 按工作流种类展示输入。`ui_automation` MUST 提供平台用例或一份里程碑 YAML，并且 MUST 从设备管理列表选择一台设备；未选设备或未提供用例输入时 MUST NOT 提交。`case_authoring` MUST 要求选择一个已确认的需求模块。`requirement_breakdown` MUST 要求一份需求文档。后两种 MUST NOT 展示设备选择，也 MUST NOT 要求里程碑 YAML。提交 MUST 只带工作流编号和该种类要求的输入，MUST NOT 带提示词、工具清单或角色编号。提交成功后弹窗 MUST 关闭，并 MUST 提示新任务编号。

#### Scenario: UI 自动化没选设备不能提交

- **WHEN** 用户为 UI 自动化工作流选择了合法用例输入，但没有选择设备
- **THEN** 提交被拒绝并提示需要选择设备

#### Scenario: 需求拆解只提交文档

- **WHEN** 用户为需求拆解工作流选择一份需求文档后提交
- **THEN** 请求体含工作流编号与该文档
- **AND** 请求体不含设备与里程碑 YAML

#### Scenario: 提交成功后关闭弹窗

- **WHEN** 任务提交成功
- **THEN** 弹窗关闭，页面提示新任务编号
