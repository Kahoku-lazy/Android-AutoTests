# sop-task-run Specification

## Purpose

控制设备任务只启动和关闭已登记的 SOP 智能体。后端把检查通过的 YAML 文件、设备序列号与可选指定用例交给智能体；工具以引擎代码为准，后端不改工具清单。智能体在跑步骤前报告配置是否加载成功。

## Requirements

### Requirement: 控制设备任务只启动已登记的 SOP
系统 SHALL 只允许控制设备任务启动已登记的智能体。当前登记表 MUST 只包含 `sop`。新建任务所选的平台小助手决定执行与验收模型，流程仍是 `sop`。任务 MUST NOT 再调用规划模型生成步骤。YAML 中出现未登记的智能体名称 MUST 使该任务加载失败，并且 MUST NOT 装配流程。

#### Scenario: 指定 sop 时可以启动
- **WHEN** 一份通过格式检查的 YAML 未写 `agent` 或声明为 `sop`，新建任务选中了平台小助手上展示的助手，且该设备没有其它运行中的任务
- **THEN** 系统启动 `sop`，步骤来自该 YAML，模型来自所选助手，而不是规划模型的产出

#### Scenario: 未登记的智能体不能启动
- **WHEN** YAML 声明的智能体不是 `sop`
- **THEN** 任务显示「加载失败」，并且不产生可运行流程

### Requirement: 工具由引擎代码决定

启动 SOP 时系统 MUST 使用该智能体在引擎代码中声明的工具集。任务请求 MUST NOT 携带工具清单。后端 MUST NOT 在启动时增加、删除或替换这些工具。平台 MUST NOT 提供任何可在任务启动前改变该工具集的装配界面或开关（原 AI 工具箱/装配台已整体下线）。

#### Scenario: 启动时使用代码中的工具

- **WHEN** 一条声明为 `sop` 的任务开始执行
- **THEN** 执行与验收使用引擎代码里为 `sop` 声明的工具，任务请求中没有工具清单

#### Scenario: 装配台开关不改变本次工具

<!-- 场景名沿自变更前：装配台已下线，本场景改为守住「不存在可改变工具集的平台开关」这一不变量 -->

- **WHEN** 检查平台是否提供任务启动前的工具装配开关
- **THEN** 不存在这样的界面或配置项，工具集只由引擎代码决定

### Requirement: YAML 必须通过格式检查
系统 SHALL 在创建任务前检查 YAML。根节点 MUST 是非空的用例列表，或单条用例映射。每条用例 MUST 含非空的 `title` 与 `steps`。`agent` 可以不写；未写时系统 MUST 按 `sop` 接受该用例。若写了 `agent`，同一文件内 MUST 全部相同且等于 `sop`。每一步 MUST 含非空的 `action` 与 `assert`。一次任务 MUST 只有一份 YAML。检查不通过时系统 MUST 拒绝创建任务并返回可读原因。csv 与 json MUST 被拒绝。

#### Scenario: 合法 YAML 可以创建任务
- **WHEN** 用户提交一份含两条用例的 YAML，两条都没有 `agent`，且每步都有非空 `action` 与 `assert`
- **THEN** 系统创建任务，并保留该 YAML 正文

#### Scenario: 缺少步骤字段或智能体不一致时拒绝创建
- **WHEN** 某步缺少 `action` 或 `assert`，或文件里出现不是 `sop` 的 `agent`，或文件里出现两个不同的 `agent`
- **THEN** 系统拒绝创建任务，并说明格式不符合

#### Scenario: 一次任务上传两份 YAML
- **WHEN** 用户在同一次提交中附上两份 YAML
- **THEN** 系统拒绝创建任务，并说明只能有一份配置

### Requirement: 执行前再次检查配置并显示结论
智能体在跑任何步骤之前 MUST 再读一遍平台传入的 YAML 文件。符合上述格式且智能体为 `sop` 时，任务 MUST 显示「配置加载成功」并开始步骤。不符合时任务 MUST 显示「加载失败」，状态进入失败，并且 MUST NOT 开始第一步。该结论 MUST 出现在任务详情中。

#### Scenario: 文件在启动时仍然合法
- **WHEN** 任务开始执行，且传入的 YAML 文件仍符合格式，并且未写 `agent` 或指定 `sop`
- **THEN** 任务详情显示「配置加载成功」，随后按文件顺序执行用例

#### Scenario: 文件在启动时已不可读
- **WHEN** 任务开始执行，但 YAML 文件缺失或内容不再符合格式
- **THEN** 任务详情显示「加载失败」，任务状态为失败，设备上的后续排队任务可以被拉起

### Requirement: 同一 YAML 的多条用例按文件顺序跑完

一次任务 MUST 按 YAML 中的用例顺序依次执行。任务指定了 `case_title` 时 MUST 只执行标题完全匹配的那一条用例，其余用例 MUST NOT 执行；`case_title` 为空时 MUST 执行全部用例。后一条用例 MUST NOT 复用前一条的角色对话。选择哪条用例 MUST 由 `case_title` 决定，MUST NOT 用任务标题或任务目标去匹配。指定的 `case_title` 在 YAML 中不存在时，系统 MUST 让任务以可读原因失败，MUST NOT 静默改为执行全部用例。某条用例失败时，系统 MUST NOT 开始排在它后面的用例。

#### Scenario: 两条用例依次执行

- **WHEN** YAML 中用例标题依次为「甲」和「乙」，`case_title` 为空，且「甲」完成
- **THEN** 系统先跑完「甲」，再跑「乙」

#### Scenario: 前一条失败则停止后续用例

- **WHEN** 「甲」未完成
- **THEN** 「乙」不会开始，任务状态为失败

#### Scenario: 指定用例只跑该条

- **WHEN** YAML 中用例标题依次为「甲」和「乙」，`case_title` 为「乙」
- **THEN** 系统只执行「乙」，不执行「甲」

#### Scenario: 指定用例不存在时失败

- **WHEN** `case_title` 为「丙」，但 YAML 中没有标题为「丙」的用例
- **THEN** 任务以可读原因失败，且不执行任何用例

### Requirement: 用户可以关闭运行中的 SOP
系统 SHALL 允许用户关闭一条运行中的控制设备任务。关闭后该任务 MUST 停止后续步骤，状态变为 cancelled，详情保留已产生的步骤记录与配置加载结论。pending 任务 MUST NOT 提供关闭。

#### Scenario: 关闭运行中的任务
- **WHEN** 用户关闭一条状态为 running 的任务
- **THEN** 该任务不再执行后续步骤，状态变为 cancelled

#### Scenario: 排队中的任务不能关闭
- **WHEN** 用户对一条 pending 任务请求关闭
- **THEN** 系统拒绝该操作，任务仍为 pending

### Requirement: 启动时组装执行与验收模型

系统 SHALL 在启动控制设备任务时，从所选助手的控制设备线路读取执行模型与验收模型，并交给 SOP。系统 MUST NOT 再调用旧规划引擎，也 MUST NOT 要求规划角色存在。执行或验收缺少模型名、密钥为空，或 provider 不是 DeepSeek 与阿里百炼之一时，任务 MUST 以失败结束，并且 MUST NOT 开始步骤。provider 不合法时，错误 MUST 指出该 provider 与合法集合。

#### Scenario: 执行与验收模型进入 SOP

- **WHEN** 控制设备线路上执行与验收都有合法的模型名、密钥与 provider，且 YAML 通过格式检查
- **THEN** 任务启动 SOP，使用这两份模型，不调用规划模型

#### Scenario: 缺少规划角色仍可启动

- **WHEN** 控制设备线路没有规划角色，但执行与验收配置合法
- **THEN** 任务仍能启动 SOP

#### Scenario: 模型配置不合法时失败

- **WHEN** 执行或验收的模型名为空、密钥为空，或 provider 不是 DeepSeek 与阿里百炼之一
- **THEN** 任务状态为失败，不开始第一步，错误说明指出缺失或非法的项

### Requirement: 开场说明由设备序列号组成

系统 SHALL 用固定模板生成执行开场说明，只交给第一条用例的第一步：

`本次要操作的设备 serial 是：{device_serial}。每一步的设备动作都必须带上它。`

开场说明 MUST 只由设备序列号决定，MUST NOT 读取任务目标、文档附件或 YAML 正文。设备序列号为空时系统 MUST 在提交阶段拒绝创建任务，MUST NOT 用空串生成开场。

#### Scenario: 设备序列号进入开场

- **WHEN** 任务设备序列号为 `R5CT62RH88F`
- **THEN** 第一步收到的开场说明为「本次要操作的设备 serial 是：R5CT62RH88F。每一步的设备动作都必须带上它。」

#### Scenario: 开场不拼目标与文档

- **WHEN** 历史任务带有任务目标或文档附件
- **THEN** 执行开场仍只有设备序列号那一句，不追加目标或文档正文

#### Scenario: 设备为空不生成任务

- **WHEN** 提交时设备序列号为空
- **THEN** 系统拒绝创建任务，不进入执行

### Requirement: 用例结束后关闭最近任务中的非桌面应用

系统 SHALL 在一条用例的步骤执行结束之后，关闭该任务设备最近任务中的非桌面应用，并回到桌面。结束包含该用例通过、失败，以及执行过程中被用户取消。尚未开始的用例 MUST NOT 触发这次关闭。桌面与系统界面 MUST NOT 被停止。这次关闭 MUST NOT 作为用例步骤交给执行角色或验收角色，MUST NOT 占用该步的验收次数。关闭失败时系统 MUST 保留该用例已经得出的通过、失败或取消结论，并且 MUST 留下可读日志。

#### Scenario: 用例通过后关闭非桌面应用

- **WHEN** 一条用例的步骤执行通过，且最近任务中有非桌面应用
- **THEN** 这些应用被关闭，设备回到桌面，该用例仍记为通过

#### Scenario: 用例失败后同样关闭

- **WHEN** 一条用例的步骤执行失败
- **THEN** 最近任务中的非桌面应用仍被关闭，设备回到桌面，任务失败结论保持不变，排在后面的用例仍不开始

#### Scenario: 执行中被取消后关闭已跑过的用例

- **WHEN** 用户在一条用例执行过程中关闭任务
- **THEN** 该用例最近任务中的非桌面应用被关闭，任务状态仍为取消，尚未开始的用例不执行也不触发关闭

#### Scenario: 桌面与系统界面不被停止

- **WHEN** 最近任务里同时有桌面、系统界面和被测应用
- **THEN** 只关闭被测应用，桌面与系统界面保持运行，设备回到桌面

#### Scenario: 关闭失败不改判决

- **WHEN** 用例已经得出通过或失败，随后关闭应用的设备操作失败
- **THEN** 该通过或失败结论不变，并留下可读日志
