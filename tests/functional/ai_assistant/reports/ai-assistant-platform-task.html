一、核心定位

平台任务是平台的测试资产生产流水线，AI 的职责是「先确认用户要做什么 → 再合理编排平台工具完成」。四条职责存在先后依赖，也可单独执行：

① 探索手机 → 元素定位       （抓页面 / 标记可点击·可滑动 / 取 XPath）
     ↓ 输出：元素定位库（XPath + 功能名标记）
② 绘制页面跳转图谱       （关联元素定位页面 / 标注每页元素数）
     ↓ 输出：页面流图谱（页↔页 + 每页元素数）
③ 阅读图谱 + 元素 → 写用例   （自动化用例脚本，存用例管理）
     ↓ 输出：用例定义
④ 执行用例             （经任务卡片 → 平台执行引擎）
     ↓ 输出：运行结果
与「控制设备」的区别：控制设备的目标是「操作设备到某状态」，平台任务的目标是「产出 / 查询平台资产」，设备（职责①的 capture_page、职责④的 run_test）只是工具。

二、职责 → 工具映射

职责编排的工具序列产物
① 探索 + 元素定位 capture_page（抓 JSON+落快照）→ analyze_page（分区/功能名/XPath/意图）→ save_page_semantic（标记 func_name）→ save_page_to_elements（写元素定位） 元素定位库（XPath + 可点击/可滑动标记）
② 页面跳转图谱 list_pages + fetch_page_elements（数元素）→ create_page_flow（建跳转边）→ save_page_flow（生成图谱文档） 页面流图谱（页↔页 + 每页元素数）
③ 用例脚本生成 get_page_flow（读图谱）+ fetch_page_elements/search_elements（读元素）→ save_case（写用例） 用例定义（存用例管理）
④ 用例执行 run_test（下发执行）→ get_run_status/get_run_results（轮询结果）→ stop_run（可中止） 执行结果
四条职责全部由现有平台工具（REASONING_TOOLS 的 22 个工具）覆盖，AI 只做编排、不新造工具。

三、「先确认用户要做什么」→ 落成 planner 职责

PLATFORM_PLANNER_PROMPT 的核心行为分两步：

步骤内容
1. 任务理解从 goal + requirements 判断用户属于哪条职责（①~④ 或 ①②③④ 组合流水线），并确认对象（哪个 App / 哪个页面 / 哪批用例 / 哪台设备）。
2. 编排规划为每个职责产出一个 GoalPlan{goal, steps, verification}——steps 即上方表格的工具调用序列，verification 即「产物是否已落库 / 结果是否正确」。
「确认用户要做什么」不是交互式追问，而是 planner 结构化输出里显式写清「我判断你要做 X，将用工具 a→b→c」，任务卡片与日志可回看。

四、分层设计（对齐 config / model / workflow，各加一个类）

文件新增内容
config.pyPlatformTaskConfig（三槽 planner/executor/verifier + max_loops）+ PLATFORM_PLANNER_PROMPT / PLATFORM_EXECUTOR_PROMPT / PLATFORM_VERIFIER_PROMPT
model.pyPlatformTask 类：planner(文本) + executor(文本, REASONING_TOOLS) + verifier(文本, PLATFORM_VERIFIER_TOOLS)
workflow.pyPlatformTaskWorkflow 类：复用 DeviceExecutionWorkflow 骨架，去掉 serial 强依赖，注入 requirements/checklist/report_name
tools.py新增 PLATFORM_VERIFIER_TOOLS（只读查询子集：get_case/search_cases/debug_case/fetch_page_elements/list_pages/get_page_flow/get_run_results/get_run_status）

五、工作流（复用三模型骨架）

user_input(goal) + requirements + checklist + report_name + device_serial(可选)
  ├─ ① planner：判断职责 → plans = [GoalPlan{goal, steps, verification}]
  └─ ② 逐目标
       └─ 内层循环(max_loops)
            ├─ executor：按 steps 编排 REASONING_TOOLS
            ├─ verifier：用 PLATFORM_VERIFIER_TOOLS 二次确认 → pass/fail
            ├─ pass → 下目标；fail → 退回重试
            └─ 用尽仍 fail → 「任务失败」
三模型全用文本模型（平台工具返回 JSON/文本、无图），区别于设备控制的 executor/verifier 用视觉模型。

六、关键决策

决策点结论说明
D1 · 写工具权限A · 自动放行save_page_semantic/save_page_to_elements/create_page_flow/save_page_flow/save_case/run_test 等写工具加入 AUTO_ALLOW_TOOLS——用户下发任务即授权。
D2 · 同步 vs 异步待定职责④ run_test 可能跑几分钟。A = 首版同步 asyncio.run（与 device_control 一致）；B = 后台任务 + AITask 状态轮询。
D3 · 借道设备A · 允许职责①需 capture_page(serial)、职责④需 run_test(serial)，允许平台任务携带设备，目标产出仍是平台资产。
D4 · 独立提示词A · 独立平台任务的 planner/verifier 语义（产出资产）与设备控制（操作设备）不同，独立提示词更准。

八、验收标准

☐ platform_task 端到端跑通（planner → executor ↔ verifier）
☐ 用例生成类任务真实落库并被 verifier 二次确认 pass
☐ 失败 max_loops 重试后返回「任务失败」
☐ 日志与 device_control 同规则（写 logs/AI-MODEL-TEST.log）
