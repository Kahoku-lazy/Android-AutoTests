🎯 第一部分：业务视角 — 用例编辑器是做什么的

1 功能定位

用例编辑器是测试工程师创建和维护自动化测试用例的核心工具，用表单 + 步骤编排的方式，让不写代码的人也能构建可在真机上执行的测试脚本。

它不是一个简单的表单——用户在这里定义用例的基本信息（标题、包名、分类），然后通过步骤编辑器一条条添加操作步骤（点击、等待、验证、滑动等 14 种类型）， 每条步骤可以绑定从元素定位模块获取的真实 XPath 定位符。保存后的用例可以在执行引擎中一键运行。

2 用户故事

👤 测试工程师 · 接到新需求
"我要为登录功能创建一条自动化测试用例：启动 App → 点击登录按钮 → 输入用户名密码 → 点击确定 → 验证跳转到首页。"
打开用例编辑器 → 填写标题"登录测试"和包名 → 在步骤编排器中添加 5 个步骤（start_app / click / click / click / verify_text）→ 从元素库选取每个步骤的 XPath → 保存 → 去执行引擎运行。
👤 测试开发 · 维护已有用例
"产品改了登录按钮的文案，我需要更新用例里的验证文本。"
在用例列表中找到"登录测试"→ 点击编辑 → 找到 verify_text 步骤 → 修改 expected_text 字段 → 保存。编辑器自动检测到修改，离开时提醒保存。
👤 自动化测试新手 · 不会写 XPath
"我想为首页各个入口写点击测试，但不知道怎么拿到元素的定位符。"
在编辑器中点击"去元素定位"按钮 → 跳转到元素定位页面 → dump 当前手机屏幕 → 选中目标元素 → 复制 XPath → 回到编辑器粘贴。不用手写一行 XPath。

3 解决的痛点

❌ 没有用例编辑器之前

  • 用例是手写的 YAML 文本，语法容易出错，缩进不对就解析失败
  • XPath 要靠人工从 dump 文件里找，复制粘贴容易漏字符
  • 改了步骤忘记保存，切换页面后丢失全部修改
  • 步骤类型记不住——不知道 wait 和 wait_disappear 的区别
  • 调试步骤要到命令行手动执行，没有可视化界面

✅ 有了用例编辑器之后

  • 表单化输入：下拉选步骤类型、填参数，不用记语法
  • 集成元素库：一键跳转选取 XPath，零手写
  • 防丢保护：未保存修改离开时弹窗确认，浏览器后退也拦截
  • 14 种步骤可视化：每种有中文名和说明，新手也能上手
  • 在线调试：选设备后可以单步/批量执行，实时看到结果

5 数据流全景 — 7 层逐层展开

📖 数据流概览

用例编辑器涉及读（打开编辑页时加载已有用例）和写（保存时创建/更新用例）两条路径。 写路径比读路径复杂——前端收集表单数据 + 步骤 JSON → POST 到后端 → update_or_create 写入 cm_test_definitions 表。

🟡 第 1 层：数据库 — cm_test_definitions 表

字段通俗含义编辑器用它做什么
id用例编号——格式 TC-20260705-143000-1234自动生成或手动输入，保存后作为主键
title用例标题基本信息表单的标题输入框
category分类标签（如"登录""支付"）基本信息表单的分类输入框
package_name被测 App 的包名（如 com.example.app）启动/关闭/重启 App 步骤的必需参数
description用例说明文字基本信息表单的描述文本域

steps_json步骤的结构化 JSON（核心数据）StepEditor 组件产出 → 序列化存入此字段

6 前端实现 — CaseEditor.vue

👁️ 从交互上你能感知到什么？

新建模式：ID 自动生成为 TC-日期-时间-4位随机码，可以点"重新生成"换一个。标题和包名是必填项，保存前校验。步骤列表初始为空，逐条添加。
编辑模式：根据 URL 中的 /cases/:id/edit 加载已有数据填充表单。修改后如果未保存就离开，浏览器会弹窗拦截（包括浏览器的后退按钮和页面内导航）。
调试模式：选设备后，StepEditor 中的步骤可以逐条在真机上执行，即时反馈。

保存流程

async function save() {
  // 1. 前置校验
  if (!form.value.title.trim()) { ElMessage.warning('请输入用例标题'); return }
  if (!form.value.package_name.trim()) { ElMessage.warning('请输入 APP 包名'); return }

  // 2. POST 到后端
  const { data } = await client.post('/cases/definitions', form.value)

  // 3. 新建 → 跳转到编辑模式（URL 变为 /cases/{id}/edit）
  if (isNew.value && data.id) {
    form.value.id = data.id
    await router.replace(`/cases/${data.id}/edit`)
  }

  // 4. 更新脏标记快照
  initialForm.value = JSON.parse(JSON.stringify(form.value))
}

7 后端实现 — definitions_handler

🔄 后端数据流转 — 用大白话讲

保存时 POST 一个 JSON 到后端 → 后端检查有没有传 case_id → 没有就自动生成一个 TC- 格式的 ID → 把 steps_data 数组序列化为 JSON 字符串（steps_json）→ 从 steps_data 自动生成可读文本摘要（steps）→ update_or_create：如果数据库里已有这个 ID 就更新，没有就新建 → 返回新 ID 给前端。 

// POST /api/cases/definitions — 核心保存逻辑
def definitions_handler(request):
    data = json.loads(request.body)
    case_id = data.get("id", "").strip()

    // 自动生成 ID：TC-20260705-143000-1234
    if not case_id:
        suffix = ''.join(random.choices(string.digits, k=4))
        case_id = f"TC-{now.strftime('%Y%m%d')}-{now.strftime('%H%M%S')}-{suffix}"

    // 序列化步骤 + 自动生成文本摘要
    steps_json = json.dumps(data.get("steps_data", []), ensure_ascii=False)

    // 写入数据库（存在则更新，不存在则创建）
    TestDefinition.objects.update_or_create(id=case_id, defaults={...})

    return JsonResponse({"ok": True, "id": case_id})

11 错误处理与日志规范

❌ 禁止

  • catch {} — CaseEditor 中 loadDevices() 的 catch(_) 是违规
  • 保存失败不报错 — 用户以为保存成功实际没存
  • 脏检测在保存成功后不更新快照 — 导致永远显示"未保存"

✅ 必须（当前已部分做到）

  • 保存前校验必填字段 + ElMessage.warning()
  • 保存失败 ElMessage.error() + 返回 false
  • 浏览器后退拦截未保存修改（onBeforeRouteLeave）
  • 页面内退出拦截未保存修改（ElMessageBox.confirm）
