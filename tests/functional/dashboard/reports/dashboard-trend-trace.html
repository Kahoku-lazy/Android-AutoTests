🎯 第一部分：业务视角 — 这个功能是做什么的

1 功能定位

趋势数据是仪表盘的核心分析模块，用最近 12 天的测试执行数据回答一个问题：项目的自动化测试质量是在变好还是变差？

它不是单纯的数字展示，而是一张"体检报告"——让测试团队一眼看清执行成功率的变化趋势、失败集中爆发的时间点、以及用例库的增长节奏。

📈
执行成功趋势
每天通过多少条用例
📉
执行失败趋势
每天失败了多少条
➕
用例增长趋势
每天新增了多少用例

2 用户故事

👤 测试负责人 · 周一早会前
"我要快速了解上周的自动化测试执行情况，判断质量趋势，决定本周的测试策略。"
打开仪表盘 → 看趋势图 → 如果失败数连续上升，本周优先修 Bug 而非加新用例；如果成功率稳定，继续推进用例覆盖。
👤 测试开发工程师 · 发布前
"我要确认最近几天没有引入新的回归失败，发布风险可控。"
打开仪表盘 → 检查趋势图最近的柱子 → 如果失败数突增，立即排查是哪个用例失败 → 点击右侧任务列表定位。
👤 项目经理 · 周报时间
"我要拿到本周的测试数据：执行了多少次、通过率多少、新增了多少用例。"
打开仪表盘 → 右侧摘要筹码直接显示三个关键数字（成功/失败/本周新建）→ 截图放入周报。

3 解决的痛点

❌ 没有趋势数据之前

  • 每次想知道测试情况，要去执行引擎一页页翻历史记录
  • 无法判断失败是偶发的还是持续恶化——看到一条失败就紧张，其实昨天也只有一条
  • 用例增长率完全靠感觉——"好像最近加了不少"
  • 周报数据要手动数、手动算，每次 10-15 分钟
  • 执行中的任务不知道进度，要跑到执行引擎页面看

✅ 有了趋势数据之后

  • 一页概览：打开仪表盘 3 秒内看到最近 12 天趋势
  • 趋势判断：连续上升/下降一目了然，不用翻历史
  • 数据驱动：用例增长有数字，汇报有底气
  • 零成本周报：摘要数字直接可用，省 10+ 分钟
  • 实时感知：右侧面板显示正在执行的任务，不用跳转页面

5 数据流全景

📖 数据流全景 — 逐层通俗解释

这张图展示了数据从数据库到屏幕的完整旅程，共 7 层。从下往上逐层看：

层名称通俗理解
1 🟡 数据库 数据的最原始形态——系统运行中自动记录下来的日志。就像银行流水，每执行一次测试就记一笔。这 4 张表分散在 3 个模块中，趋势功能只是去"读"它们，不会修改。
2 🔵 后端函数 数据加工厂——dashboard_stats() 是总指挥，它调用 _daily_execution_series()（算最近 12 天每天的成功/失败/新建数）和 _recent_tasks()（收集最近 8 条任务记录）。把散落在各表的原始数据加工成有意义的统计数字。
3 🟢 JSON 响应 数据打包成包裹——后端函数算完后，把所有数字拼成一个标准格式的 JSON 对象：{"ok": true, "data": {...}}。这个 JSON 就是前后端之间的合同——格式固定，前端按字段名取数据，后端不能随便改字段名。
4 🔴 前端数据层 拆包裹，分快递——前端拿到 JSON 后，把里面的数据拆成三个独立的变量：executionChart（给柱状图）、executionSummary（给摘要筹码）、recentTasks（给任务列表）。每个变量只包含对应组件需要的数据，互不干扰。
5 🟣 渲染组件 把数字变成画面——两个 Vue 组件各自拿到自己的数据后开始画界面：TrendBarChart 用 SVG 画柱子（纯代码绘图，不依赖任何图表库），TaskResultPanel 渲染彩色卡片和列表。这两个组件可以独立修改——比如换柱状图颜色只需改 TrendBarChart，不影响右侧面板。
6 🎨 视觉主题 统一的外观风格——所有 UI 组件（卡片、按钮、表格）都使用 animal-island-vue 动森主题 UI 库渲染。配色是暖木色系（#f8f8f0 背景 + #794f27 标题），圆角最小 12px，字体是 Nunito。Dashboard 不引入 Element Plus，保持视觉纯净。柱状图的三色（绿/红/蓝）和状态图标的五色（绿/红/黄/蓝/灰）与主题配色协调一致。

🟡 第 1 层：数据库（4 个数据源）

表名通俗含义趋势数据用它做什么
tr_test_results 每次测试的分数单——记录"哪条用例、哪天跑的、通过还是失败" 统计每天通过了几条、失败了几条
tr_test_runs 测试任务工单——记录"谁在什么时候发起了一次批量测试" 判断当前有没有正在执行的任务
cm_test_definitions 用例库目录——记录"平台上一共有哪些测试用例" 统计每天新增了多少条用例
_active_runs 服务器内存里的临时黑板——记录"现在正在跑的任务"（重启后消失） 展示"执行中"状态
💡 4 张表分散在 3 个模块中（device_pool / case_manager / test_runner），趋势功能只读不写。
↓ Django ORM 从表里取数据 → 只取统计结果（COUNT），不取原始记录 ↓

🟤 第 2 层：ORM 聚合查询 — 如何从表里取数据？

概念通俗解释
ORM 是什么 一种技术，让你用 Python 代码操作数据库而非手写 SQL。写 Device.objects.count() 等价 SELECT COUNT(*)，但更安全。Django 自带 ORM，禁止直接写 SQL。
聚合查询 不是取原始数据，而是让数据库帮忙算好总数。.count() = "数几条"、.filter(status="ONLINE") = "只看在线的"。计算在数据库内部完成，只返回数字。
循环查询问题 趋势函数在 12 天循环里每天查 3 次 → 36 次数据库往返。理想做法用 TruncDate 一次性按天分组，1 次查询搞定。
↓ ORM 返回的数字 → 交给 Python 函数加工成统计结果 ↓

🔵 第 3 层：后端函数（2 个辅助 + 1 个主函数）

函数角色通俗解释
dashboard_stats() 总指挥 被前端请求触发，负责调度所有子函数。先自己查基础数据，再调用两个子函数获取趋势和任务数据，最后把所有结果拼成一个大 JSON 返回。
_daily_execution_series(12) 趋势计算器 往前数 12 天，循环每一天去 tr_test_results 和 cm_test_definitions 表里数"当天通过几条、失败几条、新建几条"。
_recent_tasks(8) 任务收集器 从两个来源收集最近任务——先看服务器内存里有没有正在跑的（_active_runs），再翻数据库里最近结束的（tr_test_results），最多返回 8 条。
💡 _ 前缀 = 私有函数，只在本文件内部使用，外部不能直接调用。
↓ Python dict → JsonResponse 序列化为 JSON 字符串 → 准备发送 ↓

🟢 第 4 层：JSON 响应字段 — 后端交出的"数据包裹"

JSON 就像一份标准化装箱单——字段名固定，前端按名取货：

JSON 字段存储内容对应前端变量最终显示在哪里
charts.execution 4 个数组（labels / success / failed / new_cases），各 12 个元素 executionChart 左侧柱状图 — 12 组柱子
execution_summary 3 个数字（passed / failed / new_cases_week） executionSummary 右侧顶部 — 3 个彩色胶囊
recent_tasks 数组，8 个对象（每个含 id / title / status / time / cases） recentTasks 右侧下方 — 最近任务列表
↓ JSON 字符串通过 HTTP 协议传输到浏览器 → 带 JWT Token 验证身份 ↓

🔴 第 5 层：HTTP 传输 — 数据怎么从后端到前端？

概念通俗解释
请求地址 GET /api/dashboard/stats/ 像门牌号，Django 根据 config/urls.py 注册表找到处理函数 dashboard_stats。
鉴权 请求自动带 JWT Token（登录时签发的通行证），Django 中间件验证身份后注入 request.user_id，未登录用户拿不到数据。
api.js 封装 前端通过 @/shared/api-client.js 封装的 Axios 发请求——自动附加 Token、处理 401 刷新。api.js 中 fetchDashboardStats() 只是薄薄一层，组件只调 api.js，不碰 client。
↓ 前端拿到 JSON → 拆解为 3 个 Vue 响应式变量 → 通过 Props 传给子组件 ↓

🟣 第 6 层：前端数据层 — JSON 到了前端怎么处理？

前端变量来源于 JSON 的这是干什么的
executionChart charts.execution 包含 4 个数组的对象。原样传给 TrendBarChart 组件画图。
executionSummary execution_summary 3 个汇总数字。传给 TaskResultPanel 顶部显示彩色胶囊。
recentTasks recent_tasks 任务数组，最多 8 条。传给 TaskResultPanel 下方渲染列表。

💡 Vue 的 ref() 响应式变量——数据变化时页面自动刷新，无需手动操作 DOM。

↓ Vue Props 单向传递 → 子组件收到数据 → 渲染为 SVG 柱状图 + 任务面板 ↓

6 前端实现

👁️ 从交互上你能感知到什么？

当你打开仪表盘页面，浏览器会自动向后端发送一个请求（就像你点外卖下单）， 后端返回一串 JSON 数据（就像后厨做好装盒），前端把这串数据拆开、分给不同的组件：

  • 柱状图拿到最近 12 天的"成功数/失败数/新建数"三个数组，用 SVG 画成柱子
  • 摘要筹码拿到总成功/总失败/本周新建三个总数，显示在彩色胶囊里
  • 任务列表拿到最近 8 条任务记录，逐条渲染为带状态图标的行

💡 你看到的每一个数字、每一根柱子、每一个状态图标，都不是写死在代码里的——它们来自数据库，每次刷新都会重新查询。

index.vue 数据获取

页面加载时自动发请求，拿到数据后拆成三个变量，分给不同的子组件： 

// onMounted 时并行请求
const [statsRes] = await Promise.allSettled([fetchDashboardStats()])

// 从响应中提取趋势相关字段
executionChart.value  = d.charts?.execution       // → TrendBarChart
executionSummary.value = d.execution_summary       // → TaskResultPanel
recentTasks.value      = d.recent_tasks            // → TaskResultPanel

TrendBarChart.vue 纯 SVG 柱状图

这是一个不依赖任何图表库的纯手写 SVG 图表。它接收 4 个数组后， 计算出每根柱子的位置和高度，用浏览器原生 <rect> 画出来。 你看到的交互是：鼠标悬停柱子时会出现 tooltip 显示具体数值。

Props格式说明
chart{ labels, success, failed, new_cases }4 个数组，各 12 个元素
heightNumber默认 160

3 色分组柱状图：● 成功 / ● 失败 / ● 新建 | 硬编码宽度 640 | 零外部图表依赖 | hover 显示 tooltip

TaskResultPanel.vue 任务面板

右侧面板分为上下两部分：上面是3 个摘要数字（成功 / 失败 / 本周新建）， 下面是最近 8 条任务记录，每条带有状态图标（✓ ✗ △ ▶ ○）。 如果没有数据，显示一句提示引导用户去执行测试。

Props格式说明
tasksArray<{id, title, status, ...}>最多 8 条
summary{ passed, failed, new_cases_week }顶部摘要筹码

5 种状态图标：✓ 全部通过 / ✗ 全部失败 / △ 部分失败 / ▶ 执行中 / ○ 未执行 | 空态提示："暂无执行记录，前往执行引擎启动任务"

7 后端实现

🔄 后端数据流转 — 用大白话讲

当你打开仪表盘，浏览器请求 /api/dashboard/stats/，后端一个函数调用另外两个函数，各自去不同表里算数据，最后拼成一份 JSON 返回：

  1. 主函数 dashboard_stats() — 总指挥，负责调度。它先自己查设备数、用例数、Agent 数等基础统计
  2. 调用 _daily_execution_series() — 专门算趋势图数据，循环查 12 天，每天数三次（成功 / 失败 / 新增）
  3. 调用 _recent_tasks() — 专门收集最近任务，先看内存里有没有正在跑的，再翻数据库找最近记录
  4. 全部拼到一起 — 返回一个包含所有字段的大 JSON，前端拿到后各取所需

_daily_execution_series(days=12) — 趋势图数据 ⚠ 36 次查询

这个函数做的事很简单：往前数 12 天，每天统计三个数字——当天通过了几条用例、失败了几条、新建了几条。 但写法上有性能问题：每天单独发 3 条 SQL，12 天就是 36 条（应该用一条 SQL 搞定）。 

def _daily_execution_series(days=12):

        failed.append(TestResult.objects.filter(FAIL_Q, ...).count())

_recent_tasks(limit=8) — 任务列表数据

这个函数从两个地方收集任务：先看服务器内存里有没有正在跑的（实时数据，重启丢失）， 再翻数据库里最近结束的（持久化数据）。也有性能问题——获取任务标题时逐条查了数据库。

for run_id, state in _active_runs.items():

// ② 从 DB 查最近用例结果

📐 第三部分：AI 编码治理 — 让 AI 在边界内写代码

9 模块边界与依赖注入

AI 很容易为了图方便而跨层调用或引入不必要的依赖。以下规则防止架构越界。

允许依赖白名单

Dashboard 模块只能引用以下来源的代码：

来源允许示例
Django ORM（跨 App 只读）✅from apps.device_pool.models import Device
跨 App api.py（跨 App 写操作）✅from apps.test_runner.api import get_active_runs
models/constants.py（共享枚举）✅from models.constants import DeviceStatus
跨 App 内部实现（service / runner）🔴 严禁from apps.test_runner.runner import _active_runs
跨 App service.py🔴 严禁from apps.device_pool.service import ...

输入输出契约

Dashboard 对外暴露的唯一接口就是 4 个 HTTP 端点。AI 的职责是实现接口内部逻辑，不得修改接口签名：

端点方法响应格式（不可修改）
/api/dashboard/stats/GET{ ok: true, data: { devices, cases, charts, ... } }
/api/dashboard/activities/GET{ ok: true, data: [...] }
/api/devices/stats/GET{ ok: true, data: { online, busy, offline, total } }
/api/cases/stats/GET{ ok: true, data: { total, enabled, disabled } }

内部函数（如 _daily_execution_series、_recent_tasks）以 _ 前缀标识为私有方法，AI 新增辅助函数时也应遵循此约定。

11 错误处理与日志规范

AI 生成代码时经常忽略异常处理或使用 console.log。以下规则防止代码垃圾化。

强制异常捕获机制

❌ 禁止

  • catch {} — 空 catch 块，吞掉所有异常
  • catch (_) {} — 忽略错误继续执行
  • console.log(err) — 前端用 console 代替错误处理
  • print(e) — 后端用 print 代替日志

✅ 必须

  • 后端：except Exception as e: logger.error(...) + 返回 {ok: false, error}
  • 前端读操作：catch 后至少重置 loading.value = false
  • 前端写操作：catch 后 ElMessage.error() + 乐观更新回滚
  • Dashboard 特例：只读模块，无写操作，但刷新失败需重置 refreshing

日志分级与格式

级别场景必须包含的上下文
INFODashboard stats 请求成功user_id, 响应耗时, 数据量
WARN聚合查询超时 / 部分数据源不可用user_id, 超时时间, 失败的数据源
ERRORORM 查询异常 / 数据库连接失败user_id, 堆栈信息, SQL 语句, 参数

🔴 严厉禁止：print() / console.log() — 必须使用项目统一的 logging.getLogger(__name__) / console.error()

12 数据流转与持久化规则

ORM 操作规范（Dashboard 特化）

规则说明
只读原则Dashboard 只做 SELECT，禁止 INSERT / UPDATE / DELETE
查询方式使用 Django ORM（filter / count / annotate），禁止原生 SQL
跨 App 读直接 import Model 做只读查询 ✅
跨 App 写禁止 — Dashboard 无写操作场景
聚合查询使用 TruncDate + values().annotate() 替代循环内逐条查询
无自有表不需要 Migration 脚本、不需要 models.py

DTO/VO 转换规则

Dashboard 不直接返回 ORM 对象给前端。所有数据在 dashboard_stats() 中手动构造为 dict： 

// ✅ 正确：构造纯 dict 返回
return JsonResponse({
    "ok": True,
    "data": {
        "devices": { "online": device_online, "total": device_total },
    }
})

// ❌ 错误：直接返回 ORM 对象
return JsonResponse({"ok": True, "data": Device.objects.all()})

数据库 Entity（Device / TestResult 等 Model 对象）在 view 函数内部消费，转换为 dict 后才能返回。

你是 Dashboard 模块（Android-AutoTests 仪表盘聚合层）的专属高级开发工程师。 你的任务是严格按照以下约束在该模块内生成或重构代码，任何超出边界的代码都将被视为不合格。
