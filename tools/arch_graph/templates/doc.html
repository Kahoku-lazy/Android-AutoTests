最有价值的一条，不是覆盖率，是「锚点对不齐」

登录模块有 20 个测试文件、112 条用例，但只有 5 个文件在文件头写了"我守的是哪条规格"，而且写法有 3 种：一种写规格路径、一种写变更单号、还有一种是归档变更里的 delta 路径。 其中 1 处锚点已经指向一个不存在的规格了 —— 这类断裂平时没有任何工具会告诉你，图一画出来就摆在眼前。

存成什么（arch-graph/1）

照抄页面流的思路：容器 + 一段 JSON + 强类型连线

关键类比：页面流的元素带 xpath，关系图的节点必须带 anchor

页面流能长期不腐，靠的是每个跳转都挂在机器能重新定位的 xpath 上。
关系图同理：每个节点必须带一个能被程序重新解析的锚点（文件路径 / 标题 / 符号名 / 路由字面量 / 表名）。 有锚点，图随时能被重新扫描校正；没有锚点，就只能靠人维护，必烂。

节点类型含义锚点怎么落本 demo
连线类型语义谁来定

本次 demo 已经证明的三件事

      
    
        
  • 需求侧节点可以全自动抽出来 —— 规格文件里的 Requirement / Scenario 标题就是天然锚点

  • 代码侧节点可以全自动抽出来 —— 文件、符号、路由、表名都能源码解析

  • "需求 → 实现"这一段必须人声明，而且声明量很小：登录模块 6 个功能域、21 条需求，只用了 30 行声明

阶段交付是否动业务代码

      
        
P0 地基把本 demo 的扫描器变成正式工具：一份 JSON + 断锚 / 孤儿 / 未验收报告，声明层从生成器下沉到规格文件里不改，纯工具产物

P3 可选编辑在画布上人工登记"需求 → 实现"此时才需要决定要不要入库建表
